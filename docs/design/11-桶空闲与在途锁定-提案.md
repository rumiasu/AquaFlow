# 11 · 桶空闲与在途锁定

> **状态：已按「路径 B」实施（2026-09-15）**，本文剩余部分保留为设计推导与备选方案（路径 A / A′ 未实施）。
> 现状以 `src/**` 为准；桶权益的底层模型仍见 `docs/design/03-桶权益模型.md`（**未改动**）。
>
> **已实施的口径（2026-09-15，测试锁定）**：
> - **权益 right** = 已到手（`customer_barrel_lot.remain_qty` 汇总 → `customer_barrel_asset.quantity`）——**仍在送达时入账**；
> - **配送中 pending** = 已买下未送到（`customer_barrel_in_transit` 里 `PENDING`）；
> - **持有 held** = 权益 + 配送中 → 仅用于**展示**（"买了就是你的"）；
> - **占用 occupied** = 权益 + over → 物理在手 / 纯还桶上限（**不含配送中**）；
> - **下单抵扣与退押金只认权益**（在途不抵扣）：`shortage = max(0, needed − 权益)`，逐桶型；
>   付款报价（`PaymentServiceImpl.quote`）与小程序下单页（`create.js` 用 `assetQty`）同口径。
> - 欠桶（`over_qty > 0`）**只提醒不阻断**：`warnings` + 站长端 `GET /api/manager/owed-barrels`；
>   原硬拦 `MAX_OWED_BUCKETS = 5` 已移除。
> - 证据：`BarrelAvailabilityIntegrationTest`（5 例）+ `BarrelOwedIntegrationTest`（4 例），共 23 类 / 105 用例全绿；v29 迁移已在真实库执行。
>
> **未实施**：路径 A（权益提前到下单时入账）与 A′（押金到账时入账）。
> A′ 已被证伪（见 §3），A 需要把恒等式改成三项并动 8 处上限 + 取消回补 + 对账 E4/E5/E6。

## 1. 要解决的问题

现状（2026-09-15 实测）：

- 权益在**送达**才入账（`BarrelLedgerService.applyDelivery:183` 才 `createLot`）；
- 「配送中」是与权益**并列的独立池子**（`customer_barrel_in_transit`）；
- 下单抵扣用 `持有 + 在途`（`OrderServiceImpl:362`：`shortage = max(0, needed − held − pending)`）。

后果：**在途的桶会替客户抵扣掉这一单的桶需求**。但那些桶是给**上一单**用的，客户手上并没有可换水的空桶——
按业务口径，客户应当再买桶权益。表现为"客户少付了押金，账上却说不清他到底有几个桶"。

## 2. 新模型

### 2.1 粒度：一律按 `(customer_id, station_id, product_id)`

> **桶型/品类不可混算。** 19L 的空闲桶**不能**顶 18.9L 的需求；不同品牌、不同规格各自成账。

凡是"持有 / 配送中 / 空闲"的判断，**必须在同一个 `product_id` 内完成**；
**禁止**用跨品类求和的总量做任何决策（总量只允许用于展示）。

### 2.2 三个概念

| 概念 | 含义 | 落库 |
|---|---|---|
| **持有**（权益） | 客户**买下**的该桶型桶数（**含在途**） | `customer_barrel_lot.remain_qty` 汇总 → `customer_barrel_asset.quantity` |
| **配送中**（锁定） | 持有里**尚未送达**、被订单锁住的部分 | `customer_barrel_in_transit` 中 `status='PENDING'`，按 (customer, station, product) |
| **空闲** | 该桶型**可用于新订单抵扣**的部分 = 持有 − 配送中 | 派生，**不落库、不展示** |

### 2.3 不变量

- **I1** `占用 = 持有 + over`（沿用现行恒等式，`customer_barrel_over` 可负）
- **I2** `0 <= 配送中 <= 持有`（同一 `product_id` 内）
- **I3** `空闲 = 持有 − 配送中 >= 0`
- **I4** **在途的桶在订单结束前不得参与任何抵扣**：下单抵扣、退桶/退押金都只能用空闲
- **I5** 押金条与持有同步：持有 +N 时，必有一条金额对应的 `customer_barrel_lot`

### 2.4 下单校验（逐品类，伪代码）

```
for each product p in 订单的桶装水明细:
    need  = 该 p 的桶数
    held  = 持有(customer, station, p)
    lock  = 配送中(customer, station, p)          // 只数 PENDING
    idle  = max(0, held - lock)                  // 空闲：只有它能顶
    short = max(0, need - idle)                  // 必须新买的桶权益数
    押金   += short × product(p).deposit
    if short > 0:
        createLot(+short 权益)                    // 下单即入账
        建锁定条目(orderId, p, +short, PENDING)
```

反例（**必须拒绝**）：19L 空闲 2、订单要 18.9L 三桶 → 必须买 **3** 个 18.9L 的桶权益，不得拿 19L 的空闲顶。

### 2.5 状态流转

| 动作 | 持有（权益） | 锁定（配送中） | over |
|---|---|---|---|
| 下单，`short > 0` | **+short（此刻入账）** | +short（PENDING） | 不变 |
| 下单，换水（`short = 0`） | 不变 | 不变 | 不变 |
| 送达 | 不变（已入账） | PENDING → `DELIVERED`（解锁） | `+= delivered − returned − rightPurchase` |
| 取消 / 拒单 | **−short（回退权益）** | 删除 / `CANCELLED` | 不变 |
| 退桶（申请通过） | `−qty`（**只能退空闲部分**） | 不变 | 沿用现行 |

### 2.6 与现状的差异

| # | 位置 | 现状 | 新模型 |
|---|---|---|---|
| 1 | `BarrelLedgerService.applyDelivery:183` | 送达才 `createLot` | 下单即入账；送达**不再**建 lot |
| 2 | `customer_barrel_in_transit` 语义 | 与权益**并列**的池子 | 权益的**锁定标记**（`⊆ 持有`） |
| 3 | `OrderServiceImpl:362` | `needed − held − pending` | `needed − (held − pending)` |
| 4 | `PaymentServiceImpl.quote:727` | `needed − held`（与下单侧不一致） | 同上，两侧同口径 |
| 5 | 取消（`PaymentServiceImpl:575`） | 删在途行即可（权益没入账） | 必须**回退权益**（新写路径，需幂等 + CAS） |
| 6 | 退桶上限 `VO:128` | `占用 = 权益 + over` | `空闲 + over` |
| 7 | 对账 E5（`ReconciliationService:203`） | 用 `status='DELIVERED'` 计数 | `DELIVERED` 语义变了，须同步复核 |
| 8 | 三处聚合口径 | 1 处对、2 处错（见 §2.9） | 统一：只计 `PENDING` |

### 2.7 对账影响

- **E5 物理守恒**：`ReconciliationService:203` 用 `status='DELIVERED'` 的行参与计算，新语义下须重新定义"已送达"的取数。
- **E6 押金账户余额 >= 权益可退金额**：新模型下"权益已入账但押金未收"的窗口 = 货到付款从**下单**到**确认收款**（现状是送达后到确认收款）。
  → **需决策**：未付款的权益是否允许退押金？不允许则要在退押金入口加"已付款"门槛，否则存在"下单→拿权益→退押金"的套现口子。

### 2.8 存量迁移

- 当前真实库：`customer_barrel_in_transit` 中 `PENDING=0`、`DELIVERED=2` → **此刻切换零迁移风险**。
- 若切换时存在 `PENDING` 行：必须为它们**补建 lot**（否则那批桶"没有权益"），并保留其锁定状态。

### 2.9 已发现、与本提案交织的两个现存缺陷

1. **重复计数**：`BarrelServiceImpl.getBarrelSummaryByType:86` 与 `CustomerServiceImpl:256` 只排除 `CANCELLED`，
   把 `DELIVERED` 也算成"配送中" → 送达后页面显示"持有 2 个，配送中 2 个"。
   （同文件 `BarrelServiceImpl:174` 已写对并注明理由。）**已于 2026-09-15 修复**。
2. **报价/实收不一致**：`quote` 未减在途、下单减了 → 同一单两处算出不同押金。见 §2.6 #4。

### 2.10 测试清单（实施时必补）

- 你给的三个例子：`持有2/配送2 要3 → 押金3`、`持有2/配送4 要3 → 押金3`、`持有4/配送2 要3 → 押金1`
- **跨品类**：19L 空闲 2、18.9L 要 3 → 必须买 3（不得混算）
- 在途部分**不可**退押金
- 取消订单**回退权益**（重复取消幂等）
- 送达解锁后空闲恢复
- 对账在上述每种状态下都平

## 3. 两条实现路径（重要：先看这里）

**结论：你描述的全部规则（只有空闲能抵扣、在途锁定、品类不可混算），用「路径 B」就能满足，且不必动账本入账时点。**

### 路径 A：全量改造（改账本）
按 §2.6 改 8 处：权益下单即入账、在途降级为锁定标记、取消要回退权益、退押金改空闲上限、对账 E5/E6 复核、存量迁移、文档、测试。

### 路径 B：只改「计算 + 展示」（推荐先做）
保留现有账本（权益 = **已送达**才入账），只改两件事：

1. **下单/报价的计算**（`OrderServiceImpl:362`、`PaymentServiceImpl.quote:727`）：`shortage = max(0, needed − 权益)`，**逐品类**；
2. **展示口径**：「持有」显示为 `权益 + 在途(PENDING)`，「配送中」= `PENDING`。

### 为什么 B 与 A 的业务规则完全等价

| 规则 | A（改账本） | B（改计算+展示） |
|---|---|---|
| 空闲 = 能抵扣的部分 | `持有(含在途) − 锁定` | `权益(=已送达)` —— 两者**恒等** |
| 在途不可抵扣 | 锁定不计入空闲 | `needed − 权益` 天然不含在途 ✅ |
| 在途不可退押金 | 需新增「空闲上限」校验 | **现状已如此**：退押金受 lot（= 已送达权益）上限约束 ✅ |
| 取消订单 | 需新增「回退权益」写路径 | **不需要**：权益本来就没入账 ✅ |
| 对账 E5 / E6 | `DELIVERED` 语义变了，必须改 | **不动** ✅ |
| 存量迁移 | 有 `PENDING` 行就得补建 lot | **不需要** ✅ |
| 页面显示「持有 2 / 配送中 2」 | ✅ | ✅（持有按 权益+在途 算） |
| 风险面 | 核心账本 + 取消 + 退款 + 对账 + 迁移 | 2 个公式 + 3 处展示 |

→ **B 用更小的改动换来同样的对外行为**；差别只在账上「权益」这个词的时点
（A = 买下即权益，B = 送达即权益），**对客户和站长可见的行为一致**。

### 建议
先做 B（其中「重复计数」修复已于 2026-09-15 落地），把规则跑通、补齐 §2.10 的测试；
若将来确实需要「买下即权益」的账务语义（例如按「已售桶数」统计负债），再升级到 A —— 届时 B 的公式与测试可直接复用。

### 路径 B 仍需你定的展示细节
- 「持有桶对应押金合计」要不要把在途算进去？（押金在下单时**已收**，我倾向算进去；但「可退」仍以 lot 为上限）
- 文案：「持有 N 个（含 M 个配送中）」还是维持两个并列数字？

## 4. 待确认（评审问题）

1. **未付款权益能否退押金**（§2.7 的套现窗口）。
2. **部分送达**（订 3 送 2）：按实送解锁、余量继续锁？
3. **换水单（`short=0`）是否要产生一条"在途"记录**（现状没有）——影响「配送中」文案是否名实相符。
4. **展示**：只显示"持有/配送中"是否足够；站长端要不要按品类多给一列"空闲"。
5. **实施顺序**：先落显示/报价口径统一（已部分完成），再改账本入账时点。
6. **撤回 `− pending` 的副作用**：`OrderServiceImpl:340-343`（DEF-5）当初加它就是防"连下两单各算一次 shortage"。
   新规则只认空闲，于是**连点两次下单会各收一份桶押金**（客户多买桶权益）。
   需定：靠幂等键 + 前端防抖兜住，还是后端对"同客户同品类短时间重复下单"给提示？
7. **桶型不可混算的边界**：同规格不同品牌（19L 农夫山泉 vs 19L 娃哈哈）算不算同一"桶型"？
   现行账本按 `product_id` 隔离 → 默认**不通用**；若业务上通用，需要引入"桶型组"概念（新表/新列）。

## 5. 组合方案：A′（押金到账即权益）+ 欠桶警告层（2026-09-15 讨论后新增）

讨论结论：把两件事**分工**，而不是二选一。

- **账务层（A′）**：权益 = 购买凭证，**押金到账即生效**；在途期间该权益**暂停**（不可抵扣、不可退），送达解除暂停。
- **运营层（警告）**：欠桶**不阻断下单**，只作为外层标记：下单标红 + 站长端欠桶台账（欠了几个 / 欠了几天 / 欠的哪个桶型）。

### 5.1 A′ 与 A 的区别（推荐 A′）

| | A | **A′（推荐）** |
|---|---|---|
| 权益入账时点 | 下单即入账 | **押金到账即入账** |
| 水票 / 微信（下单即付） | 下单即入账 | 下单即入账（就是"刚下单更好"的那个场景） |
| 现金（货到付款） | **下单即入账**（钱还没收就先给权益） | **收款确认时入账** |
| 对账 E6（押金余额 ≥ 权益可退） | 下单起就报缺口 | **结构性恒平** |
| "没付钱却可退押金"风险 | 存在 | **不存在** |

### 5.2 好消息：A′ 的改动比想象的小

1. **`over` 结算公式不变**：`Δover = 送达 − 回收 − 在途解锁数`，与现行 `送达 − 回收 − 本单新购权益` **数值相同**
   （在途解锁数 ≡ 本单新购权益数）。账本里最复杂的那条公式**不用动**。
2. **`customer_barrel_in_transit` 就是"暂停"的天然载体**（一行 = 一单在一个桶型上的在途数），不必新建表。
3. **标红通道现成**：`OrderCreateResult.warnings` 已存在，下单流程已在往里塞缺货警告（`OrderServiceImpl:475-510`），欠桶警告直接复用。

### 5.3 代价（必须做，不能漏）

1. 「在途暂停」要**显式**实现：权益一提前入账，所有把权益当上限的地方都要减在途，
   否则客户能拿在途的桶退押金/还桶 → 8 处计算 + 前端 2 处 + 对账 2 项（清单见 §2.6）。
2. **恒等式两项变三项**：`物理在手 = 权益 − 在途 + over`。`AGENTS.md` §1 与 `docs/design/03` 要改；
   对账 E4 的判定从 `over < −权益` 改为 `over < −(权益 − 在途)`；E5 用流水重算的口径同步。
3. **取消要回补权益**（`refundOrder` 是唯一入口，历史出过"钱货分家"）。
4. 存量迁移：现在 `PENDING=0`，是切换的最好时机；若存在 PENDING 行须补建 lot。

### 5.4 欠桶台账模块（与 A′ 正交，可先独立上线）

**已定方案（2026-09-15）：只加一列 + 复用异常单，不新建事件表。**

- **天数**：`customer_barrel_over` 加一列 `owed_since datetime NULL`
  - 写入：该 (客户,水站,桶型) 的 `over_qty` **从 ≤0 变为 >0** 时写入当前时间
  - 清空：`over_qty` 回到 `<=0` 时置 NULL
  - **不重置**：`over_qty` 已是正数、又新增欠桶（如 2 → 3）时保留原值 —— 这是同一笔欠桶的延续
  - 负值（水站暂存）不算欠桶 → `owed_since IS NULL`
- **明细**：直接复用 `order_barrel_exception`（现成的「异常订单」数据）：
  取 `discrepancy > 0`（少回空桶）的记录，可得**哪个桶型**（`adjustProductId`）、**差几个**（`discrepancy`）、**哪一单**（`orderId`）、**哪天欠的**（`createdAt`）、**处理到哪一步**（`status` / `staffNote`）。
  → 因此**不需要** `barrel_owed_event` 事件表。
- **口径（必须写清，否则两个数会打架）**：
  1. **「当前欠 N 个」以 `customer_barrel_over.over_qty` 为准**（净额，已被回收/抵消过）；
  2. 异常单是**历史事件**，不会被自动核销（`status` 只表示站长是否处理过）；
  3. **两者不可相加**：列表 = 当前欠桶额 + 天数 + 「查看来源异常单」下钻；
  4. over 已归零但异常单仍在的客户**不进列表**（只展示"当前仍欠"）；
  5. 不是所有异常单都产生欠桶（`RETURN_DAMAGE` 破损 / `CUSTOMER_REFUSE` 拒收 / `STATION_SHORTAGE` 缺货）→ **必须按 `discrepancy > 0` 过滤**。
- **接口**：站长端 `GET /api/manager/owed-barrels?minDays=`（按天数倒序，返回客户/桶型/当前欠数/欠了几天/最近来源单）；
  下单标红**复用现成的 `OrderCreateResult.warnings`**（`OrderServiceImpl:475-510` 已在用），不阻断下单。
- **护栏（不可删）**：还桶上限仍必须用"物理在手"（`权益 − 在途 + over`）—— 这是 DEF-4 修过的"桶账冲穿"护栏；
  "欠桶只是警告"指的是**不影响下单决策**，不是把护栏去掉。

### 5.5 组合后的行为（业务后果，需确认）

同一场景：先下 2 桶 → 未送达前再下 3 桶 → 两单都送达、都没回收空桶。

| | 第二单补押金 | 客户总押金 | 送达后 over | 欠桶模块是否触发 |
|---|---|---|---|---|
| 现状 / 路径 B | 1 个（¥30） | ¥90 | **+2（欠 2 个）** | ✅ 触发（同时是资金敞口） |
| **A′** | 3 个（¥90） | **¥150** | **0** | ❌ 不触发（押金已收齐） |

→ A′ 让欠桶**只在"该回收的空桶没收回"时产生**，与"配送员回收失败才标记"的设想完全一致；
代价是客户首次/加订要多掏押金。
