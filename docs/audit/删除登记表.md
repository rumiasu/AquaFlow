## 1. 删除类改动的报备协议

删除代码、端点或文件前必须先**只读排查**，并给出六项：

| # | 项目 | 要求 |
|---|---|---|
| ① | 核实到哪一步 | 几遍核实、用什么方法 |
| ② | 证据 | 逐条 `文件:行号` |
| ③ | 原来为什么存在 | 它当初解决什么问题 |
| ④ | 删掉会怎样 | 连带影响的测试 / 文档 / 常量 / mapper |
| ⑤ | 推荐删或留 + 理由 | 结论要明确 |
| ⑥ | 风险等级 | 高 / 中 / 低 |

**破坏性操作**（删文件、改 git 历史、清库、跑历史迁移 SQL）先报证据与影响，**等确认后再执行**。

## 2. 核实纪律

**判据：自己 grep 出所有出现位置，逐个确认是"真调用"还是仅"常量定义 / 文档 / 注释 / 测试断言" —— 定义 ≠ 调用。**

四条硬要求：

1. **不能只靠审计脚本下结论。** 仓库根目录的 `api_reverse_audit.py` 既有假阳性也有假阴性：
   行号按剥离注释后计（系统性偏早）、只比对路径不看 HTTP 方法（报的数字是下界），
   且认不出「页面内路径常量拼接」与「路径段由函数参数传入」的调用 —— **在用端点会被判死**。
   脚本产出的是**候选清单，不是结论**。
2. **查引用必须覆盖 `.js` / `.wxml` / `.java` / `*.md` 四类。** 小程序调用常只写在 **`.wxml`**
   （`data-url` + `bindtap`），只 grep `*.js` 会把有入口的页面误判成孤儿页。
3. **要顺 handler 往下看一跳**，确认点击后真的会跳转，而不只是"绑定了一个存在的函数"。
4. **零引用确认后再跑一次全量测试**留基线，避免删掉的东西正被某条用例间接触达。

### 3.1 `POST /api/orders` 删除报备（2026-09-25，六项协议）

| # | 项目 | 结论 |
|---|---|---|
| ① | 核实到哪一步 | 三轮：① `grep` 全仓 `.java` / `.xml` / `.js` / `.wxml` / `*.md` 找 `POST /api/orders`、`orderService.save`、`orderMapper.update(`；② 逐个确认命中的是"真调用"还是"常量 / 注释 / 文档 / 测试断言"；③ 再跑全量集成测试留基线 |
| ② | 证据 | 调用链：`OrderController.save`（`@PostMapping` 类根 + 裸 `Orders`）→ `OrderService.save` → `OrderServiceImpl.save` → `OrderMapper.update`（XML `<update id="update">`）。**真调用只有这一条**；两端小程序 `grep` 结果为 **0 处**（`miniapp-user` / `miniapp-delivery` 只调 `/api/orders/create` 与 `GET /api/orders`）；测试侧仅 `TamperResistanceIntegrationTest:165` 发过一次 `{}`（用于断言被拒，本次改为断言 404）；`docs/api/01-REST-API参考.md` 已同步移除该行并登记进「已删除的端点」 |
| ③ | 原来为什么存在 | 早期管理后台/代客录单时代的"订单编辑"入口：站长改联系备注、改预约时间、改地址等。管理后台（Vue）早已删除，该端点失去唯一调用方 |
| ④ | 删掉会怎样 | 连带删除 `OrderService.save`、`OrderServiceImpl.save`、`OrderMapper.update` + XML `<update id="update">`（删后 `orderMapper.update(` 全仓零引用）。需改的测试 1 处（`TamperResistanceIntegrationTest`）；需改的文档 2 处（本篇 + `docs/api/01-REST-API参考.md`）。**不影响任何业务流程**：订单的状态 / 金额 / 履约站 / 配送员的全部合法修改都有各自的具名入口（`OrderWorkflowService` 的具名命令、`OrderMapper` 里带 expected-state 的 CAS、`updateDeliveryOutcome`、`appendSpecialNote`） |
| ⑤ | 推荐删或留 + 理由 | **删**。理由：①它是"实体全量写入口"，实测可把 `settle_station_id`（营收归属）搬到别站、把 `total_amount` 改成 0.01；②零调用方，"兼容旧调用方"不成立；③保留它就必须长期维护一份"哪些字段不许改"的黑名单——而本仓已经有过一次"整行 update 覆盖并发状态"的事故（2026-09-13 三-1），当时的修法是改成专用列更新，**这个端点属于同一根因下没被一起收口的实例**；④GPT 评审报告 §5.2 明确"不能通过'再屏蔽几个字段'长期保留实体全量写入口" |
| ⑥ | 风险等级 | **低**。零调用方 + 有 404 守护用例（`ArchReviewFixesIntegrationTest#genericOrderUpdateEndpoint_isGone`）+ 全量集成测试护栏；唯一风险是"将来有人想恢复订单编辑"，故在 `OrderController` 与 `OrderMapper` 各留墓碑注释指明正确入口 |

> 上表的零引用结论经逐条 grep 复核（覆盖四类文件），且已核对当前端点集合中确实不存在这些路径。
> 端点的当前全量清单见 [`../api/01-REST-API参考.md`](../api/01-REST-API参考.md)。

## 4. 待观察：保留但无活跃调用方的端点

有些端点**没有前端调用方但不应删除** —— 它们是运维排查或人工核对步骤的入口
（例如让维护者直接发请求看对账差异）。这类端点的判定需要区分「设计上就不面向界面」
与「界面漏接」，两者结论相反，**不要仅凭"前端零调用"就删**。
