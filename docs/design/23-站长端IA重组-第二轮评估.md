## 2. P4/P5：客户页 tab 化 —— 员工 tab 为什么不建议

### 2.1 普通 / 企业 两个 tab：可行，但**用别的方式做更好**

- 字段本就存在：`customer.customer_type`（1 个人 / 2 企业），现页已有 `全部/个人/企业` 三个筛选 chip（`customers/index.wxml:7-11`）。
- 所以这一项本质是**把已有的筛选 chip 升格为分段器**，不是新功能。数据源、接口、口径全不变。
- **建议用分段器而不是 tab 栏**：站长改的是"筛选条件"，不是"换一个页面"；用 tab 会让人以为个人客户与企业客户是两套数据。
- **要用 tab 也可以**，但 tab 内的筛选 chip 要撤掉（否则同一维度两个控件，站长会以为它们叠加）。
- 命名：卡片「客户查询」→ **「客户」**；分段器 **普通客户 / 企业客户**（服务端口径仍是 `customer_type`，别改枚举）。

### 2.2 员工 tab：三个硬理由不做

| 理由 | 证据 |
|---|---|
| 员工不是客户，是另一个实体 | `staff` 表 vs `customer` 表；`customer_type` 只有 1/2，没有"员工"这个值 |
| 数据源、接口、权限面全不同 | 员工走 `getStaffList`（`/api/delivery/...`）+ `createStaff`/`detachStaff`；客户走 `CustomerMapper.listSearchCandidates` |
| 站长自己出现在"客户"列表里语义就错了 | `createStaff(..., "STATION_MANAGER", ...)` 造的站长也是 staff 行 |

**替代方案**：客户页的 tab 只做 `普通客户 / 企业客户`。你想要的"点客户就能给他下单"放在**客户详情页**（见 §3），那才是它该在的地方。

### 2.3 客户画像页（P4）tab 化的具体拆法

现在一张长滚动页 7 个块（`customers/detail/index.wxml:10-289`）：

| 现块 | 归类建议 |
|---|---|
| 画像头 / 消费概览 / 消费特征 / 最近订单 | **「概览」tab** —— 都是"这个客户是什么人" |
| 本站资产（含还空桶 / 资产调整入口） | **「资产」tab** —— 桶 / 押金 / 水票 / 流水 |
| 客户特权 / 权限设置（货到付款开关） | **「权限」tab** —— 都是"本站给这个客户的例外规则"，`ManagerCustomerPrivilegeController` 与 `offline_payment_enabled` 同源 |

7 块 → 3 tab，这是**真瘦身**（不是把卡片换成页签）。

## 3. P6：代客下单并入客户画像 —— 撞到一个已存在的缺口

**结论：建议本轮不做。** 原因是这条路上有个比"入口放哪"严重得多的问题，我在核查时发现：

### 3.1 三处证据

| # | 事实 | 证据 |
|---|---|---|
| 1 | `POST /api/customers`（客户建档）**只 insert customer，不建任何水站绑定** | `CustomerServiceImpl.save:125-129` |
| 2 | `customer_station_config` 绑定行**唯一的写入口是"读/改货到付款权限"**（`ensureExists`），前端触发点只有那个开关 | `CustomerStationConfigMapper.java:9-13`（`insert`，**零调用**）、`:32-36`（`ensureExists`）；`ensureExists` 的调用方仅 `CustomerServiceImpl.java:157,165`（全仓 20 处引用中其余全是查询）；开关在 `customers/index.js:195`（列表页弹窗）与 `customers/detail/index.js:324`（画像页）各有一处 |
| 3 | 归属判据是**并集**：①`customer_station_config` 绑定行 ②本站订单 | `CustomerMapper.countCustomerOfStation:157-160` |

**推论**：某客户若 ①没下过本站订单、②站长没点过他的货到付款开关 ⇒ **他在站长端任何客户选择器里都查不到**（`listStationCustomers:109-121` 是 orders 驱动；`listSearchCandidates:91-103` 的 `exists` 也查不到他）。

### 3.2 顺带发现的三个产物

1. **`CustomerMapper.countCustomerOfStation` 的 javadoc 已失真**：它写「绑定行，**站长代建/认领即产生**」——
   代码里**已没有任何"代建即绑定"的路径**。这正是 AGENTS §6.1 点名的"注释与代码不符比没有注释更危险"。
2. **`CustomerStationConfigMapper.insert`（第 10-13 行）全仓零调用** —— 是一个孤儿方法，看名字人人都会以为"建档时会用它建绑定"。
3. **`place-order/index.wxml:28` 的文案是死路**："新客户请先到「客户管理」建档，再回来下单" ——
   而「客户查询」页**没有建档按钮**（`api/station-mgmt.js` 只有 `getCustomers`，没有 POST 包装）。

### 3.3 所以 P6 要分两步，不要混在一起做

- **第一步（纯 IA，本次可做）**：`代客下单` 卡片从宫格撤掉，入口改为**客户详情页的一个按钮**「用他下单」，
  点击 `navigateTo` 到 `place-order?customerId=xxx`（**该页保留，只加一个"跳过第一步"的入参**，
  不复制客户搜索逻辑 —— 复制就是"两处搜索各写一套"，`CustomerMapper.java:162-168` 记着这条教训）。
- **第二步（另开一项，需产品裁定）**：补齐"站长代客建档"闭环。三选一：
  | 方案 | 做法 | 代价 |
  |---|---|---|
  | A | 建档时同时写 `customer_station_config` 绑定行（复活那个孤儿 `insert`） | 要改 Controller→Service 两处；**注意 `CustomerController.java:109,140` 已写明"先判归属再 ensureExists"的护栏，不能反序** |
  | B | 客户列表页加"新增客户"按钮，调 `POST /api/customers` + 绑定 | 同 A，另加前端表单 |
  | C | 明确"客户必须自己扫码/登录过一次"，删掉那条误导文案 | 最小，但电话客户无法代下单 |

**建议**：先做 C（改文案）止血，真需要 A/B 再单独提。**在第二步落地之前，把代客下单藏进客户画像会让人找不到它。**

## 4. P7：死端点的完整证据链与"伴随清理"

### 4.1 零消费证据（三层都查了）

| 层 | 结论 | 证据 |
|---|---|---|
| 前端业务调用 | **零** | 全端 grep 只命中 `api/station-mgmt.js:6-12,369-370`（定义）与 `config/api.js:173-174`（常量），**没有任何页面调用** |
| 其他端 | **零** | 唯一在用的前端是 `archive/legacy-web-frontend/src/api/index.js:92-93` —— 该端**已删除**，只剩留档（AGENTS §1/§7：不维护、不引用） |
| 测试 | 1 处契约断言 | `DashboardNoticeSearchFeedbackIntegrationTest.java:37-44` 的 4 条路径里有这两条 |

### 4.2 不是安全问题的三条反证

1. 两个端点都有 `@RequireRole({"STATION_MANAGER"})`（`DashboardController.java:46,63`）。
2. 水站来自 `AuthContext.requireStationId()`，**请求里的 `stationId` 后端根本不接**（`today()`/`overview()` 方法签名没有该参数）；类 javadoc 第 23 行明写"前端不传 stationId"。
3. 两个端点都在 `@RestController` 的 `execution(public * controller..*.*(..))` 切面覆盖内。
   → **原判"错误示范"成立，"跨站隐患"不成立。**

### 4.3 真正的理由：它们是**第二份口径**（本次新发现）

| 端点 | 它算的东西 | 与正式实现的冲突 |
|---|---|---|
| `/today` | `lowStock = inventory.quantity < 20` | **同一个"低库存阈值 20"在前端也写了一份**（`products/index.wxml:19` 的「低库存(<20)」）。一个业务阈值两处硬编码 |
| `/today` | `finishedToday`、`totalOrders` | 与 `DashboardService.report()` 的完成数/订单数**同名不同算法** |
| `/overview` | `customerCount`（= `CustomerMapper.countByStationId`，**orders 驱动**） | 与 `countCustomerOfStation`（绑定∪订单并集）**口径不同**；后者正是本仓踩过两次的坑 |
| `/overview` | `orderCount`、`inventoryTotal`、`pendingOrderCount` | 同上，与 `/report` 分叉 |

而且**仓库里已有完全同形的先例**：`DashboardController.java:76-79` 的墓碑注释 ——
`GET /order-status` 与 `GET /order-trend` 就是"零前端调用 + 口径与 `/report` 分叉"被删的，
判据出自 `docs/audit/2026-09-16-死端点评估.md`。**同一条判据，同样适用。**

### 4.4 删的话必须一起清（否则留孤儿）

| # | 位置 | 处理 |
|---|---|---|
| 1 | `miniapp-delivery/api/station-mgmt.js:6-12` + `:369-370` | 删两个包装函数与导出 |
| 2 | `miniapp-delivery/config/api.js:173-174` | 删两个常量 |
| 3 | `DashboardNoticeSearchFeedbackIntegrationTest.java:37-44` | 从路径数组移除两条，并把 `@DisplayName` 的"看板 5 个端点"改成 3 个 |
| 4 | `DashboardController.java:47-61,64-74` | 删两个方法 + 随之空掉的注入字段 |
| 5 | `DashboardController.java:33` `addressMapper` | **本来就是死字段**（全文只出现在声明的第 33 行），顺手删 |
| 6 | `OrderMapper.countTodayByStationId`（`:501`） | 删后零调用 → 一并删 |
| 7 | `OrderMapper.countByStationId`（`:266`）、`CustomerMapper.countByStationId`（`:175`） | 删后零调用 → 一并删（注意 `countByStationIdAndStatus` 另有他用，**不能删**） |
| 8 | `README.md:779-780`、`docs/architecture/api-design.md:213-214` | 删表格行 |
| 9 | `RequireRoleAspect.java:24` 的注释示例 | 它拿 `/api/dashboard/today` 当"无鉴权"的例子 —— **这条例子的前提已经过期**（该端点现在有 `@RequireRole`），换成真实例子 |

**判定：可删。收益 = 消掉一份分叉口径 + 一处过期注释 + 一个死字段 + 三个孤儿 mapper 方法；风险 ≈ 0（有鉴权、不接参、零消费）。**
如果你觉得这轮不想动后端，**最低限度也建议删前端第 1、2 项**（纯死代码，零风险），后端留待下轮。

## 6. 瘦身核算（你担心"点进去还是那么多分类"）

**先承认一个账**：22 号文按"每类一页、页内页签"拆，页签总数 = 6+4+4+4+4+4 = **26 个**，
比现在 18 张卡**还多**。虽然一次点击能看到同类全貌，但它不符合你的要求。**按你的思路重做如下。**

### 6.1 扁平 7 张卡 + 2 条分隔线（不点进去）

```
──────── 日常在办的 ────────
  📋 订单管理     待分配 · 审批 · 抢单池 · 外派 · 代客下单
  💰 收款与账     待确认收款 · 应收账款 · 计件工资 · 毛利报表
  🛢 桶           待审退桶 · 欠桶 · 桶异常 · 资产调整
  👤 客户         普通客户 · 企业客户 · 企业待审 · 客户反馈
──────── 配置类的 ────────
  💧 商品与配置   商品上架 · 库存 · 水票 · 配送计费 · 营业状态与公告
  👥 员工         员工 · 绑定申请 · 员工画像
  📊 现场数据     独立一张（它是"看"，不是"办"）
```

每张卡的描述行（你现在是 `module-desc` 一行）改成**一行"里面有什么"**，用 `·` 分隔 ——
这就是"不点进去也知道里面有什么"，取代二级页签的导航作用。

### 6.2 页签总数：26 → 18

| 分组 | 页签 | 相对 26 的削减 |
|---|---|---|
| 订单管理 | 待分配 / 审批 / **抢单池＋外派（合 1）** / 订单台账 / 代客下单 = **5** | −1（两个外派方向合一） |
| 收款与账 | 待确认收款 / 应收账款 / 计件工资 / 毛利报表 = **4** | — |
| 桶 | 待审退桶 / 欠桶 / **桶异常＋资产调整（合 1）** = **3** | −1（异常与人工补正是同一件事的两面） |
| 客户 | 普通客户 / 企业客户 / **企业待审（并入"企业客户"页签顶部横幅，不单列）** / 客户反馈 = **3** | −1 |
| 商品与配置 | 商品与库存 / 水票档位 / 配送计费 / 营业状态与公告 = **4** | — |
| 员工 | 员工 / 绑定申请 = **2**（员工画像并入员工行内） | −2 |
| **合计** | **18** | **−8** |

### 6.3 还能再瘦的（可选，看你要不要）

|---|---|---|
| 「商品与库存」内部已有 3 段（全部目录/已选用/我的商品）+ 库存流水 → 归成一个页签内的分段器 | 宫格 −0 卡 | 无 |

## 7. 排序建议（按功能，不按字母也不按新旧）

按"站长一天里碰到的顺序"排，而不是按模块重要性：

1. **订单管理** —— 每天第一件事（接单、派单、处理审批）
2. **收款与账** —— 送完要收钱
3. **桶** —— 收桶、退押金、对欠桶
4. **客户** —— 客户是上面三件事的对象
5. **现场数据**（看） —— 收工前后看一眼
6. **商品与配置** —— 偶尔改一次
7. **员工** —— 偶尔改一次

分隔线放在「现场数据」之后（把"天天用"与"偶尔配"分开）。
