# 前端一次性收口执行契约

> 2026-10-01 文档定位：本篇保留当时方案、取舍及验收过程，不作为全部现行业务规格。当前站长入口见 [24](24-站长端IA重组-定稿.md)，当前桶、钱、票与退出流程见 [15](15-业务流程地图.md)，本轮未决目标只登记在 [16 §12](16-范围决策与实施路线图.md#12-核心业务决策复核2026-10-01)。


> 日期：2026-09-26。用途：把两端小程序做成一轮有边界、可完整验收的产品化收口，降低后续页面维护成本。
> 本契约只约束前端实施与验收；代码、接口、数据库和业务不变量以仓库源码、`sql/schema.sql` 与根 `AGENTS.md` 为准。
> 设计基准沿用 `docs/design/29-两端体验与视觉改造方案.md`。本契约不授权改写其中列出的待拍板业务口径。

## 1. 目标与完成判据

优化顾客订水与查单、配送员履约、站长经营三类真实任务，让普通顾客无需理解桶账术语，配送员少做文职判断，站长仍能看到经营所需数据。

完成时应满足：

1. 两端全部已注册页面都有明确用途、可达入口、页面类型、加载/空/失败/无权限行为和负责人；孤岛、未注册页必须逐项给出处置及证据，不可静默删除或擅自开放。
2. 两端遵循一份语义化设计规则：颜色、字号、间距、圆角、控件、状态文案与安全区行为相互一致。当前两端变量位于不同文件，必须有自动门禁检查关键 token 与允许例外，避免重复色板漂移。
3. 重复页面遵循少量已验收的页面模板。公共组件只抽取有重复且行为相同的控件；不得为了“组件化”把简单 WXML 拆成难追踪的碎片。
4. 所有主任务可从可见入口完成；按钮无静默空操作；显示的状态、金额、电话、桶数和退款信息都有真实数据来源。缺数据、失败、零数据彼此可区分。
5. CI 自动门禁全绿，六个既有流程套件全绿；关键任务在微信开发者工具或真机完成目视与操作验收，留存设备/视口、场景、结果和必要截图。没有微信运行时验收不得标记“前端收口完成”。
6. 维护手册说明页面模板、token、组件、路由盘点与门禁命令；后续新增页面有明确的复制起点和验收清单。

“一次性”指这轮统一规则、全量盘点、修完已确认问题并完成验收，不代表以后没有业务需求或设备兼容问题。

## 2. 范围与事实基线

- 两个原生微信小程序：`miniapp-user` 顾客端、`miniapp-delivery` 站长/配送员端。页面清单以各自 `app.json` 为准。
- 顾客端与员工端已有各自的可复用组件。两端分别维护 WXSS token；不得引入 Vue/React/新 UI 框架或将应用合并。
- 当前 `page_reach_audit.py` 的实测结果：顾客端孤岛 `pages/product/detail`；员工端未注册 `pages/station-mgmt/alerts/index`，孤岛 `pages/feedback/index`、`pages/station-mgmt/place-order/index`。这是调查入口和用途的线索，不是删除/开放授权。
- **2026-09-30 处置结果（产品拍板）**：`pages/product/detail` 与 `pages/feedback/index` **已删除**（注销 + 删文件，登记见 `docs/audit/删除登记表.md`）；**代客下单改做进客户详情页**（`customers/detail` 加「用他下单」→ `place-order?customerId=`，跳过第一步），不再在首页单独拎一张卡。该页此后不再出现在孤岛清单里。
- 当前工作区包含多轮未提交修改。实施前先 `git status --short` 并记录基线；只编辑任务明确授权的文件，保留已有修改，不做清理式回滚、不覆盖无关 diff、不提交。
- 现有交付报告承认员工端仍残留多组红色/灰色色值，站长管理子页只继承了样式，没有逐页梳理；上一轮视觉改动没有微信运行时验收。

## 3. 固定的体验规则

沿用方案 29 的信息排序与角色边界，并将以下规则用于每页审查：

- **先任务、后解释**：当前地址/商品/状态/金额/主要操作常显；复核信息折叠；重复口号、内部术语和无助于当前决定的信息移出首屏。
- **一个页面一个主动作**：重要操作给明确动词；危险或不可逆操作说明后果；日常配送不要求力工判断利润、结算站、客户归属或复杂状态。
- **真实状态优先**：零数据不等于加载失败；未付款不说已成功；未知费用不说免费；没有配送员号码不拨客户自己的号码；退款去向不作无依据承诺。
- **小屏可操作**：触控目标不小于方案 29 规格；正文与关键规则在大字体下可读；按钮、列表末项和输入框不被自绘 tabBar/安全区遮挡。
- **一致且克制**：品牌蓝只作主要交互和选中状态；状态色必须伴随文字；危险红表达危险而不是普通强调；不以彩色宫格、渐变、阴影代替信息层级。
- **保留业务不变量**：订单请求、幂等、金额、状态、角色权限、客户资产隔离、跨站隐私和服务端判定均不得由视觉改版重写。

## 4. 执行顺序与任务包

以下顺序必须串行通过门槛。DS 负责完整主线，避免同一端多人同时重排。免费模型只承担无代码或只读的页面盘点、重复色值统计、截图/入口对照等短任务；其结果由 DS 复核后才进入实现。

### A. 基线与页面清册（只读）

对所有注册页面逐页记录：角色、入口、主任务、页面类型（首页/列表/详情/表单/操作流程）、请求与关键数据、加载/空/失败/无权限状态、主要动作、关联测试、是否需运行时目视。

另查四类入口异常：顾客商品详情孤岛；员工未注册的 alerts；员工 feedback 与 report 的入口关系；站长代客下单孤岛。对每项逐条 grep 源码（`.js/.wxml/.java/*.md`）和 app 注册，辨别真实调用与仅定义，不删除页面/API、不新增入口；存在产品决策时按根 AGENTS §0.6 登记 `TODO(待拍板)`。

输出页面清册与异常证据后再进入 B。页面清册应可由源码更新，不能只列主观观感。

### B. 设计规则与公共模式

先以首页、典型列表、典型表单/流程页建立通过验收的模板。定义一份语义 token 表（品牌/文本/背景/边框/成功/警告/危险/间距/字体/圆角/阴影），明确允许的页面例外；加入静态门禁检查两端关键 token 对齐、未定义 `var()`、无授权裸色值和不合规的小字。门禁要指出文件/行和修复方法。

评估并按需建立或收口少量跨页组件：页面反馈状态（加载/失败重试/空）、列表行/分组标题、状态徽标、金额展示、确认操作、主底栏。复用必须保持既有事件、字段和可达性。不要造复杂组件框架、主题运行时或仅用于一页的抽象。

B 的模板与 token 门禁通过静态检查及微信运行时样板页验收后，才能扩展全量页面。

### C. 顾客端页面收口

按顾客任务顺序：选站/首页订水 → 地址 → 商品与数量 → 结算/支付 → 结果/订单列表详情 → 水票/桶/押金 → 我的/服务/公告。

重点验收新客首单与押金确认、现金/水票/免真实付款开发模拟、缺货与重试、返回恢复、重复提交、订单状态、逐商品桶权益与退桶预览。优先改清信息、状态与可达性，不加入会员/积分/优惠等新业务。隐藏的配送联系入口按设计 29 的待拍板项处理；退款去向保持中性文案直至产品确认。

### D. 员工端页面收口

先完成配送员高频任务：待接单/配送中/详情 → 导航/联系收件人 → 回桶与收款 → 送达/异常/历史。再完成站长任务：工作台 → 分配/外派/审批 → 客户和员工 → 桶/库存/水票 → 收款/工资/利润 → 水站配置。

重点把复杂规则留给站长，把配送员界面压到“地址、商品、实际回桶、实际收款、下一步”。站长列表与表单逐页重排，而不是仅继承 token。全部管理入口及既有审批/经营能力都要对照基线证明保留；未拍板的零待办可见性、代客下单入口等不擅自改。

### E. 联调、清障与交付

以 A 页面清册逐项验证入口、返回栈、跨角色展示、弱网重试、加载失败与重复点击。检查页面动态内容、长名称、多商品、大额/零额、长地址、无电梯/未知楼层、大字体、窄屏和自绘底栏。

检查结果必须包括：变更文件列表；每个异常的处置与依据；页面清册完成度；静态门禁及六个 JS 套件的真实命令/退出码；后端接口是否改变；微信运行时设备和测试任务记录；遗留待拍板事项；后续维护说明。不得把源码检查、浏览器示意或 Node 测试冒充真实小程序目视验收。

## 5. 必须保留和不得擅自作出的决定

下面项目只允许做到安全、中性、可达，不可由执行模型自行选择产品规则：

- 设计 29 §9 登记的问题：**顾客订单联系对象**、**零待办卡显示方式**、**代客下单入口**等（**退桶押金返还方式已于 2026-09-27 拍板**，正本 `docs/design/35` §7，不再由执行模型自选）。
- 支付/退款、跨站分账、价格与费用、回桶建议、库存、权限、财务口径及客户资产真值源。
- 任何删页面、端点、文件的动作。删除先提交 AGENTS 要求的六项引用核查和风险说明；需要破坏性确认的动作必须停在可审查报告。

不因本前端契约改变项目唯一可维护端、用户角色、导航底栏数、接口路径或服务端状态机。

## 6. 验收门禁

每次修改先跑针对改动页面的 JS 解析与关键流程，再跑完整前端门禁。项目根 CI 当前包含以下静态检查，命令以 `.github/workflows/ci.yml` 为准：

```powershell
python audit_wxml_handlers.py
python page_reach_audit.py miniapp-user
python page_reach_audit.py miniapp-delivery
python static_audit_user.py miniapp-user
python static_audit_user.py miniapp-delivery
python audit_js_syntax.py
python audit_wxss_selectors.py
python audit_comments.py
```

再逐套件执行六个既有流程测试：`order-create-flow`、`delivery-complete-flow`、`delivery-detail-return-row`、`ticket-purchase-flow`、`notice-draft-flow`、`modal-copy-limit`。不可用本机已知会误报的 `node tests/js/run-all.js` 替代逐套件结果。新增门禁要进入 CI 并给出清楚失败定位。

微信运行时至少由普通顾客、普通配送员、站长三种视角按清册完成代表任务。推荐设备覆盖 iPhone 与 Android 各一台；若只能一台，必须记录型号、微信版本、基础库、屏幕尺寸及尚未覆盖的平台。覆盖正常、无数据、局部请求失败、弱网、长文案、大字体、窄屏、安全区、连续点击和页面返回。问题修完后复测并保留截图/录屏或逐项记录。

## 7. 交付红线

- 不把“所有页面加载出来”当作完成；主任务必须走通且错误状态能恢复。
- 不只做机械色值替换：检查对比度、实际层级、异常颜色语义、对齐、换行和点击目标。
- 不为通过静态审计删除有效入口或事件；不以把失败变成空态来消除告警。
- 不改与 UI 无关的后端业务；需要新数据字段或产品决定时登记 TODO 并交付方案，不在前端拼造事实。
- 不把工作区现有未提交内容当成本轮产物；交付须说明以什么基线比较，保护并保留基线已有修改。
- 未完成微信运行时验收时，交付状态只能写“代码与自动门禁完成，待运行时验收”。

## 8. 当前下一批执行顺序（2026-09-29）

本节给接手本轮修复与验收的执行模型。前面章节保留设计基准；历史页数、测试数、未提交状态与问题清单均需对照当前代码。下一批的产物是一个经三种角色完整操作验收的版本，以及可重复使用的场景资料。

### 8.1 接续正在进行的工作

先接收 Mimo 的站间结算/配送修复，记录最终提交或文件校验值、涉及的接口/迁移、验证命令与原始结果；在这之前不交叉编辑其业务文件，不并发运行会清空同一测试库的任务。验收以最终版本为准，过程中读到的 diff 只作线索。

维持已定的开发模拟支付、逐商品旧桶回收、客户资产归属与跨站结算规则；本批不新造费用口径。影响钱、桶、库存、权限的实际错误优先于样式问题。新的经营决定仍走现有待拍板正本，不用 UI 文案替产品作决定。

### 8.2 第一项实现：顾客订单详情可恢复、状态及时更新

范围：`miniapp-user/pages/order/detail.js`、同页 WXML/JSON 与相应页面行为测试；需要复用公共反馈组件时先查现有组件。无需数据库迁移。

当前源码线索：详情 `onLoad` 请求失败后只 toast，`onPullDownRefresh` 依赖 `data.order` 已存在，页面未启用下拉刷新且未实现 `onShow`；见 `detail.js:26-41`、`:113-115` 与 `detail.json`。实现目标：

- 用路由订单 ID 保留重试目标；首次请求失败时显示常驻错误和明确重试入口，不能只留下空白。
- 首次进入只触发一次必要加载；返回详情或小程序恢复到前台时更新订单、动作能力与联系信息，避免保留旧的“待配送/可以取消”。防止重复请求与旧响应覆盖新状态。
- 加载失败时不把旧状态当最新事实，不据此放开支付/取消；已有内容可保留，但须说明未能更新并给重试。
- 如保留下拉处理函数，同步启用页面配置；手动重试与下拉共用加载入口，不依赖上一次成功后的实体。
- 联系电话或图片失败不应使订单整页失败；联系信息不可取得时给可理解的反馈，不能伪造号码。

验收：执行真实页面处理函数，注入“首次失败→重试成功”“退后台→其他角色更新订单→返回”“慢旧响应晚于新响应返回”。另在微信运行时验首次失败画面、恢复后的状态/按钮与联系入口。Node 桩测试不替代微信渲染。

### 8.3 第二项实现：按高频任务减少页面负担

保持方案 29 的品牌色、字号与控件规则。先验客户首页、配送确认页、站长收款页三个样板，再按相同模式处理相似页面。每次限定 2–3 个页面，避免各页分别设计。

| 页面/现象（当前源码线索） | 下一步目标 | 验收依据 |
|---|---|---|
| 客户首页仍有独立装饰图和问候区（`home/index.wxml`、`home/index.wxss:26-110`） | 根据小屏截图再决定是否继续压缩；收货地点、在办订单和复购/选水优先 | 360×640 与 390×844；含长站名、长地址、进行中订单；记录进入“选择水/再来一单”的滚动和点击次数，不凭源码宣称首屏已改善 |
| 旧订单备注直接解释“无法安全区分客户留言”（`order/detail.wxml:111-114`） | 用简短的不可用说明；不向顾客讲迁移/内部流水，不拆分或猜造历史留言 | 新客户备注完整显示；旧内部记录不泄露；有无留言均不挤占主要动作 |
| 待确认收款页把多类规则常铺在头部（`station-mgmt/payments/index.wxml:13`） | 头部只保留“确认前核实钱已收到”；区分订单款/买票款所需信息放到对应记录，其余按需查看 | 首屏看清客户、金额和动作；失败可重试；不能把 PENDING 当到账证明；一并复现此前白屏线索 |
| 收款按钮和说明仍包含“收款+销账”“要么全成功要么全不动”（`station-mgmt/receivables/index.wxml:125-137`） | 主按钮只表达“登记已收款”；确认时突出所选客户、订单与实际金额，复杂解释移入帮助 | 原子性/收款判权保持不变；不能缩短文案后让未收到钱的单被误确认 |
| 配送完成页有较长的选填标题与凭据解释（`order/complete.wxml:219-246`） | 正常送水优先核对商品、实际旧桶、实际收款；照片保留可见选填入口，补充说明缩短 | 已付单不多问收款；现金实收仍须人工确认；新押金桶不默认回收、旧桶照常收；不能为了省一步自动填“已收齐” |

收款入口可共用一个待处理摘要，必须保留客户欠款、待确认流水、站间结算各自的解释与真实入口；同一订单不重复累加待办金额。站长零事项不占提醒区，低频员工申请有事再提示，完整管理目录仍常驻。任何移除节点先按删除协议给出引用核查，不直接删能力。

### 8.4 固定版本的六条联合验收链

沿用 `docs/audit/2026-09-16-场景测试矩阵.md` 登记结果，不另建同职责总表。准备可重复创建的专用体验账号与测试数据；造数脚本必须限定隔离体验环境，不清空开发者正在使用的业务库。主链路用同一订单贯穿顾客/站长/配送员，避免各端分别看“像是成功”的不同样例。

1. **新客首单**：选站/地址 → 新押金桶 → 模拟支付 → 站长分配 → 配送员送达 → 顾客看到正确订单、桶与押金。
2. **老客复购/混合单**：不同商品和新旧桶并存 → 逐商品报价/回桶建议 → 实际送达 → 三端商品与数量一致。
3. **现金未收款**：送达且未收钱 → 顾客与站长均能理解仍待收款 → 后续真实登记 → 刷新后状态一致，无重复流水。
4. **取消与退桶**：配送前取消/配送中申请分别处理；退桶走收到空桶、实际交付押金两步，顾客不会被文案误导为已经到账。
5. **跨站履约**：外派/拒接/接单/送达/结清，核对当前责任站、联系入口、快照金额与客户资产站别；采用 Mimo 最终实现后的版本。
6. **意外打断**：首次加载失败、提交超时结果未知、连续点击、切后台再回来、登录过期；每次都有下一步，不重复下单/收款、不把失败显示为零。

微信开发者工具与物理手机分别记结果；不能控制某个环境就标待验，不用浏览器示意图替代。截图记录角色、订单测试编号、页面路径、视口、版本与操作后结果；保存位置由执行环境记录，仓内维护文档不得依赖未跟踪的本机路径。

### 8.5 分工、完成判据与后续

- **持续上下文的执行模型（DS，或承接当前业务修复的 Mimo）**：状态恢复、接口/业务问题、联合链路与回归；同一条业务链只有一个实现负责人。
- **Luna/免费模型**：限定页面的短文案、排版、对照清单；输入须包含允许修改的页面、已验样板和不得改的业务字段。不能把重要规则判断拆给随时中断的任务。
- **GPT 负责上游与验收**：每批主动给出下一项的优先级、具体范围和通过条件；把发现的同类问题一起核查，交付后独立判断通过/返工/待验。无需用户逐个寻找问题，也不重复询问已决定的经营口径。

完成门槛：六条链路的关键动作可走通，影响钱/桶/权限的阻断项归零；三种角色高频页面均有原生操作证据；小屏、大字体、长文本与失败状态可用。每个问题分别记录“代码已改、自动验证结果、微信运行时结果”，只写“已改”不算完成。

通过后建议安排一个水站、一个配送员和少量体验者按一天经营流程做内部模拟演练，记录哪里需要解释、退回、反复点击或改走电话/纸笔。以这些观察安排最后一批改进，再准备上线前的真实支付/退款、域名与协议入口检查。真实支付仍按用户安排在上线前接通；内部演练不得把模拟支付当成真实收款。
