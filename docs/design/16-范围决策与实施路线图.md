| D25 | **水票分「定制票」与「统一水票」，定制优先、统一兜底**（2026-09-19）⚠️ **本行的"统一票是什么"已于 2026-09-20 被 D27 收口**（当时把它做成了"站级通用票账户 `product_id=0` + 站级一个价"，是形态理解错误；本行其余部分——**定制优先**这条裁定本身——仍然有效） | **已实施（v54 闭环 + 两端入口）**。产品原话「有的商品可能有水票，有的可能没有，建议开一个混合支付吧，但是这个先别做。还有一个解决方案，就是加一个统一水票功能，统一买多少单位（个数）打多少折这种」→ 追加裁定「定制优先，**统一水票**是可以设置项，比如买 10 张都打 9.5 折、30 张统一 9 折这种，定制和统一都有的情况下，定制优先，**统一的仅在没有定制水票的桶时生效**。混合支付不好做吗，**先做统一水票**」。落地形态：**统一票 = 站级通用票账户，用 `product_id = 0` 表达**（水票四张表的 `product_id` 都没有外键，**唯一键一个没动**）；**"本站是否开通" = 有没有上架的 `product_id=0` 档位**（不新增开关列，避免两处真值打架）。判据收敛成**唯一实现** `util/TicketScope.resolveAccount`（同 `BarrelScope` 的做法）：该商品定制票余额 > 0 → **只用定制**（不够也**不**拿统一票补差额 —— 本仓没有混合支付）；否则若本站配了统一票且商品是**桶装水**（`category=1`，与押金/桶账同口径，瓶装水/一次性桶/饮水器不可用）→ 扣站级通用账户。**统一票只能按档位买**（`product_id=0` 没有商品也没有库存行，散买会算出 0 元）；**平台给预设档 10/20/100 张**（`util/TicketPreset` + `GET /api/ticket-packages/presets`），但只是**一键填入的草稿**、不替站长落库 —— 因为"有上架的 `product_id=0` 档位"就是统一票的站级开关。购买/抵扣/退款全部过同一套批次账，**对账 E8 两条等式逐字未改**（只是多了一个"商品 0"维度）。正本 `sql/migration_v54_ticket_record_account.sql`、`docs/design/26` §26.8，用例 `UnifiedTicketIntegrationTest` / `TicketScopeTest`（共 13 例）。⚠️ **混合支付仍暂缓**（难处见 `26` §26.6），"票不够"当前 = 整单失败 + 结算页提前提示 |

| D26 | **结算页：水票支付只计费「除去水票的部分」；支付方式沿用上次由前端记**（2026-09-19） | **已实施**。产品口径「默认订单里，会沿用上次支付方式，我觉得前端记一下就好，不用再写进后端，然后水票支付时，水票支付方面就不显示计费了，只计费除去水票的部分。**不用写混合支付**，点击水票后，优先水票支付，但是经校验后，发现水票不足以覆盖该订单时，会启用微信支付，即剩下的金额使用微信支付」。**拍板：只做「显示 + 校验 + 引导」，写路径一行不动** —— 差额走微信要动「一单一条活跃流水 `uk_payment_active_order`」这处地基（正是 `26` §26.6 列的混合支付第一处），且**微信渠道全仓未接入**，做出来是一条付不掉的待支付单。三点落地：① 支付方式沿用 = **纯前端**本地偏好（`payMethodStorage`，下单成功那刻才写入）；② `quote.ticketPay` 下发抵扣预览，整单可被票结清时计费区只显示「水票抵扣 N 张 · ¥X」+「本次需付 ¥0.00」；③ 票不足**提交前就地拦住**并引导改选（放过去会让订单停在 `payment_status=0`、按派单判据进不了站长视野）。⚠️ **口径关键**：水票支付是**整单**结清（扣票成功后直接 PAID + `applyDepositOnPaid`），所以"票够"时本次要付 **0**，**不是「合计 − 水费」**。正本 `docs/design/26` §26.10，用例 `TicketPayPreviewIntegrationTest` |

| D27 | **「统一水票」= 站级统一折扣，不是一种票**（2026-09-20；**收口 D25 的形态**） | **已实施（v58 建表 + v59 撤回旧列 + 两端）**。产品原话：「统一水票，**在站长端是特殊化的**，但在**用户端看起来没区别**，执行上**也不是统一定价**，而是**对应水怎么统一打折、统一打几折**的区别，**不是专门卖统一水票**」+ 追问后拍板「按统一折扣买的票进**该商品**的账户，**只能抵那款水**」。⇒ D25 把它做成「站级通用票账户 `product_id=0` + 站级一个价（8.55/张、全站通用）」是**形态理解错了**：统一的是**折扣率**，不是价格；用户端也不该多出"统一水票"这个商品。定稿：① 新表 `station_ticket_discount`（`(station_id, qty)` 唯一，**只存折扣** `discount_per_mille` 950 = 9.5 折；**价格不落库** —— 落库就会与"各款水的价"分叉）；② 价格 = **各款水自己的水票价 × 折扣**（农夫山泉 20 → 19.00、娃哈哈 12 → 11.40）；③ 「有没有上架的折扣档」= 统一折扣的开关（不另设开关列）；④ **定制优先**（D25 那条裁定不变）：该商品 `inventory.ticket_enabled=1` 且水票价 > 0 → 走定制那套（散买按站级水票价、档位按 `ticket_package` 绝对价目表）；⑤ 只覆盖**桶装水**（`category=1`）；⑥ 账户**恒为该商品**，抵扣/退款与定制票完全同一条路 —— v54 为此加的 `ticket_record.account_product_id` 已由 **v59**（破坏性 DROP，待执行）撤回。判据唯一实现 `TicketTierService`（替代已删的 `util/TicketScope`）。正本 `docs/design/26` §26.11，用例 `StationTicketDiscountIntegrationTest`（6 例，核心那条：**同一个 9.5 折，20 元的水折出 19.00、12 元的水折出 11.40**）。⚠️ **真实库 `ticket_record`/`ticket_account`/`ticket_package` 均为 0 行** → 本次收口零数据迁移成本 |

### 1.1 D10 的落地清单（2026-09-18）

| 能力 | 端点 | 落点 | 为什么它算"在营能力"而不是新功能 |
|---|---|---|---|

**两处落点与最初设想不同，判据如下（都不是"顺手换个地方"）**：

- **绑定申请历史落在 `apply-bind` 而不是 `bind-wait`**：`app.js:_targetRoute` 把配送员的 **UNBOUND / REJECTED 路由到 `apply-bind`**，而 `bind-wait` 只在"审批中"停留（遇到被拒/被解绑就 `redirectTo` 回 apply-bind）。也就是说**最需要看历史的两种状态恰恰看不到等待页**，而 apply-bind 是这两类人唯一的落点。
- **转单撤回只修了后端、界面没接**：接线调研发现后端缺两条判据（① 没有校验"调用者是不是发起人" —— 同站任意配送员都能撤掉别人的转单；② 丢弃 `resolvePendingByKind` 的受影响行数 —— 对没有待决策转单的订单也返回成功并往 `special_note` 塞标记）。**两条已修 + 用例锁定**（`CrossStationDispatchIntegrationTest`）。界面暂不接的原因是结构问题：转单发起后 `delivery_staff_id` 立即变成对方，而 `DeliveryController` 有一条"无权查看其他配送员的订单"，**发起人自己都打不开这张单** → 撤回按钮无处可挂。要么放宽该查看守卫、要么在别处给发起人一个"我发起的待决策转单"列表，属产品/UX 决定。

**明确"不接线"的两条（判据：接线即造第二条读路径）**：

- `GET /api/delivery/orders/station-completed` 与通用列表 `GET /api/orders?status=4` 的 SQL **同源**（`OrderMapper.listByStationIdAndStatus`）。多接一条并不增加能力，只会让同一个界面有两套取数出口 —— 本仓"计价双轨"事故（见 `util/PriceUtil` 文件头）就是这么来的。**保留端点、不接界面**。

### 1.2 D13「原路径返回」的口径（2026-09-18）

退款**只有一个编排入口**（`PaymentService.refundOrder`，取消订单链）与一个**站长手工入口**（`PUT /api/payments/{id}/refund` → `refundPayment`）。两者都必须按**原支付方式**把钱退回去，且留下与之一致的凭据：

| 原支付方式 | 钱退到哪里 | 凭据 | 系统还能做什么 |
|---|---|---|---|
| **3 水票** | **回补 `ticket_lot` 批次**（按 `ticket_record` 的实际消耗记录，按当时单价还原） | `ticket_record` 回补流水 + 批次 `remain_qty` | 全自动（走 `TicketLotService`，唯一写入口） |

## 2. 能不能"模仿美团"？——骨架可以，四处必须偏离

外卖平台的形态与本行业有**结构性差异**。照抄以下四点会做出一个拧巴的系统：

### 2.1 结算主体不同 → 计件工资是**站长台账**，不是平台结算

- 外卖：骑手是**平台**的众包运力，平台按单结算给骑手，商家向平台付佣金。
- 桶装水：配送员是**水站**的雇员/长期合作，**工钱由站长发**。本项目的角色模型也是这个：`staff.station_id` 是固定归属（`schema.sql:577`），跨站只是"帮忙"（`staff_station_application`）。

**后果**：不要做"平台结算单""佣金抽成""骑手钱包"。计件工资的账只在**站内**成立，见 `18-配送员计件与工资.md`。

### 2.2 计量单位不同 → 计件主口径是**桶**，不是单

- 外卖：一单 = 一份餐，按**单**计价。
- 桶装水：一单常是 1~3 桶，**每桶 18.9L ≈ 19kg**，搬运成本与**桶数**强相关。

**后果**：计件以"桶"为主单位，单数/距离/楼层是**加成项**。只按单计价会让配送员不愿接多桶单。

### 2.3 任务形态不同 → 桶装水的配送任务**天生是双向的**

外卖只有去程。桶装水一趟 = **送水（去程）+ 收空桶（回程）**，而回桶数是要当场核对的：

- `orders.delivery_bucket_qty`（送出空桶数）、`orders.return_bucket_qty`（回收空桶数）、`orders.barrel_discrepancy`（空桶差异）—— `schema.sql:456-457,472`

**后果**：
1. "完成配送"的定义**包含回桶**，不是"送到就走"；
2. 计件工资里应有**回桶率考核**（真实站长确实会为丢桶扣配送员工钱）；
3. 一条路线的收益要同时算送水与回桶两个动作。

### 2.4 楼层费必须拆成**两笔**，外卖只有一个"配送费"

- **向客户收**的楼层/上楼费 → **收入项**
- **给配送员补**的楼层费 → **成本项**

外卖模型里只有一个配送费，混在一起会导致：客户投诉乱收费 + 配送员工资算不出来 + 对账不平。这两笔**必须分开建模**，见 `17` §5 与 `18` §4。

### 2.5 另外四处"不要做"

| 不要做 | 理由 |
|---|---|
| **算法派单** | 本行业站长**自己就是调度员**（通常自己也送）。现有 `dispatch` / `transferToStaff` / `claimPool` 已够用，派单的操作者是人，不是算法 |
| **分钟级时效与超时罚则** | 桶装水的 SLA 是"半天/当天"。`orders.delivery_time_request` 是自由文本（"下午3点后""周末送"），不存在"准时宝"那套 |
| **骑手评分体系** | 样本太小（一个站 1~5 个配送员），且是长期雇佣关系不是平台派单竞争 |
| **动态定价/天气加价** | 桶装水定价是站长挂价的长期价格，不是实时撮合 |

### 2.6 可以借鉴的部分

| 借鉴 | 在本项目的落点 |
|---|---|
| 抢单池 / 转单 / 外派 | **已有**：`claimPool`/`transferToStaff`/`outsource`（`OrderWorkflowServiceImpl:698,754,809`） |
| 起送量、配送范围、运费 | 缺，本次做，见 `17` |
| 计件 + 距离/楼层补贴 | 缺，本次做，见 `18` |
| 营业状态（休息中/暂停接单） | **已有**：`StationOperatingStatus`（v32），且已是"软状态不阻断下单" |

**⚠️ 实施中踩到的一个坑（值得记住）**：给 `payment_record` 加 `NOT NULL DEFAULT 0.00` 的费用列之后，
**29 个用例一次全红**（购票、现金收款、退款、押金、取消回滚，覆盖 11 个测试类）。
根因：SQL 里的 `DEFAULT 0.00` **只在「该列没有出现在 INSERT 语句里」时才生效** ——
而 `PaymentRecordMapper.insert` 显式列出了这两列，实体字段又是 `null`，
等于把 NULL **显式**塞进 NOT NULL 列，MySQL 直接报 `Column 'delivery_fee' cannot be null`，
**整条支付链路全挂**。修法：在 mapper 的 SQL 边界用 `IFNULL(#{deliveryFee}, 0.00)` 兜住，并就地留注释。

> **判据：给已有表加 NOT NULL 列时，必须查清全仓有几条写路径、其中哪几条会显式传 NULL。
> `DEFAULT` 救不了显式 NULL。** 另外这条也说明"编译通过 + 新用例通过"远不足以判定安全 ——
> 本次新写的 3 个用例全绿，坏掉的是**别人**的 29 个用例。

## 4. 贯穿四条原则（每个功能都要过一遍）

### 4.1 凡是"钱 / 次数 / 资产"，必须有账户 + 流水 + 幂等 + 可复算

本仓已有的正面样本：桶权益（`customer_barrel_lot` 批次 + `BarrelLedgerService` 唯一写入口）、押金（`deposit_record` + 等式1）、水票（`ticket_account` + `ticket_record`）。

**反例警戒**：把"免配送次数""客户折扣"做成客户画像上的一个开关。它会退化成没有校验、没有流水、没有对账的裸状态，最后变成"站长说还有 3 次、客户说还有 5 次"的扯皮。

### 4.2 计量规则必须**同口径**，且只能实现一次

`PriceUtil` 的文件头注释记录了真实事故：`quote()` 与 `createOrder()` 各算各的，结算页价格与实际订单金额不一致（计价双轨 → 客诉）。

**判据：任何新增计费规则（起送量/运费/楼层费）必须同时进入 `PaymentServiceImpl.quote` 与 `OrderServiceImpl.createOrder`，且计算逻辑抽到 `util/` 下唯一实现，禁止两处各写一个 if。**

### 4.3 可预期的经营状态 → 业务错误（`code=1`），不要升级成系统异常

对齐 `AGENTS.md` 关于"对象存储未配置不得表现为 500"的判据。例如"低于起送量""超出配送范围""水票余额不足"都是**可预期的经营状态**，应给可读文案的 `code=1`，不得抛 `RuntimeException`。

### 4.4 金额列**只加不改**

`orders` 现有三个金额列语义已锁死且被对账依赖：

- `water_amount` 水费
- `deposit_amount` **可退押金**（退款路径按它释放押金：`PaymentServiceImpl:557-569`）
- `total_amount` 目前 = 水费 + 押金（`PaymentServiceImpl.quote:744`）

**新增运费/楼层费必须新开列，绝不允许塞进 `water_amount` 或 `deposit_amount`。**

⚠️ **塞进 `deposit_amount` 会真丢钱**：退款时按 `orders.deposit_amount` 释放押金余额（`PaymentServiceImpl:557`），把 10 元运费混进去，取消订单时会**多退 10 元到客户押金账户**。

### 5.1 验证方法（本工作流的"跑测试"标准姿势）

> 2026-09-17 加的。**背景：本工作区长期有第二个 agent 会话共享 `build/` 与 `aquaflow_test`，直接跑
> `gradlew test` 会互相污染**（实测一次全量跑出 250/278 失败，其中 250 个是"瞬时失败"而非真缺陷）。

两步隔离，缺一不可：

1. **代码隔离 —— 干净 worktree**：`git worktree add --detach .verify-r9 HEAD`。
   必须这样做的第二个理由更重要：**HEAD 之外的未提交改动会打红整个测试套件**。
   实测另一个工作流的 `ProductImageResolver` 声明了两个构造器且都无 `@Autowired`，
   Spring 找不到默认构造器 → **上下文加载失败 → 所有 250 个走 Spring 的用例一次全红**
   （唯一"通过"的 28 个是纯单元用例，它们不起容器）。**看到"大批用例同时红"先去看
   `AquaFlowApplicationTests` 的 `Caused by`，不要逐个查业务断言。**
   `application-local.yml` 是 gitignore 的，需要手工拷进 worktree（**用完删掉 worktree，
   别把带密钥的副本留在磁盘上**）。
2. **数据隔离 —— 私有测试库**：`application-test.yml` 支持 `${TEST_DB_URL:...}` 覆盖，
   所以**不用改任何文件**：
   ```powershell
   $env:TEST_DB_URL='jdbc:mysql://127.0.0.1:3306/aquaflow_test_r9?useUnicode=true&characterEncoding=utf-8&serverTimezone=Asia/Shanghai&allowPublicKeyRetrieval=true&useSSL=false'
   ```
   建库必须照 `schema.sql` 的排序规则建（`utf8mb4_0900_ai_ci`），
   再按 AGENTS §4 的**字节级重定向**导入 baseline：
   `cmd /c "mysql -uroot --password=*** --default-character-set=utf8mb4 aquaflow_test_r9 < schema.sql"`。
   自检：`information_schema.TABLES` 的表数必须与 `schema.sql` 里 `CREATE TABLE` 的条数**相等**。
   库名含 `test`，`AbstractIntegrationTest` 的护栏因此照样生效。

**判据：报告"测试全绿"前，先确认结果 XML 的时间戳晚于本次运行，且唯一性对自己的库。**
`--tests` 过滤器会清空 `build/test-results/test/`，所以"只剩目标类的 XML"本身就是过滤器生效的证据。

### 5.2 对账等式的三处假警报（2026-09-17 修正）

> 这轮把「**新增写路径跑完后原有等式仍平**」做成了一条用例
> （`ReconciliationAfterNewFeaturesIntegrationTest`：一笔配送计件 + 一张结算单 + 一次按档位购票
> + 一次应收核销，跑完断言 V1/V2 每一项都为 0）。**它一次抓出三个问题**，其中两个是这次改动之前
> 就存在的——各自的用例只断言"自己那条等式"，所以一直没人发现。

| 等式 | 症状 | 根因 | 后果 |
|---|---|---|---|
| 等式2 `p2a` | 核销后不平 | `ReceivableService.settle` 只调 `markPaidIfCollectable` 把 `payment_status` 置 2，**没补写 PAID 支付流水** | 站长**每核销一单**，日结就报一次不平并发 SYSTEM 告警 |
| 等式2 `p2c` | 买过水票就不平 | 把 `order_id IS NULL` 一律当孤儿流水，而**在线购票本来就是无订单支付**（v33） | 任何买过水票的水站，日结**天天**误报 |
| 等式3 `b3a` | 送过货就不平 | 直接数 `customer_barrel_in_transit.status='DELIVERED'` 的行数当异常，而 `BarrelLedgerService` 送达到账时**故意**把记录标为 DELIVERED 且不物理删除（供追溯，见实体类注释） | **每一笔完成过的配送**都让等式3 不平 |

**三处共同点：把"正常业务的合法状态"当成了异常。** 后果不是"少报"，而是**日结永远不平** ——
SYSTEM 告警天天发，真问题被彻底淹没（正是 `18` §7 里 E-PAY 那条注释警告过的同一件事）。

修正：
- `p2a`：核销时先 `PaymentService.recordCashCollection(orderId, "站长核销应收账款")` 补写 PAID 流水，
  再 `markPaidIfCollectable`。**没有另写一条记账实现** —— 该重载就是为此加的，实现仍只有一份
  （新增一条"补流水"路径 = 多一处可能漏写凭证的地方）。
- `p2c`：加 `AND p.ticket_qty IS NULL`，只把「既无订单、又非购票」的流水当孤儿。
- `b3a`：改成「标了已送达**却没有对应权益批次**」—— 那才是真的丢权益。

**判据：写对账等式时，先问一句"这个状态在正常经营里会不会合法出现"。**
会的话，它就不能出现在"差异计数"里，否则这条等式是天天响的假警报，等于没有。

### 5.3 交付判据：**后端就位 ≠ 用户能用上**（2026-09-18）

本轮的新功能全部是"后端 + 一个独立模块页"的形态，于是暴露出一类**不会报错**的缺口：
能力写完了、接口通了、用例也绿了，但**用户从他的日常路径走不到它**，界面上也没有它的位置。
2026-09-18 一次抓到两处，都不是代码缺陷，是**入口没接**：

| 能力 | 后端 | 用户实际能碰到的 | 后果 |
|---|---|---|---|
| 配送费 / 楼层费（v35） | `orders.delivery_fee` / `floor_fee`，报价与下单同口径 | **下单页**有：主摘要与费用明细弹窗都列了；**订单详情页没有** | 客户付完款在订单详情里看不到自己多付了什么；且**明细弹窗各项之和 ≠ 合计**（只把费用并进合计没列出来）—— 用户会以为算错了钱 |
| 水票档位（v36） | `ticket_package` 全套 CRUD + 客户端档位选择器 | 客户端有档位选择；**站长端只有独立模块**「水票档位」，商品上架/本站设置里只有"水票价格(元/张)" | 站长的视角里**水票仍在按张卖** —— 他上架时配完单张价就以为完事了，档位那页不是他的必经路径 |

**判据（新增功能的收尾清单加一条）**：
1. 写完一个能力，**从"用户从哪一步碰到它"倒着核一遍入口** —— 站长走「商品上架 → 本站设置」、
   客户走「下单 → 付款 → 订单详情」、配送员走「接单 → 完成配送」，这三条是三个角色各自的必经路径；
2. **基本能力放进必经路径的快捷形式**（就地能填的几行），**更丰富的配置才跳独立模块** ——
   反过来的做法（只给独立模块）会让功能事实上不可发现；
3. **凡是要客户掏钱/核对的数字，明细里必须逐项出现**，不能只并进合计 —— 这一条在
   `create.wxml` 里已经写过一次注释，本轮又在同一个坑上摔了一次（订单详情页）；
4. 没配就等于没有的能力（如"没挂档位只能散买"），**界面必须写明**，不能让人以为打开开关就自动有了。
