## 1. 为什么没有 Flyway

项目**未启用 Flyway**（无依赖、无配置，`src/main/resources/db/migration/` 目录不存在）。
`sql/**` 全部靠手工执行，没有版本表、没有自动校验。

这是单人项目的取舍：迁移频率低，执行证据逐条登记进 `sql/README.md` 比引入迁移框架更可控。
代价是**没有任何机制阻止你漏跑一个脚本** —— 所以第 6 节与第 7 节的流程不是建议，是防线。

## 2. 编号与命名

- 新建脚本前**先 `ls sql/` 看编号是否被占用**。
  ⚠️ **不要照任何清单的最后一个数字 + 1** —— 编号被并行占用过一次（v38 被商品图片库占用，另一个工作流改用 v39），清单不会告诉你这件事。
- 命名沿用 `migration_v<NN>_<snake_case_描述>.sql`。历史脚本还有 `migration_aq<NNN>_*`、`migration_v1_*` 等前缀，新脚本不要再沿用。
- 一个脚本只做一件事，并在文件头写清「对象 / 目的 / 幂等实现方式 / 是否有破坏性操作」。

## 3. 幂等实现范式

**所有迁移脚本必须幂等**（同一个脚本跑第二遍不能报错）。

### 3.1 唯一正确写法

MySQL 8.4 没有条件 DDL，统一用 `information_schema` 预检 + `PREPARE`：

```sql
-- 例：给表加一列（幂等）
SET @has_col = (SELECT COUNT(*) FROM INFORMATION_SCHEMA.COLUMNS
  WHERE TABLE_SCHEMA = DATABASE() AND TABLE_NAME = 't' AND COLUMN_NAME = 'c');

SET @sql = IF(@has_col = 0,
  'ALTER TABLE `t` ADD COLUMN `c` bigint DEFAULT NULL COMMENT ''说明''',
  'SELECT ''column c already exists''');
PREPARE stmt FROM @sql;
EXECUTE stmt;
DEALLOCATE PREPARE stmt;
```

删列、加索引、删索引同理（把探测条件换成 `STATISTICS` 表）。

### 3.2 ⚠️ `IF NOT EXISTS` 不可用（MySQL ≠ MariaDB）

**MySQL 不支持 `IF [NOT] EXISTS` 形式的 `ALTER TABLE` / `CREATE INDEX`**，
那是 MariaDB 的扩展。以下三种写法在 MySQL 8.4 上**直接语法报错**：

| 写法 | MySQL 8.4.8 实测 |
|---|---|
| `ALTER TABLE t ADD COLUMN IF NOT EXISTS c int` | **ERROR 1064**（语法错误） |
| `CREATE INDEX IF NOT EXISTS ix ON t(a)` | **ERROR 1064** |
| `ALTER TABLE t DROP COLUMN IF EXISTS c` | **ERROR 1064** |
| `ALTER TABLE t ADD COLUMN c int` | 正常 |

⚠️ **放在 `PREPARE` 字符串里的写法更危险**：探测分支只在"目标不存在"时才选中它，
于是**脚本平时看起来能跑通，恰好在真正需要动手的那一次失败**。

> 本仓有 9 个历史脚本用了这套语法（`migration_v15_*`、`migration_v1_alignment.sql`
> 是无条件执行；`migration_fix_schema_alignment.sql`、`migration_v14_*`、`migration_v22_*`、
> `migration_v23_*`、`migration_aq_bucket_right_v1_ddl.sql`、`v2_fix_p0_customer1.sql`、
> `v3_reconcile_v2.sql` 放在 `PREPARE` 里）。**现状与处置见 §9** —— 改动历史脚本前先读那一节。

### 3.3 `CREATE TABLE IF NOT EXISTS` 是支持的

`CREATE TABLE IF NOT EXISTS` 是 MySQL 原生语法，可以放心用（`schema.sql` 通篇都是它）。
不支持的是 `ALTER TABLE` / `CREATE INDEX` 上的 `IF [NOT] EXISTS`。

## 4. 破坏性操作

- **必须先上代码、再执行 SQL。** 老代码若还有以被删列命名的 `SELECT` / `INSERT`，DROP 之后立刻 1054。
- **执行前 `mysqldump`**，备份文件放仓库外的备份目录（`backup/` 已被 gitignore，**勿提交**）。
- **脚本自带护栏**：`migration_v41`（本仓唯一的破坏性 DROP）在删列前先数非 NULL 行，**有值就中止** DROP ——
  挂空列的前提不成立时宁可留着。新写破坏性脚本请沿用这个形状。
- 执行后按 [`../operations/01-部署与运维.md`](../operations/01-部署与运维.md) §6 跑一次对账。

## 5. ⚠️ MySQL 在解析期校验列名

对某列的 `MODIFY` / `WHERE col` **即使执行不到也会在解析期报 1054**。

推论：**删列时必须把历史迁移里对该列的引用一并清掉**。
`migration_v41` 删 `orders.batch_id` 时就因为这条，同时删掉了 `migration_v24` 里一条
只改注释的 `MODIFY COLUMN batch_id` —— 否则 v24 在跑过 v41 的库上必报 1054，
把一个"只改注释"的脚本变成不可重复执行的脚本。

⚠️ 这条也意味着：**改历史脚本要连带检查它引用的列是否还存在**。

## 6. 执行与证据登记

```bash
mysql -uroot <库名> < 脚本.sql        # 执行务必带库名
```

执行完成后**在 `sql/README.md` 登记一行**：版本号、文件名、用途、是否有破坏性操作、
**执行时间、备份文件名、执行结果**（行数变化、幂等复跑结果）。

> 该清单是迁移的**唯一正本**。不要在其他文档里复述清单 —— 有正本就不要在两处定义同一份事实。

⚠️ 清单**已知有缺陷**（漏列部分脚本、个别脚本之间存在顺序冲突，且 `v25` 改名与 `v1_backfill`
依赖旧表名）。**执行前人工核对**，不要盲跑。

## 7. ⚠️ 改了库结构必须同步 `schema.sql`

`schema.sql` 是**新建库的唯一权威基线**。老库靠迁移脚本演进，新库靠 `schema.sql`，
**两者不同步就会长出"新库缺列、旧库多列"的分裂**，而且只在特定环境暴露。

已登记的两处分裂（详见 [`../architecture/03-数据模型.md`](../architecture/03-数据模型.md) §10）：

- `station.creator_staff_id` —— 只由 `migration_fix_schema_alignment.sql` 添加，`schema.sql` 里没有；
- `barrel_record.idx_barrel_record_station` —— 同上，基线缺索引。

**新写迁移时自问**：这个改动是"新库本来就该有"的吗？是 → 同时改 `schema.sql`。

## 8. 严禁在生产执行

`reset_data.sql`、`clear_data.sql`（都是 TRUNCATE 多表）、`reconcile_order_814.sql`、
`seed_dev_account.sql`、`seed_new_user_83.sql`、`sql/archive/**`（已过期且不可执行）。

## 9. 待确认事项

| 待确认内容 | 需要的验证手段 | 影响 |
|---|---|---|
| **9 个脚本的 `IF [NOT] EXISTS` 语法在 MySQL 上不可用**（§3.2，已实测 1064） | 先复核 `sql/README.md` 里这几个脚本的"执行成功"记录是怎么过的（很可能是护栏选了另一条分支、语句从未真正执行）；再决定是改写还是标注作废 | `migration_v15_*` 与 `migration_v1_alignment.sql` 是无条件执行，**跑必报 1064**；其余 7 个**恰好在需要动手时失败** —— 这正是老库升级最可能踩的坑 |
| `sql/README.md` 的必跑清单与实际需要不一致（漏列 + 顺序冲突） | 在一个从早期基线重建的库上逐条核对清单，跑一遍全量测试 | 漏跑会让老库缺表缺列，运行时报 1054 |
| `fix_schema_alignment` 补的若干列是否都还需要 | 逐列核对代码读写点 | 其中 `station.creator_staff_id` 已确认是死列（代码只 set 不落库） |
| 历史脚本是否要统一改成 §3.1 的范式 | 改动量大、且属历史记录，需先与产品/维护者确认边界 | 不统一则新老脚本范式并存，容易照抄错的 |
