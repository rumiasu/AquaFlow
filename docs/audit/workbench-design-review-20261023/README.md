## 问题与交付影响

P0 = 影响使用或记账可信度，阻断相关操作交付；P1 = 明显体验或判断错误，相关任务试用前应修；P2 = 可延期，不据此阻断整包源码交接。分级不是把所有问题都变成全站发布阻断。

### WB-01 · P0 · 同次“还空桶”会换键重发

**路由/组件：** 员工 `pages/station-mgmt/customers/detail/index` 的还空桶弹窗。

**证据：** `miniapp-delivery/pages/station-mgmt/customers/detail/index.js:284` 无在途入口守卫，`:293` 每次生成新 `clientToken`，`:301` 超时仅 toast 后解锁；`index.wxml:335` 是绑定点击的 `view`，所谓 disabled 只加 class。后端 `AquaFlow-backend/src/main/java/com/example/aquaflow/service/impl/BarrelServiceImpl.java:1078` 仅按同 token 去重；`service/BarrelLedgerService.java:655` 校验剩余持有量后继续减桶。

**复现/影响：** 首次响应未返回时连点，两次 API 调用、不同 token；注入 `requestMayHaveOccurred=true` 后重试也是两次不同 token。若原有 4 桶、实际交 1 桶，两个请求各减 1 仍符合物理上限，可把同次交桶记两次。这一后果由后端源码链推导，未在数据库实写验证；不是已发生资金退款，也不是所有余额都会被重复扣。

**最小建议：** 入口先检查在途状态；同一交桶意图保存并复用 token，绑定原身份、客户及数量。未知结果常驻显示“先核对原登记”，重进弹窗继续核对原请求，不能换键重发；明确拒绝后才允许修改内容。沿用已有后端去重合同，不重写桶账。

**交付：** 修复并通过连点/超时/离页恢复反例前，不能把“站长代客还空桶”交作可用操作。只读评价及其他已验能力可继续交接。

### WB-02 · P1 · 资产调整后返回，详情仍像最新资料

**证据：** 同页 `index.js:40` 只在 `onLoad` 读取资料/资产；`:225` 可进入资产调整子页；没有 `onShow` 刷新。`:321` 的下拉刷新存在，故不是完全无法恢复。合成资产从 2 改成 3 后模拟返回，资产请求仍只有一次、页面仍显示 2。

**影响/最小建议：** 站长执行调整或替客下单后，回到详情可能以为没生效，或按旧上限还桶。返回时重新核对资产与资料，读取中标明旧快照；相关操作等核对完成再放开，首入避免双请求。

**交付：** 影响资产办理闭环，应在站长试用前修；不改变调整单本身的后端正确性。

### WB-03 · P1 · 资料失败连带隐藏成功的资产

**证据：** 同页 `index.js:49` 并行独立读取资料、资产；`index.wxml:13` 却以 `!loading && profile` 包住整个资产区（资产标题在 `:43`）。资料请求失败、资产请求成功时，`data.assets` 存在，但当前 WXML 条件投影没有“本站资产”。

**影响/最小建议：** 局部画像故障被扩大成资产也不可看、调整入口也不可达。让已通过权限检查的资产区独立于画像渲染，用客户编号作身份兜底，各自保留加载/失败/重试；不展示未授权内容。

**交付：** 影响局部失败下的资产可用性，站长试用前应修；未认定为越权或资产丢失。

### WB-04 · P1 · 明确选择的非默认地址被首页刷新覆盖

**路由：** 客户 `pages/address/list?from=home` → `pages/home/index` → `pages/order/create`。

**证据：** `miniapp-user/pages/address/list.js:58` 保存用户选择；`home/index.js:102` 先开始异步刷新、`:105` 接收该选择；刷新到 `:558` 后无条件改用默认/首地址，`:1035` 将其传到结算。真实 Page 合成反例：选 13，返回即时为 13，刷新结束为 12，结算 URL 也是 12。

**影响/最小建议：** 用户刚选的配送地点不生效，可能反复选择或在确认页漏看地址变化。刷新时优先保留仍在最新地址清单中的已选 ID；只有该地址确实不可用时才提示重新选择，再核实报价。保留最终确认，不调整配送计费规则。

**交付：** 客户多地址订水试用前应修；没有真实下单或声称已经错送。

### WB-05 · P1 · 经营趋势切“金额”仍画单量

**路由：** 员工 `pages/station-mgmt/dashboard/index`。

**证据：** `index.js:48` 的 `onMetricChange` 只设 metric 并 `drawTrend()`；真正计算 `orders/amount` 与标题在 `:172` 的 `prepareCharts`，未重新执行。输入单量 3、金额 120，选择金额后 `trendChart.values` 仍为 `[3]`、标题仍“订单量趋势”。多点数据时还会切成金额折线（`:262`），但数值仍未切换。

**影响/最小建议：** 页面响应了点击却展示错误经营指标，不能用颜色/曲线样式解释。切换时从同份 `report` 重算数据和标题，再绘制；补金额→单量、切周期及零数据对照。

**交付：** 金额趋势不可作为准确功能交付；订单/收款账本未被此显示错误改写。Canvas 实际初次绘制和设备像素另待原生核对。

### WB-06 · P2 · 首页列表坏图没有占位恢复

**证据：** `miniapp-user/pages/home/index.wxml:140` 的复购图和 `:181` 的商品列表图，只按 URL 非空渲染 image，未绑定错误处理；占位仅在 URL 为空时出现。对照同页海报商品 `:14`、商城 `pages/shop/index.wxml:57` 和确认页 `pages/order/create.wxml:71` 已有 `binderror`。

**影响/最小建议：** URL 过期/下载失败时，首页这两处不能转成明确占位，同类商品辨认更依赖名称。复用已存在的失败展示模式，按商品 ID+URL 记录失败，保留名称、规格、价格和数量；正常新加载允许重试。不生成伪品牌图、不接触 COS 凭据。

**交付：** 不阻断下单；“坏图时缺少恢复分支”是代码事实，实际空白/图标外观没有像素验收。

### WB-07 · P2 · 恢复清单中的下架商品静默不见

**证据：** `home/index.js:574` 保留完整存储清单，但 `:797` 仅遍历最新商品生成视图/数量，`:976` 也仅用最新商品生成结算项。合成恢复 `{10:1,11:1}`、当前商品仅 10：存储仍有两件，页面只计一件，结算候选只含 10。不是购物车被清空，也没有提交订单。

**影响/最小建议：** 部分商品下架后，顾客难以知道少了什么，可能以为恢复完整。就地说明“另有 1 项暂不可订”，允许查看并明确移除/重选；保留原草稿，不自动替换 SKU，不引入新购物车业务。

**交付：** 可延期；已有断网、重启、切站/换账号恢复本轮测试通过，不能因本问题否定这些已验能力。

### WB-08 · P2 · 普通意见反馈的未知结果仍诱导重发（既有 D01）

**证据：** `miniapp-delivery/pages/report/index.js:188` 对可能已执行的超时仍只显示失败、`:192` 释放提交锁；`index.wxml:32` 恢复“提交反馈”。实际 Page 两次确认发出两次普通反馈 API 调用。与 [既有员工复核的重要未解决项 D01](../staff-experience-review-20261023.md) 一致，未重新包装为新发现。

**影响/最小建议：** 可能新增重复普通反馈、增加处理负担。先给常驻“结果待核实”和已有反馈记录入口；不能凭正文/时间猜原反馈，严格一次写入需另定普通反馈幂等合同。此项不涉及收款、退款或资产写入。

**交付：** 不阻断本次源码/设计评价交接，作为明确后续项保留。

### WB-09 · P2 · 经营待办把主动退票目录排在退款责任前（视觉推断）

**证据：** `miniapp-delivery/pages/station-mgmt/index.wxml:121` 将六类事项合并为一个“业务待办与退出”入口；`business-waiting/index.wxml:4` 缺货、`:12` 可退水票批次、`:18` 退桶/待退款、`:29` 拒付、`:68` 返还款、`:76` 净桶依次纵向排列。`index.js:15` 仅 stock/returns/recoveries/barrels 支持定位；从完整目录进入没有 section。

**影响/最小建议：** 入口没有特定定位且票批次较多时，站长需越过主动办理目录才能看到后面的当前责任。增加轻量分区锚点或现有计数跳转，让待办责任先于主动退出目录；保留各自金额、口径和全部入口，不新增经营汇总、不改默认筛选业务。

**交付：** 非阻断建议。当前信息顺序由代码确证，滚动距离和实际首屏拥挤程度是推断；没有截图，不能认定必然遮挡。

## 验证、缺口与下一步

- 实跑 **12 套既有定向测试、228 个计数项**，退出码均 0、每套有 ASCII 完成标记，明细见 [verification.json](verification.json)。测试涵盖无站/选站、购物车恢复、费用抽屉、备注、目录失败态、管理页、经营待办和配送可读性/弹层；没有重跑全后端或无关全量检查。
- [离线反例脚本](reproduce-known-defects.cjs) 实际执行 **8 个探针**，证明 WB-01 两种情形和 WB-02/03/04/05/07/08 可复现；[结果](probe-results.json) 的成功含义是“反例成立”，不是“产品通过”。真实 Page 执行、API 桩、一次 WXML 条件投影；不使用浏览器点击、HTTP 或数据库，不模拟交易成功来充验收。
- **本轮未做：** 微信编译/真机、原生弹窗/软键盘/大字体/安全区像素、真实用户/登录、付款/退款、后端集成、腾讯云数据或凭据、部署与推送。旧图中的 Canvas 缺口是旧夹具覆盖限制，不直接指认当前生产图表没有实现；WB-05 是独立于像素的当前数据错误。

本目录是审查快照，问题正本为 [issues.json](issues.json)，没有新增待拍板业务规则。未将前次已撤回的“复购必须默认归属站”重新报为缺陷；继续尊重既有策略与 design/16 的决策边界。
