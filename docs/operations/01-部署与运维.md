## 1. 部署形态

单进程 Spring Boot 应用 + 单个 MySQL 实例。**当前假定单实例部署** —— 限流计数与部分定时任务尚未做多实例改造（见 §9）。

| 组件 | 要求 |
|---|---|
| JDK | 17 |
| MySQL | 8.4 |
| 内存 / 磁盘 | 按水站数量评估；桶账与流水表是主要增长点 |

外部依赖都是**可选**的：腾讯云 COS（不配只影响图片上传）、告警 Webhook（不配则告警只落库）。

## 2. 配置

**所有配置走环境变量**，仓库内不落任何生产配置。变量清单的权威来源是
`AquaFlow-backend/.env.example`。分三类：

> ⚠️ **先看这一句，别只读 §2.1**：下面 §2.1 只是 `RequiredConfigChecker` 那**一道**硬校验（3 项），
> **生产真正的必填项有 9 项**（§2.2 的并集）。只按 §2.1 配，缺 `DB_*` / `CORS_ALLOWED_ORIGINS` /
> 员工端 appid 时应用照样起不来，而报错是另一种（`Could not resolve placeholder`）。

### 2.1 启动期硬校验（`RequiredConfigChecker`，缺一即拒绝启动）

| 变量 | 约束 |
|---|---|
| `JWT_SECRET` | **长度必须 ≥ 32**，否则拒绝启动 |
| `WX_APP_ID` | 必填 |
| `WX_APP_SECRET` | 必填 |

### 2.2 生产必填（缺失 → **拒绝启动**）

⚠️ **这份清单是 2026-09-28 用发布物 jar 逐个实测出来的**，不是读代码猜的
（`node scripts/prod-startup-check.js` 会拿 `build/libs` 的 jar 真起 13 次，
每次摘掉一个变量，断言"必需项必须拒启、可选降级项必须能起"）。**两套机制别混**：

| 机制 | 覆盖的变量 | 怎么失败的 |
|---|---|---|
| `RequiredConfigChecker`（`@Value("${x:}")` + 手动判空） | `JWT_SECRET`（**另需长度 ≥ 32**）、`WX_APP_ID`、`WX_APP_SECRET` | 抛 `IllegalStateException`，报「缺少必需的安全配置」 |
| `application-prod.yml` 里的 **`${VAR}`（无默认值）** | `DB_URL` / `DB_USERNAME` / `DB_PASSWORD` / `WX_STAFF_APP_ID` / `WX_STAFF_APP_SECRET` / `CORS_ALLOWED_ORIGINS` | Spring 解析占位符失败，报 `Could not resolve placeholder` |

⇒ **生产必需共 9 项**：上表两行的并集（`JWT_SECRET` 只算一项）。

⚠️ **员工端那对（`WX_STAFF_APP_ID/SECRET`）在生产是必需的** —— 注意它与本地行为**不同**：
`RequiredConfigChecker` 只对它 `log.warn`（本地有 dev-login 兜底），
**真正让它拒启的是 prod yml 的无默认值占位符**。别照本地行为推断生产。

### 2.3 可选与不影响启动的变量

| 变量 | 缺失后果 |
|---|---|
| `COS_REGION` / `COS_SECRET_ID` / `COS_SECRET_KEY` / `COS_BUCKET_NAME` | **只降级，不阻断启动**：图片上传回「对象存储未配置，图片上传不可用」，订单/配送/桶账/水票/对账照常 |
| `DEV_LOGIN_ENABLED` | **生产必须 `false`**；prod 下该 Controller Bean 根本不存在 ⇒ 路径返回 `code=404`（不是"配了才安全"，是**压根没有这个入口**） |
| `MOCK_WECHAT_PAY` | **生产必须 `false`** —— 开了等于任何人选微信支付都零元购 |
| `MYBATIS_LOG_IMPL` / `RATE_LIMIT_*` / 告警相关变量 | 只影响日志实现、限流阈值、告警渠道 |

> ⚠️ **两条都不要写错**（都实测过）：
> ① **不要把 COS 写成必需** —— 它曾经是（`${COS_SECRET_ID}` 无默认值），结果是
> **没配对象存储整个水站系统起不来**，而代码本来为它设计了优雅降级；2026-09-28 已改成可选。
> 顺带发现同文件里的 `COS_REGION` / `COS_BUCKET_NAME` **没有任何代码读**，声明了也不会失败（悬空键），一并订正。
> ② **不要把 `CORS_ALLOWED_ORIGINS` / `DB_*` 写成"只 warn"** —— 它们缺失即拒启。

### 2.4 Profile

| Profile | 用途 | 说明 |
|---|---|---|
| `local` | 本地开发 | 密钥读 `src/main/resources/application-local.yml`（**已 gitignore，含真实密钥，禁止提交、禁止回显**）。该文件还开着 dev-login 与微信**模拟支付渠道**，并按 IP 关掉了登录限流 |
| `prod` | 生产 | `--spring.profiles.active=prod` + 纯环境变量 |

## 3. 发布与回滚（可重复的过程）

> **本节写给要发布的人。** 判据是"照着做就能重复一次，且每一步都能自己判断成功没有"。
> 不需要判断力的部分已经脚本化；**需要判断的三步（迁移、观察、回滚决定）写清了判据**。

### 3.1 发布前：一把过本机门禁

```bash
node scripts/verify-local.js                 # 14 项静态/一致性门禁（含"克隆得到吗"）
node tests/js/run-all.js                     # 小程序流程测试（真实执行页面处理函数）
node scripts/check-tracked-inputs.js         # CI/发布依赖件是否都已入库
```

```bash
cd AquaFlow-backend
./gradlew bootJar --no-daemon --project-cache-dir .gradle_eval
cd .. && node scripts/check-jar-no-local-config.js   # 发布物里不许有本地配置（含真实密钥）
node scripts/prod-startup-check.js                   # prod 姿态：必需 9 项缺失必须拒启、COS 缺失只降级
```

**准出判据**：以上全部退出码 0；`check-tracked-inputs.js` **没有"被忽略的必需件"**
（"未跟踪"只是警告，但发布前必须确认它们已 `git add`，否则新克隆的 CI 会红）。

> ⚠️ 三条都是真跑出来的，不是形式：`prod-startup-check.js` 会启动 13 次 JVM（约 3~4 分钟）；
> `bootJar` 之后**必须**重新跑 `check-jar-no-local-config.js` —— 它读的是刚打出来的产物。

### 3.2 发布顺序（**顺序本身是判据**）

| # | 步 | 命令 / 动作 | 判据 |
|---|---|---|---|
| 1 | **备份** | `node scripts/backup-restore-drill.js backup --keep 7` | 打印 sha256 与逐表行数；备份文件落在 `backup/`（**勿提交**） |
| 2 | **执行迁移** | 按 `sql/README.md` 的必跑清单，`mysql -uroot <库名> < 脚本.sql` | 每个脚本自行打印预检/自查结果；**出错即停**（别用 `--force`，它退出码仍是 0 会骗人） |
| 3 | **上代码** | 用 §3.1 产出的 jar：`java -jar AquaFlow-*.jar --spring.profiles.active=prod`，环境变量由部署环境注入 | 日志出现 `Started AquaFlowApplication` 且**不随后退出** |
| 4 | **冒烟** | `node scripts/smoke-check.js https://你的域名 --prod` | 存活 / 公开端点 `code=0` / 未认证 **401** / **dev-login 路径 `code=404`** |
| 5 | **对账** | 站长端 `GET /api/manager/reconciliation`，或运维查 `reconciliation_result` | `totalDiff = 0` |
| 6 | **观察** | `select * from alert_log where alert_type='SYSTEM' order by id desc limit 50;` | 无新增 `SYSTEM` 告警 |

> ⚠️ **步 2 与步 3 的先后由迁移性质决定**：**破坏性 DROP 必须先上代码再执行 SQL**
> （见 §5.3）；**纯新增（加可空列 / 建表）先跑 SQL 更稳** —— 代码先上会去查一个还不存在的表。
> 分不清就按"先备份、再看该脚本文件头的执行说明"，每份迁移的文件头都写了顺序与回滚方式。

### 3.3 小程序发布（两端各自独立）

| 步 | 动作 | 判据 |
|---|---|---|
| 1 | 把 `miniapp-*/config/api.js` 的 `prod.baseUrl` 从占位符改成**已备案的真实域名** | 跑一次 `grep -n "baseUrl: 'https://your-domain.com'" miniapp-*/config/api.js` —— **必须 0 命中**（两端各一份配置） |
| 2 | 开发者工具上传 → 设为体验版 → 真机走一遍主流程 | 真机上右上角 `…` →「打开调试」（`urlCheck` 已在 `project.config.json` 里为 `false`） |
| 3 | 提交审核 → 发布 | 两端 appid 各自独立，可分别发布 |

> ⚠️ **判据要精确到 `baseUrl:` 那一行**：直接 grep `your-domain.com` 会命中 **6 处**而不是 2 处 ——
> 另外 4 处是**护栏代码自己**（`indexOf(...)` 与那句报错文案）在两个文件里各占 2 行。
> 写成"grep 到 0"是个**永远不会成立的假判据**（写完当场就能发现：它现在应该 0 却永远是 6）。
> 2026-09-28 实测：按上面这条精确判据，当前命中 **2 处**（正是两个 `prod.baseUrl`）。

> ✅ **占位符有护栏**：`getBaseUrl()` 里判到 `your-domain.com` 会**直接抛可读错误**
> （「正式环境域名还是占位符…」），不会静默超时 —— 忘了改会当场看得见，不是上线后猜。
> ⚠️ 但**它只在 `release` 环境生效**：体验版（`trial`）走 `dev` 分支，占位符不会拦 ——
> 所以上面那条 grep 才是**发布前**的判据，不能只靠运行时护栏。

### 3.4 回滚

| 回滚对象 | 怎么做 | 边界 |
|---|---|---|
| **代码** | 换回上一个 jar 重启 | 只需旧 jar；**旧 jar 要留**（`build/libs` 只留最新，发布时自行归档） |
| **数据库结构** | 纯新增类（加列 / 建表）**不用回滚** —— 旧代码不读新列/新表 | 迁移脚本文件头都写了回滚语句 |
| **数据库结构（破坏性 DROP）** | **先回代码、再补列**：`ALTER TABLE ... ADD COLUMN` 按脚本头部的反向语句 | ⚠️ 被 DROP 的列里的**数据恢复不了**，只能从备份回灌 |
| **数据** | `mysql <库名> < backup/xxx.sql`，然后**必须**跑 §7 对账 | 回灌会丢掉回灌点之后的全部业务数据 —— 这是最后手段，不是常规回滚 |

> ⚠️ **回滚前先判断"能不能只回代码"**：绝大多数发布都是纯新增迁移，**回代码即可**，
> 不需要动数据库 —— 动数据库的回滚代价高一个量级。

## 5. 数据库迁移

**项目未启用 Flyway**：`sql/**` 全部靠手工执行，没有版本表、没有自动校验。

> **迁移清单与逐条执行证据的正本是 `AquaFlow-backend/sql/README.md`。**
> 本文不复述清单 —— 有正本就不要在两处定义同一份事实。

### 5.1 新建库

权威基线是 `AquaFlow-backend/sql/schema.sql`（全 `CREATE TABLE IF NOT EXISTS`，可重复执行）。

```bash
cd AquaFlow-backend/sql
mysql -uroot -p <库名> < schema.sql
```

> ⚠️ **必须走 shell 重定向（`<`）导入。** 不要用 PowerShell 管道
> （`Get-Content -Raw | mysql` 会按控制台代码页重编码，把中文注释写成乱码）。
> 核对是否写坏要**比字节**（`HEX(TABLE_COMMENT)`），不要看控制台输出。

### 5.2 老库升级

按 `sql/README.md` 的「基线之后必须补跑的迁移」顺序补跑，**执行务必带库名**：

```bash
mysql -uroot <库名> < 脚本.sql
```

> ⚠️ 该清单**已知有缺陷**（见 `sql/README.md` 与 `AGENTS.md` §4：漏列部分脚本、个别脚本之间存在顺序冲突）。
> **执行前人工核对**，不要盲跑。

### 5.3 脚本约定

- **迁移脚本必须幂等。** MySQL 8.4 没有 `DROP ... IF EXISTS`，统一用 `information_schema` 预检 + `PREPARE`。
- **破坏性 DROP 必须先上代码、再执行 SQL**，执行前先 `mysqldump`。
- ⚠️ **MySQL 在解析期校验列名**：脚本里对某列的 `MODIFY` / `WHERE col` 即使执行不到也会报 1054 ——
  删列时必须把**历史迁移里对该列的引用一并清掉**。
- 新建脚本前先 `ls sql/` 看编号是否占用，**不要照任何清单的最后一个数字 + 1**。

### 5.4 严禁在生产执行

`sql/reset_data.sql`、`sql/clear_data.sql`（都是 TRUNCATE 多表）、
`reconcile_order_814.sql`、`seed_dev_account.sql`、`seed_new_user_83.sql`、`sql/archive/**`（已过期且不可执行）。

## 6. 备份与恢复

- **执行任何破坏性迁移前先做 `mysqldump`**，备份文件放仓库外的备份目录（`backup/` 已被 gitignore，**勿提交**）。
- 恢复即用 `mysql <库名> < <备份文件>`。恢复后按 §7 跑一次对账，确认账目自洽。
- 备份里含真实客户数据，**按生产数据对待**：不外发、不进仓库、不进对话。

### 6.1 别手写命令：用演练件（**已实跑通过**）

```bash
node scripts/backup-restore-drill.js backup             # 备份 + 出清单（sha256 / 逐表行数 / 注释字节）
node scripts/backup-restore-drill.js backup --keep 7    # 带保留策略：只留最近 7 份
node scripts/backup-restore-drill.js drill              # ★ 全流程：备份 → 灌演练库 → R0–R6 校验 → 自动清理
```

**为什么要 `drill` 而不是"备份完了就算"**：备份**能不能恢复**、恢复出来的**中文注释有没有被编码搞坏**、
**账还平不平**，只有真灌一次才知道。R0–R6 七项判据：
sha256 与清单一致 / 表数相同 / **逐表行数相同** / **中文表注释按字节相同** /
水票批次账 E8 仍平 / 桶权益账仍平 / 订单客户无孤儿。

> ⚠️ 它**只写演练库**（`aquaflow_restoredrill`），不碰 `aquaflow` / `aquaflow_test`，成功会自己清理。
> 2026-09-28 实测：七项全过（52 张表 / 行数合计 1453）。
>
> ⚠️ **默认输出目录叫 `backup/dryrun/`** —— 那是历史命名（`drill` 与手工备份共用同一目录），
> **不是"演练专用"**：正式发布的备份也落在那里，同样已被 gitignore、**勿提交**。
> 文件前缀能区分来源：`aquaflow_manual_*.sql` = 手工/发布前备份，`aquaflow_drill_*.sql` = 演练。

## 7. 对账作业

系统维护三条独立账线（桶 / 水票 / 押金）加支付与计件工资，各由守恒等式校验，
结果每日落 `reconciliation_result` 表（每检查项一行）。

| 项 | 说明 |
|---|---|
| 定时执行 | **每日 03:00**（`ReconciliationService` 的 `@Scheduled(cron = "0 0 3 * * ?")`）；另有**每 5 分钟**的微信未付单超时清扫（`UnpaidWechatOrderSweeper`，`0 */5 * * * ?`） |
| **任务自己挂了会怎样** | **会发 `SYSTEM` 告警**（`alertService.systemFault(...)`），不是静默停摆 —— 两个任务的入口都包了 try/catch，catch 后再上抛是**刻意不做**的（定时任务是无人值守路径，抛给调度器只会让整批停摆）。用例 `ScheduledJobFailureAlertTest`（3 例） |
| 失败重试 | **不做自动重试**：重试要配退避与幂等边界，而日结对账是只读聚合（下一天会再跑一遍）；真要重跑就人工触发或等次日 |
| 站长端查询 | `GET /api/manager/reconciliation`，**只读本站即时对账**（只有 `GET`）。原 `POST /run` 会写全平台结果 = 跨租户泄露，**已删除、不要加回** |
| 结果表 | `reconciliation_result` |
| 告警落点 | `alert_log`，运维查：`select * from alert_log where alert_type='SYSTEM' order by id desc limit 50;` |

### 7.1 等式设计约束

⚠️ **写等式前先问：这个状态在正常经营里会不会合法出现？会就不能进差异计数。**
以下三种曾导致「日结永远不平」：

1. 核销只置 `payment_status = 2` 而不补 PAID 流水 → **收款必须两步**：先记流水（幂等）再 CAS 置状态。
2. 把 `order_id IS NULL` 当成孤儿 → **无订单在线购票是合法业务**。
3. 把配送中桶的 `DELIVERED` 状态当成异常 → **它是合法终态**。

### 7.2 告警分级

`alert_log` 表按类型分级投递，方向由 `AlertType` 决定，**不靠字符串比较或调用方自觉**：

| 类型 | 含义 | 投递给 | `station_id` |
|---|---|---|---|
| `SYSTEM` | 系统故障：对账不平、桶异常补偿失败、未预期 500 | **系统管理员** | 必须 NULL |
| `OPERATION` | 运营故障：桶异常待处置、补偿已执行、异常被忽略 | **该站站长** | 必填 |

**三条硬约束**：① 先落库再谈渠道（没配 Webhook 则 `notify_status = LOGGED`）；
② 落库走**独立事务**（`REQUIRES_NEW`，必须经代理调用）；③ 失败**绝不连累业务**。

> ⚠️ **系统告警没有 HTTP 入口** —— 漏给站长等于跨租户 + 越权知情。

**运维查询系统告警**：

```sql
select * from alert_log where alert_type = 'SYSTEM' order by id desc limit 50;
```

站长端只读 `GET /api/manager/alerts`。

## 8. 常见故障

| 现象 | 原因 | 处置 |
|---|---|---|
| 启动即失败，抛 `IllegalStateException` | §2.1 的三项之一缺失或 `JWT_SECRET` 短于 32 | 补环境变量 |
| 接口返回 401 | 未认证；或访问了不在公开白名单里的端点 | 检查 `Authorization` 头与 `WebMvcConfig` 白名单 |
| 真机微信登录失败，日志 `40013 invalid appid` | code 与 appid 不配对 | 确认两端 appid/secret 与签发 code 的那个一致 |
| 真机请求报「不在以下 request 合法域名列表中」 | 两处开关未同时打开 | ① `project.config.json` 的 `urlCheck` 为 `false`；② 真机右上角 `…` →「打开调试」 |
| 业务操作"看着成功但没生效" | 业务错误仍返回 HTTP 200 | **判响应体 `code`**，不要判 HTTP 状态 |
| 日结对账不平 | 见 §7.1 三种成因 | 先确认不是把合法业务状态算成了差异 |

## 9. 已知运维边界

- **单实例假定**：登录限流是内存计数；多实例部署前必须换成集中式计数器（如 Redis）。
- **微信支付未接入**：没有第三方支付回调面。⚠️ 本地模拟渠道（`MOCK_WECHAT_PAY`）在**生产必须关闭**。
- **客户端正向进度通知未接入**：站长端只有应用内红点。
- 本地开发与联调的特殊做法（不买服务器、局域网真机预览、appid 组合）见
  [`../本地运行-笔记本当服务器.md`](../本地运行-笔记本当服务器.md)。
