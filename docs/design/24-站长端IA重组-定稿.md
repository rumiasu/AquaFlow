## 1. 目的与范围

**解决什么问题**：站长端入口分散且互相重复 —— 同一件事有两张宫格卡（桶异常 / 运营告警）、同一个数字在首页与「我的」各报一遍、水站资料只有只读展示、部分入口点了界面毫无反应。

**范围**：`miniapp-delivery` 的宫格 `pages/station-mgmt/index`、首页 tab `pages/coordination/index`、「我的」`pages/mine/index`，以及这三处指向的站长端页面。

**不在范围**：表结构与资金口径（唯一涉及的数据契约是待办汇总，见 §3）；顾客端（`miniapp-user`）的任何页面。配送员侧的改动只有一处 —— 「配送」页签改名（§5.8）。

**代码注释里的旧节号**：`pages/station-mgmt/index.wxml` 引用的 `§0.11`（桶异常与运营告警合并、桶损耗删除）对应本文 §5.1。

## 2. 设计口径

### 2.1 分区与卡片（终态）

**版面口径**：每个分区头顶一条**带蓝色左竖条的区标题**，竖条之下即该分区的全部条目（对齐运营商 App 的「查询服务」分区样式），不再使用「两段式横线」。排序依据 = 站长一天里的接触顺序：接单 → 收钱 → 收桶 → 客户 → 配货与人员 → 回头看数据。

| 分区 | 卡片 → 目标页 |
|---|---|
| **A 订单** | 订单管理 → `pages/coordination/index`；异常订单 → `pages/station-mgmt/exceptions/index` |
| **B 资金** | 应收账款 → `receivables/`；待确认收款 → `payments/`；计件工资 → `payroll/`；利润报表 → `gross-profit/`（均在 `pages/station-mgmt/` 下） |
| **C 桶** | 退桶审批 → `barrel-return/`；欠桶台账 → `owed-barrels/`；资产调整单 → `customers/adjust/` |
| **D 客户** | 客户 → `customers/index`；客户反馈 → `customer-feedback/index` |
| **E 商品与配置** | 商品与库存 → `products/`；配送计费 → `delivery-config/`；营业状态与公告 → `station-status/` |
| **F 员工与水站** | 员工 → `staff/`；水站资料 → `station-info/` |
| **G 现场数据** | 经营看板 → `dashboard/` |

- G 用 `.group-divider`（左右细线 + 居中标题）与 A–F 区分：**它是「看数据」，不是「办事」**。
- 三列图标网格（`1fr 1fr 1fr`），每格 = 图标 + 名称 + 一行细述；**不足一行的分区用 `.module-card.placeholder`（透明、不接收点击）补齐**，保持列对齐。
- 卡面细述是**功能清单**（`·` 分隔），**不是营销句式** —— 它就是「不用点进去也知道里面有什么」的实现方式，取代二级导航。逐卡文案正本在 `pages/station-mgmt/index.wxml`。

**未设卡片的入口（有意为之，不是遗漏）**：

- **代客下单**：`place-order` 暂不可达 —— 待重新设计，入口未定（§7）。
- **水票档位**：从商品页「本站设置」弹窗的「更多档位设置 ›」进（已并入「商品与库存」页）。
- **订单台账**：从首页「待分配」列表底部的「看全部订单 ›」进（§5.2）。
- **资产调整单新建**：从客户画像的「资产调整」进 —— 新建必须锚定客户；宫格那格进的是**本站全部调整单台账**（§5.9）。
- **水站资料编辑**：「我的 → 我的水站 → 编辑资料 ›」，与宫格那格同一页（§5.7）。

### 2.2 导航规则

| 规则 | 内容 | 违反的后果 |
|---|---|---|
| **tabBar 页必须 `switchTab`** | 目标页是 tabBar 页（`pages/coordination/index`、`pages/home/index`、`pages/mine/index`）时只能 `wx.switchTab` | `wx.navigateTo` 对 tabBar 页**必然失败**，fail 回调只有一句 errMsg，**界面毫无反应** —— 站长会当成「点了没反应＝坏了」 |
| 分流集中一处 | 分流写在 `pages/station-mgmt/index.js`，用 `TAB_BAR_PAGES` 名单判断，并对 `switchTab` 失败给兜底提示 | 每格各自判断必然漏项 |
| 页面栈 | 宿主页内的页签切换用 `wx.redirectTo`，**不要 `navigateTo`**（每次点页签都堆一层历史栈）；「来回点」的入口要防重：从 `coordination` 进订单台账后，`onOpenOrders` 先查 `getCurrentPages()` 里有没有目标页，有就 `navigateBack` | 同一页被堆成多层，返回要按很多次 |
| options 转传 | 跳转必须把 `options` 原样转传给目标页 | `customers/detail` 与 `adjust` 都靠 query 传 `id` / `customerId`，丢了就进空页 |

### 2.3 首页顶部：「待办」卡 / tab 角标 / 红点三者的分工

**三处职责不重叠**：**tab 栏角标** = 每个页签各有多少条，点页签才展开明细；**「首页」tab 红点** = 有 P0 待办；**「其他待办」卡** = 只补 tab 覆盖不到的那些项。

**唯一判据（决定某一项进不进卡）**：**本页 tab 覆盖不到、且没有立刻可见的计数**。

「哪个条目归哪一级」**不写死**：目录是 `constant/PendingItem`（key / 中文标签 / 默认级别），端点按目录逐条算数；调整分级两条路，**都不需要改前端** —— ① 改目录里那一行；② 运行时覆盖 `aquaflow.pending.level-overrides`。

| 待办项 | 级别 | 进卡 | 理由 |
|---|---|---|---|
| 待分配订单 · 转单请求 · 客户取消申请 · 站内取消申请 | **P0** | ✗ | 与本页 tab 栏角标是**同一批数据** —— 同一件事在一屏里报两遍 |
| 他站定向外派待确认 · 待审退桶 | **P0** | ✗ | 各自页面上一眼就能看到数 |
| 抢单池可抢 | P2 | ✗ | 抢单池自己就是页签，带角标（机会，不是义务） |
| 逾期应收 · 待确认收款 · 员工绑定/解绑申请 · 企业身份待审 · 待确认结算单 | P1 | ✓ | **本来就不属于订单页**，只活在「水站管理」里；首页不报就没人知道有这回事 |
| 未填成本 · 待处理桶异常 · 运营告警 | P2 | ✓ | 同上 |

级别语义：**P0** = 不处理就卡住今天的配送；**P1** = 影响钱或他人，但客户不会干等；**P2** = 知道就行。

- **P0 在首页的唯一信号是 tab 红点**（卡里一项 P0 都没有）：P1/P2 一起算红点会天天亮着，站长就把它当背景噪音（「告警疲劳」的同形问题）。**但卡照常显示 P1/P2** —— 「红点报不报」与「要不要让站长看见」是两件事。

卡片形状：标题「其他待办」+ 副标题「不在订单页里的」+ 一行平铺（`count` / `label` / 有金额才显示 `￥`），非零项用红字（`todo-item-on`）。

- ⚠️ **不得把整张卡删光**：剔除的只是真重复项，其余项只活在「水站管理」里 —— 删掉整卡等于让站长再也不知道有这些事。
- ⚠️ 卡上标红的是「**这个计数非零**」（`hasCount`），**不是等级**：`level` 这一层前端不消费（红点用的 `p0Total` 是后端按 `level` 算好的）。
- 0 计数的项**照样显示**（与 tab 角标「0 就不显示」语义不同：角标是「有几条要办」，卡是「系统有哪些事项」），否则站长永远不知道这个功能存在。
- 服务端没下发某项（如企业身份功能关闭）时**不硬造**；服务端新增了待办项而前端未接页面时**必须出声**（`wx.showToast`），不得静默无反应。
- 金额格式化在 js 里做（wxml 不能调方法）。
- ⚠️ 卡**不再按三级铺开**；`level` 仍由服务端下发，前端**只拿它配色**。
- ⚠️ `loadTodo()` 保留，职责是两个：① 组装卡；② 刷新首页 tab 红点。红点走**完整 payload 的 `p0Total`**（含被本卡剔除的 P0 项），**不是**卡里这些项推出来的 —— 别改。
- ⚠️ 加回一项要动**两处**：`TODO_KEYS` 添 key **且** `TODO_ROUTES` 补路由。其中待分配 / 转单 / 客户取消 / 站内取消这四项本身就是本页页签，点它们应当 `switchTab`（`wx.navigateTo` 跳 tabBar 页会静默失败），另两项才是 `navigateTo`。

| 维护项 | 处置 |
|---|---|
| `TODO_KEYS` | 首页顶部**唯一需要维护的收录清单**；加回 / 去掉某项只改这里（后端一直下发全部条目） |
| `TODO_ROUTES` | 与 `TODO_KEYS` 一一对应，只做 key → 小程序页面路由（后端不认识小程序路径，故它**不是**「前端自带映射表」） |
| `.todo-card` / `decorateTodo()` / `onTodoTap()` / `data.todo` / `.todo-*` 样式 | 保留 |
| 只给三级标题用的 `.todo-group` / `.todo-group-title` / `.todo-item-p0` | 删除 |
| 自绘导航栏的营业状态胶囊 | **不动** —— 那是「今天开不开门」，必须常驻可见 |

`onTodoTap()` 目前只做 `navigateTo`（未接路由的 key 弹提示）；改路由前先看它。

### 2.4 「我的」页：统计卡按角色分叉

| 格 | 站长 | 配送员 |
|---|---|---|
| 1 | **今日净利**（¥ /「算不出」）→ 点进「利润报表 · 今日」 | 今日完成（按人统计） |
| 2 | **今日单数** → 点进同一页 | 配送中（按人统计） |
| 3 | **桶异常 · 欠桶 N 户** | 回桶数（对配送员它就是工作量，不是「异常」） |

- **为什么必须按角色分叉**：净利端点带 `@RequireRole("STATION_MANAGER")`，配送员调它拿到的是**权限错误**而不是 0；不分叉就只能给它显示空白，那比不显示更糟。
- **第 2 格**：原「待配送」是全站 `status = 1` 单数，而「配送」页第一个页签就是它（带角标），在「我的」再报是重复，故撤掉。
- **第 3 格是「换指标」不是「改名」**：原「回桶数」是配送动作量（今天拉回几个空桶），与「异常 / 未回桶」无关。**欠桶在本仓是「只提醒、不阻断」的常态**（原硬拦已按产品决定移除），长期大于 0 —— 所以它只当**副行**（「欠桶 N 户」），主数字留给真正要处理的**桶异常**。

### 2.5 净利口径

**净利 = 水费收入 + 配送费 + 楼层费 − 进货成本 − 配送员计件工钱**

后端在**同一个** `GET /api/manager/gross-profit` 响应里追加 `orderCount` / `deliveryFee` / `floorFee` / `totalIncome` / `wage` / `netProfit` / `profitBasisNote`。

| 判据 | 内容 |
|---|---|
| **同一 cohort** | 结算站 + 排除已取消 + 同一时间窗，与毛利逐字一致；单数 / 费用那条 SQL **刻意不 join `order_item`**（join 了配送费会被明细行数放大） |
| 工钱归属 | 按 `staff_earning.order_id` 挂到这批订单上，**不按工钱自己的 `create_time` 筛**；人工调整（`order_id IS NULL`）**不进日净利**（迟到扣款不是某一天订单的成本） |
| ⚠️ 缺成本 | 缺成本时 `netProfit` 与 `totalProfit` **一起为 null**（只 null 一个，站长会拿另一个当真） |
| ⚠️ 收入不含押金 | 可退的负债不是收入 |
| ⚠️ 已知边界 | 收益在订单进入**送达**时才产生 → 未送完的单暂时不计工钱，那几天净利偏高。响应里的 `profitBasisNote` 把这几条写给站长看，页面**原样展示** |

页面：`pages/station-mgmt/gross-profit/` 更名「利润报表」（宫格卡名与导航标题同步）；新增「今日」快捷区间（`?range=today`，从「我的」跳进来）与一张「减法账」卡片（单数 → 水费 → 配送费 → 楼层费 → 收入合计 → −成本 → −工钱 → **净利**）。金额一律用服务端下发值，**页面里不做任何毛利 / 净利算术**。

### 2.6 不许碰的约束

- **不改后端**（唯一的例外是待办汇总端点，见 §3）。
- **不动任何金额 / 状态口径**；文案（`statusText` / `payMethodText` 等）仍由服务端下发，**前端不新增 1/2/3 映射表**。
- `app.json` 的 tabBar **保持 3 项**（微信限 2–5 项，加 tab 会改「首页」语义）。
- 分区只是**版面分组，不是页签容器** —— 不要为分区新建宿主容器页。
- **已清除的冗余不要加回**：桶损耗读数整块（§5.1）、看板的「待收款横幅」与「欠桶客户 TOP」及其前端派生字段、「待办」卡三级标题、「配送」页白发的 `getTodayStats()` 调用、`/api/delivery/stats/today` 的 `pendingCount`、三个悬空类名（`station-info-card` / `mgmt-content` / `fee-row`）、宫格「水站资料」对 `pages/mine/index` 的旧指向。

## 3. 数据模型与数据契约

IA 重组**不改表结构、不加字段、不动资金口径**。唯一涉及的数据契约是「其他待办」的汇总：

- **待办目录**在 `constant/PendingItem`，端点按目录逐条算数（分级与运行时覆盖见 §2.3）—— **不需要为此加列或改表**。
- `ManagerPendingSummaryController` **只做编排 + 分级，不写任何聚合 SQL、不新造口径** —— 每个计数都调某个**已在用的读数入口**（`listStationPendingUnassigned` / `listPendingCustomerCancelRequests` / `ReceivableService.overview` / `OrderBarrelExceptionService.listExceptions` 等）。这是 `ManagerTodoController` 立下的判据：**否则会出现「角标说 3、点进去 0 条」**。
- 与 `todo-summary` **并存不改**：后者回答「该做的经营动作」，本端点回答「有没有人递东西过来」；重叠的待处理桶异常那一项**沿用同一个服务方法**以保证两处一致。
- ⚠️ 转单请求与站内取消申请**必须按 `order_transfer.sub_kind` 拆成两个互补的枚举集合**（`PendingItem.STAFF_TRANSFER_SUB_KINDS` 与 `SUB_CANCEL_REQUEST`），**不要用 `NOT IN` 排除式**：原先两者都取 `kind = 'STAFF'` 的整批、不分子类，于是显示成**同一个数**；而排除式写法下将来新增一个 `sub_kind` 会被**静默**算进「转单请求」，没人会发现。为此新增 `OrderMapper.listStaffRequestsBySubKinds`，**不改** `listTransferredOrders` 的契约（它另有调用方）。

## 4. 接口与权限

| 方法 / 路径 | 角色 | 站点归属 | 说明 |
|---|---|---|---|
| `GET /api/manager/pending-summary` | `STATION_MANAGER` | 取登录态 | 待办汇总（key / 标签 / 计数 / 金额 / `level` / `p0Total`）；**顾客不可读**，他站站长看到全 0 |
| `GET /api/manager/alerts` | `STATION_MANAGER` | 取登录态 | 运营告警（只读），落在「异常订单 → 处理留痕」 |
| `/api/manager/exceptions*` | `STATION_MANAGER` | 取登录态 | 桶异常单的列表 / 详情 / 发起 / 核销 / 处理 / 执行 / 统计 / 配置 |
| `PUT /api/stations/{id}` | `STATION_MANAGER` | **按 `station.creator_staff_id`（创建人）** | 整行覆盖（名称 / 电话 / 地址 / 状态） |
| `GET /api/manager/gross-profit` | `STATION_MANAGER` | 结算站 | 毛利与净利在同一响应里 |
| `GET /api/orders` | 站长 | 按 `stationId` 过滤 | 订单台账（首页「看全部订单 ›」的目标） |

⚠️ **跨站判据必须以服务端刷新的 `stationId` 为准**：`AuthInterceptor` 对 staff token **以库内 `stationId` 覆盖 token 里那个**（防调站后旧 token 继续操作原站），所以「token 里塞 null」测不出跨站 —— 正确的跨站用例判据是「**他站站长看不到本站数据**」，伪造 `stationId` 参数被忽略、不构成越权通道。

## 5. 前端落点

### 5.1 异常订单（`pages/station-mgmt/exceptions/`）

**合并依据**：「运营告警」的全部内容都来自桶异常单这**一个流程**（级别只有 `WARN 待处置` / `INFO 留痕`）—— 桶异常是待办面，运营告警是流水面；拆成两张卡两个页面，站长看到的是「两个都得点，说的却是一件事」。

| 项 | 约束 |
|---|---|
| 页面 | 由原 `barrel-exceptions/` 复用改建（**不新建页**，避免留下死页）；导航标题「异常订单」 |
| 页签 1 | 桶异常单（默认）：近 30 天统计 + 异常单列表 + 「只看待处理」 |
| 页签 2 | 处理留痕：全部 / 待处置 / 留痕三级筛选；`?tab=alerts` 直接落在这一页签 |
| 页签角标 | 页签上直接显示 **WARN（待处置）条数** —— 不点进去也知道有没有事等着 |
| 筛选计数 | 三个级别的条数**在筛选之前算好**（切到「留痕」时「待处置」不会变成 0） |
| 客户反馈 | **不进本页**（它不是订单异常），留在「客户」分区 |
| 告警范围 | ⚠️ 「处理留痕」只承载**运营告警**（该端点固定只返回 `alert_type = 'OPERATION'`）；系统告警没有 HTTP 入口，**并入这一页 = 跨租户 + 越权知情** |
| 路由 | 宫格 A 区「异常订单」；首页 `barrelException` → `exceptions`、`operationAlert` → `exceptions?tab=alerts`；「我的」第三格 → `exceptions` |
| 常量 | `config/api.js` 的 `MANAGER_EXCEPTIONS`；告警仍走 `api/station-mgmt.js` 的 `getAlerts`（**不绕开包装函数**，否则它立刻变成「定义了没人调用」的死函数） |
| 桶损耗读数 | **整块删除**（js 的 `loss` / `normalizeLoss` + wxml 的卡 + wxss 的样式）：2026-09-18 已定「本站不做桶损耗出账」，那张卡正常情况下**恒为 0**，还配一句「0 不代表没丢过桶」的免责声明 —— 纯噪音。客户弄丢 / 欠着的桶在**欠桶台账**（那是应收，不是损耗） |

### 5.2 订单管理（`pages/coordination/`）与订单台账

- 宫格**不设**「订单管理」卡：入口就是首页 tab 本身。
- 首页 tab 与订单台账是**两个视角，不互斥**，**不要把状态页签并进首页那一排**：动作维度与状态维度混在一排，站长分不清「待配送」与「待分配」。

| | 首页 tab（`coordination`） | 订单台账（`GET /api/orders?status=`） |
|---|---|---|
| 切法 | **动作**：待分配 / 审批 / 抢单池 / 外派 / 他站外派 | **状态**：全部 / 待配送 / 配送中 / 已完成 |
| 数据源 | 多条专用端点（待分配 + 转单**前端合并**、抢单池、外派追踪、他站外派、待审批） | 一条通用列表 |
| 行内操作 | 分配 / 外派 / 抢单 / 跳过 / 同意拒绝转单 / 同意拒绝取消 / 取消外派 / 重新外派 / 调解退回 | **无**，点卡片进 `order/detail` |
| 独有 | 「待办」聚合卡 | **跨站履约归并行**（履约站视角，含金额合计与明细） |

- **为什么是「台账加链接」而不是「首页加跳转」**：宫格那份功能更少（只有一个状态筛选条），而它点进去的 `order/detail` 本身就是完整操作台（`dispatchOrder` / `resolveOrder` / `requestCancel` / `transferOrder` / `returnToStation` / `completeOrder` / `refundPayment` 全在详情页）。
- 落点：首页「待分配」列表底部加一行居中文字链「看全部订单 ›」→ `navigateTo` 到通用列表（它不是 tabBar 页，可 `navigateTo`）。
- **已知缺口（单独记，不混进 IA 改动）**：台账页**不翻页**（只传 `stationId` + `status`），而 `GET /api/orders` 有单页上限（见 `OrderController`）—— 单站累计订单超过上限后，页面只显示最近一批，**界面无任何提示**。

### 5.6 员工解除的两条护栏

- **现象**：站长在员工列表里能看到**自己**那一行，且带「解除」按钮；点下去**真的成功**。
- **根因**：`POST /api/manager/bind/release` 只校验「员工存在 + 属于本站」，**没有 role 校验、也没有「别解除自己」**；而列表数据源 `StaffMapper.listByStationId`（`where station_id = ? and status = 1`）**不带 role 条件** → 站长自己就在返回集里；前端按 `item.status === 1` 渲染按钮，没判角色。
- **后果**：`staff.station_id` 置 NULL → 该站长所有 `requireStationId()` 端点全废、被路由去「创建水站」；而 `station` / 客户 / 订单 / 库存 / `customer_station_config` **全留在库里** —— 客户照常给这个站下单，却再没有任何站长能接单。重建水站拿到的是**新 id**，旧数据搬不回来。
- **修法**：① 后端两条护栏（`role` 必须是 `DELIVERY` + 不能解除自己）；② 前端两处（`pages/station-mgmt/staff/`、`pages/mine/`）把站长那一行的按钮换成一行灰字「站长 · 不可解除」。
- ⚠️ **反向验证**：临时摘掉护栏重跑用例，必须在断言处红掉 —— 证明这条测试真能抓住它，不是假绿。

### 5.7 水站资料（`pages/station-mgmt/station-info/`）

原先宫格那格指向 `pages/mine/index`（tabBar 页，点了只是跳到「我的」），「我的水站」卡**纯只读**；后端 `PUT /api/stations/{id}` 早已存在、归属校验齐全（`StationMapper.getByIdAndCreator`），只是 `config/api.js` 里**没有这个端点的常量**、前端从未接线 —— 站长建完站以后站名 / 电话 / 地址再也改不了，而客户下单要靠它们认水站。

| 约束 | 内容 |
|---|---|
| 坐标归属 | 坐标从「营业状态与公告」页**整块搬来**（那边已删干净并留了墓碑注释）：坐标是「水站资料」（固定），不是「营业状态」（临时）；**两处各写一份必然分叉**（本仓「计价双轨」的同形风险） |
| ⚠️ 整行覆盖 | `PUT /api/stations/{id}` 是**整行覆盖**（`name` / `phone` / `address` / `status` 一起 set）—— payload **必须四项给全**，只传 name 会把其余三项一并写成 NULL。页面做法：先 `getMyStation()` 读回原值，改哪项覆盖哪项 |
| 状态字段 | `status`（1 营业 / 2 停业）是**硬状态**：停业会真拒单、且不在公开选站列表里 —— 本页**不提供**它的入口，只原样带回。**别顺手做成开关** |
| ⚠️ 归属校验 | 走 `station.creator_staff_id`（**创建人**），不是 `staff.station_id` —— 所以水站转让**必须同时转移 `creator_staff_id`**，只改 `staff.station_id` 的话，接手人会「看得见水站、改不动资料、点保存报无权操作」 |
| 入口 | 宫格 F 分区那格 → `station-info`；「我的水站」卡加「编辑资料 ›」（与「管理 ›」并存：后者进的是宫格总入口，语义不同，不合并） |
| 前端常量 | `config/api.js` 的 `STATION_UPDATE(id)`、`api/station-mgmt.js` 的 `updateStation` |

### 5.8 「配送」页签：待接单 → 待配送（与配送员端共用）

- 理由：后端 `OrderStatus` 的 1 就叫「待配送」，接单配送的实际动作是 `status 1→2 + 认领`（`OrderWorkflowServiceImpl.acceptOrder`）—— 改完页签名与状态机一一对齐。
- 该页签装的本来就**不是「没人派的单」**，而是两支合并：`assigned-to-me`（已派给我、未接单）+ `orders/pending`（全站 `status = 1`）。**站长自己也会接单**，旧名字在站长眼里是错的。
- 同步处：页签名、卡片状态标签、空态文案、统计看板标签、`api/delivery.js` 的注释、`miniapp-delivery/README.md`。
- ⚠️ 「已完成」本来就是「今日」（`date(update_time) = 今天`），**没有改动** —— 全部历史在「我的 → 配送历史」（`pages/history`）。
- ⚠️ `coordination` 页那处「等待接单」是**外派**语义（他站等本站接外派单），**不动**。

### 5.9 资产调整单

落法：原方案（在「桶」分区的页签里放一张只读小结卡）不可行 —— **分区只是版面分组、不是页签容器**，没有地方挂「页内小结卡」；因此改为在桶分区**直接加一格卡**，指向现成的全站台账（`/pages/station-mgmt/customers/adjust/index` 不带 `customerId` 即返回「本站全部调整单」）。

**它不属于任何一个单一分区**（正本 `constant/AdjustType`，8 型）：`BARREL_GRANT` / `BARREL_REVOKE`（补录 / 撤销桶权益）与 `OVER_ADJUST`（订正欠桶）动**桶**；`DEPOSIT_GRANT` / `DEPOSIT_DEDUCT`（补录 / 扣减押金）动**押金**；`TICKET_GRANT` / `TICKET_DEDUCT`（补录 / 扣减水票）动**水票**。桶只占其中一部分 ⇒ 严格说放进「桶」分区名不副实，但它动的是客户在桶上的账，放这一分区最顺手；**不要**因此把它拆成多张卡。

- ⚠️ **新建必须锚定客户**：`AdjustmentCreateDTO.customerId` 必填，无 `customerId` 时点「新建」直接提示「请从客户详情页进入后再新建调整」——「先选商品、再挑客户」这条路**现在不存在**。
- 顺带（属代客下单那一批）：`CustomerMapper.countCustomerOfStation` 的 javadoc 写着「绑定行，站长代建 / 认领即产生」，而代码里已无此路径（`CustomerServiceImpl.save` 只 insert 客户、不建绑定）—— **失真注释**，随那批一起处理。

### 5.10 商品与配置

「商品与库存」页装了四件事（选品目录与本站设置、库存流水、自定义商品与上报、票务档位快捷块）。**只撤宫格「水票档位」卡**（改从商品页「本站设置」弹窗的「更多档位设置 ›」进），**页内结构不动** —— 该页计划做成**新注册店长的引导落点**，构想后续单独出。

### 5.11 设置页的「待办提醒」开关

`onToggleReminder` → `utils/pending-reminder.setReminderEnabled`，状态被 `app.onShow` 与首页 `onShow` 真正消费；**关掉只是不亮红点，待办卡照常显示**（静默吞掉待办比不提醒更糟）。副标题如实写明「打开小程序时刷新」。

**边界（写进代码注释，避免下一个人误解）**：

1. **只有应用内提醒**。小程序在前台**无法真推送** —— 红点只在「打开小程序时」刷新。
2. 要「没打开也能收到」只有**微信订阅消息**一条路；产品裁定**暂不做**：微信订阅消息除少数行业外**都是一次性授权**（推一条要用户确认一次），对站长这种高频场景摩擦过大。`WeChatNotifyService` 骨架保留不动。
3. 计数**全部由后端算**，前端不自己 filter、不自己加总。红点判据与开关状态的**唯一实现**在 `utils/pending-reminder.js`，`app.onShow` 与首页 `onShow` 各调一次；**只有站长才请求**（端点带 `@RequireRole`，配送员问了只会拿到权限错误），**非站长登录时主动清掉遗留红点**。
