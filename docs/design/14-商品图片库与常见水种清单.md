### 1.2 图片字段与渲染链路

```
product.image_object_name  (varchar(500)，存 COS 对象键，如 public/product/xxx.jpg)
        │  CosUtil.generatePublicUrl()  ← 24 小时过期的预签名 URL，带 30min 内存缓存
        ▼
   imageUrl（transient，不入库，由 Controller 注入）
        │
        ▼
   小程序 <image src="{{item.imageUrl}}">
```

| 环节 | 位置 |
|---|---|
| 字段定义 | `entity/Product.java:54-55`（`imageObjectName`） |
| URL 生成 | `util/CosUtil.java:67`（`generatePublicUrl`）、`:88`（预签名）、`:99`（`uploadPublic`） |
| 商品列表注入（员工端） | `service/impl/CatalogServiceImpl.java:336-348`（`withImageUrls`） |
| 顾客端注入 | `controller/ProductController.java:170`（`Product`）、`:181`（`StationProductVO`） |
| 顾客端返回字段名 | `imageUrl`（`dto/StationProductVO.java:47`）+ `imageObjectName`（`:28`） |
| 前端消费 | `miniapp-user/pages/shop/index.wxml:42-47` 等，**直接使用，无二次处理** |

### 1.3 发现的三个问题（做图库前必须处理）

**问题 1 · COS 在本地未配置**

`application-local.yml:44-49` 整段被注释；`RequiredConfigChecker` 对 COS 只 `log.warn` 不拒启。
后果：`generatePublicUrl` 抛异常 → 各处 try-catch 吞掉 → 接口仍 200，但 `imageUrl` 恒为 `null` → 顾客看到占位图；`/api/common/upload` 直接返回"文件上传失败"。

**问题 2 · 🔴 上传返回的是 URL，却当对象键入库（round-trip 缺陷）**

- `CommonController#upload`（`controller/CommonController.java:57-65`）返回 `cosUtil.generatePublicUrl(objectName)`，即**完整 https 预签名 URL**。
- 站长端 `miniapp-delivery/pages/station-mgmt/products/index.js:642-667` 的 `uploadImage()` 把该 URL 存进 `editForm.imageUrl`。
- `CatalogServiceImpl.createMyProduct`（`:165`）`setImageObjectName(... : dto.getImageUrl())` —— **把 URL 当成 COS 对象键落库**。
- 后续 `generatePublicUrl(那个 URL)` → 无效地址 → 被吞 → 图永远不显示。

→ 修法：上传接口应返回 `{objectName, url}` 两个字段，落库只存 `objectName`。**统一图库上线时必须一并修**，否则"选预设图"和"传自定义图"会走两套口径。

**问题 3 · 参数未配置时无本地兜底，且小程序兜底不一致**

- 后端无 `addResourceHandlers`（`config/WebMvcConfig.java` 只重写了 `addInterceptors`），**没有任何本地图片服务能力**。
- 小程序端兜底分三套：详情页 `/assets/image/default-product.png`（1251 B）、下单页 `/assets/image/default-product.jpg`（98 KB）、商城/首页用 💧 文本占位；**全端无 `binderror`**。

## 3. 统一图片库该怎么切（建议，待拍板）

### 3.1 核心判断：按「水种 × 包装」，不要按品牌

| 方案 | 说明 | 评价 |
|---|---|---|
| A. 按品牌出图 | 农夫山泉.jpg / 怡宝.jpg / 普利思.jpg … | ❌ 三个问题：① 用别家商品照片涉及商标与来源合规；② 本地长尾品牌（趵突泉/宏泉/润荷泉/百脉泉…）永远穷举不完；③ 站长卖的品牌与平台选的图不一致反而更丑 |
| B. 按**水种 × 包装形态**出图 | 纯净水-循环桶、矿泉水-循环桶、天然水-循环桶、纯净水-一次性桶、瓶装、饮水机 … | ✅ 通用、无商标风险、覆盖长尾；站长自定义商品也能用 |
| C. 按包装形态出图 | 桶装 / 瓶装 / 饮水器（= 现有 `category`） | ⚠️ 颗粒度太粗，同一 category 下 4 种水种长得一样 |

**建议取 B，并把现有 `category`（1 桶装水 / 2 瓶装水 / 3 饮水器）保留为一级维度。**

预估组合数：4 水种 × 2 桶型（循环桶 / 一次性桶）+ 瓶装 + 饮水器 ≈ **10～14 张**，数量可控。

### 3.2 图片来源（"找素材"的三种可行路径）

| 路径 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **① 统一风格插画（建议）** | 用 AI 或设计工具出一套**同一画风**的水桶/水种示意图（扁平、暖纸底、品牌蓝主色） | 无商标风险、风格与项目视觉系统一致、体积极小（webp 可压到 10~20 KB/张） | 需要一次性制作；不能表达"具体某品牌" |
| ② 实拍白底图 | 买一桶自有品牌水拍摄 | 真实感强 | 有成本；仍有品牌露出问题 |
| ③ 图标化 | 不用照片，用线性图标 + 色块表达水种 | 体积极小、可无限扩展 | 美感依赖图标质量 |

> 注意：**不要直接搜"农夫山泉桶装水 图片"下载使用** —— 商品照片和商标属于品牌方，平台方内置这类图会有合规风险。方案 ① 从根上规避了这个问题。

### 3.3 存储与下发方案对比

| 方案 | 存储位置 | 优点 | 缺点 |
|---|---|---|---|
| **A. 小程序本地资源（建议 MVP）** | 两个小程序各自 `assets/product/*.webp` | **零网络、零过期、零 COS 依赖**（当前 COS 恰好没配）；加载即时 | 换图需发版；两端各存一份 |
| B. COS **公有读** + 固定 URL | `public/preset/xxx.webp` | 后台可换图；URL 稳定可被 CDN/小程序缓存 | 需要把 bucket 改公有读并配 CDN；依赖 COS 可用 |
| C. COS 预签名（**现状**） | 同现状 | 无需改动 | ❌ URL **24 小时过期**，每次列表都重签，不适合"固定素材库" |

**建议：MVP 走 A，后续要"后台换图"再迁 B；C 只保留给站长自传的自定义商品图。**

### 3.4 需要拍板的一个技术分叉

"预设图"如何从 DB 走到 `<image src>`？两种都可行：

| 做法 | 链路 | 评价 |
|---|---|---|
| **甲：后端翻译成本地路径** | `image_preset='pure-barrel'` → 后端下发 `imageUrl='/assets/product/pure-barrel.webp'` | **前端零改动**（`src="{{imageUrl}}"` 直接可用）；代价是后端要知道小程序资源目录 |
| 乙：前端维护映射表 | 后端只下发 `imagePreset`，小程序侧 `PRESET_MAP[key] → 本地路径` | 后端不耦合前端路径；代价是两端各维护一份映射（**本仓历史事故模式：两端各写一套映射曾导致新客下单 100% 失败**） |

→ 倾向**甲**（符合本仓"展示口径全部由后端下发"的既有约定）。

### 3.5 数据层需要的最小改动

- 新增一列标识预设图（如 `product.image_preset varchar(64) NULL`），或复用 `image_object_name` 存约定前缀的键。
- 站长端选品弹窗增加"选图"区块（从预设列表里点选），**通用库商品仍保持锁死不可改**。
- 修 §1.3 问题 2（上传返回 URL 被当对象键入库）。

### 核心决定：一次性桶归入 `category=2`（用户拍板）

**划分口径**：`spec` < 16L 记为一次性桶（`category=2`，押金 0）；≥ 16L 记为循环桶（`category=1`，押金 50）。
有直接证据的以证据为准（好山好水 15L、畅饮吧 15L 水立多明确标「免押金」）。

**为什么必须处理**：`category=1` 是**唯一**的桶判据，且**押金填 0 也拦不住** ——
一次性桶会被记成"客户持有可回收桶"。而 `category=2` 在下单侧确实干净，
✅ 已由回归用例锁住（`DisposableBarrelLedgerBoundaryIntegrationTest` 下单侧用例）：

| 位置 | `category=2` 时的行为 |
|---|---|
| `OrderServiceImpl:258` | 不标记 `needStationAsset` |
| `OrderServiceImpl:361` | 走 else：`depositAmount += deposit×qty = 0` |
| `OrderServiceImpl:367` | **跳过桶计数** → 不建在途桶 |
| `OrderServiceImpl:500` | `delivery_bucket_qty = null` |
| `OrderServiceImpl:501` | `first_barrel_order = false` |
| `OrderServiceImpl:521` | `itemDeposit = deposit = 0` |
| `PaymentServiceImpl:1024` | 走 else：`totalNonBarrelDeposit += 0` |
| `miniapp create.js:470` | `isBarrel = false` → 押金 0 |

### ⚠️ 但配送侧并不干净（实测推翻设计推断，2026-09-19）

`BarrelLedgerService.applyDelivery` 的「本单送出」是**按 `order_item` 数量**统计的，
**完全不看 category**：

```java
deliveredByProduct.merge(it.getProductId(), it.getQuantity(), Integer::sum);
...
int delta = delivered - returned - rightPurchase;
```

一次性桶下单 2 件、收回 0 件、无新购权益 → `delta = +2` → `over += 2` → `owed != 0`
→ 经 `orderBarrelExceptionService.recordReturn` **仍生成桶异常单**。

**实测证据**（`DisposableBarrelLedgerBoundaryIntegrationTest` 首轮运行）：

| 用例 | 结果 |
|---|---|
| 下单侧（押金 0 / `bucket_qty=NULL` / `first_barrel_order=0`） | ✅ 绿 |
| **配送侧（`over` 期望 0）** | ❌ **红：实测 2** |
| 对照 `category=1` 首单（权益 2 / 押金条 2 / `over` 0） | ✅ 绿 |
| 对照 `category=1` 复购未还桶（`over` 2 + 异常单 1） | ✅ 绿 |

⇒ **「归类为瓶装水」只挡住了下单侧。**

### 这是既有潜伏缺陷，与本次迁移无关

真实库 `inventory` 只有 `category=1` 商品（4 行：station 1/2 × product 1/2），
`customer_barrel_over` 也全是 `category=1` 且 `over_qty=0` —— **从未被触发**。
但只要有**任何瓶装水 / 饮水器**被售出并完成配送，就会污染桶账。

**修复方向（待拍板）**：
- **A**：`applyDelivery` 内按 `product.category == 1` 过滤 `deliveredByProduct`（最彻底，混单也覆盖）
- **B**：`completeDelivery` 以 `order.delivery_bucket_qty == null` 为闸跳过 `applyDelivery`
  （改动最小，但**混合单仍有洞**：一单同时含桶装水与瓶装水时闸门为开）

发现与验收标准已落在 `DisposableBarrelLedgerBoundaryIntegrationTest` 的 `@Disabled` 用例上，
决定后启用即可作为修复的验收。

### 另一个独立边界：免押金的**循环桶**无法表达

```java
// PriceUtil.isEffectiveOverride —— 0 被当作"未覆盖"
return value != null && value.compareTo(BigDecimal.ZERO) > 0;
```

站级 `inventory.deposit_price = 0` 会**回落到商品押金**，而商品押金又**不能为 0**
（`CatalogServiceImpl:154`「桶装水必须设置大于 0 的押金」）。
⇒ **"免押金的循环桶"双重封锁**。水立多章丘站的「农夫山泉 饮用天然水 19升 **免押金**」正属此类。
**本轮未动计价链路**，仅记录。

### ① 品牌排序：修掉「同一品牌被排到货架两端」

`sort` 是历史累加出来的（v52 的 10–280 段、v53 的 290–450 段、一次性桶的 600–680 段），于是同一个品牌散落在货架两头，且 `sort=600` 有重复值、排序不稳定：

|---|---|---|
| 乐百氏 | 260 与 450 | 散落两端 |
| 农夫山泉 | 210 与 600 | 散落两端 + 600 重复 |
| 怡宝 | 240 与 620 | 散落两端 |
| 泉阳泉 | 390 / 630 / 640 | 三处分散 |
| 艺韵 | 360 与 670 | 散落两端 |

**修复方式**：用 `FIELD(brand, …)` **显式声明**品牌顺序（品牌拼音升序），同品牌内按 桶装水在前 → 参考价升序 → id。
⚠️ **不依赖数据库排序规则** —— 中文拼音序在 `utf8mb4_general_ci` 下并不可靠，显式列表才是可复现的。

### ② 下架：`status = 0` 的真实语义（读代码得到，非推测）

| 面 | 行为 | 依据 |
|---|---|---|
| 是否物理删除 | **否**，只置 `status = 0` | `ProductMapper.softDeleteOwned` 注释「软删除(停用/下架)」；`product.id` 是 15 张业务表的锚点 |
| **客户端商城** | **立即停售** | `listSellableByStation` / `listSellableByStationWithInventory` 的 WHERE 都带 `p.status = 1` |
| **站长端选品清单** | ⚠️ **原本不受影响** | `CatalogServiceImpl.listCatalog` 底层 SQL `listWithInventory` **不过滤 `product.status`** |
| 已选用（`inventory`） | 库存 / 站级价 / 水票开关都不受影响 | 这些都挂在 `inventory` 上，与 `product.status` 无关 |

⚠️ **必须同批改代码**：只改数据的话，下架了站长照样看得到、照样能选。本次改 `CatalogServiceImpl.listCatalog`，加三条可见性规则：

2. **通用库商品**须 `status = 1`（在架）；
3. 例外：通用库商品已下架但**本站已选用**（`inventoryId != null`）—— 仍可见，否则站长只能看着库存却找不到入口。
