## 本轮（2026-09-16）从这个矩阵里打出来的东西

1. **缺陷 A · 配送现场收款（collected）被静默丢弃** → 已修 + 5 例回归测试（S3.3）
   - 现象：货到付款点「已收款」完成配送，订单停 已送达(3)、`payment_status` 被写成 未付(0)、
     不写收款流水、押金不入账、AQ-043 跨站护栏成死代码；
   - 根因：`f3e702f`（2026-09-12）把请求体从裸 Map 收敛为强类型 DTO 时漏了 `collected` / `note`；
   - 影响面：**所有现金单**（本地库里 5 张订单有 4 张是现金）。
2. **缺陷 B · 权益退光但仍欠桶时「占用」算 0** → 已修 + 1 例回归测试（S5.4）
   - 现象：概览 `occupiedBuckets=0` 而按桶型 `occupiedQty=2`，客户端拿前者当还桶上限 →
     客户在页面上**还不了手上真有的桶**，后端却允许；
   - 根因：`getBarrelSummary` 只遍历 `customer_barrel_asset`（本仓库第 4 次踩这个坑）。
3. **缺陷 C · 配送备注（note）写不进 `special_note`** → 随缺陷 A 一并修复（同一处漏字段）。
4. **缺陷 D · 支付状态被倒滚，站长「待收款」合计丢钱** → 已修 + 2 处断言锁定（S3.7）
   - 现象：现金单「发起收款」（`createPayment`）与「送达未收款」（`completeDelivery`）都会把
     `orders.payment_status` 从 **待收款(1)** 改写成 **未支付(0)**；
   - 后果：`DashboardMapper` 的待收款金额口径是 `payment_status=1 且未取消` →
     这笔应收从站长「待收款」合计里**消失**（看不到该催谁）；
   - 修正：状态只前进 —— 只有真收到钱才写 已付款(2)，唯一入口 `OrderMapper.markPaidIfCollectable`
     （从 0/1 迁入）；发起收款与送达未收款都不再动它。
5. **产品规则「欠桶时不许退桶」补齐测试**（S5.6）：规则本身**早已实现**（`previewReturn` 申请拦 +
   `doRefund` 退押金拦 + `all-records` 给站长列表带 `owedBuckets` 标记，前端 `barrel-return` 页
   渲染「该商品欠桶 N 个：需先归还欠桶才能退押金」），但**一条用例都没有** —— 本轮补 4 例锁死，
   并 live 复验（`{"code":1,"message":"该商品还欠桶 2 个，需先归还欠桶后才能退桶退款"}`）。
   - 已知**不经过**这道校验的两条通道（均属站长人工订正，按设计允许）：
     `StationAdjustmentServiceImpl` 撤桶权益、`OrderBarrelExceptionServiceImpl` 异常单撤桶权益
     （都直连 `consumeLots`）。
6. **缺陷 E · 异常补偿「要求了却没执行」也标成已执行** → 已修 + 1 例锁定（S4.10）
   - 现象：站长批准退水票但没带 `adjustProductId` 时，`executeCompensation` 只 `log.warn`，

### 🔴 本批新发现：对账「押金穿底」把**合法中间态**算成差异

链路用例**首次运行**即抓到：**「送达未收款」状态下 `barrelState=1` 且 `E6_depositShortfall=1`。**

- **成因**：权益批次在**送达**时建（`BarrelLedgerService.applyDelivery`，可退金额 = 桶数 × 押金快照），
  押金却在**收款**时才入账（`PaymentServiceImpl.applyDepositOnPaid`）
  → 窗口内 `right_amount > 0` 而押金余额 `= 0`。两条入账时点各自都是**正确**的。
- **后果**：送达未收款是**合法经营状态**（本矩阵 S4.6 标 ✅，系统自己有 `delivered-unpaid` 列表就是为它开的），
