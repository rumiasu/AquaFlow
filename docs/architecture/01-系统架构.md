# 系统架构

> 本文说明 AquaFlow 的整体结构、后端分层、模块划分与外部集成。
>
> **文中的数量均为实测值，并标注了唯一真相源。** 结构类计数（Controller 数、端点数、表数）
> 会随开发漂移，冲突时以标注的真相源为准。

## 1. 系统概览

AquaFlow 是桶装水（18.9L）配送管理系统，服务对象是**水站**（一个站长 + 若干配送员 + 它们的客户）。

系统由**三个可运行部分**组成：

| 部分 | 形态 | 使用者 |
|---|---|---|
| `miniapp-user` | 微信小程序（原生） | 顾客 —— 下单、买桶、用水票、退空桶 |
| `miniapp-delivery` | 微信小程序（原生） | 站长（`STATION_MANAGER`）与配送员（`DELIVERY`） |
| `AquaFlow-backend` | Spring Boot 单体，端口 8080 | 上述两端共用的 HTTP API |

**没有 Web 管理后台。** 历史上存在过一个 Vue 后台（`AquaFlow-frontend`），已从仓库移除，
仅在 `archive/legacy-web-frontend/` 保留留档，不维护、不引用。站长与配送员的全部管理界面
都在 `miniapp-delivery/pages/station-mgmt/**`。

## 2. 部署拓扑

```
        ┌──────────────────┐        ┌──────────────────┐
        │  miniapp-user    │        │ miniapp-delivery │
        │  （顾客端）       │        │（站长 + 配送员端） │
        └────────┬─────────┘        └────────┬─────────┘
                 │    HTTPS + JWT            │
                 └─────────────┬─────────────┘
                               ▼
                 ┌───────────────────────────┐
                 │   AquaFlow-backend        │
                 │   Spring Boot 4 · :8080   │
                 │   Controller → Service    │
                 │        → Mapper           │
                 └───────┬───────────┬───────┘
                         │           │
              ┌──────────▼──┐   ┌────▼─────────────┐
              │  MySQL 8.4  │   │ 腾讯云 COS（可选） │
              │  单库强一致  │   │ 订单照片 / 商品图  │
              └─────────────┘   └──────────────────┘
```

设计取向是**模块化单体**：单库强一致、单进程部署，按业务域划分模块边界，
但**不拆微服务**。桶账、资金与对账之间有大量跨域事务，拆分会把当前数据库层面
的一致性保证换成分布式事务，代价远大于收益。

## 3. 后端分层

```
Controller   接收请求、认证与 DTO 校验、调服务、返回 Result<T>
    ↓
Service      业务逻辑、事务边界、跨域编排
    ↓
Mapper       数据访问（MyBatis 注解 SQL + XML 映射）
    ↓
Database     MySQL 8.4
```

**分层是硬约束，不是风格建议**：

- Controller 只做四件事，**禁止直接写** `orders` / `payment_record` / 库存 / 桶资产表。
  订单状态与副作用只能经由 `OrderWorkflowServiceImpl` 这类编排服务完成。
- 业务前置不满足一律抛 `BusinessException`（映射为响应体 `code = 1`），
  不用 `RuntimeException`（会被兜底成 500）。
- 所有状态改写必须走 CAS 并检查受影响行数。

统一响应体：

```json
{ "code": 0, "message": "ok", "data": { } }
```

`code` 取值：`0` 成功 / `1` 业务错误 / `404` 路由不存在 / `500` 系统异常。
**业务错误的 HTTP 状态仍是 200**，唯一例外是未认证返回真 401。
调用方必须判 `code`，不要判 HTTP 状态。

## 4. 横切关注点

| 组件 | 职责 |
|---|---|
| `AuthInterceptor` | 解析 JWT，把 userId / userType / role / stationId 注入 `AuthContext`（ThreadLocal，请求结束清理） |
| `RequireRoleAspect` | AOP 切面，切点 `execution(public * controller..*.*(..))`，校验 `@RequireRole` 与 `@RequireStation`；**新增方法自动生效** |
| `RateLimitInterceptor` | 登录类端点按来源 IP 限流，超限返回 HTTP 429；**单实例内存计数**，多实例部署前须换成集中式计数器 |
| `GlobalExceptionHandler` | 统一异常到 `Result<T>` 的映射 |
| `AlertService` | 分级告警落 `alert_log`：系统故障 → 系统管理员，运营故障 → 该站站长；走独立事务，失败不连累业务 |
| `CustomerProfileMask` | 跨租户可见面的画像抹除（只抹 `customerName` / `customerPhone`）的**唯一实现** |

**跨站校验一律以 `AuthContext` 中服务端刷新的 `stationId` 为准，不信任请求参数。**

## 5. 模块划分

后端入口 `AquaFlow-backend/`。下表按业务域归组，**Controller 数与端点数取自
`src/main/java/com/example/aquaflow/controller/` 实测**（49 个 Controller / 268 个端点映射）。

| 业务域 | 主要 Controller | 说明 |
|---|---|---|
| 认证与账号 | `LoginController`、`DevLoginController`、`DeliveryBindingController` | 微信登录、密码登录、Token 续期、配送员与水站的绑定申请 |
| 客户与地址 | `CustomerController`、`CustomerExceptionController`、`CustomerNotificationController`、`AddressController` | 客户档案、客户侧异常、通知、多地址与经纬度 |
| 商品与库存 | `ProductController`、`InventoryController`、`ManagerCatalogController`、`ManagerMyProductController` | 通用商品库、站级定价覆盖、站长自定义商品、库存与入库 |
| 订单 | `OrderController`、`OrderTemplateController`、`OrderImageController`、`ManagerOrderAssistController` | 下单、常用订单模板、配送照片、代客下单 |
| 配送履约 | `DeliveryController`、`DeliveryEarningController`、`ManagerDeliveryConfigController` | 接单/派单/外派、回桶核对、计件收益、站级配送计费配置（端点最多的一域） |
| 支付与资金 | `PaymentController`、`DepositRecordController`、`EnterpriseController`、`CompanyInfoController`、`ManagerReceivableController` | 收款与退款、押金流水、企业身份、应收账款与账期 |
| 水票 | `TicketAccountController`、`TicketRecordController`、`TicketPackageController`、`StationTicketDiscountController` | 水票账户、流水、档位套餐、站级折扣 |
| 桶资产 | `BarrelController`、`ManagerOwedBarrelController`、`ManagerBarrelLossController`、`ManagerExceptionController`、`ManagerAdjustmentController` | 退桶审批、欠桶、损耗、桶异常单闭环、资产调整单 |
| 组织与人员 | `StaffController`、`StationController`、`ManagerPayrollController` | 员工、水站、计件单价与工资结算单 |
| 运营支撑 | `DashboardController`、`ManagerReconciliationController`、`ManagerAlertController`、`ManagerGrossProfitController`、`ManagerTodoController`、`ManagerPendingSummaryController`、`ManagerSetupGuideController`、`ManagerStationStatusController`、`ManagerCustomerPrivilegeController` | 看板、对账、告警、毛利报表、待办汇总、建站引导、营业状态、客户特权 |
| 内容与文件 | `NoticeController`、`FeedbackController`、`FileManageController` | 公告、意见反馈、COS 文件登记 |
| 检索与通用 | `SearchController`、`CommonController` | 全局检索、通用字典 |

## 6. 数据层

- **MySQL 8.4，单库强一致**。表结构以 `AquaFlow-backend/sql/schema.sql` 为唯一权威基线
  （全部 `CREATE TABLE IF NOT EXISTS`，可重复执行）。表数与字段以该文件为准，本文不复述。
- **项目未启用 Flyway**：`sql/**` 全部靠手工执行，没有版本表、没有自动校验。
  迁移顺序与执行证据登记在 `AquaFlow-backend/sql/README.md`。
- MyBatis 同时使用注解 SQL 与 XML 映射，开启 `map-underscore-to-camel-case`。
  ⚠️ **注解 SQL 没有编译期校验**，新写必须手工在真实 MySQL 上跑过。
- 桶账、水票、押金三类资产表都有**唯一写入口**（见「领域模型」），不得绕开。

## 7. 外部集成

| 集成 | 状态 |
|---|---|
| 微信登录 | 已接入。`wx.login` 的 code 只能用**签发它的那个 appid + secret** 换取 openid，因此代码强制显式传端（`CUSTOMER` / `STAFF`） |
| 微信支付 | **未接入**。本地只有模拟渠道（`app.payment.mock-wechat-pay`，生产关闭），它是新客户第一单的唯一自助通道 |
| 微信订阅消息 | **不接入**。除少数行业外为一次性授权，无法静默获取，对本场景摩擦过大。站长端只有应用内红点 |
| 腾讯云 COS | 已接入（订单照片、商品图片）。未配置只 `log.warn`，只影响上传 |
| 告警 Webhook | 可选。未配置时告警只落库（`notify_status = LOGGED`） |

## 8. 小程序结构

两个小程序是**两套独立代码**，无框架、无分包、无 npm 构建步骤。

| | `miniapp-user` | `miniapp-delivery` |
|---|---|---|
| 使用者 | 顾客 | 站长 + 配送员 |
| 注册页面数 | 23 | 42 |
| tabBar | 订水 / 订单 / 我的 | 首页 / 配送 / 我的 |
| 页面根目录 | `pages/` | `pages/` + `pages/station-mgmt/` |

> 页面数以各自 `app.json` 的 `pages` 数组为准（上表为 2026-09-23 实测）。
> 本地开发时两端使用同一个正式 appid —— 微信的 `jscode2session` 要求 code 与 appid 配对，
> 测试号换不出可用的 openid。代价见「已知边界」。

小程序侧有三条硬约定（违反会静默失效，CI 有对应静态门禁）：

- `wxml` 内禁止调用 Page 方法、`Math.`、`Date.`；绑定的事件处理函数必须真实存在，否则**点击静默无反应**。
- 展示文案一律由后端下发，前端禁止自带 `1/2/3` 映射表。
- 文件不要写出 BOM。

## 9. 关键架构决策

| 决策 | 理由 |
|---|---|
| 客户是全局身份 | `customer` 表**没有 `station_id` 列**；订单、桶、水票、押金一律按 `(customer_id, station_id)` 隔离。客户可自由选择不同水站下单 |
| 三站语义 | 订单区分归属站（定价方）、履约站（库存与配送）、结算站（营收与应收）。跨站外派时「钱认结算站、客户资产认归属站」，写错就是真丢钱 |
| 模块化单体，不拆微服务 | 桶账、资金与对账之间大量跨域事务，拆分会把数据库级一致性换成分布式事务 |
| 无 Web 后台 | 站长与配送员都在微信生态内，多维护一个 Web 端没有收益 |
| 数据库迁移手工执行 | 单人项目，迁移频率低；执行证据逐条登记，比引入迁移框架更可控 |
| 状态改写全部 CAS 并查行数 | 配送、收款、结算都是多角色并发操作，无 expected-state 的更新会静默覆盖 |

## 10. 已知边界

以下是**有意接受的现状**，不是缺陷：

- 微信支付未接入，生产暂只开放现金与水票；客户端正向进度通知全程为 TODO。
- 本地开发两端共用同一 appid：一个 appid 只能发布一个小程序，两套代码**不能各自发布**；openid 也不再按端隔离（但 `customer` / `staff` 仍是两张独立表，功能不受影响）。
- 限流计数与部分定时任务假定**单实例部署**。
- `GET /api/notices`（顾客端公告列表）不做水站过滤，任一顾客能看到所有水站的已发布公告。
