## 1. 目的与范围

水票模型有两个可选方向，本文给出两者的**对比、定稿口径与被否决方案的理由**，并登记水票相关业务口径的未决项。

- **方案 A（混合支付）**：一单里同时用票与现金 / 微信。**技术评估完成，结论是不做**（见 §7）。
- **方案 B（统一水票）**：把「票」从逐商品绑定改为站级折扣工具。**已实施**，形态是**统一折扣**而非「一个站级通用票账户」（见 §5「被否决的形态」）。

范围之外：票的批次账与对账等式实现口径（正本 `docs/architecture/02-领域模型.md`、`docs/architecture/03-数据模型.md`）。事实基准：`src/**` > `sql/schema.sql` > 集成测试 > 本文。

## 2. 两方案对比与结论

| 维度 | A 混合支付（一单里票 + 现金 / 微信） | B 统一水票（票与商品解绑 + 分档折扣） |
|---|---|---|
| 解决的问题 | 一单多支付方式 | 票与商品解绑 + 分档折扣 |
| 动支付状态机 | **是**（引入"部分已付"） | 否 |
| 动退款路径 | **是**（两路拆分） | 否（仍是整体抵扣） |
| 动对账等式 | 等式 2 + E8 | 仅 E8 |
| 动前端 | 下单 / 支付 / 详情三处 | 购票页 + 抵扣展示 |
| 存量迁移 | 无（但存量数据为零也意味着收益低） | **几乎为零**（当时无票账户、无档位） |
| 风险 | **高** | 中 |
| 建议顺序 | **第二步**（B 之后，需求会自然缩小） | **第一步**（趁存量数据为零的窗口做） |

**结论：先做 B，A 记为"等 B 上线后再评估"。** 理由：B 用很小的改动面换来"票不再绑商品 + 分档折扣"两个真实收益，且**存量数据为零的窗口期**是最佳时机；A 要动的是本仓最硬的两块（支付状态机、退款原路），而它解决的问题在 B 之后大部分会消失——B 做完后"A 水能抵、B 水不能抵"这个分裂本身就消失了。**B 已实施**（形态见 §3 与 §5），**A 的技术评估与最终裁定见 §8**。

## 3. 设计口径

| 项 | 定稿 |
|---|---|
| 优先级 | **定制（按商品的水票）优先**；统一折扣**只在"该商品没有定制票"时生效** |
| 「统一」统一的是什么 | **折扣率**（站级一处配：买 10 张 9.5 折、30 张 9 折），**不是价格**——农夫山泉按农夫山泉的价打 9.5 折（20 → 19.00），娃哈哈按娃哈哈的价（12 → 11.40） |
| 定制优先的判据 | 该商品 `inventory.ticket_enabled = 1` 且站级水票价 > 0 → 走**定制**那套（散买按站级水票价、档位按 `ticket_package` 绝对价目表）；**即使站里配了统一折扣也不走** |
| 统一折扣的生效判据 | **本站有上架的折扣档**（不另设开关列）；全下架 = 关闭 |
| 统一折扣的覆盖范围 | 只覆盖**桶装水**（`category = 1`，与押金 / 桶账同口径）；且该商品**没开定制票**、本站**有上架折扣档** |
| 只能按档买 | 走统一折扣的商品**没有单张价**（它连站级水票价都没配），所以只有档位可买——这不是限制，是"折扣长在张数档上"的必然 |
| 账户与退款 | 票进**该商品**的账户；抵扣 / 退款与定制票**完全同一条路**（`consumeTicket` / `refundTicket` 恒用 `productId`），退款不再需要读流水自证账户 |
| 一句话理解 | 统一折扣 = 站长的**折扣工具**（多买多送，站长端是特殊化的、顾客端看起来没区别）；定制票 = 某款水的专属票 |
| 顺序 | **先做统一折扣**；混合支付**不做**（评估见 §8） |

**站长的价值**：档位一次配好全站通用，不用逐商品配；折扣是经营工具。
**顾客的价值**：不会再出现"我的票不能买这桶水"。

## 4. 问题的根源（现状事实）

| 事实 | 依据 |
|---|---|
| 水票账户**按商品 × 按站**：`ticket_account` 唯一键 `uk_customer_product_station(customer_id, product_id, station_id)` | `sql/schema.sql` |
| 批次（余额真相源）同样按商品：`ticket_lot` 带**单价快照** `unit_price`（退票按它退，不按退时的当前价） | `sql/schema.sql` |
| 档位也是按商品的：`ticket_package` 唯一键 `(station_id, product_id, qty)` | `sql/schema.sql` |
| 支付方式是**订单级单值**：`orders.payment_method`（1 微信 / 2 现金 / 3 水票），下单时选定、之后不改 | `constant/PayMethod.java` |
| 票的扣减发生在**下单之后那次支付请求**里（扣成功才置 `payment_status = 2`，单子才进站长视野） | `TicketAccountServiceImpl` + 推送判据 |
| "有的商品有票、有的没有"是真的：同一个站里可以有的商品 `ticket_enabled = 1`、有的为 0 | `inventory` 实测 |
| **功能已上线但还没人配档位、没人买过票**（`ticket_package` / `ticket_account` 存量均为 0 行） | 真实库实测——这正是"趁零存量窗口改形态"的依据 |

**两个痛点**：① 同一客户在同一站，A 水能用票、B 水不能用票 → 想一次买两样时**整单只能选一种支付方式**——这是"混合支付"的动机；② 票被绑在商品上，客户要记住"我哪张票能买哪桶水"，站长配档位也要逐商品配——这是"统一水票"的动机。

## 5. 被否决的形态：站级通用票账户

「统一水票」曾被实现为**站级通用票账户**（`product_id = 0` 的账户 + 站级一个总价），后经产品裁定收口为「统一折扣」。两种形态的差别如下，**这是本方案最容易走错的地方**：

| 站级通用票账户（错） | 统一折扣（对） |
|---|---|
| 统一票 = **站级通用账户**（`product_id = 0`），买 10 张全站通用 | 统一票**不是一个账户**；账户永远是**那一款水**的 |
| **统一定价**：站长填一个站级总价（10 张 ¥85.50），1 张 = 8.55，全站同价 | **统一折扣**：站长只填折扣（10 张 9.5 折），价格 = **各款水自己的水票价 × 折扣** |
| 顾客端多一个商品「统一水票（站级通用）」 | 顾客端**只有真实商品**，看不出两种来源 |
| 判据 `util/TicketScope`：定制余额 > 0 用定制，否则用统一票账户 | 判据 `TicketTierService`：该商品**开了定制票**就走定制，否则按统一折扣折算档位 |
| 为此加列 `ticket_record.account_product_id`（"扣自哪个账户"） | 账户恒等于 `product_id` → **该列已撤回**（迁移 `v59`） |

**为什么必须撤回**：站级一个总价会立刻与"各款水的价"分叉（贵的水和便宜的水卖出同一个单价），而折扣率天然跟着各款水自己的价走，站长也更容易解释。

**购买路径的一条硬约束**：走统一折扣的商品**只能按档位买**（`packageId` 必传）。原因：这类商品既没有商品级也没有站级水票价，散买会走"站级水票价 → `product.ticket_price`"两级阶梯、算出 **0 元** = 白送票；折扣本来就在档位上，这条限制不损失任何能力。

**幂等**：购票沿用 `uk_payment_idempotency(customer_id, idempotency_key)`；`POST /api/tickets/purchase` 的 `idempotencyKey` 必传（`order_id` 为 NULL 时 `uk_payment_active_order` 对它零保护）。

## 6. 数据模型（只写设计理由）

| 对象 | 设计理由 |
|---|---|
| `station_ticket_discount`（`(station_id, qty)` 唯一，只存 `discount_per_mille`，950 = 9.5 折） | **价格不落库**——落库就会与"各款水的价"分叉。整数千分比运算，避免浮点误差；**不另设开关列**，"本站有没有上架档位"就是生效判据 |
| `ticket_lot.unit_price`（买入当时单价快照） | 档位意味着票价分段，站长改了档位价之后「客户账户里已买的票值多少钱」与「退票按什么价退」无从回答。桶账早就解决过同一问题（"2026 年 30 元买的，2027 年退就退 30 元"），照抄该模型 |
| `ticket_lot` / `ticket_record` 的 `product_id` | 账户维度恒等于 `product_id`（统一折扣的票也进该商品的账户），故**不需要**"扣自哪个账户"的额外列；该列由 `v59` 按破坏性撤列规程处理（先上代码、再执行 SQL，脚本自带「列内有非 NULL 值就中止」护栏） |

**批次与对账**：E8 恒等式 `remain_quantity == Σ lot.remain_qty` 与 `right_amount == Σ remain_qty × unit_price` **逐字未改**，统一折扣只是多了一个"某个商品"的账户维度；用例对**两个账户**分别复核。**批次唯一写入口是 `TicketLotService`**（`createLot` / `consumeFifo`），退票沿用 FIFO + 买入均价。

⚠️ **MySQL 的 `SET` 从左到右求值**：后面的表达式看到的是已更新的列值 —— `SET remain_qty = remain_qty - q, status = CASE WHEN remain_qty - q = 0 ...` 里的 `remain_qty` 已是 0，CASE 永远算不出 0。**要把 `status` 赋值排在 `remain_qty` 前面。**

## 7. 接口与权限

| 方法 | 路径 | 角色 | 说明 |
|---|---|---|---|
| GET / POST / DELETE | `/api/ticket-discounts` | `STATION_MANAGER` | 站级统一折扣档的读 / 建 / 删；站别取自 `AuthContext` |
| GET | `/api/ticket-discounts/presets` | `STATION_MANAGER` | 平台预设档（**一键填入的草稿，不是自动落库**）；顾客令牌调不动——这是站长定价的辅助信息，不是商品数据 |
| GET | `/api/ticket-packages?stationId&productId` | 顾客端可调 | 定制档位（含已下架）；`productId=0` 现在返回空（不再有"站级通用票"这种商品） |
| POST | `/api/tickets/purchase` | 顾客（身份取自 `AuthContext`） | 在线购票；统一折扣的商品**必须传 `packageId`**，不再接受 `productId = 0`（会以"商品不存在"拒绝） |

**判据唯一实现**：该商品走定制还是走统一折扣，只由 `service/impl/TicketTierService` 判一次（同 `BarrelScope` 的做法）——否则定制 / 统一两套逻辑会在报价、下单、支付、退款四条路径上各写一遍，迟早分叉。

### 7.1 结算页水票口径（`PaymentServiceImpl.quote`）

| # | 判据（含失败表现） |
|---|---|
| 1 | ★ **水票支付是整单结清**：`createPayment` 在 `paymentMethod = 3` 时扣票成功后直接置 `PAID` 并 `applyDepositOnPaid` —— 水费、押金、配送费、楼层费**全部随票一并结清**。所以"票够"时本单要付的是 **0**，**不是「合计 − 水费」**（那会凭空多出一笔押金 + 配送费）。已用反证钉住：把 `payable` 改回"合计 − 水费"，两条"票够"用例立刻红 |
| 2 | 选中水票且**整单可被票结清**时，计费区不再逐项列水费 / 押金 / 配送费，只显示「水票抵扣 N 张 · ¥X」+「本单需付 ¥0.00」（取值见 `PaymentServiceImpl.ticketPayPreview`：`coverQty` / `coverAmount` / `fullyCovered` / `payableAmount` / `reason` / `hint`） |
| 3 | **覆盖判据与真实扣票逐条对齐**：逐行判定，账户由 `TicketTierService` 选，且必须**余额 ≥ 整行数量**才算这行能抵——`consumeTicket` 用的是 `remain_quantity >= qty` 的原子 SQL，**不存在"先抵一部分"**。所以预览也必须是全有或全无：不够就是整单用不了票；否则页面说"还差 1 桶"，提交时整行被拒 |
| 4 | **票不足时提交前就地拦住**并提示改选。放过去让它失败的后果很实际：`deductTickets` 抛错 → 订单已创建但 `payment_status` 停在 0 → 按推送判据**这单进不了站长视野**（客户以为下单成功，实际没人看得见）。拦截前会**重跑一次报价**（客户可能刚补了票），不会误伤 |
| 5 | **只提示、不拦阻**：结算页下发的提示文案（"将使用本站统一折扣（1 张抵 1 桶），余额 N 张" / "定制水票余额 N 张、本单需要 M 张" / "不能用票支付：没有定制水票，本站也未配置统一折扣"）只做提示；真正的闸门在提交路径（下单闸门 + 扣票的原子 SQL）。结算页拦一道会让"票刚好在别处补上了"的客户无法下单 |
| 6 | **展示值 vs 真实金额**：`totalAmount` 永远是**真实订单金额**；展示值单独放 `ticketPay.payableAmount`（前端 `payableAmountText`）。两者刻意分开——展示值混进提交参数就是"计价双轨" |
| 7 | **支付方式沿用是纯前端**（`utils/storage.js` 的 `payMethodStorage`，只存本地）：它是**交互偏好**不是业务事实，存后端就要跟客户档案走、考虑多端同步与脏数据。写入时机是**下单成功那一刻**——失败 / 被拒不该污染"上次成功用过的"那一项；记住的方式在本站不可用时，按 `PayMethod.availableMethods()` 下发的 `enabled` 回退到默认项 |

## 8. 混合支付：技术评估与结论

### 8.1 四类改动面

| 维度 | 改动面 |
|---|---|
| 数据 | 一张订单要能挂**多条**支付流水（票一条、现金一条）。`payment_record` 已支持多行，但 `uk_payment_active_order`（`active_order_id` 生成列）× **一单只允许一条活跃流水** → 该约束必须重新设计 |
| 状态 | `orders.payment_status` 是**单值**。混合支付下"部分已付"没有表示法 → 要么引入新状态，要么约定"票先扣、差额付清才算已付"。⚠️ 本仓硬规则：**状态只前进、不倒滚**，加状态容易、回退极难；`DashboardMapper` 的待收款口径与应收账款的 `settlement_status` 都要跟着重新定义"部分付款算什么" |
| 退款 | 必须**原路拆两路**：票退回批次（FIFO 回补）+ 现金记负数冲正 / 微信走渠道。微信渠道未接入 → 混合了微信的单根本退不了 |
| 对账 / 前端 | 等式 2（`p2a` / `p2c`）与 E8 都要按"一单多流水"重写；支付方式选择器从"三选一单值"改成"票抵扣 + 差额方式"，下单页 / 支付页 / 订单详情三处都要改，文案要能说清"已抵扣 X 张、还需付 ¥Y" |

### 8.2 为什么不做（两处硬拦）

1. **微信支付渠道全仓未接入**（`PayMethod.availableMethods()` 里恒 `enabled = false`「暂未开通」）→ 做出来是一条**付不掉的**待支付单。
2. "票 + 差额" = **一单两条活跃流水**，会撞 `uk_payment_active_order`（生成列 `active_order_id` 在 `status ∈ (1,2)` 时等于 `order_id`，唯一键保证一单一条）——这正是 §8.1「数据」那一栏，与"不用写混合支付"冲突。

⇒ **等微信渠道接入后再评估。** 一句话：**难的不是把钱算对，而是让"一张单可以有两种钱"这件事，在派单与退款两条链路上都站得住。** 当前"票不够"的场景由「整单失败 + 结算页提前说清」承担，仍无部分抵扣。

### 8.3 若要重启，先拍板四项业务口径（不是实现细节）

| # | 决策点 | 为什么它会卡住 |
|---|---|---|
| A | 余额用什么方式收 | 微信渠道未接入 ⇒ 实际只有"现金（货到付款）"一条路；而现金又要求客户已获该站授权，该授权对"已注册、还没下过单"的新客户目前开不了 —— **先解决归属，再谈混合支付** |
| B | 押金与配送费能不能用票抵 | 现状"整单用票"时票**能**抵押金 + 配送费；改成"只抵水费"更好解释，但会改变现有行为 |
| C | "一单一条收款凭据"这条限制放宽到什么程度 | 决定改造范围，也决定对账要不要重写 |
| D | 要不要新增"部分已付"这个订单状态 | 不加状态最省事（票扣了、订单仍显示"待收款"），但要在文案里说清；**加状态则回撤极难** |

### 8.4 运营上的四类成本（不是技术风险）

① **对账变复杂**：同一张单里两种钱，站长月底核对"这单到底收了多少钱、从哪儿收的"要拆开看，现在是"一单一方式"、一眼对得上。② **客诉面明显变大**："我付了钱为什么还是待收款？"——部分付款的**中间态**客户最难理解。③ **退款更容易出错**：一张单退钱要同时退票（回账户）与退现金（冲正），两条路各自都可能失败；而票是按批次买入的价退的，客户与站长的预期常常不一致。④ **站长操作面变宽**：待收款列表里会混进"已经抵了票、只差一点钱"的单，容易被误催收、误当欠款。

⇒ **在没有真实需求之前，不值得引入。**

### 8.5 替代做法（已实施）

`PayMethod.availableMethods` 里水票那一项的说明文案改为**「使用账户水票抵扣 · 票不足可先购买水票」**：它是**唯一文案来源**（选项列表由后端下发、两端一致），改一处即生效、**不新增任何 UI**；原本客户只有在提交后才被拦下，在选项上先说一句，客户点水票之前就知道"不够可以买"。**不承诺折扣**（本站折扣档可能为空，宣传"多买多折"会是假话）。

## 9. 实施落地与计划外发现

### 9.1 逐条落地

| 计划 | 实际 |
|---|---|
| `product_id = 0` 表示站级通用 | 形态已收口：账户恒等于该商品的 `product_id`（§5） |
| 站级折扣档 | ✅ `station_ticket_discount` 只存折扣千分比；**配了上架档位 = 已开通统一折扣，全下架 = 关闭**，刻意不加开关列（多一个开关就多一处会与档位状态打架的真值） |
| 购买走现有在线购票链路 | ✅ 只是必须按档位买（§5 硬约束） |
| 抵扣顺序：定制优先、统一兜底 | ✅ 判据收敛成唯一实现 `TicketTierService` |
| "定制票不够"怎么办 | ✅ 按裁定收 **a 案**：**余额 > 0 就只用定制票，不够也不拿统一折扣补差额**（"统一仅在没有定制水票的桶时生效"的字面口径）。这一条单独写进了判据类的注释与用例，**防"顺手优化"成混合支付** |
| 批次与对账 E8 不变 | ✅ 两条等式逐字未改 |
| 退票沿用 FIFO + 买入均价 | ✅ 沿用（`TicketLotService`） |
| 只抵桶装水 | ✅ `category = 1`，与押金 / 桶账口径同源；瓶装水 / 一次性桶 / 饮水机**不可用** |

### 9.2 三条计划外发现（都必须补上才不漏钱）

1. **退款必须回到"当初扣的那个账户"，不能重新判定。** 退款那一刻余额早已变化：客户把定制票**刚好用光**之后再取消订单，重新判定会判成"走统一折扣" → 票退进客户从没扣过的账户。判别用例 `refundGoesBackToCustomAccountEvenWhenBalanceHitZero`（定制 2 张、下单 2 桶 → 余额归 0 → 取消）；**已做反证**：临时把回补改成"重新判定账户"，只有这一条红、其余全绿。
2. **`uk_ticket_consume(order_id, product_id, source)` 曾不能承载"账户"这个语义**：消费流水必须记**订单行商品**（幂等键与 `countConsumeByOrderAndProduct` 都按它判重），若把统一票的流水也写成 `product_id = 0`，同一张单里**两个都走统一票的商品**会撞唯一键 → 第二条被 `catch (DuplicateKeyException)` 当成"并发重复"**静默跳过** → **少扣一张票**。形态收口后账户恒等于 `product_id`，该列已不需要；但判重与幂等键仍按订单行商品，**用例里专门有一条「两商品同单」盯这个坑**。
3. **展示层必须给账户补齐可读口径**（不能下发 `null` 让界面显示空）：客户水票明细（`TicketAccountMapper.listByCustomerAndStationWithDetail`）的名称兜底、面值取**派生列** `right_amount / remain_quantity`（= 批次加权均价，这是它唯一的真实价值口径）；水票流水（`TicketRecordMapper.RECORD_DETAIL_COLUMNS`）与客户画像资产明细（`CustomerServiceImpl`）的 `productName` 用 CASE 兜；站长"加票 / 资产调整补录"的**推断单价**取该商品本站水票价（`TicketAccountServiceImpl.inferredUnitPrice`）——**不这么兜就是 0**，会让 `right_amount` 凭空少一块，推断值仍需标记（退票需二次确认）。

## 10. 前端落点

| 端 | 位置 | 约束 |
|---|---|---|
| 站长 | `miniapp-delivery/pages/station-mgmt/ticket-packages` | 商品选择里有一个**特殊入口**配的是**折扣**（表单只有张数 + 折扣，没有总价输入框）；配了上架档位 = 开通本站统一折扣，全下架 = 关闭。另有**平台预设档**卡片 |
| 顾客 | `miniapp-user/pages/ticket` | 列表只放**真实商品**（开了定制票的 + 桶装水）；档位拉回来看不出两种来源（`source` 只给前端决定回传 `packageId` 还是 `unifiedQty`）；走统一折扣的商品只能选档位（隐藏数量步进器），因为它没有单张价 |
| 顾客 | `miniapp-user/pages/order/create.{js,wxml,wxss}` | 支付方式选择器 + 计费区：展示 `payableAmountText` 与 `ticketPay`，前端不做任何抵扣算术 |

**平台预设档**：形态是"一键填入的草稿"，**不是自动落库的档位**——上架档位**就是**统一折扣的站级开关，平台若替所有水站自动插三行，等于替他们开通了一个折扣工具；定价是站长的经营决定，系统只给建议。预设张数 10 / 20 / 100 张、折扣 9.5 / 9 / 8.5 折（`950‰ / 900‰ / 850‰`，整数运算不用浮点）；基准价是**本站已上架桶装水里最便宜的那一桶**，单价走 `PriceUtil.calcUnitPrice(…, TICKET)` 那一级（站级水票价 → 通用库水票价 → 零售价）——与客户**用票抵扣时订单水费的计算口径同源**，否则按建议价卖票会亏；依据文案按**最终胜出的那个商品**判定（判据 `PriceUtil.hasEffectiveTicketPrice`，与 `calcUnitPrice` 共用同一个覆盖判定，不会分叉）；金额算法与 `TicketPackageController.save` 逐字相同（总价 = 基准 × 张数 × 折扣，均价 = 总价 ÷ 张数），所以"界面显示的均价"与"保存后快照进批次的均价"必然是一个数。**没有桶装水就不给建议**（`presets: []` + `basePriceBasis: null`），前端提示"先上架桶装水或自己填价"，**绝不凭空捏一个数**。⚠️ 千分比换"折"要 **÷100**（950‰ → 9.5 折），写成 ÷10 会让界面显示「95 折」——`TicketPresetTest` 钉住了这条。

⚠️ **通用判据（混编码）**：`.wxss` / `.wxml` 出现"**编译错误但不指名文件**"，先查 BOM、再查**一个文件内前后半段编码不一致**；静态门禁发现不了混编码（它们不解析编码）。同一文件前半 UTF-8、后半 GBK 会让微信开发者工具按 UTF-8 解码时报错。

## 12. 待确认事项

| 待确认内容 | 需要的验证手段 | 影响 |
|---|---|---|
| 票面值口径（**已知偏差，未闭合**） | 见下 | 要不要改成"按批次均价记账"**需要产品拍板**——改了会动营收 / 毛利报表口径 |
| 混合支付（一单里票 + 现金 / 微信） | 先接微信渠道；并按 §8.3 拍板四项业务口径 | 未做；当前"票不够"= 整单失败，由结算页提示提前告知 |
| "1 单位 = 金额额度"备选口径 | 产品拍板是否要按元抵扣 | 未做，只做了"1 张 = 1 桶"。按金额抵扣会让"贵水 / 便宜水"扣的额度不同，站长更难解释 |
| 瓶装水 / 一次性桶 / 饮水机能否用票 | 产品拍板（建议不可用） | 现状只覆盖桶装水（`category = 1`） |

**票面值口径的具体内容**：水票抵扣时订单水费仍走 `PriceUtil.calcUnitPrice(…, TICKET)`（站级水票价 → 通用库 → 零售价）。对**走统一折扣的商品**来说，它没配站级水票价 → 实际按**零售价**记订单水费，而客户实付是**折扣价**。这是"折扣只在购买那一刻固化进批次均价"这条既有口径的延续（与定制票档位**同一口径**，不是本批引入），但它意味着"**账面营收按挂牌价、实收按折扣价**"，且**统一折扣把这个差额放大了**（折扣越深、账面与实收差得越多）。
