## 1. 删除类改动的报备协议

删除代码、端点或文件前必须先**只读排查**，并给出六项：

| # | 项目 | 要求 |
|---|---|---|
| ① | 核实到哪一步 | 几遍核实、用什么方法 |
| ② | 证据 | 逐条 `文件:行号` |
| ③ | 原来为什么存在 | 它当初解决什么问题 |
| ④ | 删掉会怎样 | 连带影响的测试 / 文档 / 常量 / mapper |
| ⑤ | 推荐删或留 + 理由 | 结论要明确 |
| ⑥ | 风险等级 | 高 / 中 / 低 |

**破坏性操作**（删文件、改 git 历史、清库、跑历史迁移 SQL）先报证据与影响，**等确认后再执行**。

## 2. 核实纪律

**判据：自己 grep 出所有出现位置，逐个确认是"真调用"还是仅"常量定义 / 文档 / 注释 / 测试断言" —— 定义 ≠ 调用。**

四条硬要求：

1. **不能只靠审计脚本下结论。** 仓库根目录的 `api_reverse_audit.py` 既有假阳性也有假阴性：
   行号按剥离注释后计（系统性偏早）、只比对路径不看 HTTP 方法（报的数字是下界），
   且认不出「页面内路径常量拼接」与「路径段由函数参数传入」的调用 —— **在用端点会被判死**。
   脚本产出的是**候选清单，不是结论**。
2. **查引用必须覆盖 `.js` / `.wxml` / `.java` / `*.md` 四类。** 小程序调用常只写在 **`.wxml`**
   （`data-url` + `bindtap`），只 grep `*.js` 会把有入口的页面误判成孤儿页。
3. **要顺 handler 往下看一跳**，确认点击后真的会跳转，而不只是"绑定了一个存在的函数"。
4. **零引用确认后再跑一次全量测试**留基线，避免删掉的东西正被某条用例间接触达。

## 3. 已删除端点登记

| 端点 | 删除理由 |
|---|---|
| `PUT /api/orders/{id}/status` | 状态改写只允许经 `OrderWorkflowServiceImpl` 编排。开放通用改状态入口等于绕开 CAS、副作用与判权 |
| `POST /api/manager/reconciliation/run` | 会写**全平台**对账结果 = 跨租户泄露。现只保留只读的 `GET`（本站即时对账），运维记录由定时任务落表 |
| `GET /api/payments/config` | 站点级线下支付总开关已移除；货到付款的唯一控制点收敛为**客户级**授权 |
| `GET /api/barrels/assets` | 被桶权益批次模型取代（余额真相源改为批次表） |
| `POST /api/barrels/handle-exception` | 被桶异常单闭环取代（登记 → 处置 → 核销 / 撤回权益） |
| `GET /api/dashboard/station-exception*` | 同上，随异常单闭环一并下线 |

> 上表的零引用结论经逐条 grep 复核（覆盖四类文件），且已核对当前端点集合中确实不存在这些路径。
> 端点的当前全量清单见 [`../api/01-REST-API参考.md`](../api/01-REST-API参考.md)。

## 4. 待观察：保留但无活跃调用方的端点

有些端点**没有前端调用方但不应删除** —— 它们是运维排查或人工核对步骤的入口
（例如让维护者直接发请求看对账差异）。这类端点的判定需要区分「设计上就不面向界面」
与「界面漏接」，两者结论相反，**不要仅凭"前端零调用"就删**。

## 5. 历史存档

更早期做过一次逐条零引用核实（覆盖数十个端点，逐条带证据、日期与"删 / 接线 / 保留"三类结论），
