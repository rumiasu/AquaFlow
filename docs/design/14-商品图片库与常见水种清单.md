## 1. 目的与范围

平台统一商品库（`product.owner_station_id IS NULL`）需要一套商品图，让站长建商品时从平台预设图里"选"，而不是各自拍照上传。本文定义**允许的图源、解析与下发口径、商品行的挂图与上下架规则**，并附一份桶装水市场调研（水种、品牌、规格、价格带、押金与水票惯例）作为选品定价参考。

不在范围内：商品与库存的结构化模型（正本 [`docs/design/12-商品与库存重构.md`](12-商品与库存重构.md)）；桶权益、押金与桶账模型（正本 [`docs/architecture/02-领域模型.md`](../architecture/02-领域模型.md)）。

### 2.6 押金、起订与水票惯例（2026-09 实采）

**押金**：

| 口径 | 金额 |
|---|---|
| 大品牌（农夫山泉 / 娃哈哈 / 冰露 / 怡宝） | **50 元 / 个**，退桶可退 |
| 本地品牌（普利思 / 泉娃 / 百脉泉） | **50 元 / 个**；且**三品牌空桶可互换** |
| 低价位本地（百圣泉） | **30 元 / 个** |
| 一次性桶 | **免押金**（但售价更高，约 27–30 元/桶） |

**配送与起订**：多数水站 **5 桶以上免运费**，少量订购收 5–10 元；部分水站 **2 桶起订**、部分 **10 桶起订**（视定位：居民站门槛低、单位配送站门槛高）。归 `station_delivery_config`。

**水票（"卖法"的核心）**：桶装水**普遍推行水票**，主流政策是 **买十赠一 / 买十送一**（普利思、百脉泉均明示）；另有 **20 张 / 30 张套餐**（如 200 元 15 张 ≈ 13.3 元/桶）、**满 100 张送立式饮水机**。

> ⚠️ 实现口径：水票的**面值**（一张抵多少钱）落在 `product.ticket_price` / `inventory.ticket_price`；
> 「买十赠一」是**赠**不是**降价**，它的归宿是**站级** `ticket_package` 档位（`qty=11 / price=10 张的钱`）。
> 见 [`AquaFlow-backend/sql/README.md`](../../AquaFlow-backend/sql/README.md) 中「定价结构不是促销引擎」一节。

## 3. 设计口径

### 3.1 图源（红线）

| 图源 | 是否允许 | 判据 |
|---|---|---|
| 品牌官网实拍图 | ✅ 当前唯一允许的商品行图源 | 受下方版权红线约束 |
| 平台自制图（AI 生成 / 设计工具绘制或加工） | ❌ 禁止 | 产品口径：**平台不提供任何自行生成 / 加工的图**。曾试 AI 生成路线，独立文生图会得到桶型 / 视角 / 光照各异的散图，不成套 |
| 从搜索引擎 / 电商下载的品牌商品照片 | ❌ 禁止用于平台内置图库 | 商品照片与商标属品牌方，平台内置这类图有合规风险 |

> ⚠️ **版权红线**：商品行上挂的品牌官网图**未经授权**，仅适用于开发 / 内测阶段。正式对外上线前必须取得授权或换成有授权的图。这是产品已知情并接受的内测期权宜，**不是可以带到线上的状态**。

> ⚠️ **平台预设图库（站长选图面板）当前为空**：`constant/ProductImageKeys` 的映射表无任何条目，`GET /api/manager/catalog/preset-images` 返回空数组，前端显示「暂无预设图」。恢复该面板前必须先定图源 —— 品牌官网图用于平台内置库有商标与授权风险，自制图已被否决，见 §8。

### 3.2 平台统一商品库机制（复用，不新建）

| 事实 | 出处 |
|---|---|
| `product.owner_station_id IS NULL` = **通用商品库**（开发者维护、站长只读，只能"选用"） | `entity/Product.java`、`sql/migration_v31_catalog_and_station_pricing.sql` |
| 站长侧写入口只有 `/api/manager/catalog*` 与 `/api/manager/my-products*`；旧 `/api/manager/products*` 已删除 | [`docs/design/12-商品与库存重构.md`](12-商品与库存重构.md) |
| 通用库商品的**名称 / 规格 / 图片对站长锁死**；只有"本站自定义商品"可改图片 | 同上 |
| 通用库商品的图片 / 描述**由开发者维护**（COS 直传，或迁移脚本写 `image_object_name`） | 同上 |

→ 本需求 = 把通用商品库的图片填充做扎实 + 给站长一个选图入口，**不新增机制**。

### 3.3 图片字段与渲染链路

```
product.image_object_name  (varchar(500)：本地资源路径，或 COS 对象键)
   │  util/ProductImageResolver.resolve()  ← 全系统唯一判据；以 / 开头即原样直通
   ▼  imageUrl（transient，不入库，由 Service / Controller 注入）
   小程序 <image src="{{item.imageUrl}}">
```

| 环节 | 位置 |
|---|---|
| 字段定义 | `entity/Product.java`（`imageObjectName`） |
| 解析 | `util/ProductImageResolver.resolve` |
| COS 上传与签名 | `util/CosUtil.uploadPublic` / `CosUtil.generatePublicUrl` |
| 列表注入 | `service/impl/CatalogServiceImpl.withImageUrls` |
| 顾客端注入 | `controller/ProductController`（`Product` / `StationProductVO`） |
| 返回字段名 | `imageUrl`（`dto/StationProductVO`）+ `imageObjectName`；前端消费点见 §6 |

**解析契约三条**（实现 `util/ProductImageResolver.resolve`，确定性用例 `ProductImageResolverTest`）：

1. 以 `/` 开头的值 = **小程序包内本地资源，原样返回**，且**绝不调用签名器** —— 本地图能不能显示与 COS 配没配无关，这是商品图能显示出来的根本；
2. 其它非空值 = COS 对象键 → 返回签名 URL（24 小时有效，带内存缓存）；
3. 签不出来（COS 未配置 / 网络失败 / 对象不存在）→ **返回 `null`，绝不抛异常**。一张图签不出来不能让整个选品列表失败。

> ⚠️ `null` 的语义是「这张图当前不可用」，**不是**「没有配图」—— 两者在数据层可区分（`image_object_name IS NULL` vs 有值但签不出来）。前端对两者一律渲染占位图，**不要在调用点用"是不是 null"反推原因**。

> ⚠️ **COS 未配置时的表现**：`config/RequiredConfigChecker` 对 COS 密钥只 `log.warn`、不拒启。此时 `generatePublicUrl` 抛异常 → 被 catch 吞掉 → 接口仍返回 `code=0`，但 `imageUrl` 恒为 `null` → 顾客看到占位图，**不报错**。`POST /api/common/upload` 在同样情况下返回「对象存储未配置」（文案由 `CosUtil.uploadFailureMessage` 统一给，否则只有一句笼统的"上传失败"，分不清是没配还是配错）。判据：**商品图链路的故障形态是静默无图，不是报错** —— 排查先确认图值是不是以 `/` 开头。

### 3.4 存储与下发方案

| 方案 | 存储位置 | 评价 |
|---|---|---|
| **A. 小程序本地资源（当前采用）** | 两个小程序各自 `assets/product/*.webp` | **零网络、零过期、零 COS 依赖**，加载即时。代价：换图需发版；两端各存一份 |
| B. COS **公有读** + 固定 URL | `public/preset/xxx.webp` | 后台可换图；URL 稳定，可被 CDN 与小程序缓存。需把 bucket 改公有读 |
| C. COS 预签名 | 同现状 | ❌ URL **24 小时过期**、每次列表都重签，**不适合固定素材库**；只留给站长自传的自定义商品图 |

**切换口**：A → B 只需把 `image_object_name` 的值换成 COS 地址，**代码零改动**（判据见 §3.3 第 1 条）。

### 3.5 key → 路径的翻译位置

预设图如何从数据走到 `<image src>`，**已选甲**：

| 做法 | 链路 | 评价 |
|---|---|---|
| **甲：后端翻译成本地路径（已采用）** | 后端下发 `imageUrl = '/assets/product/xxx.webp'` | **前端零改动**（`src="{{imageUrl}}"` 直接可用），符合本仓「展示口径全部由后端下发」的既有约定。代价：后端要知道小程序资源目录 |
| 乙：前端维护映射表 | 后端只下发 key，小程序侧 `key → 本地路径` | 后端不耦合前端路径。代价：两端各维护一份映射 —— **本仓历史事故：两端各写一套映射曾导致新客下单 100% 失败** |

> ⚠️ 配套口径：站长端点选预设图后，值必须写进 `imageUrl` 且**以 `/` 开头** —— 后端 `CatalogServiceImpl.pickImageValue` 只认这种形式（`http` 开头的一律视为上传回填的过期预签名 URL 而丢弃）。

### 3.6 落库口径（round-trip 缺陷）

缺陷形态：`POST /api/common/upload` 返回的是**预签名 URL**，站长端把它回填进 `editForm.imageUrl`，旧实现又把它**当 COS 对象键落库** → `resolve(那个 URL)` 永远签不出有效地址 → 图永远不显示。

**判据**（`service/impl/CatalogServiceImpl.pickImageValue`，用例 `ProductImageIntegrationTest`）：

1. `imageObjectName` 是**对象键或本地资源路径**，本就该落库 → **优先**；
2. `imageUrl` 只有在**以 `/` 开头**（本地路径）时才接受；
3. 其余（预签名 URL）**记 warn 日志并丢弃**，落 `null`。

理由：**半坏的图比明确的"无图"更难排查** —— 宁可显示占位图，也不要存一个永远签不出来的值。

### 3.7 商品行挂图：为什么图必须"去统一化"

平台**预设图库**与**商品行的实际图**是两件事：它们共存于同一列 `image_object_name`，解析链路一视同仁（都以 `/` 开头 → 原样下发）。

| | 平台预设图库 | 商品行实际图 |
|---|---|---|
| 面向 | 站长建自定义商品时"选一张" | 通用库商品挂自己的品牌图 |
| 映射 | `constant/ProductImageKeys` 的 key → 路径表 | 商品行直接存路径，**不经过 key 体系** |
| 当前状态 | 空数组（见 §3.1） | 能采到官网图的品牌已挂 |

> ⚠️ **全部商品行共用同一张图是必须避免的状态**：站长在选品界面**无法凭图区分品牌**，货架视觉退化成一张图重复 N 次。判据：**只要有该品牌可用的官网实拍图，就换成该品牌的图**；采不到的**不要硬挂**通用图或自制图，按 §3.8 下架。
>
> ⚠️ **挂图以实际画面内容为准，不采信源图文件名**：素材库有命名错误（标着 18.9L 循环桶的实为 3.78L 小桶，标着「蓝桶 / 蓝桶2」的实为山泉 / 矿泉水大桶），照名字匹配会挂错图。

> ⚠️ **已知代价**：一张图覆盖多个规格时，小规格（如 5L / 12L 一次性桶）会显示 18.9L 循环桶的画面。这是"一图一行"的已知取舍，不是缺陷。

### 3.8 上架 / 下架

`status = 0` 的真实语义（读代码得到，非推测）：

| 面 | 行为 | 依据 |
|---|---|---|
| 是否物理删除 | **否**，只置 `status = 0` | `ProductMapper.softDeleteOwned` 注释「软删除(停用/下架)」；`product.id` 是业务流水表的锚点，仓规**永不物理删商品** |
| **客户端商城** | **立即停售** | `ProductMapper.listSellableByStation` / `listSellableByStationWithInventory` 的 WHERE 都带 `p.status = 1` |
| **站长端选品清单** | ⚠️ **底层 SQL 不过滤 `product.status`** | `ProductMapper.listWithInventory` |
| 已选用（`inventory`） | 库存 / 站级价 / 水票开关不受影响 | 这些挂在 `inventory` 上，与 `product.status` 无关 |

> ⚠️ **只改数据是不够的**：`listWithInventory` 不过滤 `product.status`，所以下架之后站长照样看得到、照样能选。`CatalogServiceImpl.listCatalog` **必须同批加可见性规则，三条缺一不可**：
>
> 1. **本站自定义商品**（`ownerStationId` 非空）—— 平台下架管不到它，始终可见；
> 2. **通用库商品**须 `status = 1`（在架）；
> 3. 例外：通用库商品已下架但**本站已选用**（`inventoryId` 非 null）—— 仍可见，否则站长只能看着库存却找不到入口（历史订单与库存都还挂在它身上）。

> ⚠️ **副作用（须知情）**：已被水站选用的商品若因无品牌图一并下架，会**从客户端商城消失**（商城判据是 `p.status = 1`）；站长端仍可见（属「本站已选用」豁免），**库存与历史订单不受影响**。恢复售卖只需把该行 `status` 置回 1。

**恢复路径（二选一）**：① **补图后恢复** —— 采到官网图 → 挂图 + `status = 1`，逐品牌恢复；② **整体恢复** —— `UPDATE product SET status = 1 WHERE owner_station_id IS NULL;`。

### 3.9 下架行必须同时清空图片引用

> ⚠️ **删图片文件还不够，必须同时改数据**：`image_object_name` 指着已删除的路径就是**死链**。将来重新上架时，界面会去加载一个不存在的包内资源：表现是**静默无图**、**不报错**，与"本来就没配图"无法区分，排查成本高。⇒ 置 `NULL`，让"没有图"在数据层如实反映。

**脚本安全闸**：待清理行里**还有在架的**则**直接终止** —— 防止把在架商品悄悄变成无图。

**恢复方式**：见 §3.8 的恢复路径；若要同时恢复选图面板，把实拍图登记进 `ProductImageKeys` 的静态块即可，**无需改任何调用方**（`GET /api/manager/catalog/preset-images` 直接读该表）。

### 3.10 商品命名与卖法

1. **商品名带水种**（`{品牌} {水种} {规格} 桶装水`），**图不带水种**。同品牌同规格下纯净水与天然矿泉水是**不同的品**、价格差近一倍（普利思 12 vs 16）；**水种差异体现在名字与价格，不体现在视觉**。
2. **只挂图、不改名**：`product_id` 被订单明细、押金流水、水票流水、桶资产等多张业务表引用，改 `name` 会**篡改历史订单与资产记录的留痕** —— 商品名是快照信息，不是可随时改的展示字段；同时 `preset_uk`（`name|brand|spec` 生成列）会被触发，有撞唯一键的风险。**新增商品写入时直接带水种，不回改存量行。**
   - 存量改名若确有必要，安全前提是：`order_item` 有 `product_name_snapshot` / `brand_snapshot` / `spec_snapshot` 三个快照列，`OrderMapper` / `DashboardMapper` / `GrossProfitMapper` 的下单、看板、毛利展示**全走快照**，引用**按 `product_id` 不按名**。
   - 唯一可见副作用：`CustomerMapper.listFavoriteProducts`（客户画像「常用商品 TOP3」）用 `ifnull(p.name, oi.product_name_snapshot)`，**活名优先** → 标签跟着变新名（文案级，且更准确）。
3. ⚠️ **改通用库押金会真的改变计费**：站级 `inventory.deposit_price` 为 NULL 时按 `PriceUtil.calcDeposit` 回落到 `product.deposit`，客户首单缺桶押金随之变化。改参考押金前先确认各站是否已设站级押金。
4. **卖法落到既有列，不新增字段**：`price` 参考零售价 / `deposit` 空桶押金 / `ticket_enabled` + `ticket_price` 水票开关与面值。
5. ⚠️ `ticket_price` 设为**等于零售价** —— 票的**面值**就是"一张抵一桶的钱"；而「买十赠一」是**赠**不是**降价**，归宿是**站级** `ticket_package` 档位（见 §2.6）。
6. 平台迁移**只写 `product`**（通用库参考价），**一行不动 `inventory`**：站长选不选、卖多少钱，是站长的事。站级水票档位（`ticket_package`）与配送计费参数（`station_delivery_config`）都是每个水站自己的经营参数，**不该由平台替他定**。

### 3.11 通用库的收录规则

**只收目标城市（本文为济南）水站 / 配送商明确在售的品牌。** 排除的五类及理由：

| 排除类 | 对象 | 理由 |
|---|---|---|
| 无本地在售证据 | 康师傅 / 屈臣氏 / 昆仑山 | 只有电商与超市渠道，济南水站不上架 |
| B2B 定制代工 | 鹤知源（邹平）/ 甘雨露（日照）/ 普利森 / 达利园 | 不是水站货架上的零售品 |
| 配送平台 | 水鲤鲤 / 好柿到家 / 水立多 | 是**渠道**不是水品牌 |
| 其他城市本地品牌 | 北纬39度 / 汇云山泉（天津）、悦玛泉（天津） | 目标城市无在售证据 |
| 证据不足 | 艾珂 | 仅出现于「主营品牌」列表，无规格、无水种、无价 |

> ⚠️ **普利思（济南普利思饮用水）≠ 普利森（山东普利森饮用水）**，是两家不同企业，不要合并。

> ⚠️ **写迁移前先看 `sql/` 目录的现有编号**，别照迁移清单尾部的数字 +1 —— 清单更新有滞后，本仓已因此撞过号。迁移顺序的正本是 [`sql/README.md`](../../AquaFlow-backend/sql/README.md)。
>
> ⚠️ **迁移必须幂等**：`UPDATE` 带「目标值 ≠ 现值」或 `IS NULL` 条件。

### 3.12 排序

> ⚠️ **品牌顺序用 `FIELD(brand, …)` 显式声明**（品牌拼音升序），同品牌内按 桶装水在前 → 参考价升序 → id。**不依赖数据库排序规则** —— 中文拼音序在 `utf8mb4_general_ci` 下并不可靠，显式列表才是可复现的。

- 历史形态：`sort` 由多批迁移分段累加而来，同一品牌散落在货架两端，且可能产生**重复 `sort` 值**（排序不稳定）。重建时按上口径**一次性重排**，不追加分段。
- 脚本自带断言：品牌不在 `FIELD` 列表中（返回 0、排到最前）则**直接终止**。

### 3.13 一次性桶的归类

**划分口径**：`spec` < 16L 记为一次性桶（`category=2`，押金 0）；≥ 16L 记为循环桶（`category=1`，押金 50）。有直接证据的以证据为准（如 15L 明确标「免押金」）。

**为什么必须处理**：`category=1` 是**唯一**的桶判据，且**押金填 0 也拦不住** —— 一次性桶会被记成"客户持有可回收桶"：既按件收押金、又进配送中桶、送达后要求回桶 → **凭空生成桶异常单**。归入 `category=2` 后下单侧确实干净：不标记 `needStationAsset`、押金 0、**跳过桶计数**（不建配送中桶）、`delivery_bucket_qty = null`、`first_barrel_order = false`。

> ⚠️ **配送侧曾经不干净（已修复）**：`BarrelLedgerService.applyDelivery` 的「本单送出」若按 `order_item` 数量统计、不看 category，一次性桶下单 2 件、收回 0 件、无新购权益 → `delta = +2` → `over += 2` → `owed != 0` → 经 `orderBarrelExceptionService.recordReturn` **凭空生成桶异常单**。⇒ **「归类为瓶装水」只能挡住下单侧。**

**现行判据 —— 唯一实现在 `util/BarrelScope`**：凡是要判断"要不要收押金 / 要不要进桶账 / 算不算桶数"的地方，**一律调 `BarrelScope.isBarrel` / `BarrelScope.isBarrelCategory`**，**不要在调用点写 `category == 1` 或 `category != 1`** —— 判据只留一处，将来支持"循环箱装水"之类新形态时改这里一处即可（那时才引入 `reuse_mode`）。

> ⚠️ **被否决的偷懒修法**：以 `order.delivery_bucket_qty == null` 为闸跳过 `applyDelivery` —— 改动最小，但**混合单仍有洞**：一单同时含桶装水与一次性桶时闸门是开的。必须按**品类**过滤。

**押金只对桶装水生效**（读写双保险）：读侧 `PriceUtil.calcDeposit` 对非桶装一律返回 0；写侧 `CatalogServiceImpl` 对非桶装设押金**直接拒绝**并说明原因（"只有桶装水能设押金……不收押金（也无需退）"）。只靠读侧会变成"站长填了、系统不认、还不报错"。

> ⚠️ **免押金的循环桶当前无法表达**（未修）：站级 `inventory.deposit_price = 0` 会被 `PriceUtil.isEffectiveOverride` 当作"未覆盖"而回落到商品押金，而商品押金又**不能为 0**（`CatalogServiceImpl`：「桶装水必须设置大于 0 的押金」，依据是"没有押金 = 桶白送，与桶账模型冲突"）⇒ **"免押金的循环桶"双重封锁**，站级无法做免押促销。水立多章丘站的「饮用天然水 19L 免押金」正属此类。见 §8。

## 4. 数据模型

只写设计理由；表结构与列定义以 [`AquaFlow-backend/sql/schema.sql`](../../AquaFlow-backend/sql/schema.sql) 为准。

1. **不新增 `image_preset` 列**：`image_object_name` 本就只承载"一个字符串"，**新增列会让"哪一列是真值"产生二义性**，故否决。判据改为「值以 `/` 开头即本地资源路径」。
2. **两种口径共存于同一列**：本地资源路径与 COS 对象键都存 `image_object_name`，由 `util/ProductImageResolver.resolve` 一视同仁地解析（切换口见 §3.4）。
3. **`image_object_name` 可空，且"有值"不等于"可显示"**：签不出来时降级为 `null`（见 §3.3）—— 因此 `NULL` 的语义是「没有配图」，"有值但签不出来"是「这张图当前不可用」。
4. **不物理删商品行**：`product.id` 是订单明细、押金流水、水票流水、桶资产等流水的锚点。下架一律走 `status = 0`。
5. **一次性桶复用 `category=2`**，不新增"复用方式"列。代价是 `category=2` 同时表示瓶装水与一次性桶，语义偏宽；要精确区分需引入 `reuse_mode`（见 §8）。
