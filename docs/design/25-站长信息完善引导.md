## 1. 目的与范围

把「站长该填什么、为什么必须填、不填会怎样、建议值是多少」从口头经验变成系统行为。范围是引导规则目录与判据、缺字段后果、引导机制、默认值来源、平台预设库；各配置项本身的口径不在范围内（配送计费见 [17-配送计费与配送范围.md](17-配送计费与配送范围.md)，水票档位见 [19-水票档位与批次单价.md](19-水票档位与批次单价.md)）。三条硬要求：**电话加进建站必填**；**有员工则工资结构必填**（选固定工资则不填，见 §7）；**配送费相关必填**。

---

## 2. 设计口径：规则目录是单一数据源

`StationSetupGuideService` 配 `GET /api/manager/setup-guide`（`@RequireRole("STATION_MANAGER")`，站点取自登录态）。**每加一条规则只改这一个类**；页面只渲染后端下发的中文（`label` / `why` / `where` / `level` / `done` / `suggestion` / `action`），**前端不自建 key→文案映射**。

| key | 级别 | 判据 | 不填的后果（不是「不完整」，是「功能静默失效」） | 去哪填 |
|---|---|---|---|---|
| `stationPhone` | P0 | `station.phone` 非空 | 下单页显示「水站电话：请咨询客服」占位文案，退桶 / 催单只能干等 | 水站资料；**建站已必填** |
| `stationLocation` | P0 | `station.lat` 与 `lng` 都非空 | 算不出距离 → **配送范围整段失效**、超范围单照接（`GeoUtil#distanceMeters` 可为 null → 「拿不准就不判」） | 水站资料；点地图选点 |
| `stationAddress` | P1 | `station.address` 非空 | 客户选站与找路靠它 | 水站资料 |
| `catalogOnShelf` | P0 | 至少 1 个 `inventory.enabled = 1` 的商品 | 客户看不到商品就没法下单；**「选品」不等于「上架」** | 商品与库存 |
| `deliveryFee` | P0 | `station_delivery_config` **有行**（哪怕全 0） | 没保存过 = 起送量 / 范围 / 运费 / 楼层费一条都没生效 | 配送计费 |
| `staffPayroll` | P1 | 无配送员 **或** 站级默认计件单价已配 | 有配送员却没单价 → 送的水**按 0 元记工钱**，结算单也是 0（`StaffEarningServiceImpl#rateOf` 回落零价，**不报错**） | 工资设置 |
| `ticketPackage` | P1 | 开了水票的商品都有上架档位 | 客户想买票却看不到价目表 | 商品与库存 |
| `stationNotice` | P2 | 恒 true（软状态） | 歇业 / 放假时客户不能提前知道（不阻断下单） | 营业状态与公告 |

**「配送计费」为什么用「有没有保存过」当判据**：「没配」与「配成全 0（= 明确表示不收）」因此区分得开——不必强迫站长填假数字，也不会把「本来就不收」误判成「没配」。这就是「配送费相关必填」的可操作定义。

这些字段缺失时系统**不报错**，只会「少做一件事」——正是本仓最忌讳的**静默失效**；引导的目标是**让站长知道哪条规则在空转**。

⚠️ **标了 `*` 就必须真的拦**：库中水站的坐标全是 NULL、电话也有空串，而建站页把「定位水站位置」标了 `*` 却不校验——等于给站长一个假承诺。

⚠️ **`constant/PendingItem` 是待办条目的唯一目录**：`ManagerPendingSummaryController` 按目录逐条算数，级别取默认值与配置覆盖 `aquaflow.pending.level-overrides` 的合并结果——调整「哪件事算紧急」**只动目录一行或加一个配置键**。**前端 tab 红点只报 P0**（P1 / P2 一起算，红点天天亮着就成了背景噪音），且**不得自带 key→中文映射表**。

## 3. 引导机制（从「提醒」到「一键完成」）

1. **待办层**：把缺口做成待办条目，站长一进「水站管理」就看到。**建议新增 `STATION_PROFILE_INCOMPLETE`（P1）**：缺坐标 / 电话 / 金额门槛时亮一条，点进去直达对应页面；新增 key **只改 `PendingItem` 一行**。
2. **页面层**：字段所在页面自己说清「为什么必须填」。已落地：配送计费页的「还差金额门槛」引导卡，文案与建议值由后端 `guidance` 下发。
3. **一键层**：能算的默认值绝不让站长手填。已落地：金额门槛建议值 = 本站最便宜的一桶水 × 2（起送）/ × 3（免运费），取整到元，点「一键填入建议值」即完成；**没有已上架商品时不给建议值**（不凭空捏造一个数）。阈值常量 `DeliveryConfigGuideService#MIN_ORDER_BUCKETS_EQUIVALENT` / `#FREE_DELIVERY_BUCKETS_EQUIVALENT`。

---

## 4. 默认值从哪来（给谁默认、不给谁默认）

| 字段 | 能否给默认 | 来源 | 为什么 |
|---|---|---|---|
| 起送量金额 / 免运费金额 | ✅ 建议值 | 本站已上架**桶装水最低价** × 2 / × 3 | 站长的心理单位是「几桶水的钱」，可解释、可改 |
| 起送桶数 / 免运费桶数 | ⚠️ **不给默认** | —— | 给了默认等于**替站长决定接不接单**，属经营决策 |
| 水站坐标 | ✅ 可预填 | 地图选点 | 不能凭空给 |
| 水票档位 | ✅ 可预置 | 平台预设 10 / 20 / 100 张，按当前水票价 × 折扣 | `ticket_package` 有 `title` / `sort`，天然支持「预设」 |
| 商品规格 / 品牌 / 图片 | ✅ 平台预设库 | 见 §5 | 「从官网调取」的合规落地 |
| 营业状态 | ✅ 默认「营业中」 | `station.operating_status` 默认值 | 已经是默认值 |

**原则：只有「能算出来、且改错了不会改变接单行为」的才给默认值**；会改变「接不接单、收不收钱」的一律只给**建议值 + 一键填入**——这一按就是站长的决定，而不是系统替他决定。

## 5. 「可以从官网调取」怎么落地（不做抓站）

小程序端抓品牌官网在技术与合规上都不可行（跨域、反爬、图片版权）；就算抓到，官网价格也不等于本站售价。**可行方案 —— 平台预设库**：把「常见品牌 + 官方规格 + 参考价 + 官方图」作为**平台维护的目录行**写进通用商品库（`product.owner_station_id IS NULL`，站长只读）。已有基础：商品图片库与常见水种清单（[14-商品图片库与常见水种清单.md](14-商品图片库与常见水种清单.md)）、`constant/ProductImageKeys`。站长建自定义商品时**选品牌 → 自动带出规格与图片 → 只填售价与押金**：少填 3~4 个字段，「规格」这种最容易写错的字段不再手打。

## 6. 接口与权限 / 前端落点

| 方法 | 路径 | 角色 | 说明 |
|---|---|---|---|
| `GET` | `/api/manager/setup-guide` | `STATION_MANAGER` | 站点取自 `AuthContext.requireStationId()`；返回规则条目（含 `level` / `done` / `suggestion`） |
| `GET` | `/api/manager/pending-summary` | `STATION_MANAGER` | 站点取自登录态，**不接受请求参数**，按 `PendingItem` 目录逐条算数 |
| `GET` | `/api/manager/delivery-config` | `STATION_MANAGER` | 响应里的 `guidance` 承载金额门槛引导文案与建议值 |
| `GET` | `/api/stations/{id}/public-phone` | 公开 | 只返回 id / name / phone，避免泄露站长等内部字段 |

**前端落点**：`miniapp-delivery/pages/station-mgmt/station-info/` 承载坐标与电话引导；`miniapp-delivery/pages/station-mgmt/delivery-config` 承载金额门槛引导卡。两处都在同一页面内，站长端信息架构调整时跟着走即可。

## 7. 待确认事项

| 待确认内容 | 需要的验证手段 | 影响 |
|---|---|---|
| 员工「固定工资」结算方式 | 代码里**没有**这个概念：`staff_payroll` 只有「期间 + 合计」，`staff_piece_rate` 是唯一的工资参数。候选形态 `staff_salary_config(staff_id, mode, monthly_amount)`：计件模式校验站级默认单价必须存在，固定模式把月薪作为结算单金额来源 | ⚠️ 会动 `staff_earning` / `staff_payroll` 的金额来源（现在是纯计件），属资金口径变更；**必须先定「固定工资算不算进 E-PAY 对账」** |
| 坐标是否也改成建站强制 | 前端已补齐校验（标了 `*` 就真的拦）、**后端仍不强制**——当场可能拿不到定位 | 现状是「前端拦 + 引导项 P0 提示」；若要更强可改成「允许跳过，但 24 小时内必须补坐标，否则配送范围规则不生效」，需定时 / 待办支持 |
| 补齐下列引导项（每项只改 `StationSetupGuideService` 一处，落进 §2 目录新增 key） | 逐项按 §2 的判据列写 `done` 判定并补对应用例 | ① **营业时间**——现只有 `operating_status` 软状态与 `status_note`，客户最常问「几点送」；② **有坐标却没设配送范围**——白设；③ **货到付款未开通的进度提示**——它没有站点级总闸（只能逐个客户开），新站常见困惑是「客户选不了货到付款」；④ **员工入职引导**（绑定后提示配工资结构）——与固定工资那条同批落地；⑤ **档位预设一键生成**（10 / 20 / 100 三档）——与统一水票一起做，否则两套口径分叉（[26-水票两方案评估.md](26-水票两方案评估.md)）；⑥ **平台预设库**——见 §5 |
