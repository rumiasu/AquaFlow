## 1. 结论先行：这块的投入比想象的小

计件工资看起来是"人事/薪酬模块"，容易高估工作量。实际上**数据采集已经全部就位**：

| 需要的数据 | 现有落点 | 证据 |
|---|---|---|
| 谁送的 | `orders.delivery_staff_id` | `schema.sql:458` |
| 送了几桶 | `order_item.quantity`（桶数） | `schema.sql:390` |
| 送出空桶 / 收回空桶 | `orders.delivery_bucket_qty` / `return_bucket_qty` | `schema.sql:456-457` |
| 空桶差异 | `orders.barrel_discrepancy` | `schema.sql:472` |
| 送达时间 | `orders.update_time`（状态转 3 的时刻） | `schema.sql:471` |
| 今日完成 | `DeliveryController.getCompletedToday`（`:128`） | 已有端点 |

**所以缺的不是采集，是三样东西**：站级计件单价配置、按人按天的**收益明细**、可核对的**结算单**。

⚠️ 全仓检索 `提成|计件|工资|salary|commission` 在业务代码中 **0 命中**；`staff` 表无任何薪酬字段（`schema.sql:570-583`）。

## 2. 与外卖平台的偏离（照抄会错的地方）

| 维度 | 外卖平台 | 本项目（桶装水） |
|---|---|---|
| **谁发钱** | 平台结算给骑手，商家付平台佣金 | **站长直接发**。所以：不做平台结算单、不做佣金抽成、不做骑手钱包 |
| **计件单位** | 单 | **桶**（一单 1~3 桶，19kg/桶）。只按单计价 → 配送员不愿接多桶单 |
| **任务形态** | 单程（取餐→送达） | **双向**（送水 + 收空桶），且回桶数要当场核对 |
| **楼层** | 无独立项 | **必做**，且要拆成"向客户收"与"给配送员补"两笔 |
| **运力归属** | 众包，骑手同时接多平台 | `staff.station_id` 固定归属（`schema.sql:577`），跨站只是帮忙 |

### 2.1 发钱是线下动作，系统只做台账（2026-09-17 补充）

站长发工资**不一定走小程序**——现实里就是微信转账或当面给现金。所以这块的边界是：

**不做**：打款 / 提现 / 钱包 / 余额 / 代发。这些需要支付牌照与资金存管，而本项目连微信支付渠道都还没接（`16` §D1），做这个是空中楼阁。

**要做**：**算得清 + 留得下痕**。

- 结算单需要 `status`：`草稿 → 已确认 → 已发放`
- 发放时记 `paid_time` + `operator_id`（谁在什么时候给的）

**判据：「算出来」与「发出去」必须分开。** 如果只有一个状态，站长改一条明细就会**悄悄改掉已经发过的钱**——下个月对不上时无从追溯。这条与 `station_adjustment` 的"确认后不可原地改、要改走反向单/下期调整"是同一个设计语言。

**展示入口可以先不做。** 后端接口 + 站长端只读页就够站长发工资；配送员"我的工资"页属体验优化，可后置（它只读 `staff_earning`，不涉及任何新的账务口径）。

## 3. 数据模型建议

### 3.1 `staff_piece_rate`（站级计件配置）

| 列 | 含义 |
|---|---|
| `station_id` | 水站 |
| `product_id` | 可空 = 该站默认价；非空 = 某商品的专属单价（18.9L 与 5L 搬运成本不同） |
| `per_bucket_amount` | 每桶计件价 |
| `floor_bonus_per_level` | 每超一层补贴 |
| `distance_bonus_per_km` | 每公里补贴（可空 = 不启用） |
| `per_order_amount` | 每单基础奖励（可空） |

配置的真相源是**站级**（与 `inventory` 的站级定价同构）。**不要做阶梯/加权/复杂公式**——真实水站的计件价就是"一桶 X 元"。

### 3.2 `staff_earning`（收益明细，一行 = 一个动作）

| 列 | 含义 |
|---|---|
| `station_id` | **结算站**（见 §6.2） |
| `staff_id` | 收益归属人 |
| `order_id` | 关联订单（人工调整类可空） |
| `kind` | `DELIVERY_BUCKET` 送桶 / `RETURN_BUCKET` 回桶 / `FLOOR_BONUS` 楼层补贴 / `DISTANCE_BONUS` 距离补贴 / `ORDER_BONUS` 单奖 / `PENALTY` 扣减 / `ADJUST` 人工调整 |
| `qty` | 数量（桶数/层数/公里数），调整类可为空 |
| `unit_amount` | 单价快照 |
| `amount` | 金额（扣减类为**负数**，见 §3.4） |
| `payroll_id` | 已结算时写入；NULL = 未结算 |
| `note` | 备注 |

**唯一键（防重复结算的核心）**：`uk_earning(order_id, staff_id, kind)` —— 与 `orders.idempotency_key`（`schema.sql:486`）同一种防重思路。

### 3.3 `staff_payroll`（结算单）

单据头：`station_id` / `staff_id` / `period_start` / `period_end` / `total_amount` / `status`（草稿/已确认/已发放）/ `operator_id`。

**锁定语义**：结算单确认后，其下 `staff_earning.payroll_id` 写死，**不允许再改动**（要改只能对下一期做 `ADJUST`）。这与 `station_adjustment` 的"反向单撤销、不原地改"是同一条思路。

### 3.4 方向由类型决定（本仓铁律）

照 `DepositType` 的既有口径：**`kind` 决定正负，调用方一律传正数**，落库时由一处统一转符号（`DepositRecordServiceImpl:56-64` 就是这么做的，且是对账等式1的前提）。

**判据：不要在每个生成收益的地方各写一次 `amount.negate()`。** 一旦分散，将来必然有一处写反，而"工钱算错"不像"账不平"那样有对账兜底（见 §7）。

## 4. 计件构成

> ⚠️ **2026-09-18（v42）起只有两项**（下面第二段是当时的设计稿，保留作对照）：
>
> ```
> 本次配送收益 = 送桶数 × per_bucket_amount            （按商品可单独定价，未配则回落默认价）
>              + max(0, 楼层 − 免费层) × floor_bonus_per_level
> ```
>
> **删掉的三项及理由**：`return_bucket_amount`（回桶奖励）、`per_order_amount`（每单固定补贴）、
> `penalty_per_bucket`（少收空桶扣减）—— 站长实际只会用"每桶多少钱 + 上楼加钱"这两项；
> 回桶与单量本来就能并进桶价，而"少收空桶自动扣钱"直接引发劳资纠纷（本仓对欠桶一贯的口径是
> **只提醒不扣钱**）。库列已由 `migration_v42_piece_rate_two_items.sql` 删除；`EarningKind` 里
> 那三个类型保留但停用，只为显示历史流水。
>
> ⚠️ **少收空桶仍然有痕迹**：订单的 `barrel_discrepancy` + `order_barrel_exception` 异常单照旧，
> 只是不再自动折算成扣款。要扣就在结算单上手工 `ADJUST`（人工调整），并写清理由。

原设计稿（对照用）：

```
本次配送收益 = 送桶数 × per_bucket_amount
             + 回桶数 × return_bucket_amount     （已删，v42）
             + max(0, 楼层 − 免费层) × floor_bonus_per_level
             + 距离(km) × distance_bonus_per_km   （从未实现）
             + per_order_amount                   （已删，v42）
             − 空桶差异扣减                        （已删，v42）
```

**关于"楼层补贴"与 `17` 的楼层费是两笔钱**（见 `16` §2.4）：

- `17` 的 `orders.floor_fee` = **向客户收**（收入）
- 本节的 `FLOOR_BONUS` = **给配送员补**（成本）

**两者金额可以不同，必须分别配置、分别落库。** 合成一个字段会导致：客户投诉乱收费时查不清、工钱算不准、对账不平。

### 4.1 楼层补贴的依据：**配送员上报的楼层**（v43，2026-09-18）

上面那个"两笔钱"的口径之下还有个更细的问题：**楼层补贴该按谁的数算？**

- 客户在地址里填的楼层是**收费**依据（下单时快照进 `orders.floor_fee`），
  但它不该同时当**发钱**依据 —— 楼层补贴是给配送员的钱，只有他知道自己爬了几层；
  只认客户填的值，等于拿别人的话给自己发工资，虚报没有任何痕迹。
- 所以 v43 起：**配送员在完成配送时选填楼层数**（`orders.reported_floor`，选填：有的填、没有的不填），
  **填了就以此为准**；没填就**沿用地址楼层**（不惩罚不填的人、也不多付）。
- 与地址不一致时，收益明细的 `note` 会写成「上报 8 层（与地址 6 层不一致），超 7 层」——
  **这就是防虚报的痕迹**，站长在结算单明细里直接能看到。
- 照片**不强制**（产品决定）：`order_image.type=3` 楼层凭证，配送员完成配送时可拍，
  **站长事后也能补传**（同一个上传接口，角色都允许）—— 与客户对峙时它是唯一的凭证。
- ⚠️ 电梯口径：地址里**明确写了"有电梯"**就不补（不管有没有上报）；地址里电梯为 `null`（客户没确认过）
  而配送员报了几层 → 按他报的给（他确实爬了，凭证可核）。
- ⚠️ 上报值**只写一次**（`OrderMapper.saveReportedFloor` 带 `reported_floor is null`）：
  完工那一刻的快照，之后谁都不许悄悄改写发钱的依据；真要改走结算单上的人工调整（`ADJUST`）留痕。

**回桶考核**（v42 后）：`orders.barrel_discrepancy` 照旧记录少收空桶数，但**不再自动扣钱** ——
它现在只出现在订单差异说明与桶异常单里，扣款一律走结算单上的人工调整（`ADJUST`），避免误扣引发劳资纠纷。

## 5. 收益产生时点：钉在"送达"，天然免疫取消

**建议：`staff_earning` 只在订单状态进入 `3 已送达` 的那次状态变更中产生。**

这样做的好处（很重要）：本仓订单状态**只前进、不倒滚**，且 `OrderStatus.isCancellable` 已拦掉 `4 已完成 / 5 已取消`（`AGENTS.md` §1）。所以：

- 订单能取消的时机只有 `1 待配送 / 2 配送中` —— **此时还没有产生收益**；
- 一旦到 `3 已送达`，订单不可能再被取消 → **不存在"收益产生了又要撤回"的回滚问题**。

**判据：不要用"已接单"或"已分配"作为计件时点**，那会在取消单上留下需要人工清理的收益行。

并发防护：触发点必须是 `OrderWorkflowServiceImpl.completeDelivery` 里的**一次成功 CAS**（`updateStatusIf`），再以 `uk_earning(order_id, staff_id, kind)` 兜底。**只要唯一键在，重复调用最多报 1062 而不是多算一笔工钱。**

## 6. 归属与边界

### 6.1 归属人 = 实际完成人

`orders.delivery_staff_id` 是当前指派者。经历"转单"（`transferToStaff`，`OrderWorkflowServiceImpl:809`）后，它指向最终完成的人。**按完成时刻的 `delivery_staff_id` 结算**即可，不需要额外的转单分账。

### 6.2 归属站 = **履约站**，不是归属站

本仓已有双水站口径：`orders.station_id` = 交易/营收归属，`orders.delivery_station_id` = 实际履约归属（`AGENTS.md` §1，`StationUtil`）。

**配送员的工钱是履约成本，所以应记 `delivery_station_id`（履约站）。** 跨站外派单由外派站的配送员跑腿，工钱就该外派站发——这与"钱和票记归属站、库存走履约站"的既有划分是一致的：工钱既不是客户的钱，也不是库存。

**判据：`staff_earning.station_id` 取履约站；若为空（异常数据）则该单不产生收益并告警，而不是回落到归属站。**

## 7. 对账：**独立的等式，不要混进客户对账**

`ReconciliationService` 现有的等式都是**客户/资产**维度（押金、支付、桶、库存、权益）。**工钱不参与这些等式**——它是水站与人之间的账，与客户无关。

**误接的后果**：把工资算进客户对账 → 每天 03:00 的日结必然报不平（`ReconciliationService.dailyReconcile` 会发 SYSTEM 告警），告警疲劳后真问题会被淹没。

**正确做法：新增一条独立的等式**

```
E-PAY: staff_payroll.total_amount == SUM(staff_earning.amount WHERE payroll_id = 本期)
```

形态与押金等式1（`balance == SUM(deposit_record.amount)`）同构。

**告警分级**（按 `constant/AlertType`）：工资单对不上属于**运营问题**，应由站长看到（`OPERATION` + `station_id` 必填），不是系统故障。别投给系统管理员。

## 8. 迁移与验收

- 新迁移：`sql/migration_v34_staff_piece_rate.sql`（依赖 `v33`，见 `17` §7）
- 无破坏性变更（只加表），可安全在生产先上代码后跑 SQL

### 验收清单

1. 完成一单后，`staff_earning` 有对应行，金额 = 配置 × 数量。
2. **重复调用 `completeDelivery` 不产生第二笔收益**（走唯一键，报 1062 或幂等跳过）。
3. 订单在 `1/2` 状态被取消 → **无任何 `staff_earning` 行**。
4. 跨站外派单的收益记在**履约站**（`delivery_station_id`）。
5. 转单后收益归**最终完成人**。
6. 结算单确认后，其下明细不可再改（改则拒绝或要求走下一期 `ADJUST`）。
7. `E-PAY` 等式成立；`ReconciliationService` 的**原有四项等式不受任何影响**（这是最重要的回归）。

## 9. 2026-09-18 收口：员工自助 + 告警路由

### 9.1 配送员自看工资（`GET /api/delivery/earnings`）

在此之前只有站长端能查工资（`GET /api/manager/earnings?staffId=`），**配送员看不到自己挣了多少** ——
一句"我这个月多少钱"就得站长去查，是这类系统最常见的日常摩擦。

- 端点：`GET /api/delivery/earnings?from=&to=`（缺省 = 本月 1 日 ~ 今天），返回期间明细 + 期间合计 +
  **未结合计** + 我的结算单（状态文案由实体 `StaffPayroll.getStatusText()` 派生下发）。
- 页面：`pages/my-earnings/index`，入口在「我的」页首屏菜单（配送员与自己也在送水的站长都能进）。
- ⚠️ **身份只取自 `AuthContext`，端点不接受 `staffId` 参数** —— 一旦接受，配送员改个数字就能看到同事的工钱。
  站长端那个端点**必须**带 `staffId`（他看全站），两者校验点不同，**不要合并成一个**。
- ⚠️ **自助查询只按 `staff_id`、不按 `station_id`**：`staff_earning.station_id` 记的是**履约站**，
  跨站外派时可能与配送员所属站不同，带上站点过滤会让外派挣的那部分工钱凭空消失。
  站长结算用的 `listUnsettled(stationId, staffId)` 则必须锁本站 —— 这两组查询刻意不共用同一个方法。
- ⚠️ 期间上界仍必须是**结束日 + 1 天**（AGENTS §8.19）：写成 `<= 结束日` 时**今天的工钱一条都看不到**。
- 用例 `DeliveryMyEarningsIntegrationTest`（4 例：自己的数、同事看不到 / 传别人的 `staffId` 也无效、
  结算单状态流转到「已发放」、顾客与站长的角色边界）。

### 9.2 E-PAY 的投递路由修对了（原来投给了系统管理员）

本文 §7 与 `constant/AlertType` 都写明"工资单对不上属 `OPERATION`、投该站站长"，
但实现里 E-PAY 混在 `runReconcileV2()` 的返回表里，而 `dailyReconcile()` 只要 V2 **任一项**非 0
就调 `systemFault(...)`。后果很具体：站长与配送员之间的账对不上时，**平台管理员收到告警，
而唯一能改结算单的站长一条都收不到**。

- 现在 V2 在投递前按 `STATION_LEDGER_KEYS` 拆成两张表：客户账 → `systemFault`（照旧）；
  站长台账（E-PAY）→ `alertStationLedgerImbalance`，**按站逐张结算单投 `stationFault`**。
- ⚠️ **`reconciliation_result.level` 是"严重度"，不是"投给谁"**：E-PAY 落表仍是 `ERROR`，
  但收件人是站长 —— 这两件事分别由 `level` 与 `AlertType` 决定，别当成一个字段。
- ⚠️ 投递条数封顶 20 条（单价录错会让整批结算单同时不平），差异总数写在告警正文与日志里。
- 用例 `AlertRoutingIntegrationTest.payrollImbalanceGoesToStationManagerNotAdmin`：断言产生
  `OPERATION` 告警且收件人是该站站长，同时断言 `alert_log` 里**没有任何 SYSTEM 告警的正文含 `EPAY`**。

## 10. 站长自定义工资条目（v44，2026-09-18）

### 10.1 为什么要有它

v42 之后工资只有**两项自动收益**：每桶计件 + 楼层补贴。其余加减钱（迟到扣款、破损赔偿、
高温补贴、临时帮忙费……）只能走 `kind='ADJUST'` 的人工调整，而人工调整**只有一个自由文本 `note`**：

| 问题 | 具体后果 |
|---|---|
| 每次都要重新打字 | 同一个扣款项在不同月份写成「迟到」「迟到扣款」「迟到罚款」 |
| 汇总不出来 | 站长想知道"这个月迟到一共扣了多少"，只能一页页数 |
| 没有约束 | 打错字没人拦，而这是**会真的从人家工资里扣掉的钱** |

于是引入**条目字典**：站长自己定义「加项 / 扣项 + 名称」，录钱时选条目、只填金额，
**方向由条目决定**。刻意**不是**规则引擎：条目不参与任何自动计算、不产生任何金额、不进对账等式 ——
它只是人工调整那条流水上的一个**标签**（表 `staff_earning_item`，v44）。

### 10.2 三条口径

1. **方向由条目决定，调用方一律传正数**（`constant/EarningItemDirection`：1 加项 / 2 扣项）。
   传了 `itemId` 还传负数 → **直接拒绝**，不静默取绝对值。与 `EarningKind` 同一条铁律：
   让录的人每次自己判"这次是补还是扣"，等于把最容易错、错了直接从工资里体现的一步交给手感。
   （不传 `itemId` 的老自由文本调整保持原样：金额仍自带符号，那是它唯一的用途。）
2. **`item_name` 是写入时的快照**，条目改名**不改写已经发生过的工资历史** ——
   与 `order_item.product_name` 同一口径。汇总时优先显示条目当前名，条目已不存在才回落快照。
3. **被流水用过的条目只能停用、不能删**。删掉它，那些流水在界面上就成了"无条目的人工调整"，
   站长再也说不清那笔钱是什么。停用只挡**新录入**，历史照旧。

### 10.3 端点与界面

| 端点 | 说明 |
|---|---|
| `GET /api/manager/earning-items` | 本站条目（默认含停用；`?enabledOnly=true` 只取启用的 = 录一笔时的可选集） |
| `POST /api/manager/earning-items` | 新建（同站同名拒绝，名称 1~20 字） |
| `PUT /api/manager/earning-items/{id}` | 改名 / 改方向 / 改顺序 |
| `POST /api/manager/earning-items/{id}/status` | 启用（1）/ 停用（0） |
| `DELETE /api/manager/earning-items/{id}` | 删除（用过的拒绝，提示改为停用） |
| `POST /api/manager/payroll/adjust` | 原有端点，请求体新增可选 `itemId` |
| `GET /api/manager/earnings?staffId=` | 响应新增 `itemSummary`（按条目汇总） |

⚠️ **`itemSummary` 只统计带条目的流水，不等于 `unsettledTotal`** —— 自由文本调整没有条目。
两者不是同一口径，页面上不要把差额显示成错误。汇总的 `total` 是**带符号**的（扣项为负），
免得前端自己再判一次方向。

### 10.4 顺手修掉的一个越权（同一次改动，2026-09-18）

`POST /api/manager/payroll/adjust` 原本只收 `staffId`，**不校验这个人与本站有没有关系**。
而「我的工资」自助查询（§9.1）刻意**只按 `staff_id` 过滤、不带站点**（否则跨站外派挣的那部分会消失）——
两者一叠加：**任何站长传一个别站配送员的 id，就能往那个人的「未结工资」里塞钱或扣钱**。

现在的判据是**并集**（与客户归属的 `countCustomerOfStation` 同一形状）：
`staff.station_id == 本站` **或** 该人在本站已有 `staff_earning` 记录（跨站外派：人属于 B 站、给 A 站跑腿，
A 站给他记一笔完全正常）。角色也必须是 `DELIVERY` / `STATION_MANAGER`。

用例 `StaffEarningItemIntegrationTest`（5 例：条目 CRUD 与同名/能力校验、方向与快照、
用过的条目不可删、按条目汇总与未结合计的口径差、外站配送员的归属拦截与跨站放行）。
