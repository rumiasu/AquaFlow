## 1. 目的与范围

针对第一轮提出的七个问题（P1~P7，见 `22-站长端信息架构重组.md`）逐条给出裁定与依据，核查执行中会撞到的既有缺口，并把重叠 / 冲突项列清。范围限于七条裁定、客户页分段方式、代客下单的落地路径、死端点的证据链与伴随清理、重叠 / 冲突清单；宫格最终形态与实施批次见 `24`。

## 2. 逐条判定

| 项 | 判定 | 关键依据 |
|---|---|---|
| **P1** 员工管理两份 | 修。宫格「员工」那份为主，「我的」那份降级为「跳过去」 | `staff/index.js` 与 `mine/index.wxml` 同调 `getStaffList` / `detachStaff` |
| **P2** 绑定申请审批在「我的」 | 不修，但推荐长跳转：`mine` 空状态加「去员工页审核 ›」 | 现状可接受，只是入口深一层 |
| **P3** 水票档位 | 撤掉宫格卡，档位只在商品「本站设置」弹窗里配；`ticket-packages/index` 保留为「更多档位」二级页（`products/index.js` 已有入口） | 两处打的是同一份 `/api/ticket-packages` 数据 |
| **P4 / P5** 客户页分 tab 并改名 | **部分可行**：普通 / 企业两个 tab 可以，**员工 tab 不建议**（§3） | `customer.customer_type` 只有 1 个人 / 2 企业；员工在 `staff` 表 |
| **P6** 代客下单并入客户画像 | **不做**（不是不行，是撞到缺口，见 §4） | `CustomerServiceImpl.save` 只 insert、不建绑定 |
| **P7** 两个死接口 | 证毕：**可零风险删**，且应与一批伴随清理同时删（§5） | 见 §5 证据链 |

## 3. 客户页 tab 化：员工 tab 为什么不建议

**普通 / 企业两个 tab 可行，但用分段器更好。** 字段本就存在（`customer.customer_type`：1 个人 / 2 企业），现页已有「全部 / 个人 / 企业」三个筛选 chip —— 这一项本质是**把已有的筛选 chip 升格为分段器**，不是新功能。

⚠️ **用分段器而不是 tab 栏**：站长改的是「筛选条件」，不是「换一个页面」；用 tab 会让人以为个人客户与企业客户是两套数据。**要用 tab 也可以**，但 tab 内的筛选 chip 必须撤掉，否则同一维度两个控件、站长会以为它们叠加。命名：卡片「客户查询」→「客户」；分段器「普通客户 / 企业客户」（服务端口径仍是 `customer_type`，**别改枚举**）。

**员工 tab：三个硬理由不做。**

| 理由 | 依据 |
|---|---|
| 员工不是客户，是另一个实体 | `staff` 表 vs `customer` 表；`customer_type` 只有 1 / 2，没有「员工」这个值 |
| 数据源、接口、权限面全不同 | 员工走 `getStaffList` 与 `createStaff` / `detachStaff`；客户走 `CustomerMapper.listSearchCandidates` |
| 站长自己出现在「客户」列表里语义就错了 | `createStaff(..., "STATION_MANAGER", ...)` 造的站长也是 staff 行 |

**替代方案**：客户页的 tab 只做「普通客户 / 企业客户」。

**客户画像页的 tab 拆法**：现在是一张长滚动页、7 个块，按「这个客户是什么人 / 本站给了他什么资产 / 本站给了他什么例外」拆成三个 tab —— **概览**（画像头、消费概览、消费特征、最近订单）、**资产**（本站资产，含还空桶与资产调整入口）、**权限**（客户特权与权限设置：货到付款开关，`ManagerCustomerPrivilegeController` 与 `offline_payment_enabled` 同源）。**7 块 → 3 tab 是真瘦身**，不是把卡片换成页签。

## 4. 代客下单并入客户画像：撞到一个已存在的缺口

**结论：不做。** 这条路上有个比「入口放哪」严重得多的问题：某客户若 ① 没下过本站订单、② 站长没点过他的货到付款开关 ⇒ **他在站长端任何客户选择器里都查不到**。

| # | 事实 | 依据 |
|---|---|---|
| 1 | `POST /api/customers`（客户建档）**只 insert customer，不建任何水站绑定** | `CustomerServiceImpl.save` |
| 2 | `customer_station_config` 绑定行**唯一的写入口是「读 / 改货到付款权限」**（`ensureExists`），前端触发点只有那个开关 | `CustomerStationConfigMapper.insert` **零调用**、`ensureExists` 的调用方只有 `CustomerServiceImpl`；开关在客户列表页弹窗与画像页各一处 |
| 3 | 归属判据是**并集**：① `customer_station_config` 绑定行 ② 本站订单 | `CustomerMapper.countCustomerOfStation` |

推论：`listStationCustomers` 是 orders 驱动，`listSearchCandidates` 的 `exists` 也查不到他 —— 两者都漏掉「已建档但没绑定的新客户」。

**顺带查实的三个产物**：

1. **`CustomerMapper.countCustomerOfStation` 的 javadoc 已失真**：它写「绑定行，**站长代建 / 认领即产生**」，而代码里**已没有任何「代建即绑定」的路径**。这正是「注释与代码不符比没有注释更危险」。
2. **`CustomerStationConfigMapper.insert` 全仓零调用**：一个孤儿方法，看名字人人都会以为「建档时会用它建绑定」。
3. **`place-order/index.wxml` 的文案是死路**：「新客户请先到『客户管理』建档，再回来下单」—— 而「客户查询」页**没有建档按钮**（`api/station-mgmt.js` 只有 `getCustomers`，没有 POST 包装）。

**所以要分两步，不要混在一起做**：

- **第一步（纯 IA，可做）**：`代客下单` 卡片从宫格撤掉，入口改为**客户详情页的一个按钮**「用他下单」，点击 `navigateTo` 到 `place-order?customerId=xxx`。**该页保留，只加一个「跳过第一步」的入参**，不复制客户搜索逻辑 —— 复制就是「两处搜索各写一套」。
- **第二步（另开一项，需产品裁定）**：补齐「站长代客建档」闭环，三选一：A 建档时同时写 `customer_station_config` 绑定行（复活那个孤儿 `insert`；⚠️ `CustomerController` 已写明「**先判归属再 ensureExists**」的护栏，**不能反序**）；B 客户列表页加「新增客户」按钮，调 `POST /api/customers` + 绑定；C 明确「客户必须自己扫码 / 登录过一次」，删掉那条误导文案 —— 最小，但电话客户无法代下单。

**建议**：先做 C（改文案）止血，真需要 A / B 再单独提。**在第二步落地之前，把代客下单藏进客户画像会让人找不到它。**

## 5. P7：死端点的证据链与伴随清理

**零消费证据（三层都查）**：**前端业务调用零** —— 全端 grep 只命中 `api/station-mgmt.js` 的包装函数定义与 `config/api.js` 的路径常量，**没有任何页面调用**；**其他端零** —— 唯一在用的前端是已删除的 Vue 管理后台（只剩 `archive/` 留档，不维护、不引用）；**测试**只有 1 处契约断言点名了这两条路径。

**不是安全问题的三条反证**：① 两个端点都有 `@RequireRole({"STATION_MANAGER"})`；② 水站来自 `AuthContext.requireStationId()`，**请求里的 `stationId` 后端根本不接**（方法签名没有该参数）；③ 两者都在 `class` 级切面覆盖内。→ **原判「错误示范」成立，「跨站隐患」不成立。**

**真正的理由是它们是第二份口径**：

| 端点 | 它算的东西 | 与正式实现的冲突 |
|---|---|---|
| `/today` | `lowStock = inventory.quantity < 20` | **同一个「低库存阈值 20」在前端也写了一份**（`products/index.wxml` 的「低库存(<20)」）—— 一个业务阈值两处硬编码 |
| `/today` | `finishedToday`、`totalOrders` | 与 `DashboardService.report()` 的完成数 / 订单数**同名不同算法** |
| `/overview` | `customerCount`（= `CustomerMapper.countByStationId`，**orders 驱动**） | 与 `countCustomerOfStation`（绑定 ∪ 订单并集）**口径不同** —— 后者正是本仓踩过两次的坑 |
| `/overview` | `orderCount`、`inventoryTotal`、`pendingOrderCount` | 同上，与 `/report` 分叉 |

**同形先例**：`GET /order-status` 与 `GET /order-trend` 就是「零前端调用 + 口径与 `/report` 分叉」被删的（`DashboardController` 里留有墓碑注释），判据出自当时的死端点评估（该报告已移出仓库，结论登记在 [`docs/audit/删除登记表.md`](../audit/删除登记表.md)）。**同一条判据，同样适用。**

**删的话必须一起清，否则留孤儿**：

| 位置 | 处理 |
|---|---|
| 前端 `api/station-mgmt.js` 的两个包装函数与导出、`config/api.js` 的两个路径常量 | 删（已执行） |
| `DashboardNoticeSearchFeedbackIntegrationTest` 的路径数组与 `@DisplayName` 的端点数 | 从路径数组移除这两条，端点数同步改 |
| `DashboardController` 的两个方法 + 随之空掉的注入字段 | 删端点方法 |
| `DashboardController` 的 `addressMapper` | **本来就是死字段**（全文只出现在声明处），顺手删 |
| `OrderMapper.countTodayByStationId`、`OrderMapper.countByStationId`、`CustomerMapper.countByStationId` | 删后零调用 → 一并删。⚠️ `countByStationIdAndStatus` 另有他用，**不能删** |
| 根 `README.md`、`docs/architecture/api-design.md` 的接口表格行 | 删表格行 |
| `RequireRoleAspect` 的注释示例 | 它拿 `/api/dashboard/today` 当「**无鉴权**」的例子，**该前提已过期**（现在有 `@RequireRole`），换成真实例子 |

**判定：可删。** 收益 = 消掉一份分叉口径 + 一处过期注释 + 一个死字段 + 三个孤儿 mapper 方法；风险 ≈ 0（有鉴权、不接参、零消费）。

## 6. 重叠 / 冲突清单

| # | 重叠或冲突 | 判定 |
|---|---|---|
| **C1** | **首页 tab 的 5 个订单页签**（待分配 / 审批 / 抢单池 / 外派 / 他站外派）与宫格「订单管理」是两套入口 | ⚠️ **最大冲突**。建议把 5 个页签**整体**设为「订单」分组页的页签，首页 tab 只保留待办卡 + 一张「订单」卡；否则同一个订单在两个地方以两种形态出现 |
| **C2** | 首页**待办卡**与**数据看板**都在报「待收款金额 / 欠桶」 | ⚠️ 真重叠。待办卡 = `overdueReceivable`（逾期应收，含金额）；看板 = `pendingAmount`（本期待收款）+ `owedCustomers` TOP。**建议看板删掉「欠桶客户 TOP」与待收款横幅**，只留趋势与分布 |
| **C3** | 员工管理**三处**：宫格「员工」+「我的」配送员管理 + 员工画像 | ⚠️ 修法见 P1 / P2；员工画像并入「员工」页签 |
| **C4** | 资产调整单**两处**：客户画像入口 + 宫格外的 `customers/adjust` 列表 | 并入「桶」分组（它是桶 / 押金 / 水票的人工补正），**从客户画像移走**，画像只留「还空桶」 |
| **C5** | 企业身份审核落点：客户查询页顶部横幅 + 宫格企业身份阈值设置 | 两者并成「客户」分组的一个页签，列表页只留**角标** |
| **C6** | 「商品与库存」页实际装了 4 件事：商品与本站设置、库存流水、自定义商品与上报、票务档位 | 页内 tab 或分组页签；P3 撤卡后档位归位 |
| **C7** | 分组命名查重 | ✅ 已核：现场数据 / 收款与账 / 桶 / 客户 / 商品与配置 / 员工 —— 与现有页面标题无一对撞 |

## 7. 待确认事项

| 待确认内容 | 需要的验证手段 | 影响 |
|---|---|---|
| 首页 tab 的 5 个订单页签是否收进「订单」分组页（首页只留待办卡 + 一张订单卡） | 产品裁定 | 全局唯一的大改；不做则同订单仍有两套入口 |
| 数据看板是否删掉「欠桶客户 TOP」与待收款横幅 | 产品裁定 | 不删则与待办卡持续重复报同一件事 |
| 后端两个死端点及其伴随清理是这轮一起删，还是只删前端、后端留下轮 | 产品裁定 | 只删前端则后端仍留一份分叉口径与一个死字段 |
| P6 第二步（站长代客建档闭环）要不要现在立项 | 产品裁定；建议先只改文案止血 | 不立项则电话客户无法代下单，且那条误导文案继续存在 |
| `countCustomerOfStation` 的失真注释与孤儿 `CustomerStationConfigMapper.insert` 如何收口 | 随 P6 第二步一并处理，或单独立项 | 注释继续误导后来者按「代建即绑定」实现 |
