# AquaFlow

AquaFlow 管理水站从订水、配送到桶和资金结清的业务。客户使用一个微信小程序，站长和配送员共用另一个小程序，后端提供统一服务。

项目的核心是把四件事分别记清：客户买了什么服务、交了多少押金、实际拿着多少桶、各水站还有什么未履行责任。送达、收款、退桶和退款都各自代表一个事实，不能用一个“完成”状态代替。

## 一次订水如何完成

1. 客户选择水站、商品和送达地址。首次使用循环桶时，可单独办理桶权益，也可在订水时明确确认逐商品新增押金，与水款同次付款、分项记账；实际收款后权益成立，交付才改变实际持桶。
2. 客户可以买水票，也可以直接订水。购票检查是否已有相应权益；订水检查本次可分配权益，并预留履约站库存。
3. 站长分配配送员或安排他站履约。首次领取的部分免回桶，已有桶换水的部分核对实际回收。
4. 配送员登记实际交付和回收。普通货到付款订单可以先送达再收款，未收到的钱持续作为应收；本单含新增押金时须实际收齐水款和押金后才能激活并交付，不能登记虚假实收。
5. 客户结束用桶时先线上申请，站长批准安排和费用，客户确认后实际交桶，最后按原押金批次办理退款。未领取容量无需交不存在的桶。

水票消费退款、水费和服务费退款、押金退出、额外补偿是不同业务，分别保留依据和后果。

## 业务边界

| 问题 | 当前规则 |
|---|---|
| 客户属于哪个站 | 客户身份全局唯一；资产和订单按站隔离。一个客户可分别与多个站交易。 |
| 权益是否等于拿到桶 | 不等于。独立押金形成可用容量，实物送出或收回才改变实际持桶。 |
| 能否混合支付 | 水票与现金/微信不混用。水款和本次新增押金可同次付款、分项记账，也可先独立办理；水票不能支付新模型的新增押金。 |
| 同一权益能否同时用于两单 | 不能。同一站、商品、数量被进行中订单或退还申请占用后，不再参与其他分配。 |
| 外派后谁负责服务 | 接单站负责本单履约与沟通；客户押金和水票留在原归属站。接单前确定完整报酬，净桶交接另行约定。 |
| 拒付是否扣押金 | 不直接扣。确认拒付后保留债务、关闭新增线下付款，并按站核实冻结退押金资格。 |
| 缺货能否继续接单 | 可以在明确告知并确认等待后接单；只有足额预留和实物条件满足才可登记完成交付。 |

详细现行规则见[领域模型](docs/architecture/02-领域模型.md)和[业务流程](docs/design/15-业务流程地图.md)。仍需产品决定的核心点集中在[范围与决策](docs/design/16-范围决策与实施路线图.md#12-核心业务决策复核2026-10-01)，不会隐藏成实现默认值。

## 当前交付状态

独立押金、权益分配、申请制退桶、分项消费退款、拒付处理、外派报价和站间追偿已形成后端及两端入口。历史活动流程保留原来源，新模型不会凭历史桶数重发首次领取资格。

2026-10-01 的隔离库验证：后端全量 655 个用例通过，后续补改的相关回归通过；小程序 15 个套件、165 项断言通过。[执行记录](docs/design/16-范围决策与实施路线图.md#116-实施交付与边界2026-10-01)说明具体范围。数字是这次验证快照，不表示所有现实经营情形均已验证。

2026-10-04 阶段归档 `5ceb712` 的[完整 CI](https://github.com/rumiasu/AquaFlow/actions/runs/37190679139)已通过，范围及 GUI 限制见[阶段交付](docs/audit/2026-10-04-本地阶段交付.md)。这是一份准确提交的验证快照，后续改动须重新核验，不沿用为当前工作区全量已通过。

真实微信支付和退款仍未接入，本地模拟渠道只用于开发。生产迁移、真机验收和正式部署尚未在这轮完成。正常站间结清和工资发放目前登记线下事实，不执行平台转款；当前销售报表也不等于完整的站间利润及资金报表。
