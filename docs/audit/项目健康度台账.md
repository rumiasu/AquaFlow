# AquaFlow 项目健康度台账

> **本文件写给**：项目负责人 / 接手工程师 / 在仓库里工作的 AI agent。
> **一句话**：一张**可复算的分数**（现在能不能上线）+ 一份**未关闭问题登记**（下一步改什么最值）。
> **状态**：2026-09-30 首版（全仓静态复核）。分数与登记项**每次改动后重算**，见 §6。

## 0. 为什么要这份东西

本仓已有很完整的**判据**（`AGENTS.md`、`docs/architecture/**`、`.dsh/skills/aquaflow-known-traps`），
但缺一样：**"现在整体是什么水平、改完这批涨了多少"的可比数字**。
判据回答"这样写对不对"，台账回答"这个仓库现在值几分、缺口在哪、值不值得先改它"。

三条使用规则：

1. **分数只认 §2 的检查项**，不认印象。任何维度分都能被第三方按 §5 的命令复算出来。
2. **问题登记册（§4）是唯一的"未关闭问题"正本** —— 关掉一条就改它的状态，不要另开一份清单。
3. **不重述别处的数值**：端点正本在 `controller/**` 注解、表结构在 `sql/schema.sql`、
   测试件数在 `build/test-results/test/*.xml`、迁移顺序在 `sql/README.md`。本文件只记**快照值 + 复算方法**。

## 1. 评分模型

### 1.1 打分规则

- **10 个维度**，权重合计 **100**；每个维度 0–5 分。
- 每个维度由若干**检查项**组成，逐项取 `0` / `0.5` / `1`：

  | 取值 | 含义 |
  |---|---|
  | `1` | 有机制，且**本轮被实际验证过**（机器门禁绿、或本轮逐条 grep 核对无违规） |
  | `0.5` | 有机制但存在**已知缺口**，或只能靠人工自觉、无机器门禁 |
  | `0` | 没有机制，或机制**形同虚设**（存在可复现的绕过/漏检） |

- 维度分 = `5 × (Σ检查项 ÷ 检查项数)`；总分 = `Σ(权重 × 维度分 ÷ 5)`，四舍五入取整。

### 1.2 红线封顶（让"分数好看但有 P0"不可能）

| 条件 | 总分封顶 |
|---|---|
| 存在未关闭的 **P0** | **79** |
| 存在未关闭的**资金 / 越权**类 **P1** | **89** |

封顶值写在分数旁边（例：`实测 62 / 封顶 79`），避免"总分高 ⇒ 没事"的误读。

### 1.3 分数带（口径是"能不能上线"，不是"代码好不好看"）

| 分数 | 结论 |
|---|---|
| ≥ 85 | 可上线稳态 |
| 75–84 | 可上线，需盯着登记册里的 P1 |
| 65–74 | 有条件上线：先清掉与自己部署场景相关的那几条 P1 |
| < 65 | 不建议上线：先清 P0 与红线类 P1 |

## 2. 维度、权重与检查项

### D1 资金与账务正确性（权重 18）

> 为什么最高：出错直接对应"钱多收 / 少收 / 退不出去"，没有测试能兜底。

| # | 检查项 | 判据（什么算 1 分） | 度量方法 |

| 1.1 | 置 `payment_status=2` 的写入口 | **只能从 0/1 迁入**（`markPaidIfCollectable` 语义）；不接受"expected = 当前值"的退化 CAS | 读 `OrderMapper.java:38/:52` + 逐个调用点 |
