# AquaFlow 小程序设计评审报告（2026-10-06）

> 评审范围：`miniapp-user`（23 页）与 `miniapp-delivery`（43 页）的交互流程、信息组织与呈现、视觉一致性、性能与可维护性。
> 方法：全量阅读两端 app.json / app.js / 设计变量 / 核心页面（用户端：首页、下单、订单列表/详情/结果、桶账、水票、我的、商城、地址、登录；配送端：工作台、配送首页、订单详情、完成配送、水站管理宫格、商品与库存、我的）+ 关键组件与工具层，并对疑点做 grep 交叉验证。
> 边界：本报告只给意见与方案，**未改动任何代码**。证据标注 `文件:行号`。

## 结论速览

整体设计纪律**远高于同类作品的平均水平**：「失败 ≠ 空数据」的 loadError 体系、结算页金额护栏（服务端报价唯一来源）、完成配送页钱卡三态、站长端五组宫格，都是成熟的做法，应保留。主要问题集中在四类：

1. **口径自净运动有漏网**：本仓反复修过的"单位错配 / 白屏 / 死刷新"，在订单详情等高流量页仍有残留；
2. **配送端视觉变量被大面积绕过**（实证统计），同一产品两种视觉语言；
3. **高频操作弹窗链过长**，确认疲劳会反噬真正重要的风险提示；
4. **两端 request.js 会话防护不对称**，配送端换账号存在数据串号风险。

优先级：P0 = 13 / 1 / 2 / 14；P1 = 3 / 4 / 5 / 8 / 9 / 18（功能色部分）/ 20；P2 = 其余。

## 一、交互流程与用户体验

### 🔴 1. 下拉刷新「死开关」4 处 + 「空转」1 处

- **问题**：js 定义了 `onPullDownRefresh` 但页面 json 未开 `enablePullDownRefresh`（处理器永远不被触发）：
  - `miniapp-delivery/pages/coordination/index.js:482`（**站长工作台首页**——全端刷新诉求最高的页面）
  - `miniapp-delivery/pages/station-mgmt/apply-bind/index.js`
  - `miniapp-user/pages/order/detail.js:34`（**客户订单详情**）
  - `miniapp-user/pages/notice/index.js`
  反向 1 处：`miniapp-user/pages/template/index.json` 开了刷新但没有处理器，下拉后没有 `wx.stopPullDownRefresh`，一直转圈。
- **影响**：站长在工作台下拉无反应，只能靠切 tab 触发 onShow 重拉；客户想刷新订单状态同样无效；模板页下拉卡在刷新态。用户感知是"应用卡了/坏了"，且这类缺陷静态检查和人工走查都很难发现。
- **改进建议**：① 补齐 4 处 json 配置；② template 页补处理器（或关掉刷新开关）；③ 把"handler ↔ json 配置一致性"写进既有静态门禁家族（`audit_wxml_handlers.py` / `page_reach_audit.py` 同族新增一条规则），这类问题值得机器守。

### 🔴 2. 配送端 request.js 无会话防护，换账号存在数据串号

- **问题**：用户端 `utils/request.js` 有 5 处 `epoch` / `credentialVersion` / `refreshFlights` 单飞防护；配送端同文件 **0 处**（grep 实证，只有 `isRefreshing` 布尔）。配送员/站长换账号是日常操作。
- **影响**：切换账号瞬间，在途 401 会拿**新会话的 refreshToken** 去重发**旧账号的请求**——A 身份的操作落到 B 身份上，后端日志完全正常，线上几乎无法定位。这不是体验问题，是数据正确性问题。
- **改进建议**：把用户端 `utils/token.js` 的会话 epoch 机制（`captureSession` / `isCurrentSession` / 单飞 refresh）整体移植到配送端 `utils/request.js`；两端能力对齐后，把"401 重放必须校验会话"写进两端共用注释。

### 🟠 3. 高频操作弹窗链过长（一次操作 3–4 层打断）

- **问题**：站长外派一单：ActionSheet（选外派方式）→ Modal（确认外派）→ 风险确认 Modal → Loading → Toast（`coordination/index.js:821-892`）；抢单：ActionSheet（选配送员）→ Modal（抢单确认）→ 风险 Modal（`:902-954`）。配送端全量 375 处 `showToast` + 140 处 `showModal`。
- **影响**：确认疲劳——站长每单点 3 次以上确认，会形成"秒点确认"的肌肉记忆，真正需要阅读的押金/跨站风险提示也被秒掉，护栏形同虚设。
- **改进建议**：① 把"操作确认 + 风险提示"合并为**一张底部确认卡**：订单摘要、金额去向、风险文案同屏呈现，一次确认；② 风险确认卡与普通确认卡做视觉区分（警示色头部），让"这次不一样"可被感知；③ 低频高危操作（按挂牌价、客户拒付、同意取消）保留独立强确认。

### 🟠 4. 报价请求无防抖，步进器每点一次打一次报价

- **问题**：首页步进器 `onCartQtyChange → refreshDerived → refreshRightsQuote`（`home/index.js:741-752, 637`）；结算页 `onQtyChange / onQtyInput → refreshQuote`（`create.js:585-612`）。连点 5 下加号 = 5 次完整服务端报价。
- **影响**：弱网下"正在核实报价"反复闪烁、合计金额跳动；序号兜底防住了错数据，防不住流量与服务器压力的浪费。
- **改进建议**：报价入口加 300–500ms 防抖（序号机制保留做最终正确性兜底）；数量输入框改为失焦/确认后触发，而非每键触发。

### 🟠 5. 订单列表无分页，首页全量拉单

- **问题**：用户端订单列表 `getOrders(params)` 全量返回（`order/list.js:41-65`）；首页同样 `getOrders({})` 全量（`home/index.js:343`）。注：后端接口本身支持 `page/size`（`barrel/index.js:357` 已在用）。
- **影响**：老客户订单量上来后，列表页与首页首屏的传输与 setData 开销线性膨胀（setData 大数据是小程序性能头号杀手）。
- **改进建议**：① 订单列表分页 + 上拉加载更多；② 首页改用"进行中订单 + 最近一单"的轻量端点，不为两张卡拉全量订单。

### 🟡 6. 购物车只存内存，冷启动即丢

- **问题**：购物车挂在 `globalData`（`app.js:11-12`），小程序被回收后选购数量全部丢失。
- **影响**：客户选好数量、切出去回个微信，回来要重选——这是订水场景的高频打断路径。
- **改进建议**：按站持久化到 storage（生命周期跟随 `stationStorage`），下单成功/换站确认后清除对应站的键。

### 🟡 7. 登录页协议链接不可点（代码内已自述）

- **问题**：`login/index.js:36-37` 注释自述《用户协议》《隐私政策》是纯文本、点了没反应。
- **影响**："点击登录即同意"需要可查阅的协议文本支撑，否则合规与审核都站不住。
- **改进建议**：补两个静态协议页（无正文可先用占位结构），链接可点；这属于上线前必清项。

## 二、信息筛选、优先级与组织

### 🟠 8. 客户订单页签直接照搬内部状态机

- **问题**：tabs = 全部/待配送/配送中/已送达/已完成/已取消（`order/list.js:9-18`）。"已送达(3)"与"已完成(4)"的差别是**系统内部语义**（收款确认/完成动作），不是客户心智；而对客户最重要的"已送达待收款"混在页签里没有辨识度。
- **影响**：客户在两个看起来都是"送到了"的页签间找不到单；需要自己行动的（待支付/待收款确认）状态没有被前置。
- **改进建议**：按客户行动视角重组：**进行中**（待配送+配送中）/ **待我处理**（待支付 + 已送达待收款）/ **历史**（已完成+已取消）；"待我处理"中的单在卡片上给醒目的行动标。

### 🟠 9. OrderCard 取消按钮判据与详情页不一致

- **问题**：卡片用 `order.status === 1` 决定显示取消（`components/OrderCard/index.wxml:42`）；详情页用后端派生 `order.canCancel`（`order/detail.js:89`）。后端派生字段早已下发，卡片没用。
- **影响**：同一单在列表与详情两个入口的"可取消性"不一致（如配送中可申请取消的单，列表上看不到取消入口）——这正是本仓家规"判据只留一份"的违反实例。
- **改进建议**：卡片统一读 `order.canCancel`，删除前端 status 判据。

### 🟠 10. 「我的」页资产格的落点与占位

- **问题**：① "押金"与"我的桶"两格都跳 `/pages/barrel/index`（`mine/index.wxml:35,43`）；② "余额"格（`getCustomerStats.balance`）占位第一格，但在无充值/余额业务场景下对绝大多数客户没有实际意义（**需产品核实该字段真实使用面**）。
- **影响**：两格同落点会让客户以为"点了没反应/功能重复"；首格长期无数据是首屏噪音。
- **改进建议**：① "押金"格直落押金流水页（与菜单行"押金流水"语义一致），"我的桶"落桶账页，落点错开；② 核实"余额"的业务含义与使用率，无实际场景则降权或并入账单记录。

### 🟡 11. 配送端订单详情底部操作堆叠

- **问题**：`order/detail.wxml:196-263`：action-bar（导航/完成配送/异常反馈）之下，转单/撤回转单/退回站长/申请取消/客户拒付 5 个文字按钮竖排堆叠，视觉权重与主动作接近。
- **影响**：配送员在门口单手操作时误触成本高；主动作被稀释。
- **改进建议**：低频善后操作收进"更多操作 ›"底部弹层；主区只留 导航 + 完成配送 + 至多 1 个情境次动作（如待收款时的"确认收款"）。

### 🟡 12. 「购物车 / 清单」术语两端三处不统一

- **问题**：首页称"订水清单/加入清单"（`home/index.wxml:120`、`home/index.js:694`），商城页称"购物车/已加入购物车"（`shop/index.js:225`、`shop/index.wxml:71-73`）。
- **影响**：同一概念两个名字，增加理解成本。
- **改进建议**：统一为"订水清单"（与"去结算"语义链一致）或"购物车"，文案收敛进一份常量。

## 三、信息呈现与表达

### 🔴 13. 配送端订单详情「× N 桶」单位硬编码——自曝口径事故的漏网

- **问题**：`miniapp-delivery/pages/order/detail.wxml:94` 写死 `× {{it.quantity}} 桶`。而本仓在 `home/index.js:121-124`、`coordination/index.js:97-101`（goodsView）、`order/complete.js:22-24`（buildDeliveryItems）三处都用大段注释修过**同一个错**：`quantity` 是全单总件数（含瓶装水/饮水器），单位必须按 `category` 映射（桶/瓶/台/件）。详情页是漏改的第 4 处。
- **影响**：混合单（3 桶水 + 1 瓶水 + 1 台饮水机）在配送员最常用的详情页上显示成"瓶装水 ×1 桶、饮水机 ×1 桶"——配送员按错数搬货、与客户当面核对数量时各说各话。这正是本仓注释里反复说的"信息不准引发柜台争执"的原形。
- **改进建议**：单位映射抽成 `utils/item-unit.js` 一份（以 complete.js 的实现为正本），详情页、列表页、完成页共用；把"任何数量渲染必须带正确单位"写进静态检查。

### 🟠 14. 用户端订单详情页：加载失败 = 白屏

- **问题**：`order/detail.js:119-121` 的 catch 只弹 toast，页面 `wx:if="{{order}}"` 恒不满足 → **白屏**；`loadImages` 失败同样静默置空（`:166-172`）。本仓 §8.22 修复运动已覆盖首页/订单列表/桶/票/我的/商城/工作台，唯独这个高流量页漏了。
- **影响**：弱网或后端异常时打开订单详情就是白屏，与"订单不存在"无法区分——本仓在 8 个页面修掉的正是这同一个形状。
- **改进建议**：补 loadState 三态（loading / ok / failed + 重试按钮），直接参照 `order/success.js:62-84` 的现成实现。

### 🟠 15. 水票页裸按钮与错误条内默认样式按钮

- **问题**：`ticket/index.wxml:10`「剩余水票退出说明」是未样式化的原生 `<button>` 且置顶在余额卡之前；`:13-21` 恢复提示条内嵌 4 个原生默认按钮（重试原购买/结束原购买/另买一笔等关键恢复动作）。
- **影响**：与设计系统（卡片 + 品牌色按钮体系）违和，像调试残留；恢复类关键操作在视觉上与正文无层级，用户不知道该先看哪个。
- **改进建议**：① 退出说明降级为帮助入口（标题行问号图标或底部文字链）；② 恢复条按钮套用既有小按钮样式（`create.wxml:201-202` 的 warn-action 是先例），主次分明（查询原购买 = 主，结束原购买 = 次）。

### 🟡 16. 退桶弹窗内混着一条无样式裸文本

- **问题**：`barrel/index.wxml:242` `<view wx:if="{{summary.independentRights}}">必须先批准并确认安排…</view>` 无 class，夹在两行表单项之间。
- **改进建议**：纳入 `preview-hint` / `preview-storage` 同款提示条样式。

### 🟡 17. 新旧两套桶账词汇同屏暴露给客户

- **问题**：`independentRights` 两套文案并存于同一页面（`barrel/index.wxml:17-19, 84-85, 181`）：持有桶/用桶权益/可用权益/实际在手，转型期四种说法并存。
- **影响**：客户在不同时间/页面看到不同词汇描述同一样东西，"我的桶呢"类咨询的直接来源。
- **改进建议**：面向客户的词汇收敛为一套（建议"我的桶 / 可退桶"），模式差异只影响数值来源、不暴露名词；词汇表写进 docs/design 文案正本，两端引用。

## 四、视觉一致性

### 🔴 18. 配送端页面样式大面积绕过设计变量（实证统计）

- **问题**：token 已在 `app.wxss` 定义齐全（2026-09-26 轨道 D 与用户端同值），但页面 WXSS 硬编码色值统计：`#1677ff`×13、`#1976d2`×11、`#FF3B30`×10、`#f56c6c`×19、`#888/#666/#333` 系灰、`#e8f5e9`、`#fff3e0` 等——是一套 Element/AntD 色板，与锁定体系（品牌蓝 `#2E4A68` / 成功 `#2E9E6B` / 警示 `#C9764B` / 错误 `#B5442C` / 暖纸底 `#FAF7F0`）完全不同。用户端也有漏网：`#1e40af`×6、`#007aff`×6。另有 `miniapp-delivery/pages/home/index.json` 的 `backgroundColor: #f0f4f8`。
- **影响**：同一产品两种视觉语言（暖纸米白 vs 冷蓝白）；更严重的是**状态色语义漂移**——同一个"待收款/异常"在两端用不同的红/橙表达，跨端对话时对不上。
- **改进建议**：① 分两批收口：先统一**功能色**（成功/警示/错误/状态点/待收款），再统一中性色与背景；② 只做"值替换"不动结构，风险可控；③ 把"页面 WXSS 禁出现白名单外十六进制色值"写成 lint 门禁，否则替换完还会回潮。

### 🟡 19. 配送端"蓝头详情页"与"暖纸列表页"混排，缺一条成文规则

- **问题**：`order/detail.wxss:8-12` 用 `var(--header-gradient)`（已降级纯色 `#2E4A68`）蓝头白字，而其余页面是暖纸底；配送端内部两种页型混排，无规则可循。
- **改进建议**：二选一并成文：① 详情页蓝头降级为暖纸 + 状态章（与用户端语言统一）；② 明确"详情页 = 深色头、列表页 = 暖纸"作为成文规则，推及所有详情页（目前 barrel-records、history、my-earnings 等是否同规未见一致）。

## 五、性能与可维护性

### 🟠 20. 配送端两套「商品摘要」格式化器并存

- **问题**：`coordination/index.js:105-113`（goodsView）与 `home/index.js:133-142`（summaryOf）做同一件事，兜底规则有微妙差异（'等 N 桶' vs '等 N 件'、firstProductName 兜底文案不同）。
- **影响**：这正是本仓注释反复警告"同一段逻辑两端各写一份迟早分叉"的形状；第 13 条（详情页单位错配）就是这种漂移已经发生的证据。
- **改进建议**：抽 `utils/item-summary.js` 一份两页共用，配单元测试；与第 13 条的工具函数合并为一个"订单明细展示"工具模块。

### 🟡 21. 遗留 CloudBase 模板文档误导协作

- **问题**：`miniapp-delivery/CODEBUDDY.md` 是 CloudBase 模板路由文档（`wx.cloud` / envId / tcb CLI），与本项目 Spring Boot + 原生小程序架构完全无关。
- **影响**：AI 协作者与新成员会被引导到不存在的技术栈上。
- **改进建议**：删除，或替换为本目录真实的开发说明（两端结构、设计变量、门禁命令）。

### 🟡 22. 用户端订单编号直接暴露自增主键

- **问题**：`order/detail.wxml:17-19` 展示 `order.id`；配送端用 `order.orderNo || order.id`。
- **影响**：客户报单号时报的是数据库自增 ID，既不专业也泄露单量规模。
- **改进建议**：统一下发并展示 `orderNo`（无则后端生成带日期前缀的业务单号），两端一致。

### 🟡 23. 「低库存」阈值 20 硬编码在前端

- **问题**：`products/index.js:145` `(i.quantity || 0) < 20`。"低库存"是经营判据，阈值定在前端代码里。
