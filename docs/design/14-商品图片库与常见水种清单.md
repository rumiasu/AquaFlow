### 1.2 图片字段与渲染链路

```
product.image_object_name  (varchar(500)，存 COS 对象键，如 public/product/xxx.jpg)
        │  CosUtil.generatePublicUrl()  ← 24 小时过期的预签名 URL，带 30min 内存缓存
        ▼
   imageUrl（transient，不入库，由 Controller 注入）
        │
        ▼
   小程序 <image src="{{item.imageUrl}}">
```

| 环节 | 位置 |
|---|---|
| 字段定义 | `entity/Product.java:54-55`（`imageObjectName`） |
| URL 生成 | `util/CosUtil.java:67`（`generatePublicUrl`）、`:88`（预签名）、`:99`（`uploadPublic`） |
| 商品列表注入（员工端） | `service/impl/CatalogServiceImpl.java:336-348`（`withImageUrls`） |
| 顾客端注入 | `controller/ProductController.java:170`（`Product`）、`:181`（`StationProductVO`） |
| 顾客端返回字段名 | `imageUrl`（`dto/StationProductVO.java:47`）+ `imageObjectName`（`:28`） |
| 前端消费 | `miniapp-user/pages/shop/index.wxml:42-47` 等，**直接使用，无二次处理** |

### 1.3 发现的三个问题（做图库前必须处理）

**问题 1 · COS 在本地未配置**

`application-local.yml:44-49` 整段被注释；`RequiredConfigChecker` 对 COS 只 `log.warn` 不拒启。
后果：`generatePublicUrl` 抛异常 → 各处 try-catch 吞掉 → 接口仍 200，但 `imageUrl` 恒为 `null` → 顾客看到占位图；`/api/common/upload` 直接返回"文件上传失败"。

**问题 2 · 🔴 上传返回的是 URL，却当对象键入库（round-trip 缺陷）**

- `CommonController#upload`（`controller/CommonController.java:57-65`）返回 `cosUtil.generatePublicUrl(objectName)`，即**完整 https 预签名 URL**。
- 站长端 `miniapp-delivery/pages/station-mgmt/products/index.js:642-667` 的 `uploadImage()` 把该 URL 存进 `editForm.imageUrl`。
- `CatalogServiceImpl.createMyProduct`（`:165`）`setImageObjectName(... : dto.getImageUrl())` —— **把 URL 当成 COS 对象键落库**。
- 后续 `generatePublicUrl(那个 URL)` → 无效地址 → 被吞 → 图永远不显示。

→ 修法：上传接口应返回 `{objectName, url}` 两个字段，落库只存 `objectName`。**统一图库上线时必须一并修**，否则"选预设图"和"传自定义图"会走两套口径。

**问题 3 · 参数未配置时无本地兜底，且小程序兜底不一致**

- 后端无 `addResourceHandlers`（`config/WebMvcConfig.java` 只重写了 `addInterceptors`），**没有任何本地图片服务能力**。
- 小程序端兜底分三套：详情页 `/assets/image/default-product.png`（1251 B）、下单页 `/assets/image/default-product.jpg`（98 KB）、商城/首页用 💧 文本占位；**全端无 `binderror`**。

## 3. 统一图片库该怎么切（建议，待拍板）

### 3.1 核心判断：按「水种 × 包装」，不要按品牌

| 方案 | 说明 | 评价 |
|---|---|---|
| A. 按品牌出图 | 农夫山泉.jpg / 怡宝.jpg / 普利思.jpg … | ❌ 三个问题：① 用别家商品照片涉及商标与来源合规；② 本地长尾品牌（趵突泉/宏泉/润荷泉/百脉泉…）永远穷举不完；③ 站长卖的品牌与平台选的图不一致反而更丑 |
| B. 按**水种 × 包装形态**出图 | 纯净水-循环桶、矿泉水-循环桶、天然水-循环桶、纯净水-一次性桶、瓶装、饮水机 … | ✅ 通用、无商标风险、覆盖长尾；站长自定义商品也能用 |
| C. 按包装形态出图 | 桶装 / 瓶装 / 饮水器（= 现有 `category`） | ⚠️ 颗粒度太粗，同一 category 下 4 种水种长得一样 |

**建议取 B，并把现有 `category`（1 桶装水 / 2 瓶装水 / 3 饮水器）保留为一级维度。**

预估组合数：4 水种 × 2 桶型（循环桶 / 一次性桶）+ 瓶装 + 饮水器 ≈ **10～14 张**，数量可控。

### 3.2 图片来源（"找素材"的三种可行路径）

| 路径 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **① 统一风格插画（建议）** | 用 AI 或设计工具出一套**同一画风**的水桶/水种示意图（扁平、暖纸底、品牌蓝主色） | 无商标风险、风格与项目视觉系统一致、体积极小（webp 可压到 10~20 KB/张） | 需要一次性制作；不能表达"具体某品牌" |
| ② 实拍白底图 | 买一桶自有品牌水拍摄 | 真实感强 | 有成本；仍有品牌露出问题 |
| ③ 图标化 | 不用照片，用线性图标 + 色块表达水种 | 体积极小、可无限扩展 | 美感依赖图标质量 |

> 注意：**不要直接搜"农夫山泉桶装水 图片"下载使用** —— 商品照片和商标属于品牌方，平台方内置这类图会有合规风险。方案 ① 从根上规避了这个问题。

### 3.3 存储与下发方案对比

| 方案 | 存储位置 | 优点 | 缺点 |
|---|---|---|---|
| **A. 小程序本地资源（建议 MVP）** | 两个小程序各自 `assets/product/*.webp` | **零网络、零过期、零 COS 依赖**（当前 COS 恰好没配）；加载即时 | 换图需发版；两端各存一份 |
| B. COS **公有读** + 固定 URL | `public/preset/xxx.webp` | 后台可换图；URL 稳定可被 CDN/小程序缓存 | 需要把 bucket 改公有读并配 CDN；依赖 COS 可用 |
| C. COS 预签名（**现状**） | 同现状 | 无需改动 | ❌ URL **24 小时过期**，每次列表都重签，不适合"固定素材库" |

**建议：MVP 走 A，后续要"后台换图"再迁 B；C 只保留给站长自传的自定义商品图。**

### 3.4 需要拍板的一个技术分叉

"预设图"如何从 DB 走到 `<image src>`？两种都可行：

| 做法 | 链路 | 评价 |
|---|---|---|
| **甲：后端翻译成本地路径** | `image_preset='pure-barrel'` → 后端下发 `imageUrl='/assets/product/pure-barrel.webp'` | **前端零改动**（`src="{{imageUrl}}"` 直接可用）；代价是后端要知道小程序资源目录 |
| 乙：前端维护映射表 | 后端只下发 `imagePreset`，小程序侧 `PRESET_MAP[key] → 本地路径` | 后端不耦合前端路径；代价是两端各维护一份映射（**本仓历史事故模式：两端各写一套映射曾导致新客下单 100% 失败**） |

→ 倾向**甲**（符合本仓"展示口径全部由后端下发"的既有约定）。

## 3.8 已实施：通用「桶装水」一张图入库 + 站长选图入口（2026-09-17）

**产品口径修正（用户拍板）**：**不做"水种 × 包装形态"四张细分图**。原话：

> "不说循环桶，直接就是桶装水就行，**业务逻辑是循环而已**。直接入库看看效果吧，能让站长直接选择的那种"

含义：「循环」是**桶的资产属性**（桶要回收、押金可退、占用=权益+over），**不是一种商品分类**。按水种拆视觉等于把资产属性误当商品属性 —— 客户在货架上看到的是"一桶水"，不是"一桶纯净水（循环式）"。因此**只做一张通用桶装水图**。

### 三条关键设计判断

1. **判据是"以 `/` 开头即本地路径"**，不是新增 `image_preset` 列（§3.5 的原提案）。
   理由：`image_object_name` 本就只承载"一个字符串"，新增列会让"哪一列是真值"产生二义性。
   复用同一列后，**将来接 COS 只需换值、代码零改动** —— 这正是用户选的"先本地、留好 COS 切换口"。

2. **只挂图、不改名**（推翻了用户原先选的"改名成通用名"）。
   `product_id` 被 **15 张表**引用（含 `order_item` / `deposit_record` / `ticket_record` / `customer_barrel_*`），
   且 `inventory` 已有 2 条真实选用记录（station_id=1，product_id=1/2）。
   改 `name` 会**篡改历史订单与资产记录的留痕** —— 商品名是快照信息，不是可随时改的展示字段。
   同时 `preset_uk`（`name|brand|spec` 生成列）会被触发，有撞唯一键的风险。**证据已向用户报告并获认可。**

3. **配置下发的是"路径"而不是"key"**（§4 待确认第 4 项选"甲"）。
   后端翻译的好处是前端不硬编码路径段，将来换 COS 前端零改动；
   代价是接口多返回一个字段 —— 值得。

### 同时修掉的 §1.3 问题 2（round-trip 缺陷）

站长上传图片时 `/api/common/upload` 返回的是**预签名 URL**，前端回填后旧实现把它**当对象键落库** → 永远签不出地址。
现由 `CatalogServiceImpl.pickImageValue()` 兜住：`imageObjectName` 优先；`imageUrl` 只有以 `/` 开头（本地路径）才接受；
其余（预签名 URL）**记 warn 日志并丢弃**，绝不把 URL 当对象键写进去。

### 幂等与回滚

- UPDATE 带 `image_object_name IS NULL` 条件 → 二次执行影响 0 行（已实测）。
- 回滚：`UPDATE product SET image_object_name = NULL WHERE owner_station_id IS NULL AND image_object_name = '/assets/product/barrel-water.webp';`
- 备份：`backup/aquaflow_before_v38_20260917-224458.sql`
