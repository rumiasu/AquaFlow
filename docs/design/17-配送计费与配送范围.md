## 1. 要解决的四件事

| 能力 | 一句话定义 | 归属 |
|---|---|---|
| **起送量** | 低于门槛不接单（或加收配送费） | 站级参数 |
| **配送范围** | 超出范围不接单（或加收远程费） | 站级参数 + 距离计算 |
| **运费** | 一单收多少配送费 | 站级参数 + 订单费用项 |
| **楼层费** | 无电梯要不要加收、加多少 | 站级参数 + 地址楼层 + 订单费用项 |

四者共用一套"站级参数 + 下单时快照"的机制，所以放一份文档。

## 3. 数据模型建议

### 3.1 站级计费配置（表 `station_delivery_config`，站级一行）

> **状态：已实施（v35）**。⚠️ 下表是**实现前的提案**，落地时的列名略有出入
> （如 `free_delivery_threshold_buckets` → `free_delivery_buckets`）。
> **实际列名与注释以 `sql/schema.sql` 与 `sql/migration_v35_station_delivery_config.sql` 为准**
> —— 有正本就不要在这里重述（`AGENTS.md` §0.4）。
> 另外落地时补了一条本文没写的语义：**免运费的两个门槛都为空 = 一直收基础配送费**
> （不是"一直免"），已由 `DeliveryFeeUtilTest.noFreeThresholdAlwaysCharges` 锁定。

只存**经营参数**，不存计算结果：

| 列 | 含义 | 备注 |
|---|---|---|
| `station_id` | 主键 | 一站一行 |
| `min_order_buckets` | 起送桶数 | NULL/0 = 不限 |
| `min_order_amount` | 起送金额 | 与桶数**取或**（满足其一即可） |
| `delivery_radius_m` | 配送半径（米） | NULL = 不限 |
| `over_radius_mode` | 超范围处理：`REJECT` 拒单 / `WARN` 仅提示 / `FEE` 加收远程费 | 见 §4.2 |
| `remote_fee` | 超范围附加费 | 仅 `FEE` 模式用 |
| `base_delivery_fee` | 基础配送费 | 0 = 免运费 |
| `free_delivery_threshold_buckets` | 免运费桶数门槛 | 与金额门槛取或 |
| `free_delivery_threshold_amount` | 免运费金额门槛 | |
| `floor_free_level` | 免费楼层（如 1 层） | |
| `floor_fee_per_level` | 每超一层加收 | |
| `floor_fee_mode` | 楼层费口径：`PER_ORDER` 每单一次 / `PER_BUCKET` 每桶 | 建议默认每单，见 §5.3 |

### 3.2 `station` 表加坐标

`lat` / `lng`（`decimal(10,6)`，地址同款精度）。站长端用 `wx.chooseLocation` 选点写入。

**判据：没有站点坐标就无法做距离校验；不能靠"用地址字符串模糊匹配"糊过去。**

### 3.3 `address` 表加楼层信息

`floor`（int，可空）、`has_elevator`（tinyint，可空，NULL = 未确认）。

**判据：`has_elevator` 必须可空并区分"未知"与"无电梯"。** 把 NULL 当"无电梯"会向客户乱收钱；把 NULL 当"有电梯"会漏收。未知时**不下楼层费并提示站长**，而不是默认收。

### 3.4 `orders` 加费用列（**只加不改**）

- `delivery_fee` decimal(10,2) DEFAULT 0
- `floor_fee` decimal(10,2) DEFAULT 0

新口径：

```
total_amount = water_amount + deposit_amount + delivery_fee + floor_fee
```

⚠️ 三条硬约束：

1. **不得塞进 `water_amount`** —— 污染水费口径；水费与退款、报表、对账都相关。
2. **不得塞进 `deposit_amount`** —— 那是**可退押金**，退款路径按它释放押金（`PaymentServiceImpl:557-569`），混入运费会导致取消订单时**多退钱**。
3. 快照列要同步：运费/楼层费是"下单那一刻算出来的"，**必须落在订单上而不是每次重算**。这与 `orders` 已有的地址快照（`receiver_name`/`address_snapshot`/`address_snapshot_lat/lng`，`:462-466`）是同一条原则——客户改地址后，历史单的金额不能跟着变。

同理由，`payment_record` 也要能表达这笔费用（新增列或明确"运费含在 amount 里但 water_amount 不含"）。**改这张表前先看 §6 的对账影响。**

## 4. 规则设计

### 4.1 起送量：默认**软提示**，不是硬拦

本仓已有先例：欠桶从"硬拦 ≥5"改成"只提醒不阻断"（`AGENTS.md` §1）。同一逻辑适用于起送量。

- 默认 `WARN`：下单放行 + 响应 `warnings` 提示"未达起送量"
- 站长可将本站配置为 `REJECT`
- 若配了 `FEE` 模式：未达起送量则加收小额配送费，仍然放行

**判据：任何"硬拦"都必须由站长显式开启。** 现实中老客户只要 1 桶，站长一定会通融；系统硬拦等于让站长绕过系统下单（那就会破坏桶账真实性）。

### 4.2 配送范围：距离用**直线距离**，判定用**软处理**

- 计算：站点坐标到地址坐标的 Haversine 直线距离。
- **不要接地图 API 的骑行/驾车距离**：桶装水是电动车/三轮车，直线距离够用，且第三方距离 API 有配额与费用。
- 默认 `WARN`；`REJECT` / `FEE` 由站长选。

**判据（三条边界，缺一个就会误拦）：**

1. 站点坐标为空 → **跳过范围校验**（不是拒单），只提示站长去补坐标；
2. 客户地址坐标为 NULL → **跳过范围校验**，只提示；
3. **跨站外派单：距离与费用都按「下单水站（归属站）」算，且只在下单那一刻算一次** ——
   `calcForOrder` 的两个调用点（`OrderServiceImpl` 下单、`PaymentServiceImpl` 试算）传的都是下单水站，
   `DeliveryFeeServiceImpl` 的配置与坐标都取**传入的那个站**。外派 / 抢单**一律不重算**
   （`claimPool` 只改 `delivery_station_id` 与配送员），费用始终是下单快照。
   ⚠️ **本条原文写的是「跨站外派单用履约站坐标算距离」，与代码不符**（下单时履约站还不存在），
   2026-09-18 按产品裁定与代码订正：**定价按外派方（归属站）、钱归实际履约站** ——
   所以抢单池与「他站外派」两个列表会把「费用快照 + 定价来源站名 + 结算去向文案」一起下发，
   让目标站在**认领之前**就知道这单值多少钱、价是谁定的（见 `DeliveryController` 的 `feeInfoOf`）。
   **判据：外派与认领都不得触发第二次计价** —— 在这里重算就是"计价双轨"（`util/PriceUtil` 文件头记的那次事故），
   会出现"抢单页一个价、订单详情另一个价"。
   **钱归谁（v47，2026-09-18）**：本单营收 = **水费 + 配送费 + 楼层费**，归 **`orders.settle_station_id`（结算站）** ——
   **未外派时 = 归属站，被抢单 / 定向外派后 = 实际履约站**；`delivery_station_id` 只管库存与计件工钱，
   押金 / 水票 / 桶权益仍在归属站（正本 `sql/migration_v47_order_settle_station.sql`）。
   抢单池与「他站外派」列表在**认领之前**就下发费用快照 + 定价来源站名 + 钱货去向（`DeliveryController.feeInfoOf`），
   读取一律 `coalesce(o.settle_station_id, o.delivery_station_id, o.station_id)`。

### 4.3 运费

保持简单，不做动态定价。规则形态：

```
if (桶数 >= 免运费门槛) or (水费金额 >= 免运金额门槛)  → delivery_fee = 0
else                                                  → delivery_fee = base_delivery_fee + (超范围 ? remote_fee : 0)
```

**注意与"免配送次数"的关系**：`16` §D2 提到的"买水票套餐送免配送次数"是一种**客户资产**，不是配置项。落地时它应扣减一个次数账户（见 `19` 与 `20` §4），运费计算里只做"本次是否用掉一次"。**不要把它做成配置里的一个布尔开关。**

### 4.4 楼层费（向客户收的那一笔）

```
if (has_elevator == 1) or (floor == NULL) or (floor <= floor_free_level) → floor_fee = 0
else → floor_fee = floor_fee_per_level × (floor − floor_free_level) × (PER_BUCKET ? 桶数 : 1)
```

**判据：**
- 楼层信息来自**下单时的地址快照**，必须同时快照 `floor` / `has_elevator` 进订单，否则客户事后改地址，这笔费无法复算 → 站长与客户扯皮。
- `has_elevator` 为 NULL（未确认）时**不收**，并在响应 `warnings` 里提示站长确认。
- 电梯楼但有台阶/半层（常见于老小区）不在系统建模范围内，靠 `orders.special_note` / `delivery_time_request` 这类自由文本兜住。

## 5. 与现有流程的接口

### 5.1 必须同时改的两个入口

| 入口 | 位置 | 改什么 |
|---|---|---|
| 报价 | `PaymentServiceImpl.quote:665` | 加费用项、返回给前端展示 |
| 下单 | `OrderServiceImpl.createOrder`（`setSource` 在 `:430` 附近） | 加费用项、快照进订单 |

**两处必须调用同一个计算函数**（建议新增 `util/DeliveryFeeUtil`，与本仓"计价唯一入口 `PriceUtil`"的风格一致）。

### 5.2 前端展示

运费/楼层费由**后端下发文案与金额**，前端不自算、不自带映射——这是本仓铁律（`PayMethod`/`OrderStatus` 的文案都只由后端下发，见 `AGENTS.md` §6）。

> ⚠️ **缺口已补（2026-09-17）**：全仓 grep `floor|hasElevator|楼层|电梯` 时发现，
> 顾客端录入、站长端配楼层费、站长端代客下单能看到客户楼层、计件工资页配「楼层补贴/层」——
> **唯独真正要爬楼的那个人（配送员）的订单页一处都没有**。
> 也就是说这两个字段此前只服务「计价」，没有服务「干活」：楼层费按它向客户收、
> 楼层补贴按它给配送员补，而配送员出车前并不知道这一单要不要上楼。
>
> 已补三处（**纯读取，没有加列、没有改口径**）：
> ① `Orders` 加两个关联查询字段 `addressFloor` / `addressHasElevator`；
> ② 配送员的**任务列表**查询（`OrderMapper.listByDeliveryStaffId`）带出这两列；
> ③ 订单详情（`orderMapper.getById` 是纯 orders 查询、不带地址关联）在 `DeliveryController`
>    里按 `address_id` 补读一次地址。
> 前端在小程序里展示：配送任务列表与订单详情各一行，文案由 `utils/address.buildFloorText`
> 统一生成（**只有一处实现**），不确定时整行不显示。
>
> 两条判断（都已写成用例 `DeliveryFloorVisibilityIntegrationTest`）：
> ① **取当前地址的值、不是下单快照** —— 配送员要知道"客户现在在哪层"；
>   `orders` 只快照了地址文本与经纬度，**没有快照楼层**，这里也**不要**为此加列
>   （计费用的历史口径已经落在 `orders.floor_fee` 上）；
> ② **`has_elevator` 是三态**（NULL = 没确认过 / 0 = 无电梯 / 1 = 有电梯）——
>   只有确认过"无电梯"才说无电梯。把 NULL 说成"无电梯"既误导配送员，
>   也与后端收费口径相反（拿不准时后端是不收楼层费的）。



### 5.3 一个建议：楼层费默认按"每单一次"

按桶收楼层费（`PER_BUCKET`）在现实里更常见（"无电梯 2 元/桶"），但会产生**客户在结算页看到 3 桶 × 2 元 = 6 元而放弃下单**的摩擦。建议默认 `PER_ORDER`（每单一次），把 `PER_BUCKET` 作为站长可选项。这是产品取舍，不是技术限制。

## 6. 对账影响（**最容易出事的地方**）

本仓的对账等式在 `ReconciliationService`（等式1~4 + E3~E7）。新增费用列时必须逐条过一遍：

| 检查项 | 是否受影响 | 处置 |
|---|---|---|
| 等式1：押金余额 == SUM(deposit_record.amount) | **不受影响**（只要不把运费塞进 `deposit_amount`） | — |
| 等式2：订单支付状态与流水是否相符 | **受影响** | 若 `payment_record.amount` 含运费而 `orders.total_amount` 口径不同，会报"有凭证未置已付"。**两边口径必须一次对齐** |
| 等式3/4：桶三态、库存与流水 | 不受影响 | — |
| E5：物理桶守恒 | 不受影响 | — |

**验收判据：加完费用列后必须跑一次完整日结对账，四项全平。**

另：`PaymentServiceImpl.quote` 返回的 `totalAmount` 被小程序结算页直接使用（`result.put("totalAmount", ...)`，`:750`），改口径必须同步核对两端展示。

## 7. 迁移与验收

- 新迁移：`sql/migration_v33_delivery_fee_and_range.sql`（当前最高 **v32**，已核）
- 迁移必须幂等：用 `information_schema` 预检 + `PREPARE`（本仓约定，MySQL 8.4 无 `DROP IF EXISTS`）
- 新列全部**可空或带默认值**，保证老库补跑后旧订单不炸

### 验收清单

1. 未达起送量：默认放行 + 响应带 `warnings`；站长开 `REJECT` 后拒绝，返回 `code=1` 可读文案。
2. 超范围：站点无坐标 / 地址无坐标 / 有坐标 三种情形各一条用例（前两种必须**放行**）。
3. 楼层费：有电梯=0；无电梯 6 层按配置算；`has_elevator` NULL 时收 0 且带提示。
4. 免运费门槛：桶数门槛与金额门槛各一条。
5. **口径一致**：`quote` 的 `totalAmount` 与 `createOrder` 落库的 `total_amount` 在同样输入下必须相等（这是 `PriceUtil` 事故的回归口径）。
6. **取消退款**：带运费/楼层费的订单取消后，`deposit_amount` 释放的金额**不包含**运费（防多退钱）。
7. 日结对账四项全平。
