## 1. 业务形态

**不做通用促销引擎**（满减/优惠券/活动叠加/优先级/退款摊分是无底洞），营销能力收敛为**水票档位套餐**：

| 档位 | 售价 | 单张均价 | 附加权益 |
|---|---|---|---|
| 1 张（散买） | 按 `inventory.ticket_price` | — | — |
| 10 张一组 | 套餐价（便宜一些） | 低于散买 | — |
| 20 张一组 | 套餐价（更便宜） | 更低 | — |
| 100 张一组 | 套餐价（最便宜） | 最低 | 例如"免 N 次配送费" |

**这是"定价结构"，不是"促销活动"。** 区别在于：档位是**站长挂出来的固定价目表**，永远可买、不叠加、不互斥、不需要活动引擎。这个降维是对的。

## 2. 现状（动代码前必须知道）

| 事实 | 证据 |
|---|---|
| 水票价是**单张价**，站级配置 | `inventory.ticket_price`（`schema.sql:301`）；真相源经 `PriceUtil:57-65` 取值 |
| `product.ticket_price` 是**历史列、实际恒为 0**，真正生效的是站级 | `schema.sql:547` 注释 |
| 水票账户**只有数量，没有单价** | `ticket_account`：`remain_quantity` + `(customer_id, product_id, station_id)` 唯一键（`schema.sql:625-634`） |
| 水票流水**没有单价列** | `ticket_record`（`schema.sql:635-658`），`source` 取值：购买/赠送/消费/退款/人工调整补入/扣减（`TicketAccountServiceImpl:96,127,157,191,217`） |
| 在线购票**已有位置**记商品与张数 | `payment_record.ticket_water_type_id` / `ticket_qty`（`schema.sql:506-507`） |
| 水票**无有效期** | `ticket_account` 无过期列 |
| 赠送水票**没有正式入口** | `source` 里 `赠送` 只有语义位，实际写入口是购买/消费/退款/人工调整 |

### 2.1 桶账已经解决过同一个问题（**这是本文最重要的参照**）

`customer_barrel_lot` 是"批次单价快照"的完整实现：

- `unit_price` —— "2026 年 30 元买的，2027 年退就退 30 元"（`schema.sql:181`）
- `remain_qty` —— 剩余未退数（`:183`）
- `source_type` 1订单购买/2历史迁移/3人工补录（`:184`）
- `price_source` 1订单实付/2当时商品押金/3当前商品押金兜底（`:185`）
- `is_migrated` 1=历史迁移批次（单价为推断，退款需二次确认）（`:189`）
- 汇总侧：`customer_barrel_asset.right_amount` = `Σ lot.remain_qty × unit_price`（`:151`）

`BarrelLedgerService:237-238` 明确写过：schema 早就为这三种来源预留了列，**这套"批次 + 来源 + 价格来源"就是给"非订单来源的购买"准备的**。

**水票档位正好是同一类场景**（一次购买、多张、单价随档位变化、将来要按原价退），所以**照抄桶的批次模型，不要另发明一套**。

## 3. 数据模型建议

### 3.1 `ticket_package`（站级档位表）

| 列 | 含义 |
|---|---|
| `station_id` | 水站（水票按站隔离，见 `ticket_account` 唯一键） |
| `product_id` | 商品 |
| `qty` | 张数（10 / 20 / 100） |
| `price` | 套餐总价 |
| `unit_price` | 均价 = price / qty（**落库冗余**，用于快照与展示，不要每次除） |
| `bonus_delivery_count` | 附赠免配送次数（可空，见 §5.2） |
| `status` | 上下架 |
| `sort` | 排序 |

唯一键 `(station_id, product_id, qty)`。

**判据：档位是站级的，不是全局的。** 与 `inventory` 站级定价、`ticket_account` 按站隔离一致；全局档位会让 A 站买的票在 B 站有价差。

### 3.2 `ticket_lot`（水票批次，照抄 `customer_barrel_lot`）

字段与 `customer_barrel_lot` 对齐：`lot_no` / `customer_id` / `station_id` / `product_id` / `unit_price` / `qty` / `remain_qty` / `source_type` / `price_source` / `is_migrated` / `payment_record_id` / `status` / `operator_id` / `note`。

汇总侧：`ticket_account` 保留 `remain_quantity`（= Σ lot.remain_qty），并可增一个 `right_amount`（= Σ lot.remain_qty × unit_price），与 `customer_barrel_asset.right_amount` 完全同构。

### 3.3 需要补的标识列

- `payment_record.ticket_package_id`（可空）—— 记录"这笔记的是哪个档位"
- `ticket_record.unit_price` + `ticket_lot_id` —— 让流水能自证单价来源

**为什么要落 `ticket_package_id`**：档位价格会变。历史流水若只记"买了 100 张、收了 800 元"，**几个月后无法自证当时是哪个档位**，也就无法解释"为什么这 100 张均价 8 元而现在均价 9 元"。这与 `orders.deposit_amount` 快照、`customer_barrel_lot.unit_price` 快照是同一条原则。

## 4. ✅ 已修的幂等漏洞（v33，2026-09-17 完成）

> **状态：已修复并测试锁定**。改动见 `sql/migration_v33_payment_idempotency.sql`、
> `TicketAccountServiceImpl.purchaseTicket`、`TicketPurchaseDTO`、
> 用例 `TicketPurchaseIdempotencyIntegrationTest`（5 例）。
> 下面保留漏洞的原始描述与推理，作为"为什么当初必须修"的记录。

### 4.1 漏洞本体

`payment_record` 的防重靠生成列 + 唯一键：

- `active_order_id` = `case when status in (1,2) then order_id else NULL end`（`schema.sql:514`）
- `UNIQUE KEY uk_payment_active_order (active_order_id)`（`:527`）

**但在线购票的 `order_id` 是 NULL**（`:498` 注释："水票直购等无订单支付时为空"）→ `active_order_id` 也是 NULL → **MySQL 唯一键中 NULL 互不冲突 → 这条路径零保护**。

这与 `AGENTS.md` §1 记载的 `uk_ticket_consume` 在 `order_id IS NULL` 时零保护**是同一个形状的坑**（`:654-656` 已就地留了注释）。

### 4.2 后果

客户连点两次"买 100 张票"→ **两笔 PENDING 流水 + 两次入账 = 200 张**。档位套餐是大额（100 张），金额越大越疼；而站长端"待确认收款"列表（`PaymentController:203-212`）里会出现两条几乎一样的记录，站长手工确认时**很可能两条都确认**。

### 4.3 修法

在线购票加**客户端幂等键**（照 `orders.idempotency_key` 的做法，`schema.sql:483,486`）：

- `payment_record.idempotency_key` + 唯一键（或独立 `uk_ticket_purchase(client_token)`）
- 客户端在进入购票页时生成一次，**提交时携带；重试沿用同一个 key**
- 服务端先查后建，并把 `DuplicateKeyException` 作为幂等命中处理（不是错误）

**（原判据）这个修复必须与档位功能同批上线。** 档位是同一条代码路径，新功能会把这条路径的调用频率显著抬高。

**执行结果（2026-09-17，已提前于档位功能完成）**：

| 项 | 落地 |
|---|---|
| 唯一键 | `uk_payment_idempotency(customer_id, idempotency_key)` —— **带上 `customer_id` 是必需的**：只按 token 唯一的话，客户端传别人的 token 会直接拿回别人的支付记录（跨客户泄露）。用例 `keyIsScopedByCustomer` 锁死这一点 |
| 幂等键 | `POST /api/tickets/purchase` 的 `idempotencyKey` **必传**（缺/空串/纯空白一律 `code=1`）。设成必传而非可选：「可选」等于默认没有保护，而漏传的代价是重复入账 |
| 命中时机 | 幂等判定放在**所有业务校验之前** —— 这笔购买若已成功建过流水，此后站长即使关掉水票开关或改价，重放也应返回原流水 |
| 并发 | 真并发由唯一键兜底，捕获 `DuplicateKeyException` 后**抛出**而不是吞掉继续（本方法在事务内，吞掉会让 Spring 抛 `UnexpectedRollbackException` 把并发拒绝伪装成 500）；客户端用同一个 key 重试即命中幂等分支 |
| 金额后果 | 用例断言的不是"流水条数"而是**确认收款后水票只多一份**（3 张而非 6 张）—— 流水条数只是手段 |
| 迁移 | 测试库已执行并验证幂等（二次执行全 skip）；真实库待执行 |

## 5. 规则设计

### 5.1 退票：按**批次单价**退，与退押金同口径

`PriceUtil#calcDeposit` 的注释已把这条原则写死（`PriceUtil:78-85`）：

> 退押金一律按 `customer_barrel_lot.unit_price`（买入时快照）结算，**不要**调本方法重算，否则改价会改到客户已经付过的钱。

**水票退票必须沿用同一口径**：按 `ticket_lot.unit_price` 退，不退现金而退到水票账户或按站长规则。

**业务开关**：是否允许退票应由站长可配（现实中大量水站"票不退不换"）。但**只要允许退，就必须按批次价退**。

### 5.2 "买得多免几次配送费"

⚠️ **这一条不能做成配置里的布尔开关。**

"免 N 次配送费"本质是一种**客户资产（次数账户）**，与水票/押金同类，需要：账户 + 流水 + 幂等 + 有效期 + 对账。

- 做成画像上的一个勾 → 会出现"站长说还有 3 次、客户说还有 5 次"的扯皮（见 `16` §4.1）
- 正确形态：`customer_delivery_credit`（次数账户）+ `delivery_credit_record`（流水），赠送时记 `+N`，抵扣时记 `-1`，唯一键防重

**并且它有前置依赖**：得先有"配送费"这个实体（见 `17` §3.4）。所以 `17` 必须先于本条的这部分落地。

**建议：本期只做"档位单价便宜"，"免配送次数"单独切一期。** 理由是前者纯属定价（无新资产），后者是新的资产账户（工作量与风险都高一个量级）。

### 5.3 档位与散买共存

`inventory.ticket_price` 继续作为**散买单张价**，档位是"批量更便宜"。`PriceUtil` 的取值阶梯不变（站级覆盖 → 通用库参考值），**档位不走 `PriceUtil`**（它不是单价，是套餐），而是走独立的 `TicketPackageUtil` 或在购票服务里取档位行。

**判据：不要让 `PriceUtil` 开始认"数量"参数。** 它现在的职责是"单价/押金"，一旦引入数量维度，所有调用点都要重新审一遍（那是 `AGENTS.md` 反复强调的计价双轨事故的入口）。

## 6. 对账：新增 E8

现有 E3 是"权益汇总与押金条批次相符"（`ReconciliationService`）。水票批次引入后，应有同构的一条：

```
E8: ticket_account.right_amount == SUM(ticket_lot.remain_qty × ticket_lot.unit_price)
    AND ticket_account.remain_quantity == SUM(ticket_lot.remain_qty)
```

**告警分级**：按 `constant/AlertType`，账目不平属**系统故障** → `SYSTEM`（`station_id` 必须为 NULL），与 E3/E5 同级，不要投给站长。

### 验收清单

1. **幂等**：同一 `idempotencyKey` 连提两次购买 → 只产生一笔流水、只入账一次（这是 §4 漏洞的回归口径）。
2. 档位购买后：`ticket_account.remain_quantity` 增加 = 档位张数；`ticket_lot` 有对应批次且 `unit_price` = 档位均价。
3. 站长改档位价后，**已购批次的 `unit_price` 不变**（快照生效）。
4. 退票按批次价退；`is_migrated=1` 的批次要求二次确认。
5. `E8` 成立；E3~E7 不受影响。
6. 站间隔离：A 站买的票不在 B 站可见/可用（沿用 `ticket_account` 唯一键）。
