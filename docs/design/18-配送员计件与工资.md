## 1. 结论先行：这块的投入比想象的小

计件工资看起来是"人事/薪酬模块"，容易高估工作量。实际上**数据采集已经全部就位**：

| 需要的数据 | 现有落点 | 证据 |
|---|---|---|
| 谁送的 | `orders.delivery_staff_id` | `schema.sql:458` |
| 送了几桶 | `order_item.quantity`（桶数） | `schema.sql:390` |
| 送出空桶 / 收回空桶 | `orders.delivery_bucket_qty` / `return_bucket_qty` | `schema.sql:456-457` |
| 空桶差异 | `orders.barrel_discrepancy` | `schema.sql:472` |
| 送达时间 | `orders.update_time`（状态转 3 的时刻） | `schema.sql:471` |
| 今日完成 | `DeliveryController.getCompletedToday`（`:128`） | 已有端点 |

**所以缺的不是采集，是三样东西**：站级计件单价配置、按人按天的**收益明细**、可核对的**结算单**。

⚠️ 全仓检索 `提成|计件|工资|salary|commission` 在业务代码中 **0 命中**；`staff` 表无任何薪酬字段（`schema.sql:570-583`）。

## 2. 与外卖平台的偏离（照抄会错的地方）

| 维度 | 外卖平台 | 本项目（桶装水） |
|---|---|---|
| **谁发钱** | 平台结算给骑手，商家付平台佣金 | **站长直接发**。所以：不做平台结算单、不做佣金抽成、不做骑手钱包 |
| **计件单位** | 单 | **桶**（一单 1~3 桶，19kg/桶）。只按单计价 → 配送员不愿接多桶单 |
| **任务形态** | 单程（取餐→送达） | **双向**（送水 + 收空桶），且回桶数要当场核对 |
| **楼层** | 无独立项 | **必做**，且要拆成"向客户收"与"给配送员补"两笔 |
| **运力归属** | 众包，骑手同时接多平台 | `staff.station_id` 固定归属（`schema.sql:577`），跨站只是帮忙 |

### 2.1 发钱是线下动作，系统只做台账（2026-09-17 补充）

站长发工资**不一定走小程序**——现实里就是微信转账或当面给现金。所以这块的边界是：

**不做**：打款 / 提现 / 钱包 / 余额 / 代发。这些需要支付牌照与资金存管，而本项目连微信支付渠道都还没接（`16` §D1），做这个是空中楼阁。

**要做**：**算得清 + 留得下痕**。

- 结算单需要 `status`：`草稿 → 已确认 → 已发放`
- 发放时记 `paid_time` + `operator_id`（谁在什么时候给的）

**判据：「算出来」与「发出去」必须分开。** 如果只有一个状态，站长改一条明细就会**悄悄改掉已经发过的钱**——下个月对不上时无从追溯。这条与 `station_adjustment` 的"确认后不可原地改、要改走反向单/下期调整"是同一个设计语言。

**展示入口可以先不做。** 后端接口 + 站长端只读页就够站长发工资；配送员"我的工资"页属体验优化，可后置（它只读 `staff_earning`，不涉及任何新的账务口径）。

## 3. 数据模型建议

### 3.1 `staff_piece_rate`（站级计件配置）

| 列 | 含义 |
|---|---|
| `station_id` | 水站 |
| `product_id` | 可空 = 该站默认价；非空 = 某商品的专属单价（18.9L 与 5L 搬运成本不同） |
| `per_bucket_amount` | 每桶计件价 |
| `floor_bonus_per_level` | 每超一层补贴 |
| `distance_bonus_per_km` | 每公里补贴（可空 = 不启用） |
| `per_order_amount` | 每单基础奖励（可空） |

配置的真相源是**站级**（与 `inventory` 的站级定价同构）。**不要做阶梯/加权/复杂公式**——真实水站的计件价就是"一桶 X 元"。

### 3.2 `staff_earning`（收益明细，一行 = 一个动作）

| 列 | 含义 |
|---|---|
| `station_id` | **结算站**（见 §6.2） |
| `staff_id` | 收益归属人 |
| `order_id` | 关联订单（人工调整类可空） |
| `kind` | `DELIVERY_BUCKET` 送桶 / `RETURN_BUCKET` 回桶 / `FLOOR_BONUS` 楼层补贴 / `DISTANCE_BONUS` 距离补贴 / `ORDER_BONUS` 单奖 / `PENALTY` 扣减 / `ADJUST` 人工调整 |
| `qty` | 数量（桶数/层数/公里数），调整类可为空 |
| `unit_amount` | 单价快照 |
| `amount` | 金额（扣减类为**负数**，见 §3.4） |
| `payroll_id` | 已结算时写入；NULL = 未结算 |
| `note` | 备注 |

**唯一键（防重复结算的核心）**：`uk_earning(order_id, staff_id, kind)` —— 与 `orders.idempotency_key`（`schema.sql:486`）同一种防重思路。

### 3.3 `staff_payroll`（结算单）

单据头：`station_id` / `staff_id` / `period_start` / `period_end` / `total_amount` / `status`（草稿/已确认/已发放）/ `operator_id`。

**锁定语义**：结算单确认后，其下 `staff_earning.payroll_id` 写死，**不允许再改动**（要改只能对下一期做 `ADJUST`）。这与 `station_adjustment` 的"反向单撤销、不原地改"是同一条思路。

### 3.4 方向由类型决定（本仓铁律）

照 `DepositType` 的既有口径：**`kind` 决定正负，调用方一律传正数**，落库时由一处统一转符号（`DepositRecordServiceImpl:56-64` 就是这么做的，且是对账等式1的前提）。

**判据：不要在每个生成收益的地方各写一次 `amount.negate()`。** 一旦分散，将来必然有一处写反，而"工钱算错"不像"账不平"那样有对账兜底（见 §7）。

## 4. 计件构成

```
本次配送收益 = 送桶数 × per_bucket_amount
             + 回桶数 × return_bucket_amount     （可选，用于激励按时回收）
             + max(0, 楼层 − 免费层) × floor_bonus_per_level
             + 距离(km) × distance_bonus_per_km
             + per_order_amount
             − 空桶差异扣减
```

**关于"楼层补贴"与 `17` 的楼层费是两笔钱**（见 `16` §2.4）：

- `17` 的 `orders.floor_fee` = **向客户收**（收入）
- 本节的 `FLOOR_BONUS` = **给配送员补**（成本）

**两者金额可以不同，必须分别配置、分别落库。** 合成一个字段会导致：客户投诉乱收费时查不清、工钱算不准、对账不平。

**回桶考核判据**：`orders.barrel_discrepancy` 已有值（`:472`）。差异为正（少收空桶）时扣减，扣减规则由站长配；**不要默认扣**，先做成"在结算单上高亮提示站长"，避免误扣引发劳资纠纷。

## 5. 收益产生时点：钉在"送达"，天然免疫取消

**建议：`staff_earning` 只在订单状态进入 `3 已送达` 的那次状态变更中产生。**

这样做的好处（很重要）：本仓订单状态**只前进、不倒滚**，且 `OrderStatus.isCancellable` 已拦掉 `4 已完成 / 5 已取消`（`AGENTS.md` §1）。所以：

- 订单能取消的时机只有 `1 待配送 / 2 配送中` —— **此时还没有产生收益**；
- 一旦到 `3 已送达`，订单不可能再被取消 → **不存在"收益产生了又要撤回"的回滚问题**。

**判据：不要用"已接单"或"已分配"作为计件时点**，那会在取消单上留下需要人工清理的收益行。

并发防护：触发点必须是 `OrderWorkflowServiceImpl.completeDelivery` 里的**一次成功 CAS**（`updateStatusIf`），再以 `uk_earning(order_id, staff_id, kind)` 兜底。**只要唯一键在，重复调用最多报 1062 而不是多算一笔工钱。**

## 6. 归属与边界

### 6.1 归属人 = 实际完成人

`orders.delivery_staff_id` 是当前指派者。经历"转单"（`transferToStaff`，`OrderWorkflowServiceImpl:809`）后，它指向最终完成的人。**按完成时刻的 `delivery_staff_id` 结算**即可，不需要额外的转单分账。

### 6.2 归属站 = **履约站**，不是归属站

本仓已有双水站口径：`orders.station_id` = 交易/营收归属，`orders.delivery_station_id` = 实际履约归属（`AGENTS.md` §1，`StationUtil`）。

**配送员的工钱是履约成本，所以应记 `delivery_station_id`（履约站）。** 跨站外派单由外派站的配送员跑腿，工钱就该外派站发——这与"钱和票记归属站、库存走履约站"的既有划分是一致的：工钱既不是客户的钱，也不是库存。

**判据：`staff_earning.station_id` 取履约站；若为空（异常数据）则该单不产生收益并告警，而不是回落到归属站。**

## 7. 对账：**独立的等式，不要混进客户对账**

`ReconciliationService` 现有的等式都是**客户/资产**维度（押金、支付、桶、库存、权益）。**工钱不参与这些等式**——它是水站与人之间的账，与客户无关。

**误接的后果**：把工资算进客户对账 → 每天 03:00 的日结必然报不平（`ReconciliationService.dailyReconcile` 会发 SYSTEM 告警），告警疲劳后真问题会被淹没。

**正确做法：新增一条独立的等式**

```
E-PAY: staff_payroll.total_amount == SUM(staff_earning.amount WHERE payroll_id = 本期)
```

形态与押金等式1（`balance == SUM(deposit_record.amount)`）同构。

**告警分级**（按 `constant/AlertType`）：工资单对不上属于**运营问题**，应由站长看到（`OPERATION` + `station_id` 必填），不是系统故障。别投给系统管理员。

## 8. 迁移与验收

- 新迁移：`sql/migration_v34_staff_piece_rate.sql`（依赖 `v33`，见 `17` §7）
- 无破坏性变更（只加表），可安全在生产先上代码后跑 SQL

### 验收清单

1. 完成一单后，`staff_earning` 有对应行，金额 = 配置 × 数量。
2. **重复调用 `completeDelivery` 不产生第二笔收益**（走唯一键，报 1062 或幂等跳过）。
3. 订单在 `1/2` 状态被取消 → **无任何 `staff_earning` 行**。
4. 跨站外派单的收益记在**履约站**（`delivery_station_id`）。
5. 转单后收益归**最终完成人**。
6. 结算单确认后，其下明细不可再改（改则拒绝或要求走下一期 `ADJUST`）。
7. `E-PAY` 等式成立；`ReconciliationService` 的**原有四项等式不受任何影响**（这是最重要的回归）。
