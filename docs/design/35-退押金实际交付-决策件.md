# 退押金「实际交付」缺口 · 决策件

> **本文件写给**：做第三轮「退押金实际交付」的产品/工程师。它只回答一件事：
> **现在退押金的账记到哪一步为止、缺的那一步有哪两种补法、各自代价是什么。**
>
> 状态：**已拍板（2026-09-27）** —— 采纳**方案 A**，并附加两条运营口径（见 **§7**）。
> 正本登记在 `docs/design/16-范围决策与实施路线图.md` §8。
> §1–§6 是拍板前的取证与方案，**保留原样不改**（拍板依据要能回看）。
> **未改任何代码。**

## 1. 现在记到哪一步（实测，2026-09-27）

退桶审批是两步（`1→2→3`，不允许跳步），第 3 步 `doRefund`（`BarrelServiceImpl:605-669`）依次做：

| 步 | 动作 | 落点 |
|---|---|---|
| 1 | 按押金条批次 FIFO 核销，算出应退金额 | `barrel_record_lot`（哪几张押金条、各退多少） |
| 2 | **扣押金账户余额**（扣不到就抛错，不静默） | `customer_deposit_account.balance` |
| 3 | **写负数押金流水**（`-refund`，`type=6 退桶退押金`） | `deposit_record`（`operator_id` = **站长**） |
| 4 | 置「已退押金」并写回实退金额 | `barrel_record.status=3` + `handle_time` |

**⇒ 账做到了「按批次算出该退多少、并把这笔钱从客户押金账户上扣掉」。**

## 2. 缺的那一步

**没有任何字段记录「这笔钱什么时候真的交到顾客手上、经谁的手」。**

- `deposit_record.operator_id` = **操作这笔账的人**（站长点"已退押金"的那个），不是"交钱给顾客的人"；
- `barrel_record.handle_time` = **审批时间**，不等于交钱时间；
- 于是这两种情形在系统里**完全同形**：
  ① 站长当场把 50 元现金给了顾客；
  ② 顾客的桶被回收、账上显示"已退押金"，但钱还没给（等下次送水时抵、或顾客忘了来拿）。

第 ② 种在真实水站里很常见 —— 配送员上门收桶时**身上不一定带现金**。

**为什么这是个问题（而不是"口径不同"）**：顾客来问"我的押金退了吗"，系统会答"已退"；
对账也是平的（账户与流水一致）。**账平 ≠ 钱到手**，而这一格的验收标准正是
「每一笔钱知道谁收、谁欠谁、**什么时候算办完**」。

## 3. 仓库里已有的同形判据（可作样板）

`docs/design/16` §5.3 的原路径返回表里，**现金一行**写的是：

> 钱在站长/配送员手上，**由站长当面退还** → 凭据：负金额 `payment_record`（status = REFUNDED）
> → 系统还能做什么：**只记账，不能假装打了款**

同一份文档里，计件工资也是同一形状：「**发钱是线下动作**……系统只记 `paid_time` 与 `operator_id`」。

⇒ **仓库已有两次"线下动作 + 只记事实"的先例**。退押金缺的不是新概念，
而是**把"已交付"这一事实也记下来**（现在只记了"已核销"）。

## 4. 两种补法

### 方案 A（推荐）：加一列「交付确认」，两步变三步

| 项 | 内容 |
|---|---|
| **形状** | `barrel_record` 增两列：`refund_paid_time DATETIME NULL`、`refund_paid_by BIGINT NULL`（谁交的）。`status=3`（已退押金）语义**不变**＝"押金已从账户核销"，新增"已交付"是它之上的一步。 |
| **为什么单独一列而不是复用 `operator_id`** | 核销的人与交钱的人**可以是两个**（站长核销、配送员下次上门时交给顾客），复用会让两件事再也分不开 —— 同 §8.16「两个概念共用一个量」的形状。 |
| **接口** | 新增 `PUT /api/barrels/records/{id}/refund-paid`（站长；按 `AuthContext` 取站、校验归属），幂等（已确认再点只回成功）。 |
| **界面** | 退桶审批页在「已退押金」旁边给一个「押金已交顾客」按钮；配送端在「我的任务」里可见待交付的退押金（作为下次上门的提醒）。 |
| **对账** | **不新增等式**：这笔钱在核销时就已入账，交付确认只补事实。可另加一个**只读**计数「已核销未交付 N 笔 / ¥X」给站长查。 |
| **代价** | 一条迁移（纯加可空列，无破坏性）；一个端点；两处界面。 |
| **风险** | 低。不动任何金额、不动状态机前两步。 |

### 方案 B：复用「站长资产调整单」记一笔线下交付

| 项 | 内容 |
|---|---|
| **形状** | 不改表，交付时让站长开一张调整单（`/api/manager/adjustments`，已有 `uk_deposit_adjustment` 幂等键）。 |
| **代价** | 零迁移。 |
| **为什么我不推荐** | ① 把那套基建用于"确认一件已完成的事"，语义不对（调整单是**改账**的，这里账已经对了）；② 站长每退一笔押金都要多开一张单，纯增操作；③ 「已核销未交付」这个查询会退化成"拿调整单反查"，与本仓「同一判断只实现一次」相悖。 |

## 5. 建议与拍板后落点

**建议方案 A**，理由：它把两件事分开记（核销 / 交付），且**不新增任何账务概念** ——
与仓库已有的"线下动作只记事实"两处先例一致。

拍板后要动的地方（**都在本文一份正本里，别另开**）：

1. 迁移：`sql/migration_vXX_barrel_refund_paid.sql`（纯加两列，幂等写法照 `sql/README.md` 的既有脚本）。
   ⚠️ **编号在真动工时再定**：本文写作时 `ls sql/` 实测最新是 `v65_reservation_need_snapshot`，
   所以下一个大概率是 v66 —— 但本仓判据是**新建前自己 `ls sql/` 看占用，别照任何清单的最后一个数字 +1**；
2. 实体 / Mapper / Service：`BarrelRecord.refundPaidTime/refundPaidBy`、`markRefundPaid`（CAS + 检查行数，照 §6 的"状态改写必须 CAS"）；
3. 端点：`BarrelController` 新增 `PUT /{id}/refund-paid`（类上已有站长判权，沿用）；
4. 界面：站长端退桶审批页 +（可选）配送端待交付提醒；
5. 用例：`BarrelReturnGuardIntegrationTest` 旁补一条 —— 断言"已核销未交付"可查、交付后计数减一、重复确认幂等；
6. 文档：`docs/architecture/02-领域模型.md` §5（退款两入口那张表）补一行"交付确认"。

## 6. 未验证 / 边界

- **没查真实水站现在怎么处理这笔现金**（是当场给、还是下次抵扣）—— 这决定方案 A 的界面该放在哪一页，**需要产品确认**。
- **没查配送端是否已有"下次上门带现金"这类任务位**；若无，方案 A 的配送端提醒可能无处可挂（同 `docs/design/16` §5.4「转单撤回界面无处可挂」的形状）。
- **对账等式**我按"交付确认不改金额"来写；若产品要求「未交付的押金不算已退」，那 E 系列等式要动，
  **那是另一个量级**（账的语义变了），需要单独评估 —— 本文不做。

## 7. ✅ 已拍板（2026-09-27，产品裁定）：采纳方案 A + 「不现场给钱的不要退」+ 优先原路退回

产品原话：

> 「5.a，但是我建议**不现场给钱的不要退**，甚至我觉得可以**走选择系统退款**，之前也有限制类客户吧。」

三段话对应三条规则，逐条落成可执行口径：

### 7.1 `5.a` = 采纳 §4 的**方案 A**（加两列 + 交付确认，幂等端点）

按 §5 的施工清单执行。**追加一条**：§5 第 2 条只写了 `markRefundPaid`，
实际要写入的是**两列**，所以端点的入参必须能带「谁交的」——
站长自己交就取 `AuthContext` 的员工 id，**将来由配送员代交时要能写成那个配送员的 id**
（这正是 §4 方案 A 里"核销的人与交钱的人可以是两个"那条理由的落点）。

### 7.2 「不现场给钱的不要退」= **核销与交付必须发生在同一次操作里**

这条是本次裁定对 §4 方案的**实质性收窄**，别写反：

| | 拍板前的理解 | ✅ 拍板后的口径 |
|---|---|---|
| 第 3 步（`status 2→3`）语义 | 「押金已从账户核销」，交付是它**之后**另一步 | 「押金已核销**并且已经交到顾客手上**」，两件事在**同一次点击**里完成 |
| 「已核销未交付」 | 一个正常的中间状态 | **不允许出现** —— 它变成一条**异常计数**，用来抓"没给钱就先核销"的站 |
| 界面 | 「退押金」 | 「**退押金并当面交付**」，提交前必须勾选/确认"钱已当面交给顾客" |

- **不许**做成"先点退押金、钱以后再给" —— 那正是第 ② 种情形（顾客的桶被回收、账上显示已退、钱还没给），
  也是 §2 说的问题本身。
- 因此 §4 方案 A 的两列**仍然要加**，但它记的是**交付事实**（谁、什么时候），
  不是"允许欠着交付"：`refund_paid_time` 为空而 `status=3` 的记录 = **违规数据**，站长端要能筛出来（只读计数）。
- ⚠️ **`deposit_record` 的负数流水仍在第 3 步同一次事务里写**（§1 的四步顺序不变），
  不要因为"钱还没给"就把流水挪到交付那一步 —— 一挪，对账等式 1
  （`balance == SUM(deposit_record.amount)`）会在中间态不平。

### 7.3 「走选择系统退款」= 优先**原路返回**，通道不可用就**明确拒绝**（不许假装已退）

- **押金当初怎么收的，就怎么退**（`docs/design/16` §5.3 的原路径返回表已定这条）：
  线上支付的押金走**线上原路退回**；只有现金收的押金才走「现金当面交付」。
- 所以第 3 步要给站长**两个显式选项**：`refundChannel = ONLINE | CASH`
  （枚举入参**必须白名单校验**，见 AGENTS §6）。
  - `ONLINE`：若这笔押金当初不是线上收的、或**微信退款通道尚未接入** ⇒ **明确拒绝**并写清原因
    （「微信退款通道未接入，本单不能假装已退，请改用现金当面交付或线下退款」）。
    **AGENTS §1.1 已定：微信未接入 → 不许假装已退**（现有的手工退款也是直接拒）。
    实现落点见 `docs/design/16` §5.3 与 `PaymentServiceImpl` 的退款分支。
  - `CASH`：走 7.2 的口径（核销 + 当面交付同一次完成）。
- **为什么不做"默认线上"**：线上通道没接之前默认它，等于每笔退押金都失败一次。

### 7.4 「之前也有限制类客户吧」= 沿用既有信用风险拦截，**并补上第二道**

- 已有实现：`BarrelServiceImpl.previewReturn` 的信用风险拦截（`CustomerRiskService` 的
  `ALERT` / `FREEZE` → 复用 `blocked` 通道，与「欠桶不许退桶」同一条）。
- ⚠️ **实测缺口**：`doRefund`（`BarrelServiceImpl:605-669`）**只重查 `overQty`，没有重查风险级别**
  —— 申请（`status=1`）到审批（`status=3`）之间客户风险可能变化，那笔钱照样退出去。
  本仓对「欠桶」用的正是**硬拦两处**（申请 + 退款各一次），风险这一条只有一处。
- **本次补第二处**：`doRefund` 里在扣账户之前再查一次风险级别，命中即抛 `BusinessException`
  （文案复用 `customerRiskService.returnBlockedReason`）。
  ⚠️ **只在确实要退钱时拦**（与 `previewReturn` 同判据：`refund > 0`），
  查询性质、或本来就退不了的调用不该被它挡住。
