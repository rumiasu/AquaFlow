### D4-a 关于"入库采购单独写还是合并在库存里"

**结论：合并，不要新模块。**

`inventory_record.type` 已含 `INBOUND入库`（`schema.sql:315`），"采购入库"这件事在代码里**已经存在**，缺的只是成本：

- `inventory`（站级商品）**无** `cost_price`（`schema.sql:292-309`）
- `inventory_record`（入库流水）**无** `unit_cost`（`schema.sql:310-324`）

全仓检索 `cost_price|成本|进价|毛利|profit` 在业务代码中 **0 命中**。所以要做的只是"加一个成本字段 + 一个毛利看板"，而不是供应商/采购单/应付账款那一整套（那才是真的做不过来）。

## 2. 能不能"模仿美团"？——骨架可以，四处必须偏离

外卖平台的形态与本行业有**结构性差异**。照抄以下四点会做出一个拧巴的系统：

### 2.1 结算主体不同 → 计件工资是**站长台账**，不是平台结算

- 外卖：骑手是**平台**的众包运力，平台按单结算给骑手，商家向平台付佣金。
- 桶装水：配送员是**水站**的雇员/长期合作，**工钱由站长发**。本项目的角色模型也是这个：`staff.station_id` 是固定归属（`schema.sql:577`），跨站只是"帮忙"（`staff_station_application`）。

**后果**：不要做"平台结算单""佣金抽成""骑手钱包"。计件工资的账只在**站内**成立，见 `18-配送员计件与工资.md`。

### 2.2 计量单位不同 → 计件主口径是**桶**，不是单

- 外卖：一单 = 一份餐，按**单**计价。
- 桶装水：一单常是 1~3 桶，**每桶 18.9L ≈ 19kg**，搬运成本与**桶数**强相关。

**后果**：计件以"桶"为主单位，单数/距离/楼层是**加成项**。只按单计价会让配送员不愿接多桶单。

### 2.3 任务形态不同 → 桶装水的配送任务**天生是双向的**

外卖只有去程。桶装水一趟 = **送水（去程）+ 收空桶（回程）**，而回桶数是要当场核对的：

- `orders.delivery_bucket_qty`（送出空桶数）、`orders.return_bucket_qty`（回收空桶数）、`orders.barrel_discrepancy`（空桶差异）—— `schema.sql:456-457,472`

**后果**：
1. "完成配送"的定义**包含回桶**，不是"送到就走"；
2. 计件工资里应有**回桶率考核**（真实站长确实会为丢桶扣配送员工钱）；
3. 一条路线的收益要同时算送水与回桶两个动作。

### 2.4 楼层费必须拆成**两笔**，外卖只有一个"配送费"

- **向客户收**的楼层/上楼费 → **收入项**
- **给配送员补**的楼层费 → **成本项**

外卖模型里只有一个配送费，混在一起会导致：客户投诉乱收费 + 配送员工资算不出来 + 对账不平。这两笔**必须分开建模**，见 `17` §5 与 `18` §4。

### 2.5 另外四处"不要做"

| 不要做 | 理由 |
|---|---|
| **算法派单** | 本行业站长**自己就是调度员**（通常自己也送）。现有 `dispatch` / `transferToStaff` / `claimPool` 已够用，派单的操作者是人，不是算法 |
| **分钟级时效与超时罚则** | 桶装水的 SLA 是"半天/当天"。`orders.delivery_time_request` 是自由文本（"下午3点后""周末送"），不存在"准时宝"那套 |
| **骑手评分体系** | 样本太小（一个站 1~5 个配送员），且是长期雇佣关系不是平台派单竞争 |
| **动态定价/天气加价** | 桶装水定价是站长挂价的长期价格，不是实时撮合 |

### 2.6 可以借鉴的部分

| 借鉴 | 在本项目的落点 |
|---|---|
| 抢单池 / 转单 / 外派 | **已有**：`claimPool`/`transferToStaff`/`outsource`（`OrderWorkflowServiceImpl:698,754,809`） |
| 起送量、配送范围、运费 | 缺，本次做，见 `17` |
| 计件 + 距离/楼层补贴 | 缺，本次做，见 `18` |
| 营业状态（休息中/暂停接单） | **已有**：`StationOperatingStatus`（v32），且已是"软状态不阻断下单" |

**P0-4 的一处偏离**：原计划同时抽 `util/DeliveryFeeUtil`，**改为推迟到 Phase 1**。
理由：它要读 `station_delivery_config`（P1-B 才建），Phase 0 抽出来就是一个没有调用方、
也没有配置来源的空壳 —— 本仓对"存在但没接线"的东西一贯警惕（死端点评估就是为此做的）。
函数签名与规则已在 `17` §4 定稿，Phase 1 连同配置表与两个调用点一次落地。

**⚠️ 实施中踩到的一个坑（值得记住）**：给 `payment_record` 加 `NOT NULL DEFAULT 0.00` 的费用列之后，
**29 个用例一次全红**（购票、现金收款、退款、押金、取消回滚，覆盖 11 个测试类）。
根因：SQL 里的 `DEFAULT 0.00` **只在「该列没有出现在 INSERT 语句里」时才生效** ——
而 `PaymentRecordMapper.insert` 显式列出了这两列，实体字段又是 `null`，
等于把 NULL **显式**塞进 NOT NULL 列，MySQL 直接报 `Column 'delivery_fee' cannot be null`，
**整条支付链路全挂**。修法：在 mapper 的 SQL 边界用 `IFNULL(#{deliveryFee}, 0.00)` 兜住，并就地留注释。

> **判据：给已有表加 NOT NULL 列时，必须查清全仓有几条写路径、其中哪几条会显式传 NULL。
> `DEFAULT` 救不了显式 NULL。** 另外这条也说明"编译通过 + 新用例通过"远不足以判定安全 ——
> 本次新写的 3 个用例全绿，坏掉的是**别人**的 29 个用例。

- 迁移：`sql/migration_v34_delivery_fee_and_floors.sql`（纯新增 8 列，无破坏性变更）
- **硬门槛**：本阶段结束必须跑一次日结对账，等式1~4 + E3~E7 **全平**。

> **编排结论**：Phase 3 的 4 个已完成项**互相独立**，每个都能单独上线；`E10` 与既有等式 1~4/E3~E8 正交
> （它只查 `orders` 表内两个状态列的一致性），所以**没有把工钱、账期混进客户对账**——那正是 Phase 2 踩过的坑。

### 3.4 整个项目至此的评估

**工作量粗分档**（以"能上真实水站跑"为完成标准，不是"代码写完"）：

| 档 | 项 | 说明 |
|---|---|---|
| **小**（≤1 天） | P1-A 幂等键、P0-3 加列、代客下单页面、进货成本字段、桶损耗枚举、挂空列处置 | 后端大多已就位或只是加字段 |
| **中**（2~3 天） | P0-1/P0-2 坐标与楼层、P1-B 配置表+页、P1-C 计费接入、P2-A/B/C 计件三表、客户特权 | 新表 + 新页面 + 新用例 |
| **大**（≥1 周） | P1-D 水票档位+批次+回填、P1-E/P2-D 新对账等式、应收账款 | 涉及存量回填与对账口径 |

**风险排序（前三位都要"先修再建"）：**

1. **购票幂等**（P1-A）—— 现存漏洞 + 唯一线上大额入口，金额越大越疼。
2. **计费改 `quote`/`createOrder`**（P1-C）—— `PriceUtil` 文件头注释记录过"计价双轨"事故（结算页与订单金额不一致 → 客诉）。这是复发点。
3. **金额列写错**（P0-3）—— 把费用塞进 `deposit_amount` 会导致取消订单**多退钱**（`16` §4.4）。
4. **存量回填**（P1-D）—— 本仓有"测试库全绿、真实库不可用"的前科（`AGENTS.md` §8.12），且约束在唯一键上，必须到真实库核对 `information_schema.STATISTICS`。
5. 计件三表 —— 结构简单，但**不能接进客户对账**。

**建议砍掉的：** 免配送次数（是一种新资产账户，工作量与风险高一个量级，见 `19` §5.2）；发票（外部服务商依赖，先只攒开票信息）。

**不建议现在做的：** 微信支付（D1）、SaaS/多租户（D4）、上游供应链与加盟（D4）、动态定价与天气加价、算法派单、骑手评分（§2.5）。

**每个 Phase 的收尾动作固定两条**：① 跑完整集成测试；② 跑一次日结对账，确认**原有等式全部仍平**。

## 4. 贯穿四条原则（每个功能都要过一遍）

### 4.1 凡是"钱 / 次数 / 资产"，必须有账户 + 流水 + 幂等 + 可复算

本仓已有的正面样本：桶权益（`customer_barrel_lot` 批次 + `BarrelLedgerService` 唯一写入口）、押金（`deposit_record` + 等式1）、水票（`ticket_account` + `ticket_record`）。

**反例警戒**：把"免配送次数""客户折扣"做成客户画像上的一个开关。它会退化成没有校验、没有流水、没有对账的裸状态，最后变成"站长说还有 3 次、客户说还有 5 次"的扯皮。

### 4.2 计量规则必须**同口径**，且只能实现一次

`PriceUtil` 的文件头注释记录了真实事故：`quote()` 与 `createOrder()` 各算各的，结算页价格与实际订单金额不一致（计价双轨 → 客诉）。

**判据：任何新增计费规则（起送量/运费/楼层费）必须同时进入 `PaymentServiceImpl.quote` 与 `OrderServiceImpl.createOrder`，且计算逻辑抽到 `util/` 下唯一实现，禁止两处各写一个 if。**

### 4.3 可预期的经营状态 → 业务错误（`code=1`），不要升级成系统异常

对齐 `AGENTS.md` 关于"对象存储未配置不得表现为 500"的判据。例如"低于起送量""超出配送范围""水票余额不足"都是**可预期的经营状态**，应给可读文案的 `code=1`，不得抛 `RuntimeException`。

### 4.4 金额列**只加不改**

`orders` 现有三个金额列语义已锁死且被对账依赖：

- `water_amount` 水费
- `deposit_amount` **可退押金**（退款路径按它释放押金：`PaymentServiceImpl:557-569`）
- `total_amount` 目前 = 水费 + 押金（`PaymentServiceImpl.quote:744`）

**新增运费/楼层费必须新开列，绝不允许塞进 `water_amount` 或 `deposit_amount`。**

⚠️ **塞进 `deposit_amount` 会真丢钱**：退款时按 `orders.deposit_amount` 释放押金余额（`PaymentServiceImpl:557`），把 10 元运费混进去，取消订单时会**多退 10 元到客户押金账户**。

### 5.1 验证方法（本工作流的"跑测试"标准姿势）

> 2026-09-17 加的。**背景：本工作区长期有第二个 agent 会话共享 `build/` 与 `aquaflow_test`，直接跑
> `gradlew test` 会互相污染**（实测一次全量跑出 250/278 失败，其中 250 个是"瞬时失败"而非真缺陷）。

两步隔离，缺一不可：

1. **代码隔离 —— 干净 worktree**：`git worktree add --detach .verify-r9 HEAD`。
   必须这样做的第二个理由更重要：**HEAD 之外的未提交改动会打红整个测试套件**。
   实测另一个工作流的 `ProductImageResolver` 声明了两个构造器且都无 `@Autowired`，
   Spring 找不到默认构造器 → **上下文加载失败 → 所有 250 个走 Spring 的用例一次全红**
   （唯一"通过"的 28 个是纯单元用例，它们不起容器）。**看到"大批用例同时红"先去看
   `AquaFlowApplicationTests` 的 `Caused by`，不要逐个查业务断言。**
   `application-local.yml` 是 gitignore 的，需要手工拷进 worktree（**用完删掉 worktree，
   别把带密钥的副本留在磁盘上**）。
2. **数据隔离 —— 私有测试库**：`application-test.yml` 支持 `${TEST_DB_URL:...}` 覆盖，
   所以**不用改任何文件**：
   ```powershell
   $env:TEST_DB_URL='jdbc:mysql://127.0.0.1:3306/aquaflow_test_r9?useUnicode=true&characterEncoding=utf-8&serverTimezone=Asia/Shanghai&allowPublicKeyRetrieval=true&useSSL=false'
   ```
   建库必须照 `schema.sql` 的排序规则建（`utf8mb4_0900_ai_ci`），
   再按 AGENTS §4 的**字节级重定向**导入 baseline：
   `cmd /c "mysql -uroot --password=*** --default-character-set=utf8mb4 aquaflow_test_r9 < schema.sql"`。
   自检：`information_schema.TABLES` 的表数必须与 `schema.sql` 里 `CREATE TABLE` 的条数**相等**。
   库名含 `test`，`AbstractIntegrationTest` 的护栏因此照样生效。

**判据：报告"测试全绿"前，先确认结果 XML 的时间戳晚于本次运行，且唯一性对自己的库。**
`--tests` 过滤器会清空 `build/test-results/test/`，所以"只剩目标类的 XML"本身就是过滤器生效的证据。
