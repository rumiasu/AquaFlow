### 0.11.1 依据：这两张卡本来就是一件事

`pages/station-mgmt/alerts/index.js` 里 `RELATED_TEXT = { ORDER_BARREL_EXCEPTION: '桶异常单' }`

## 0.10 第 8 批：「我的」统计卡分叉 + 配送页签改名 + 净利（2026-09-19）

**产品反馈**：①「我的」里那三个数要改（今日完成 → 今日盈利，可看利润/成本/单数）；
②「配送」tab 的「待接单」语义不对（**站长自己也会接单**），改叫「待配送」；
③ 待配送已转到配送 tab，「我的」不要重复；④「回桶数」想换成异常/未回桶之类。

**产品裁定（本轮四问）**：净利取**真净利**口径；第二格用**今日单数**；
第三格**异常与欠桶都要**；统计卡**按角色分叉**。

### 0.10.1 三个数：15 → 撤一格、换一格、改一格

| 格 | 改前（两种角色同一套） | 改后·站长 | 改后·配送员 |
|---|---|---|---|
| 1 | 今日完成（**我**今天完成的单数） | **今日净利**（¥ /「算不出」）→ 点进「利润报表 · 今日」 | 今日完成（不变，按人统计） |
| 2 | 待配送（后端 `pendingCount` = **全站** status1 单数） | **今日单数** → 点进同一页 | 配送中（按人统计） |
| 3 | 回桶数（**我**今天带回的空桶数） | **桶异常 · 欠桶 N 户** | 回桶数（不变 —— 对配送员它就是工作量，不是"异常"） |

- **第 2 格为什么撤得掉**：「待配送」在「配送」页就是第一个页签（还带角标），
  在「我的」再报一遍正是 §0.9 要消除的重复。
- **第 3 格是"换指标"不是"改名"**：原「回桶数」是配送动作量（我今天拉回几个空桶），
  与"异常/未回桶"没有关系。**欠桶**在本仓是**只提醒不阻断**的常态（原硬拦已按产品决定移除），
  长期大于 0 —— 所以它只当**副行**（"欠桶 N 户"），主数字留给真正要处理的**桶异常**。
- **为什么按角色分叉**：净利走的端点是 `@RequireRole("STATION_MANAGER")`，
  配送员调它拿到的是**权限错误**而不是 0；不分叉就只能给它显示空白，那比不显示更糟。

### 0.10.2 净利口径（四个数字来自**同一批订单**）

**净利 = 水费收入 + 配送费 + 楼层费 − 进货成本 − 配送员计件工钱**

后端在**同一个** `GET /api/manager/gross-profit` 响应里追加
`orderCount` / `deliveryFee` / `floorFee` / `totalIncome` / `wage` / `netProfit` / `profitBasisNote`：

- **同一 cohort 是硬要求**：结算站 + 排除已取消 + 同一时间窗，与毛利逐字一致；
  单数/费用那条 SQL **刻意不 join `order_item`**（join 了配送费会被明细行数放大）；
- **工钱按 `staff_earning.order_id` 挂到这批订单上**，不按工钱自己的 `create_time` 筛；
  **人工调整（`order_id IS NULL`）不进日净利**（迟到扣款不是某一天订单的成本）；
- ⚠️ **缺成本时 `netProfit` 与 `totalProfit` 一起为 null**（只 null 一个，站长会拿另一个当真）；
- ⚠️ **收入不含押金**（可退的负债不是收入）；
- ⚠️ 已知边界：收益在订单进入**送达**时才产生 → 未送完的单暂时不计工钱，那几天净利偏高。
  响应里的 `profitBasisNote` 把这几条写给站长看，页面**原样展示**。

**页面**：`station-mgmt/gross-profit/` 更名「利润报表」（宫格卡与导航标题同步），
新增「今日」快捷区间（`?range=today` 从「我的」跳进来）与一张"减法账"卡片
（单数 → 水费 → 配送费 → 楼层费 → 收入合计 → −成本 → −工钱 → **净利**）。
金额一律用服务端下发值，**页面里不做任何毛利/净利算术**（同本页原有判据）。

### 0.10.3 「配送」页签：待接单 → 待配送

- 理由：后端 `OrderStatus` 1 的名字**就叫「待配送」**；按「接单配送」的实际动作是
  `status 1→2 + 认领`（`OrderWorkflowServiceImpl.acceptOrder`）。改完 tab 名与状态机一一对齐。
- 该页签装的本来就**不是"没人派的单"**，而是两支合并：`assigned-to-me`（已派给我、未接单）
  + `orders/pending`（全站 status=1）。**站长自己也会接单**，所以旧名字在站长眼里是错的。
- 同步改了：页签名、卡片状态标签、空态文案、统计看板标签、`api/delivery.js` 两处注释、
  `miniapp-delivery/README.md` 三处。
- ⚠️ **「已完成」本来就是"今日"**（`date(update_time) = 今天`），本轮**没有改动** ——
  产品原以为它列全部历史；全部历史在「我的 → 配送历史」（`pages/history`）。
- ⚠️ `coordination` 页那处「等待接单」是**外派**语义（他站等本站接外派单），**不动**。

> ⚠️ **2026-09-19 的一次假失败（值得记住的教训）**：本轮第一次跑全量时出现
> 「412 tests completed, **6 failed**」，失败集中在桶异常 / 跨站池 / 配送计费 / 配送台四个

## 0.6 【越界但有价值】「解除」把站长解除掉 → 水站变孤儿（2026-09-19 已修）

推进 P1（员工合并）时顺带发现并修掉的一个**真实缺陷**，它不在原 IA 范围里，但比 IA 严重：

| 项 | 内容 |
|---|---|
| 现象 | 站长在员工列表里能看到**自己**那一行，且带「解除」按钮；点下去**真的成功** |
| 根因 | `POST /api/manager/bind/release` 只校验「员工存在 + 属于本站」，**没有 role 校验、也没有"别解除自己"**；而列表数据源 `StaffMapper.listByStationId`（`where station_id=? and status=1`）**不带 role 条件** → 站长自己就在返回集里；前端两处都按 `item.status === 1` 渲染按钮，没判角色 |

| 修法 | ① 后端加两条护栏（`role` 必须是 `DELIVERY` + 不能解除自己）；② 前端两处（`station-mgmt/staff/`、`mine/`）把站长那一行的按钮换成一行灰字「站长 · 不可解除」 |
| 回归 | `DeliveryBindingIntegrationTest.managerReleaseUnbindsDirectly` 增补 4 条断言（解除自己被拒、解除另一站长被拒、两次被拒后归属原样保留） |
| 反向验证 | **临时摘掉护栏重跑，用例在断言处红掉**（`站长不得解除自己 ==> expected: not equal but was: <0>`）—— 证明这条测试真能抓住它，不是假绿 |
| 记录 | AGENTS §8.29 |

## 3. 已裁定的决策与依据

### C1 订单管理：撤卡，**不并页签**（用户裁定 + 事实校正）

| | 首页 tab（coordination） | 宫格「订单管理」（orders） |
|---|---|---|
| 切法 | **动作**：待分配 / 审批 / 抢单池 / 外派 / 他站外派 | **状态**：全部 / 待配送1 / 配送中2 / 已完成4 |
| 数据源 | 6 条专用端点（`station-pending`+`station-transfer` **前端合并**、`pool`、`dispatch-tracking`、`directed-incoming`、`pending-approvals`） | 1 条通用列表 `GET /api/orders?status=` |
| 行内操作 | 分配 / 外派 / 抢单 / 跳过 / 同意拒绝转单 / 同意拒绝取消 / 取消外派 / 重新外派 / 调解退回 | **无**，点卡片进 `order/detail` |
| 独有 | 「待办」聚合卡（4 项，含逾期应收金额） | **跨站履约归并行**（履约站视角，含金额合计与明细） |

**关键校正**：宫格那份**功能更少** —— 只有一个状态筛选条；而它点进去的 `order/detail`
本身就是完整操作台（`dispatchOrder` / `resolveOrder` / `requestCancel` / `transferOrder` /
`returnToStation` / `completeOrder` / `refundPayment` 全在详情页）。

**所以"在页签里加跳转"这个方向要反过来**：不是首页加跳转到宫格，而是
**待分配列表底部加「看全部订单 ›」→ `navigateTo` 到通用列表**（它不是 tabBar 页，可 navigateTo）。
**不把状态页签并进首页那一排**：动作维度与状态维度混在一排，站长分不清"待配送"与"待分配"。

**既有缺口（单独记，不混进 IA 改动）**：`GET /api/orders` 默认每页 **200**、上限 500
（`OrderController:97-100`），而订单管理页**不翻页**（`orders/index.js:73` 只传 `stationId` + `status`）。
单站累计超 200 单后，页面只显示最近 200 单且**界面无任何提示**。

### C2 数据看板：删两块重复内容（✅）

- `:17-21` 待收款横幅 —— 与待办卡的 `overdueReceivable`（含金额）重复。

### C3 员工：合并三处（✅）

宫格「员工管理」(`staff/index`) 与「我的」里的「配送员管理」(`mine/index.wxml:122-164`)

### C4 资产调整单：取 **A —— 不设卡片**（✅）

**它是三合一**（`constant/AdjustType.java`）：

| 类型 | 文案 | 动什么 |
|---|---|---|
| `BARREL_GRANT` / `BARREL_REVOKE` | 补录 / 撤销桶权益 | 桶 |
| `OVER_ADJUST` | 订正欠桶 | 桶（欠桶） |
| `DEPOSIT_GRANT` / `DEPOSIT_DEDUCT` | 补录 / 扣减押金 | **押金** |
| `TICKET_GRANT` / `TICKET_DEDUCT` | 补录 / 扣减水票 | **水票** |

**桶只占三分之一** ⇒ 塞进「桶」组会让组名名不副实（同 P3 的判据：别把不相关的往里塞）。

另两条已核实事实：
1. **全站台账本来就能跑**：`adjust/index.wxml:12` 自己写着「本站全部调整单 · 共 N 张」，
   `listAdjustments` 不带 `customerId` 即返回全站 —— 缺的只是入口。
2. **必须锚定客户**：`AdjustmentCreateDTO.customerId` 必填，新建表单里"商品"是表单内 picker；
   `adjust/index.js:117-121` 在无 `customerId` 时点「新建」直接提示
   「请从客户详情页进入后再新建调整」。所以"先选商品、再挑客户"这条路**现在不存在**。

**落法（A）**：不新增卡片；「桶」组页签里放一张**只读的"最近人工调整"小结卡**，
点进去看全站台账（`adjust/index` 不带参数即可）。新建仍从客户画像进。
