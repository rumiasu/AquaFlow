# 押金「收款方式」的口径 · 线上建议与线下风险（已拍板）

> **本文件写给**：做「客户下单时怎么收押金」这件事的工程师。
> 它只回答一件事：**第一单要收押金时，系统该给客户什么建议、选了线下要提示什么。**
>
> 状态：**已拍板（2026-09-27）**，正本登记在 `docs/design/16-范围决策与实施路线图.md` §8。
> 相关但不同的一件事：**退**押金的实际交付见 `docs/design/35-退押金实际交付-决策件.md`。

---

## 1. 产品原话与拆解

> 「5 客户下单的话，建议**第一单押金单走线上**吧，**弹个建议**。**线下的提示风险，系统无法检测，产生纠纷时自负**。」

三句话 = 三条规则：

| # | 规则 | 落点 |
|---|---|---|
| 1 | **第一单**（要收押金的单）**建议走线上** | 下单页的「首次资产/押金告知」弹窗（契约 A2）里加一句建议 |
| 2 | 是**建议**，不是硬拦 | 客户仍可选现金；**不许**把线下选项藏起来或置灰 |
| 3 | 选线下 → **提示风险 + 责任归属** | 选了现金且本次含押金时，页面上一行风险提示 |

## 2. 为什么这是"建议"而不是"规定"（本仓已有的三条事实）

1. **线上渠道在生产上还没接**（`app.payment.mock-wechat-pay` 生产关闭，真实微信支付未接入）——
   把线上做成唯一路径，等于**新客户第一单直接下不出来**（AGENTS §1.1：
   「新客户下不了第一单」已有定论，是**渠道未接入的部署状态**，不是判据缺陷）。
   所以建议的**触发条件必须包含"线上渠道当前可用"**：渠道不可用时不能建议一条走不通的路。
2. **现金（货到付款）是按客户逐户开通的经营权限**，没开通的客户**整项不下发**
   （`PayMethod.availableMethods`，2026-09-26 产品裁定）。所以"选了线下"这件事只在
   该客户**已开通**货到付款时才可能发生 —— 风险提示的受众因此是确定的。
3. **押金必须能被系统核对**：线下现金押金是"站长手工记一笔"，
   系统**没有任何手段核实钱是否真的收了**（这正是产品说的"系统无法检测"）。
   线上支付有渠道流水可对，纠纷时能自证。

## 3. 文案（由**服务端**下发，前端原样展示）

判据来源：AGENTS §6「展示文案由后端下发，前端禁止自带映射表」 + §6「面向顾客的文案禁止出现开发词」。
所以这句话**不写在小程序里**，由 `PaymentServiceImpl.quote` 随报价一起下发：

| 字段 | 何时有值 | 文案（**建议稿，实现时以代码为准**） |
|---|---|---|
| `depositOnlineAdvice` | 本次要收押金 **且** 线上渠道可用 | 「这单要先付桶押金。建议用**微信支付**：钱有渠道流水，退押金时也有据可查；现金押金只能由水站手工登记，过后对不上账时不好说清。」 |
| `depositOfflineRiskNote` | 本次要收押金 **且** 客户选了现金 | 「现金押金由水站当面收取并手工登记，**系统无法核实这笔钱是否已收到**。请向水站索取收据；发生纠纷时需双方自行协商解决。」 |

⚠️ 两条都**不许**出现开发词（`接口`/`后端`/`字段`/`落库`/`端点`…），也不许写"系统错误"这类
把经营口径说成故障的话（AGENTS §6 的历史事故：排障提示渲染给了站长）。

## 4. 拍板后改哪里（施工清单）

| # | 落点 | 动作 |
|---|---|---|
| 1 | `PaymentServiceImpl.quote` | 报价响应新增 `depositOnlineAdvice` / `depositOfflineRiskNote`；判据用**已有的** `wechatPayEnabled` 与 `depositAmount > 0`，**不新造渠道开关** |
| 2 | `miniapp-user/pages/order/create.js` | 把两个字段放进 `assetNotice`（契约 A2 的那个弹窗数据），前端**不自己拼文案** |
| 3 | `miniapp-user/pages/order/create.wxml` | A2 弹窗里渲染建议；选中现金且含押金时渲染风险提示行 |
| 4 | 用例 | ① 渠道可用 + 含押金 ⇒ 两条文案都下发；② 渠道不可用 ⇒ **不给线上建议**（不能建议一条走不通的路）；③ 不含押金 ⇒ 两条都不下发；④ 两条文案都不含星号与开发词 |
| 5 | `docs/design/16` §8 | 登记本裁定 |

## 5. 未验证 / 边界

- **"第一单"的判据沿用既有的 `firstStationAsset`**（服务端 `AssetService`），
  **没有**新造一个"是不是第一单"的判断 —— 但那一条判的是"客户在本站还没有桶权益"，
  与"这一单要收押金"（`depositAmount > 0`）**不是同一个条件**：
  老客户在别的水种上仍可能产生新押金。**实现取的是 `depositAmount > 0`**
  （"要不要收押金"才是客户真正要做的选择），这一点与产品原话的"第一单"**有偏差**，
  已在 `docs/design/16` §8 记为**待确认**。
- **没有验证真机上客户会不会读这句建议**（文案效果要真机反馈）。
- **线下押金没有收据号字段**：文案里说"请向水站索取收据"，但系统**不记录收据号**。
  若产品要"线下押金也要有凭据号"，那是 `deposit_record` 加一列的事，本文不做。
