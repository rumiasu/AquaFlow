# 多会话并行推进任务包（配合《项目健康度台账》）

> **本文件写给**：被指派执行某个任务包（WP）的会话/工程师，以及负责合并的集成者。
> **一句话**：把台账 §4 的 36 条问题切成**文件写权互不重叠**的任务包，让多个会话能同时开工而不互相踩。
> **上游正本**：[`项目健康度台账.md`](./项目健康度台账.md)（问题编号 `F-xx` 与验收判据都以它为准）。
> **状态**：2026-09-30 首版。**假设并发度 4–6 个会话**；波次可调。

## 0. 为什么不能"一条问题一个会话"

真正会打架的不是"问题"，是**文件**。本仓有几处天然耦合，必须先看清：

| 耦合点 | 后果 |
|---|---|
| `OrderWorkflowServiceImpl.java` / `PaymentServiceImpl.java` | F-00、F-05、F-11、F-32 全落在这一两个文件上 ⇒ **必须同一个包** |
| `LayeringArchitectureTest.java` | F-01（正则）与 F-12（动词表）同一个文件 ⇒ 同一个包 |
| `ci.yml` + `verify.sh` + `verify-local.js` | 本仓有 `check-gate-parity.js` 强制**三处门禁清单一致** ⇒ 加门禁必须一次改齐三处 |
| `AbstractIntegrationTest.java` | 测试基类，被大量用例依赖 ⇒ **串行资源**，只给一个包 |
| `docs/audit/项目健康度台账.md` | 所有人都会想改它 ⇒ **只由集成者写**，执行包一律"汇报不改" |
| `docs/audit/删除登记表.md` | 删除类改动要登记 ⇒ 执行包把六项报备写进汇报，集成者登记 |
| `docs/api/01-REST-API参考.md` | 被 `check-api-doc.js` 双向对账（含**类名+方法名**）⇒ **改 Controller 类名/拆类会打红它** |

## 1. 协调规则（每个包开工前必须接受）

### 1.1 工作区与构建

1. **同一个工作区，不要建 git worktree。** 本仓已知坑：worktree 只含 HEAD、**不含未提交文件**，
   而且没有 `application-local.yml`（必需变量要从环境变量传，缺了 `RequiredConfigChecker` 拒启）。
   多包之间的改动也需要互相可见。
2. **构建串行**：`GRADLE_USER_HOME='D:\backend\project\AquaFlow\.gradlehome'` + 各自
   `--no-daemon --project-cache-dir .gradle_wp<编号>`。**同一时刻只允许一个会话跑 Gradle**
   （否则撞 `fileHashes.lock`）。建议：各自写代码，构建/测试到一个约定窗口串行跑。
3. **集成测试必须用独立库**：把 `DB_URL` 指向 `aquaflow_test_wp<编号>`
   （`AbstractIntegrationTest` 只要求库名含 `test`，`aquaflow_test_wp1` 能过护栏）。
   **两个会话同时跑测试会互相 TRUNCATE 同一个库**，表现为"我的用例莫名红了"。
4. **不要 commit / push**，改动留在工作区（仓库 §7）。也不要 `git add -A`。

### 1.2 交互纪律

5. **只碰自己包的文件**（§2 的写权表）。需要别人包的文件时，**不要改**，写进汇报让集成者协调。
6. **不要改 `docs/audit/项目健康度台账.md`** —— 报状态，集成者统一回填。
7. **不要动**：`archive/**`、`AquaFlow-backend/build/**`、`out/`、`.gradle*`、`backup/`、生成物、
   `project.private.config.json`、`application-local.yml`。
8. **定位用符号名，不要用台账里的行号**：台账的行号是 2026-09-30 的快照，
   **任何包一改文件，行号就漂**。一律用 `grep` / `code_search` 按方法名、SQL 片段定位，
   再在心里核对"是不是台账描述的那一处"。
9. **改代码必须同步改注释**（注释与代码不符比没有注释更危险）；**作废的 javadoc 要删掉，不许悬空**。
10. **删任何代码/端点/文件前给六项报备**（核实到哪一步 / 证据 / 原来为什么存在 / 删掉会怎样 /
    推荐删或留 + 理由 / 风险等级），写进汇报；登记由集成者做。
11. **悬置的产品决定当场落 `TODO(待拍板)`**，写明"问什么 / 两种选择的差别 / 拍板后改哪里"，
    并在唯一正本登记（同一问题只留一处正本）。
12. **诚实汇报**：跑不了就写"没跑 + 为什么"。本仓铁律：**只判退出码不算判过**；
    "沙箱/环境拿不到子进程输出"是环境限制，不是测试失败，更不许写成"通过"。

## 3. 开工前的 5 分钟核对（每个包都要做）

1. `git status --short` 看清工作区现状，**确认自己要改的文件现在长什么样**（可能有别的包已动过相邻代码）。
2. 按 §4 里自己那个包的**证据行**用符号名重新定位一次，确认问题**现在仍然存在**（可能已被别人顺手修掉）。
3. 确认自己**没有**踩到别人的写权（§2）。
4. 想清楚**验收判据**：这个包做完，什么命令/什么用例能证明它好了；写进汇报。

## 7. 这份方案的已知边界

1. **写权表是按 2026-09-30 的文件状态划的**；如果某个包先合并、动了别人包旁边的代码，
   后面的包必须**重新核对写权**（尤其 WP10 会大量移动 `DeliveryController` 的代码）。
2. **并发度按 4–6 估算**；实际能开几个取决于机器（Gradle 构建串行是硬约束，
   同一台机器上 6 个会话同时编译只会互相等锁）。
3. **本机沙箱可能起不了子进程**（本轮实测 shell 完全不可用）⇒
   各包很可能**只能改代码、不能跑验证**。这种情况下 §6 的"验证证据"要如实写"没跑"，
   由集成者在能跑的环境集中跑一遍再回填分数 —— **不要把"没跑"当成"通过"**。
4. 本方案**不创造新的产品决定**；出现的悬置项一律走 `TODO(待拍板)` 进唯一正本。
