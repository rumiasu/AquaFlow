## 1. 目的与范围

本文规定水站**营业状态（软状态）**与**站长公告**的取值、提示口径、写入口与页面落点。

范围：营业状态**只做提示、不做任何下单校验**；公告支持草稿与下架两态，站长端管理列表必须能管理未发布的那部分。**不在范围内**：硬状态 `station.status` 的语义、状态定时恢复与公告置顶 / 定时发布（后三项见 §7）。

## 2. 设计口径

| # | 决定 | 判据与说明 |
|---|---|---|
| 1 | **软状态，一律不阻断下单** | 顾客照常下单，只是会看到提示：页面横幅 + 下单响应 `warnings`。**不做任何下单校验。** |
| 2 | 状态由**站长自己设**，随时可改 | 无审批、无平台干预；站别取自 `AuthContext.requireStationId()`，不信任请求参数 |
| 3 | 站长能写**一句留言** | 状态的具体说明（如"今天休息，明早 8 点正常送"），**≤100 字**（与 `station.status_note varchar(100)` 对齐），原样展示给顾客；空白串归一为 `NULL` |
| 4 | 站长能**发公告** | 本站公告（标题 + 内容），支持草稿 / 下架；顾客端只读已发布的 |
| 5 | 文案由**后端下发** | ⚠️ 前端不写状态映射表（本仓历史事故：两端各写一套 1/2/3 映射导致新客下单 100% 失败） |

### 2.1 ⚠️ 与 `station.status`（硬状态）的分界，谁都不能混

| | `station.status`（硬状态，旧） | `station.operating_status`（软状态） |
|---|---|---|
| 取值 | 1 营业 / 2 停业 | 1 正常运营 / 2 休息中 / 3 配送延迟 / 4 暂停配送可预约 |
| 对下单的影响 | **直接拒绝**（`OrderServiceImpl` 抛"水站不存在或已停业"） | **不阻断**，只提示 |
| 对选站列表 | `status = 2` 不出现在 `/api/stations/public` | 仍出现在列表里（带状态文案） |
| 判据 | "这家站没了" | "这家站现在什么情况" |

> ⚠️ **唯一红线**：把"休息中"塞进 `station.status` 就等于把"休息"实现成"关张"，会真的挡住客户下单。用例 `StationOperatingStatusIntegrationTest.restingDoesNotBlockOrderButWarns` 锁住了它。

### 2.2 状态取值与提示文案

| 值 | 文案 | 典型场景 |
|---|---|---|
| 1 | 正常运营 | 默认 |
| 2 | 休息中 | 打烊 / 午休 |
| 3 | 配送延迟 | 爆单 / 天气 / 人手不足 |
| 4 | 暂停配送，可预约 | 今天不送了，订单明天统一处理 |

- 文案唯一来源：`constant/StationOperatingStatus`（`textOf` / `customerHint` / `isValid`）；值为 1 时 `customerHint` 返回 `null`，页面据此不展示横幅，2 / 3 / 4 返回同一条提示模板。
- 加状态只需在 `StationOperatingStatus` 加常量 + 文案 + 前端 `statusOptions` 一项（前端只提交 value）。候选（暂未加）：`5 仅配送预约单`、`6 暂停营业（长期）`——后者其实应当用硬状态 `status = 2`。

### 2.3 ⚠️ 公告的可见性约束

- ⚠️ **管理列表必须含草稿与已下架**：`NoticeMapper.listForStation(stationId)` 的 SQL **不带发布状态过滤**，只按 `station_id` 过滤。列表若带上 `status = 1`（旧 `listByStationId` 的写法），会出现两个"界面说了、系统没做到"的缺陷：① 保存草稿后提示成功、**列表里却没有它**（界面文案还写着"草稿只有你自己可见"）；② 点「下架」后公告**从列表消失、再也点不回来**（无法重新上架）。即草稿 / 下架这两个状态在界面上等于不存在。`notice.status` = `0 下架`（草稿，只有本站站长可见）/ `1 发布`（顾客端与员工端都能读）。
- ⚠️ **状态文案必须由后端下发**：唯一真相源 `constant/NoticeStatus`（`textOf` / `isPublished`）+ `Notice.getStatusText()`；页面只渲染后端下发的 `statusText`。前端写 `status === 1 ? '已发布' : '草稿'` 与 §2 第 5 条冲突（映射表两处维护必然分叉），`status == 1` 只许出现在 `isPublished` 一处。
- ⚠️ **`GET /api/notices`（顾客端列表）不做站过滤（未修，见 §7）**：走 `listPublished()`（`where status = 1`，**不带站点条件**），任何顾客能看到**所有水站**的已发布公告。按 id 读**他站草稿**那条已修：详情端点对员工校验同站、对顾客/未登录只放行 `status = 1`。

### 2.4 顾客提示模板

值为 2 / 3 / 4 时 `customerHint` 返回同一条模板（页面横幅与下单 `warnings` 共用）：

> 水站当前：⟨文案⟩ · ⟨留言⟩（仍可下单，站长会按上面的说明安排配送）

⚠️ 括号里的**"仍可下单"是必需内容**，不是修饰：缺了它客户会误以为下不了单而放弃。

## 3. 数据模型（v32）

```sql
ALTER TABLE station
  ADD COLUMN operating_status   tinyint  NOT NULL DEFAULT 1,  -- 软状态，不阻断下单
  ADD COLUMN status_note        varchar(100) NULL,            -- 站长留言（≤100 字）
  ADD COLUMN status_update_time datetime NULL;                -- 最近修改时间
```

- 三列全部**可空或带默认值**：存量水站自动为 `1 正常运营`（前端零感知）。
- ⚠️ **不要**用 `StationMapper.update`（它会整行覆盖 `name` / `phone` / `address` / `status`）来改营业状态，用专用的 `updateOperatingStatus`（只改这三列并校验 affected 行数）；`affected == 0` 必须报"保存失败：水站不存在"，不能静默成功。

## 4. 接口与权限

| 方法 | 路径 | 角色 | 站点归属校验 | 说明 |
|---|---|---|---|---|
| GET | `/api/manager/station-status` | 站长 | `@RequireRole` + `@RequireStation` | 读本站状态（含 `statusText` / `note` / `customerHint`） |
| PUT | `/api/manager/station-status` | 站长 | 同上，**只改登录站长所属站** | 设状态 + 留言；校验取值与长度 |
| GET | `/api/stations/{id}/status` | **公开（免登录）** | 按路径 id | 顾客端横幅用；含 `hardStatus` 便于前端区分软硬状态 |
| GET | `/api/stations/public` | 公开 | — | 选站列表，实体自动带出三个新字段 |
| GET | `/api/notices` | 公开 | — | 顾客端/员工端读已发布公告（**跨站可见性见 §2.3**） |
| GET | `/api/notices/{id}` | 公开 | 员工校验同站；顾客只放行已发布 | 公告详情 |
| GET | `/api/notices/all` | 站长 | `@RequireRole` + `@RequireStation` | 管理列表，**含草稿与已下架** |
| POST / PUT / DELETE | `/api/notices`、`/api/notices/{id}` | 站长 | 先查归属，禁止改/删他站公告 | 发布 / 编辑 / 删除；新建时 `station_id` 强制绑定登录站 |

- ⚠️ 公开端点必须在 `WebMvcConfig` 白名单里（`/api/stations/{id}/status`）—— 漏配会得到 401，而不是业务错误。
- 下单响应：`OrderServiceImpl` 在 `warnings` 末尾追加营业状态提示（客户可能没注意到横幅）。

## 5. 前端落点

**员工端**：页面 `pages/station-mgmt/station-status/index`，上半 = 营业状态（4 选 1 + 留言 + 保存 + **顾客视角预览**），下半 = 本站公告（列表 + 发布/编辑/上下架/删除，**草稿态可见**）；入口是卡片墙「营业状态与公告」卡片。

**顾客端**

- `pages/shop/index`（商城）与 `pages/order/create`（下单页）：顶部**黄色横幅**显示 `customerHint`，**不隐藏商品、不禁用下单按钮**；⚠️ 接口失败时静默（不能因为提示失败让人买不了水）。
- 下单成功后：`proceedToPayment` 先展示 `warnings`（营业状态 / 欠桶 / 缺货），点「知道了」再进支付或成功页 —— 前端此前从未读过 `warnings`，等于后端白提醒。

## 6. 验收用例

`StationOperatingStatusIntegrationTest`：

| 用例 | 锁住的判据 |
|---|---|
| `managerCanSetOperatingStatusAndCustomerCanSeeIt` | 状态与留言落库、回读、公开端点可见、顾客提示含留言；**非法取值与超长留言被拒** |
| `restingDoesNotBlockOrderButWarns` | **休息中不阻断下单**（订单真的落库）但 `warnings` 带留言 —— 软状态红线 |
| `hardStatusStillBlocksOrder` | **硬状态停业仍然阻断下单** —— 软状态不得削弱旧开关 |

公告侧：管理列表同时返回发布态与草稿态两种记录，两条 `statusText` 都由后端下发（`NoticeMapper.listForStation` + `NoticeStatus`）。

## 7. 待确认事项

| 待确认内容 | 需要的验证手段 | 影响 |
|---|---|---|
| 状态是否要在**客户端首页 / 我的**也显示（目前只有商城 + 下单页） | 走查顾客端其余页面 | 提示覆盖面 |
| **状态定时恢复**（如"休息中"设到 18:00 自动回正常运营） | 需定时任务 + 落库设计 | 不补则站长忘改，客户会一直看到"休息中" |
| 顾客横幅显示"x 分钟前更新"（`statusUpdateTime` 已下发，前端尚未用） | 前端取用已有字段 | 纯展示 |
| 公告是否支持**置顶**与**定时发布**（当前只有发布 / 草稿两态） | 需产品拍板 + 迁移 | 涉及表结构与列表查询 |
| 顾客端 `GET /api/notices` 的跨站可见性（§2.3） | 属可见性口径，需产品决定 | 建议形态：加可选 `stationId`，SQL 改为 `status = 1 and (station_id = #{stationId} or station_id is null)`（`NULL` = 平台级公告），**详情端点必须一并处理**，否则按 id 仍能读到别站已发布公告 |
| 真机走查（新页面入口、客户端横幅、库存交互） | 微信开发者工具 + 真机 | 发布前必做 |
