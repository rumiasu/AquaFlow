# 两端体验与视觉改造方案

> 本文件写给：实施小程序改版的工程师/执行模型。职责：确定信息层级、视觉规则、页面改造顺序与验收方法。
> 2026-09-26，提案，可用于分批实施；不是已完成记录。依据当前工作区抽查，尚未在微信运行时做整端视觉验收。不把历史 Markdown 当当前行为。客户订水、配送员履约、站长经营三类任务分别设计。

## 1. 目标与当前判断

目标：顾客少思考即可订水；配送员看一眼知道送哪里、送什么、收多少空桶和钱；站长能处理经营事项而不必记住系统规则。美术服务于这些目标。

保留客户端现有米白底、深蓝主色、真实商品图和直接加减数量的方向。保留现有两端及角色划分、三站语义、按站隔离客户资产、服务端报价和能力判定。员工端采用同品牌色和排版规则，信息密度、字号与操作尺寸单独适配。

不进行全仓框架重写、不换组件库、不先做插画与动画。先完成代表页面，再按验证过的模式扩展；每批必须保留原入口与业务状态的可达性。

## 2. 统一的信息取舍规则

按“此刻要判断什么”排序，不按数据库有哪些字段排序。

| 层级 | 常显内容 | 处理方法 |
|---|---|---|
| 当前任务 | 地址、商品数量、真实支付/配送状态、本次实际应付、当前可执行动作 | 正文、清晰字号；不能靠打开帮助才知道 |
| 影响决定 | 新增押金、配送延迟、缺货、少回桶、未收款、跨站接单收益和风险 | 仅相关状态出现，但在动作前可见 |
| 复核依据 | 订单号、费用拆分、历史记录、完整规则、成本口径 | 明细/展开；保留可达入口 |
| 无助于当下操作 | 重复口号、恒常“温馨提示”、内部术语解释、反复展示相同数值 | 从默认视图移出；移除代码仍按仓库删除协议 |

“没有事项”与“数据没加载出来”必须不同。提醒区为空不等于相关功能消失：完整功能目录始终有入口。待办总数不简单相加不同口径/可能重叠的集合；同一事项在摘要和列表出现时说明是同一批，不伪造新的总数。把服务端未知待办折叠起来也不能使其无法发现。

每个任务区域一个明确的主动作；打电话、导航是辅助动作，保留文字。正常操作尽量直接执行；取消、退款、跨站资产确认保留必要确认。一个确认说明后果并让流程继续，避免连续多个“知道了”。

## 3. 客户端：买水与等待配送

保留底栏“订水 / 订单 / 我的”。不增加会员、积分、营销频道。

### 订水首页

顺序：水站名与营业状态 → 收货地址 → 当前订单/待支付提示（有才显示）→ 再买上次/常用水 → 商品列表 → 桶与押金入口。压缩问候语和装饰头图，不占首屏主要空间。选站与选地址保留现有业务顺序，不能因为排版调整自动切站。

商品行只放：真实图、商品名称/必要规格、水价、数量操作；与本次购买有关的押金提示一行说明。详细桶账户计算不放在商品行。搜索与“更多商品”统一成一个可识别的目录入口，但原搜索功能保留。

首页价格是预估时明确写“商品小计”，主按钮“去结算”；配送费/楼层费等以服务端结算报价为准。不能把首页合计叫最终实付。“再买上次”先恢复选择，重新报价，不直接付款；商品下架、换站、票不足等仍走现有处理。

“待配送”不承诺“备货中”，“配送中”不承诺“正在赶来”或到达时间，除非有相应事实。多张进行中订单要给“查看全部”入口，不在首页堆多张大卡。

### 确认订单与结果

顺序：地址 → 商品/数量 → 支付方式 → 费用摘要 → 备注（可选）→ 底部主动作。

费用摘要显示水费、新增桶押金、配送费、楼层费及合计；金额来自同一次服务端报价。重要新增费用不能只藏在底栏的明细里；零费用可合并说明，不把未知当免费。水票全额结清时清楚显示扣几张与本次现金应付 0；不诱导混合补差价。

首次资产确认在同一层展示水站、押金、本单应付、资产按站使用的短说明及当前要求的阅读勾选，详细条款可展开；不再让顾客寻找灰色按钮的解锁条件。具体退款资格取服务端预览，不用“归还后立刻到账”等承诺。

下单后按真实状态显示“待付款 / 等待配送 / 配送中 / 已送达 / 已取消 / 退款状态”，保留支付与配送两个维度。有订单号后网络失败围绕原单恢复；页面不得再次回到可重复建单的初始状态。开发模拟支付继续走现有后端渠道，不能用视觉成功替代账务成功。

### 我的、桶和水票

我的：当前水站 → 水票/桶/押金入口 → 地址 → 账单与客服。把技术性资产词改为具体名称。

桶明细逐商品展示，区分已到手、配送中、欠还/暂存；不能把权益、占用、持有统一重命名成“手里有几个桶”。首页“押金余额”与退桶预览“本次可退”分开；欠桶的退桶限制按商品处理。水票页突出可用张数和适用商品/水站，批次成本与 FIFO 不给客户解释。退款进度必须可查。

## 4. 配送员：只管理自己眼前的履约

保留“配送 / 我的”底栏。站长仍可在配送页处理自己承接的单，角色权限不变。

配送列表顺序：小区/街道与楼栋门牌 → 楼层/电梯（知道才显示）→ 本单商品与数量 → “已付 / 需收 ¥X” → 联系/导航 → 接单或送达主动作。订单号次要显示，方便报问题；号码不必成为视觉主角，但可直接联系收货人。

混合商品必须准确：摘要例如“纯净水 2 桶，矿泉水 1 桶”，超长可“共 2 种商品 · 查看”，不能显示“第一款水 × 全单总桶数”。列表端缺商品明细时，先查现有投影能力，不能为每张卡新增一轮详情请求。瓶装水按真实单位显示。

完成配送仍是一页，分三段：本次送货摘要、实际收回空桶、本次收款。每行按服务端 `barrelItem/suggestedReturnQty` 给建议，用户只改实际数；少回时才出现差额与原因，正常回收无需读规则。新押金桶不要求本次回收，非桶装商品不画回桶控件。

收款时明确“已收齐 / 未收款”，不默认已收齐。不新增前端虚假的部分收款账；已有“部分收款交站长核对”提示保留，任何新金额字段必须先有后端记录能力。数据不全时指出“该单暂不能确认，联系站长处理”，不让配送员核对预留凭据或事务。

“配送遇到问题”提供现有真实操作入口，具体后果在选中动作后说明。常规配送不让配送员选择归属站、结算站、成本等经营信息。

## 5. 站长：工作台与经营管理

第一阶段维持现有三项底栏及角色行为。首页以站名/营业状态开头，常驻“水站管理”入口；其下先是待分配与需要审批的订单，再是“其他待处理”，抢单机会和外派追踪保留明确入口，按需展开。不是把所有业务揉成一个混合列表。

待处理只显示计数非零、加载失败或必须关注的条目；零条目从提醒区移到完整功能目录。不能截断后隐去剩余事项，使用“全部待处理（N 项）”；未接路由的服务端事项也有明确提示。红点沿用服务端级别判据，不能由页面擅自把所有计数非零都变红。

水站管理按“订单与客户 / 收款与工资 / 桶与库存 / 水站设置 / 经营数据”分组，以清楚行列表代替到处三列彩色宫格；同级入口不用每个附一串功能清单。保留可搜索/可找的完整入口，先迁移展示，不删除端点。我的页保留个人资料、工资（本人）、设置和水站摘要，员工列表可折叠；具体审批移入工作台前先证实待办到达链路。

经营数字按服务端真实口径命名：“订单收入”“未收款”“利润”等不能互相替代。利润只有覆盖的成本项齐全才报数；未计成本说明放紧邻数值的展开入口，不能用看起来很精确的数字冒充净利润。

跨站接单前应看清：送货地点/楼层、全部商品、本站可得收入、本店成本与计件、预计利润（算不出就说缺哪项）、需要承担的资产处理事项。客户资产仍归原站、外派双方确认保留；不可读取原站成本/客户画像。用户已定“接单确定收益，送达后结清”，**这是产品口径，不等于真实打款链已实现**。若当前读接口缺这些投影，单列后端任务给 DS；Luna 不在前端拼“订单金额减估计成本”的利润，也不提前实现真实转款。

## 6. 视觉规格

设计方向：“清楚、安静、可靠的送水服务”。保留暖底与深蓝，不用大面积品牌色、彩虹标签、渐变页头、厚阴影与装饰性仪表盘。视觉差异依靠留白、对齐、字号和状态，不靠每块换颜色。

| 项 | 建议实施值/规则 |
|---|---|
| 主色 | 延续 `#2E4A68`，主要按钮、选中项、链接使用；员工端同品牌色 |
| 背景 | 客户端 `#FAF7F0`、白色内容面；员工端可用更中性的浅底，内容面白色 |
| 文字 | 主要 `#2B2A26`；次要建议 `#66635B`，灰色占位不承载价格、地址、警告 |
| 状态色 | 绿=完成，琥珀=需关注，红=失败/危险动作；同时给文字，不靠颜色独立传意 |
| 字号 | 正文 28–30rpx；配送地址/现场数量 32–36rpx；辅助 24–26rpx；禁止用 20rpx 承载关键规则 |
| 间距 | 8rpx 基础步长，页面横向 32rpx，区块间 24rpx；缩空白先于缩字 |
| 控件 | 主按钮高 88–96rpx，员工现场操作可更大；数字加减目标至少 88rpx，图形可小 |
| 圆角 | 普通容器 16rpx；按钮 12–16rpx；胶囊只用于状态/筛选，不把所有东西做成药丸 |
| 卡片 | 有共同动作/语义的一组才包卡；卡内用分隔线，避免卡套卡 |
| 商品图/图标 | 商品图统一框和留白、保证标签可辨；复用现有可信素材。图标同线宽，员工端逐步去除表情符号，动作旁保留文字 |
| 屏幕适配 | 320/375/430 CSS 像素等效宽度、小程序大字体、长站名地址、键盘弹出；底栏/弹窗安全区不能挡主动作 |

先建立少量稳定样式：页面骨架、信息行、订单卡、主次按钮、状态提示、空/错/加载状态。两端是不同小程序包，可维护同规范的各自 token；不引入跨包运行时共享、不新造“万能业务组件”。共同组件不得承担计费、桶账、权限判断。

## 7. 文案规则及示例

一句事实 + 一个可做动作；服务端业务状态与拒绝原因在其源头修改，不在前端按中文字符串替换。前端静态标签可局部修改。保留清楚、礼貌的普通话，不把“专业化”改成粗糙口语。

| 当前表达 | 建议表达/条件 |
|---|---|
| 已享 N 个桶权益，无需再付押金 | 本次无需加收桶押金（仅服务端报价支持时） |
| 权益 N · 占用 M | 首页改“水桶与押金 ›”；数量明细在桶页分真实口径展示 |
| 可退押金 ¥X（实为账户余额） | 押金余额 ¥X；本次可退看退桶预览 |
| 其他待办 / 不在订单页里的 | 其他待处理；去掉关于页面分类的副标题 |
| 调解 | 配送遇到问题（入口）；下一级说明具体操作后果 |
| 地址没加载出来（内部原因） | 地址加载失败，重试；详细原因仅保留可理解且能行动的部分 |
| 首次下单·押金桶无需回桶 | 本单新押金桶无需回收；不能暗示用户此前没买过票 |
| 当前预留/凭据不足 | 本单备货不足，请联系站长；具体短缺按服务端提供展示 |
| 商品小计 + 配送费以结算页报价为准（首页） | 商品小计 ¥X；运费在结算时确认 |

说明用“归还空桶并经水站确认后可退押金”，避免暗示送水时普通回桶会自动把押金全退。部分收款、跨站确认、异常处置等影响钱货去向的文字不为追求短而删条件。

## 8. 分批实施与成本控制

| 批次 | 交付范围 | 执行者 | 验收闸门 |
|---|---|---|---|
| 1 代表页 | 客户首页、确认订单静态排版与样式；先完成首页再结算 | Luna，分两张任务卡 | 有真实渲染对照，所有原入口/状态保留；不动后端 |
| 2 配送现场 | 配送订单卡、完成页、现有字段的准确呈现 | Luna；缺字段清单交 DS | 首单/混合单/现金/少回桶实测，权限与回桶规则不退化 |
| 3 站长工作台 | 待办层级、完整管理入口、我的摘要 | Luna；待办/利润投影缺口由 DS | 非零事项不漏、0 与失败不同、经营入口可达 |
| 4 同风格扩展 | 更多商品、订单列表/详情/结果、桶水票、管理列表表单 | Luna 或免费模型，各次 2–3 页 | 复用已验模式，禁止各页自由再设计 |
| 5 真机收口 | 大字体、弱网、长文本、键盘、弹窗、回退和重复提交 | 人工路径 + GPT 复核证据 | 同一示例数据前后截图与可执行回归 |

GPT 负责规则/任务边界/关键 diff 验收；Luna 做有确定输入输出的页面改造；DS 仅处理新增或调整服务端投影、复杂资金与状态问题。免费模型适合静态文案清单、颜色残留清单、截图对照、入口核对；不给它连续业务改造。
