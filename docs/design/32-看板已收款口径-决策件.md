## 1. 更正：**算法没错，错的是名字**

我（agent）最初把这条写成"看板的数是错的"。**核对代码注释后要更正：设计口径是明确写过的** ——

`DashboardMapper.java:22-23` 的类注释：

> 营业额(grossAmount) = 未取消订单的应收合计；**已收款(paidAmount) 以 `payment_status=2` 为准**；
> 待收款(pendingAmount) = `payment_status=1 且未取消`。三者分开返回，前端不做二次推导。

**实现与这条注释完全一致**（`sum(case when payment_status = 2 then total_amount else 0 end)`）。
所以：

| 层面 | 判定 |
|---|---|
| 计算实现 | ✅ **按设计**（`payment_status=2` 就是"这单付过款"） |
| 类注释 | ✅ 写得清楚 |
| **界面上的中文名「已收款」** | ❌ **误导**：站长读它 = "本站收到了多少钱"，而设计说的是"已付款订单金额" |

**后果仍是实的**（实测的虚增与漏计不会因为"设计如此"而消失）：
接单站显示 ¥168 而它一条流水都没有；无订单购票的 ¥960 完全看不到。
**但修法因此收窄成一件小事：改文案。** 不需要动聚合。

## 2. 现在错在哪（一句话）

界面标签「已收款」被读成"本站收到的钱"，而它的口径是"**已付款订单的金额合计**"。
两者在**没有外派、也没有预售**时数值相同，所以一直没被看出来；
一旦发生外派（接单站虚增）或有在线购票（漏计），就会分叉。

## 3. 改成按 `payment_record` 聚合，会变成什么（实测）

| 站 | 现在看板「已收款」 | 按流水聚合 |
|---|---|---|
| 站1（归属站） | ¥1101.00 | **¥2229.00** |
| 站2（接单站） | ¥168.00 | **¥0.00** |

**合计**：现在两站之和 1269；流水全部之和 **2229** ⇒ 差额 960 = **无订单在线购票**（看板不统计它）。

## 4. 改成流水聚合前必须定的四件事（都有实测依据）

### 4.1 ✅ 已核实：按流水聚合**不会重复计入** —— 但前提要说清

实测水票单（如 order 134）：**一单只有一条流水**（流水 91，金额 12.00、状态 2），
**不是"买票 + 用票"各一条**。所以直接 `SUM(amount)` 安全。

| 支付方式 | 有流水的单 / 总单数 |
|---|---|
| 微信(1) | 48 / 106 |
| 现金(2) | 15 / 22 |
| 水票(3) | 2 / 5 |

> ⚠️ 但「有流水的单」远少于总单数，**这不是重复计入的反面证据，而是另一件事**：
> 未付款/未收款的单本来就不该有 PAID 流水。聚合时要**按 `status` 过滤**，不能不看。

### 4.2 「已收款」与「营业额」会变成两个不同的数（必须同时给口径说明）

- **营业额**按**结算站**（营收归谁）；
- **实收**按**流水站**（钱在谁手上）。

站里一外派，这两个数就不一样 —— 与报告 §9.2 已修的「报表 vs 订单列表」是**同一类问题**。
⇒ 若选改算法，**界面必须同时说明**："实收看钱在哪，营业额看单算谁的"。

### 4.3 退款怎么算（**必须一起定**）

现状：`payment_record` 里 **状态 3（已退款）1 笔、¥22**；负金额流水 **0 笔**（当天范围内）。

- **减掉** ⇒ 得到"净收"，但它与「营业额」的口径又缠在一起；
- **不减** ⇒ 收过的钱一直显示着，**站长看不出退过款**。

### 4.4 无订单购票算不算（当天 **26 笔 / ¥2064**，全站口径）

它是本站**真收到**的钱，但不对应任何订单：

- **算** ⇒ "已收款"含预售（客户买了票还没兑水）；
- **不算** ⇒ 与"本站实收"这个名字不符（钱明明收了）。

> 这一条影响最大：全站 2064 里它占大头。**建议单独给一个「水票预售」指标**，
> 而不是塞进"已收款"或干脆丢掉。

## 5. 我看的两条路（附推荐）

| | 方案 A · 改算法 | 方案 B · 改文案（推荐先做） |
|---|---|---|
| 动作 | `paidAmount` 改为按 `payment_record` 站别聚合（按 status 过滤） | 保留现算法，改名为「已付款订单金额」，并加一句"不等于本站收到的钱" |
| 改动面 | 一处 SQL + 两处文案 + 契约用例 | 一处文案 + 一处展示 |
| 解决什么 | 接单站不再虚增（168→0）；但仍**看不到**无订单购票 | 站长不再被误导（名字不再声称"收到"） |
| 遗留 | 退款/预售口径要一起定 | 指标本身仍不是"实收" |
| 代价 | 需要产品先定 4.3 / 4.4 | 最小、可立刻做 |

**我的建议：先做 B（当天可完成、纯文案、零账务风险），把 A 与 4.3/4.4 一起排到第三轮**
—— 因为 A 一旦动了聚合口径，就必须同时回答退款与预售两问，否则会从"名字错"变成"数错"。

## 8. ✅ 已拍板（2026-09-27，产品裁定 `1.b`）：**改名字，不改算法**

即 §5 的**方案 B**。落地内容与两处偏离说明：

| # | 落点 | 做了什么 |
|---|---|---|
| 1 | 后端 `DashboardServiceImpl` | 新增下发 `paidAmountNote`（与既有 `scopeNote` 同一做法：**文案属口径、由服务端下发**，前端原样展示） |
| 2 | 员工端 `dashboard/index.js` | `mk('paidAmount', '已收款', …)` → **`'订单已付款'`** |
| 3 | 员工端 `dashboard/index.wxml` | 指标卡下面加一行 `.scope-note` 渲染 `paidAmountNote` |
| 4 | 用例 `DashboardNoticeSearchFeedbackIntegrationTest` | 新增 `dashboardReportCarriesPaidAmountNote`：断言说明**必须存在**、必须点破「不等于本站收到的钱」、且不许带星号与开发词 |
| 5 | 算法 | **一个字都没动** —— `sum(case when payment_status = 2 then total_amount else 0 end)` 保持原样（§1 已核：它与 `DashboardMapper` 的设计口径逐字一致） |

**两处偏离 §6 建议的地方（都是有意，不是漏做）**：

1. **标签没用建议的「已付款订单金额」（7 字），用了「订单已付款」（5 字）** ——
   指标卡那一格是 22rpx 的三列网格，7 个字会换行挤掉下面的环比行。**口径的完整性由第 3 条那行说明承担**，
   所以判据是"**标签 + 说明合起来读不会误解**"，而不是"标签自己说全"。
   （用例锁的是**说明**必须存在且说清，没有锁标签字数 —— 版式会变，锁死了反而挡下次改版。）
2. **没有顺手做 §5 提到但归在方案 A 的「水票预售」单独指标** ——
   拍板的是 B，加新指标属于 A+ 的范围（§6 末段），不在本次裁定内。
   `paidAmountNote` 里用一句"客户先买票、还没兑水的钱也不在内"把这个缺口**如实告知**，
   这比默默漏计强，也比擅自新增一个指标稳妥。**

**没做的事（如实登记）**：§4.3 退款口径、§4.4 无订单购票口径**仍然没有被回答** ——
它们只在"改成方案 A（按流水聚合）"时才成为必答项；选了 B 之后它们不阻塞任何东西。
若将来要动算法，这两问必须**先答再动**（§5 的原话：否则会从"名字错"变成"数错"）。
