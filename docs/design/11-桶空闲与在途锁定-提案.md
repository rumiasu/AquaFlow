## 1. 目的与范围

本文固定**桶权益与「配送中」之间的抵扣口径**：哪些桶能顶新订单的需求、哪些不能，以及配套的欠桶台账口径。

**已实施**（现状以 `src/**` 为准）：

- 权益（= 已到手）**只在送达时入账**，下单时不提前给权益；
- 下单抵扣与退押金**只认权益**，「配送中」的桶不参与抵扣、也不可退；
- 欠桶**只提醒、不阻断**下单，站长端有只读欠桶台账。

**未实施**：把记账时点前移的方案（下单即入账、或押金到账即入账），以及随之而来的「在途暂停」、恒等式扩项、取消回补权益、对账 E4/E5/E6 复核。本文保留这些方案的设计推导供将来升级复用；**未同步改造这些下游之前，不得单独改动入账时点**。

## 2. 设计口径（逐条可判定）

### 2.1 粒度：一律按 `(customer_id, station_id, product_id)`

- 桶型/品类**不可混算**：19L 的空闲桶**不能**顶 18.9L 的需求，不同品牌、不同规格各自成账。
- 凡「持有 / 配送中 / 空闲」的判断，**必须在同一个 `product_id` 内完成**；**禁止**用跨品类求和的总量做任何决策（总量只允许用于展示）。
- 反例（**必须拒绝**，用例 `BarrelAvailabilityIntegrationTest.differentBarrelTypesDoNotOffset`）：19L 空闲 2、订单要 18.9L 三桶 → 必须买 **3** 个 18.9L 桶权益。

### 2.2 四个概念与取值

| 概念 | 含义 | 落库 |
|---|---|---|
| **权益 right** | 客户**已到手**的该桶型桶数 | `customer_barrel_lot.remain_qty` 汇总 → `customer_barrel_asset.quantity` |
| **配送中 pending** | 已买下、尚未送达的部分（= 权益的锁定标记） | `customer_barrel_in_transit` 中 `status = 'PENDING'` |
| **持有 held** | 权益 + 配送中 | 派生，**仅展示**（"买了就是你的"） |
| **占用 occupied** | 权益 + over（`customer_barrel_over` 可为负 = 水站暂存） | 派生，**还桶上限**，**不含配送中** |

- 四者一律按 `(customer_id, station_id, product_id)` 取值。

- **配送中只计 `PENDING`**：`DELIVERED` 表示桶已送到顾客手上，一并计入会把已收到的桶误判成还在路上，界面出现「持有 2 个，配送中 2 个」的重复计数（用例 `BarrelAvailabilityIntegrationTest.heldIncludesInTransitButOccupiedDoesNot`）。
- 恒等式 `占用 = 权益 + over`；同一 `product_id` 内 `0 <= 配送中 <= 权益`，越界按数据异常处理，不夹取。

### 2.3 硬约束（⚠️ 破坏任一条都会产生资金敞口或假告警）

1. ⚠️ **下单抵扣与退押金只认权益**：配送中的桶**在订单结束前不得参与任何抵扣**。
   - 下单侧 `OrderServiceImpl.createOrder`：`shortage = max(0, needed − 权益)`，**逐品类**；押金 = Σ `shortage × 本站押金单价`（`util/PriceUtil.calcDeposit`）。
   - 报价侧 `PaymentServiceImpl.quote` 必须与下单侧**同一口径**（用例见 §6：报价 `totalAmount` 必须等于下单 `total_amount`）。
   - 顾客端下单页用后端下发的 `assetQty` 算「我还差几个桶」；`assetQty` 必须保持「权益（已到手）」语义，不得改成持有数。
   - ⚠️ **三处口径不许单改一处**：任一处多减（或多加）一个 `pending`，就会重演"报价一个价、下单另一个价"（三处不一致是历史事故）。
2. ⚠️ **还桶上限 = 占用（权益 + over），绝不能用持有（权益 + 配送中）**。把配送中算进上限 = 允许顾客退掉还没送到手上的桶，直接冲穿桶账（`BarrelLedgerService.returnEmpty` 与 `previewReturn` 都以占用校验；占用 ≥ 0 恒成立，故 `over >= −权益` 自动满足，无需 clamp）。
3. ⚠️ **退桶/退押金上限 = 权益**（`BarrelLedgerService.consumeLots`：`qty > rightQty` 即拒）。退款金额 = Σ `qty × lot.unit_price`，**与 over 完全无关**（over < 0 不多退一分钱，也不阻止退款）。
4. ⚠️ **权益入账时点不得单独前移**：权益的唯一写入口是 `BarrelLedgerService.createLot`，送达结算（`applyDelivery`）既建批次又把配送中记录置 `DELIVERED`（**不删除**）。**漏改任何一处下游都会让顾客拿在途的桶退押金/还桶**，连带改造清单见 §2.4。
5. ⚠️ **权益不会凭空出现或消失**：取消订单之所以不需要"回补权益"，正因为权益本来就没在下单时入账；任何权益提前入账方案都必须同时补齐取消回补（`refundOrder` 是取消的单一编排入口，历史上出过"钱货分家"）。
6. ⚠️ **排除配送中的理由不能挪走**：原 `needed − held − pending` 的写法（防"连点两次下单各算一次 shortage"）已被有意撤销，代价是**连点两次下单会各收一份桶押金**（客户多买桶权益）。因此下单幂等键必须继续生效（`OrderServiceImpl` 强制查 `idempotencyKey`，缺失时服务端生成 UUID，使任何请求都强制幂等），前端也必须防连点。若将来恢复"配送中抵扣"，必须同时改报价侧与下单页，否则三处又会打架。

### 2.4 提案部分的设计推导：与现状的差异

| 位置 | 现状（已实施） | 提案（权益提前入账） |
|---|---|---|
| `BarrelLedgerService.applyDelivery` | 送达才 `createLot` | 下单/押金到账即入账；送达不再建批次 |
| 下单 / 报价两处 | 均为 `needed − 权益` | 改为 `needed − (权益 − 在途)`，两侧仍须同口径 |
| 取消订单 | 删在途行即可（权益没入账） | 必须回补权益（新写路径，需幂等 + CAS） |
| 还桶上限 | `占用 = 权益 + over` | `空闲 + over` |
| 对账 E4 / E5 | E4 判 `over < −权益`；E5 用 `status = 'DELIVERED'` 计数 | E4 改判 `over < −(权益 − 在途)`；E5 因 `DELIVERED` 语义变化须同步复核 |
| over 结算公式 | `Δover = 送达 − 回收 − 本单新购权益` | 同式（在途解锁数 ≡ 本单新购权益数，数值相同，**不必改**） |
| 存量迁移 | 无 | 有 `PENDING` 行时必须补建批次（否则那批桶"没有权益"，客户凭空少桶）并保留锁定状态；`PENDING = 0` 时切换零风险 |
| 前端上限 | 退押金受批次（= 已到手权益）上限约束 | 8 处把权益当上限的计算都要减在途，否则顾客能拿在途的桶退押金/还桶 |

**收益与代价**：把记账时点绑到押金到账，可让对账 E6（押金账户余额 ≥ 权益可退金额）**结构性恒平**，并消掉"没付钱却可退押金"的窗口——现金单从**下单**到**确认收款**这段窗口不复存在。代价是客户首次/加订要多掏押金，且欠桶只会在"该回收的空桶没收回"时产生（与"配送员回收失败才标记"的设想一致）。

### 2.5 两条路径的取舍

| 规则 | 路径 A（改账本，权益下单即入账） | 路径 B（只改计算 + 展示，**已实施**） |
|---|---|---|
| 可作为抵扣的部分 | `持有(含配送中) − 锁定` | `权益(= 已到手)` —— 两者**恒等** |
| 配送中不可抵扣 / 不可退押金 | 需新增「空闲上限」校验 | `needed − 权益` 天然不含配送中；退押金受批次（= 已到手权益）上限约束 ✅ |
| 取消订单 | 需新增「回补权益」写路径 | 不需要：权益本来就没入账 ✅ |
| 对账 E4 / E5 / E6、存量迁移 | `DELIVERED` 语义变了必须改；有 `PENDING` 行就得补建批次（否则那批桶"没有权益"，客户凭空少桶） | 两者都不动 ✅ |
| 风险面 | 核心账本 + 取消 + 退款 + 对账 + 迁移 | 2 个公式 + 3 处展示 |

→ **路径 B 用更小的改动换来同样的对外行为**；差别只在账上「权益」这个词的时点，对客户与站长可见的行为一致。将来确实需要「买下即权益」的账务语义（例如按已售桶数统计负债）再升级，届时 B 的公式与用例可直接复用。

## 3. 数据模型（只写设计理由）

- `customer_barrel_lot.remain_qty` 是**权益真相源**，`customer_barrel_asset.quantity` 只是派生汇总。批次表承担"押金条"职责：单价快照决定退桶能退多少钱，所以下单缺桶押金必须取**本站押金**并快照进 `customer_barrel_in_transit.unit_price`，不能在退桶时回读当前价。
- `customer_barrel_in_transit` 是「配送中」的**天然载体**（一行 = 一单在一个桶型上的数量），不必新建表。状态取 `PENDING`（配送中）/ `DELIVERED`（已送达，**合法终态，不是待清理的脏数据**）/ `CANCELLED`。
- `customer_barrel_over` 新增列 `owed_since datetime NULL`（欠桶起始时间）：欠桶是 (客户, 水站, 桶型) 维度上的**持续状态**而非事件，天数只能由这一列算；改用异常单事件表承载天数会算错（同一笔欠桶被反复计数）。
- 表结构与列定义见 `sql/schema.sql`，迁移清单见 `sql/README.md`。

## 4. 接口与权限

| 方法 | 路径 | 角色 | 站点归属校验 | 说明 |
|---|---|---|---|---|
| GET | `/api/manager/owed-barrels` | 站长 | 站别取自 `AuthContext` | 欠桶台账（**只读**）；按欠桶天数倒序，支持 `minDays` 过滤；返回客户 / 桶型 / 当前欠数 / 欠了几天 / 最近来源单 |
| POST | `/api/orders/create` | 顾客 | 归属按登录态 | 响应 `OrderCreateResult.warnings` 追加欠桶提醒（**只标红、不阻断**） |

- 欠桶的写入只随 `over` 变化发生，不提供任何手工写入口。
- 归属判据只认并集 `CustomerMapper.countCustomerOfStation`（绑定 ∪ 本站订单），不要用 `getStationCustomer`（后者按订单算，会把没下过单的新客户判成"不属于本站"）。

## 5. 前端落点

- 顾客端下单页：下单成功后必须先展示响应里的 `warnings`（营业状态 / 欠桶 / 缺货），点「知道了」再进支付或成功页 —— 此前前端从未读过 `warnings`，等于后端白提醒。
- 顾客端「按桶型」页：`heldTotalQty`（持有，含配送中）与 `occupiedQty`（占用，**还桶上限**）由后端分别下发，前端只渲染、不做加总；还桶数量输入的上限取 `occupiedQty`，不得用持有数。
- 站长端欠桶台账页：列表 = 当前欠桶额 + 欠桶天数 + 「查看来源异常单」下钻。

## 7. 欠桶台账口径（已实施，与记账时点方案正交）

- **判据：欠桶只提醒、不阻断**。原硬拦 `MAX_OWED_BUCKETS = 5` 已移除、**不要再加回**；`warnings` 每次都提醒（幂等命中路径同样下发），物理护栏不变（占用 = 权益 + over ≥ 0）。
- `owed_since` 的唯一维护点是 `CustomerBarrelOverMapper.syncOwedSince`：`over_qty` 从 ≤0 变为 >0 时写入当前时间、回到 ≤0 时清空、已是正数再增加时**保留原值**（同一笔欠桶的延续）。**该列只用于展示，不参与任何校验。**
- **明细复用现成的异常单**：取 `order_barrel_exception` 中 `discrepancy > 0`（少回空桶）的记录，可得哪个桶型（`adjustProductId`）、差几个（`discrepancy`）、哪一单（`order_id`）、哪天欠的（`created_at`）、处理到哪一步（`status` / `staffNote`），因此**不需要**新建欠桶事件表。
- ⚠️ **两个数不可相加**（否则界面上的欠桶数与下钻明细永远对不上）：
  1. **「当前欠 N 个」以 `customer_barrel_over.over_qty` 为准**（净额，已被回收/抵消过）；
  2. 异常单是**历史事件**，不会自动核销（`status` 只表示站长是否处理过）；
  3. 列表 = 当前欠桶额 + 天数 + 「查看来源异常单」下钻；
  4. `over` 已归零但异常单仍在的客户**不进列表**（只展示"当前仍欠"）；
  5. 不是所有异常单都产生欠桶（`RETURN_DAMAGE` 破损 / `CUSTOMER_REFUSE` 拒收 / `STATION_SHORTAGE` 缺货）→ **必须按 `discrepancy > 0` 过滤**。
- ⚠️ **护栏不可删**：「欠桶只是警告」指的是**不影响下单决策**，不是把上限拿掉——还桶上限仍必须是占用（权益 + over）；退桶（退押金）与欠桶互斥（欠着空桶先还清，按商品各算）。

## 8. 待确认事项

| 待确认内容 | 需要的验证手段 | 影响 |
|---|---|---|
| 未付款（现金单从下单到确认收款之间）的权益能否退押金 | 造现金单走完下单→送达→未收款，调退押金入口观察是否放行 | 放行则存在"下单→拿权益→退押金"的套现口子；不允许则要在退押金入口加"已付款"门槛 |
| 部分送达（订 3 送 2）如何解锁 | 造部分送达场景，查 `customer_barrel_in_transit` 行与批次数量 | 按实送解锁、余量继续锁，还是整单解锁；影响 `applyDelivery` 的取数 |
| 换水单（`shortage = 0`）是否要产生一条配送中记录 | 造换水单，查有无 `PENDING` 行 | 影响「配送中」文案是否名实相符 |
| 站长端要不要按品类多给一列"空闲"；「持有桶对应押金合计」是否把配送中算进去 | 与站长确认展示诉求 | 只影响展示层，不改口径；「可退」仍以批次为上限 |
| 同规格不同品牌（19L 农夫山泉 vs 19L 娃哈哈）算不算同一"桶型" | 查现行账本按 `product_id` 隔离的边界 | 现行默认**不通用**；若业务上通用，需要引入"桶型组"概念（新表/新列） |
| 连点两次下单各收一份桶押金，是否要在后端对"同客户同品类短时间重复下单"给提示 | 连点/并发下单实测 | 现状靠幂等键 + 前端防连点兜住；后端提示属增强 |
| 何时升级到"押金到账即权益"的账务语义 | 负债统计需求出现时评估 | 升级需一并改 §2.4 表各处 + 对账 E4/E5/E6 + 存量迁移 |
