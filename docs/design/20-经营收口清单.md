## 1. 单位客户月结与发票

### 1.1 现状：一个空壳 + 一堆挂空列

| 对象 | 实际状态 | 证据 |
|---|---|---|
| `orders.settlement_status`（1未结算/2已结算） | **挂空列**：全仓无 mapper / service / controller 读写 | `schema.sql:454`；`entity/Orders.java:222` |
| `orders.due_date`（应付款日期） | **同上** | `schema.sql:455`；`entity/Orders.java:225` |
| `company_info`（企业资料 + `payment_method` + `due_days`） | 只有一张表 + 一个 CRUD 控制器 + 一条"按客户隔离"的测试；**下单/收款/账单链路完全不消费它** | `CompanyInfoController`、`CompanyInfoMapper`、`TicketDepositNotificationIntegrationTest.companyInfoIsPerCustomer` |
| `customer.customer_type`（1个人/2企业） | 只在 VO 里出文案，无任何差异化规则 | `CustomerStationVO:71`、`CustomerProfileVO:85` |

**结论：企业账期在系统里目前是一张"填了资料但没有任何闭环"的表。**

⚠️ `AGENTS.md` 已记录过三次因"悬空注释/过期字段"导致的误用事故。**`settlement_status` / `due_date` 必须二选一：接上，或者删掉。挂空列比没有更危险**——下一个人会以为它在生效。

### 1.2 建议的拆法：先做"应收账款"，发票留到后面

| 层次 | 做什么 | 能不能自己做 |
|---|---|---|
| **A. 应收账款** | 挂账订单标记 + 账期（`due_date`）+ 待收款合计 + 逾期催收提醒 | **能**，且站长价值最直接 |
| **B. 对账单** | 按客户+期间生成账单明细（一个账期内的所有订单） | 能，工作量中等 |
| **C. 发票** | 开票信息、开票记录、对接税控/电子发票服务商 | **不建议现在做**（见 §1.4） |

**A 的落点**：`DashboardMapper` 已有"待收款"口径（`payment_status=1 且未取消`，见 `AGENTS.md` §1）——**具体 SQL 以其实现为准**。应收账款实质是"给待收款加上账期维度"，所以是**扩展而不是新建**。

**A 的关键判据：**
- 挂账订单的 `payment_status` 仍是 `1 待收款`，**不要发明新的支付状态值**（`AGENTS.md` §1："支付状态只前进、不倒滚"）。
- `settlement_status` 若要启用，语义应明确为"**该订单的应收是否已核销**"，且**只前进**（未结算 → 已结算），走 CAS。
- 账期到期不能自动改任何金额，只能**提醒**（对齐本仓"欠桶只提醒不阻断"的既有风格）。

### 1.3 账期存在哪：站级，不是客户级

> ⚠️ **2026-09-22 订正（v60）**：本节原文写的是 `company_info.due_days`（**客户级**）。
> v60 之后账期改为**站级** —— 存在 `customer_station_config.due_days`，判别式是
> 「同一个客户在 A 站是月结、在 B 站可以是现结」。
> **`company_info.due_days` 已不再被任何代码读取**（列还在，数据留着，效果等价于"账期一律清空、由站长重设"）。

`customer_station_config.due_days` 是**该客户在该站的默认账期**，
`orders.due_date` 是**订单级实际到期日**（下单时按账期推算并快照）。
锚点是**当月最后一天**（`MONTHLY` 月结）而不是下单日 —— 见 `ReceivableService.resolveDueDate`。

**判据：账期必须快照进订单**，理由与地址/金额快照同源——站长事后改客户账期，不能改到历史单的到期日。
（唯一例外是站长显式调用的「未结账单重算」，它只改 `payment_status=1` 且未取消的单，且逐单留痕。）

### 1.4 发票：现在只攒数据，不对接

对接电子发票需要企业资质 + 税控/服务商（航信、百望、诺诺等），测试阶段成本与收益不成比例。

**务实做法**：只在 `company_info` 上补开票信息字段（`invoice_title` 抬头 / `tax_no` 税号 / `invoice_email` / `invoice_type` 普票或专票），**把数据攒起来**，等真有企业客户要票再对接服务商。
**本轮未做**：加了字段却没有任何读写入口，正是本文 §6 点名的"挂空列"——攒数据也要有地方填。等有真实企业客户要票时，连 §4 的"开票信息"表单一起做。

### 1.5 实施状态：A 层已完成（2026-09-17）

> **状态：✅ A 层（应收账款）已完成**；B（对账单）与 C（发票）未做。
> **本轮没有新建迁移** —— `orders.settlement_status` 与 `orders.due_date` 两列本来就在（Phase 0 之前就有），
> 缺的只是读写路径。这也是"挂空列比没有更危险"的正面样本：接上它只花了一个 service + 一个 controller。

| 落点 | 实现 | 口径 |
|---|---|---|
| 账期快照 | `ReceivableService.resolveDueDate`（下单时调一次，写 `orders.due_date`） | **只有现金(货到付款)单才有应付日期**；微信即时到账、水票下单即视同已付，两者都不产生账期。未设账期 → `due_date` 为 NULL（存量水站行为不变） |
| 设置账期 | `PUT /api/manager/customers/{id}/credit-terms` → **`customer_station_config.due_days`**（v60 起为站级；站别取自 `AuthContext`，不接受请求参数） | 用**只改 `due_days`/`settlement_cycle` 两列**的专用 mapper。⚠️ 不要用 `CompanyInfoMapper.updateByCustomerId`（那是整行覆盖，会把客户自己填的企业资料抹成 NULL）；`CompanyInfoMapper.updateDueDays` 自 v60 起**已无调用点**，是墓碑 |
| 台账 | `GET /api/manager/receivables`（按客户汇总 + 逾期）、`/receivables/orders`（明细，可按客户/只看逾期） | **金额真相源仍是 `payment_status = 1 AND status <> 5`**，与 `DashboardMapper` 的待收款合计逐字同源；本功能只**加账期维度**，不新造金额口径 |
| 核销 | `POST /api/manager/receivables/settle`（收款 + 核销，同一事务） | 收款走全仓唯一收钱入口 `markPaidIfCollectable`，核销走 `settleIfCollected` 的 CAS。**已核销的单跳过而不报错**（幂等重放）；其余任何一处失败**整批回滚**并说明是哪一单 |
| 对账 | **E10** `settlement_status = 2 AND payment_status <> 2`（只查单向） | 抓"账销了、钱没到"。反向（收了钱还没核销）**是正常状态**（现金单送货上门当场收钱、站长之后才走月结），谁改成双向比较日结就会天天误报 |
| 站长端页面 | `miniapp-delivery/pages/station-mgmt/receivables/`（台账 → 客户明细 → 核销；含账期设置） | 入口在站长端首页「应收账款」。金额、逾期天数、核销金额**全部**用服务端下发的值，页面里没有任何算术；核销只调一次接口（收款 + 销账由服务端同一事务完成）。⚠️ 补页面时发现并修掉一处：`listByCustomer` 原本**没有下发客户级账期**（`due_days`），页面会把已设账期的客户一律显示成"未设账期（即时结清）"—— **不报错，但站长会按错的方式报价**。已补 `left join`（v60 前是 `company_info`，v60 后改为 `customer_station_config`），并用断言把它锁住 |

**三条实现判据（改这里之前先读）：**

1. **归属判据不能用 `getStationCustomer`** —— 它的 SQL 带 `exists (select 1 from orders ...)`，
   是「客户画像」口径（有订单才有画像），会把**没下过单的新客户**判成"不属于本站"，
   而给新客户设账期恰恰是最常见的场景。用 `countCustomerOfStation`（绑定 **或** 本站订单，取并集）。
   2026-09-17 该写法已在客户特权上导致三个用例全红。
2. **核销 ⟹ 已收款**，由 CAS 钉在 SQL 层。B2B 最怕"账面销了、钱没到"。
3. **逾期只提醒、不改任何金额** —— 对齐"欠桶只提醒不阻断"的既有风格；本功能没有任何写金额的分支。

**已知边界（不是缺陷，是范围）**：`settlement_status` 只在**挂账单**（`due_date IS NOT NULL`）上有意义，
判别式就是 `due_date IS NOT NULL`；即时结清的现金单在配送员当场收款时不会自动置 2，
由站长在台账里核销。用例 `ReceivableIntegrationTest`（5 例，含"反向不报不平"）。

## 2. 进货成本（**只加字段，不做采购模块**）

> **状态：✅ 已实施**（2026-09-17，迁移 `v39`；测试库已执行并验证幂等，⚠️ 真实库待执行）。
> 落了方案 ①：`inventory.cost_price` + `GET /api/manager/gross-profit`（毛利报表）
> + `PUT /api/manager/gross-profit/cost`（设置成本）。
> ⚠️ 编号用 **v39**：`v38` 已被另一个工作流占用（商品图片库）。
> ⚠️ 实施时补了一条本文没写的护栏：**没填成本的商品不给毛利数字**（而不是把成本当 0 相减）——
> 后者会让站长以为自己赚了整整一个售价，是最坏的一种"看起来正确"。
> 另一条：**清除成本必须显式传 `clear: true`**，否则客户端把键名拼错就会变成一次静默清空。
> **距离补贴式的悬空字段教训在这里也适用**：没接线的列一个都不建。
>
> **前端状态（2026-09-17 补齐）**：入口在站长端首页「毛利报表」
> （`miniapp-delivery/pages/station-mgmt/gross-profit/`）—— 期间选择（本月/近 7 天/近 30 天）、
> 收入/成本/毛利三个合计、按商品明细、以及点任意一行直接补录进货成本。
> 三条落地判据：① **`totalProfit` 为 null 时不给数字**（显示"算不出"），
> **绝不能当 0 相减** —— 那正是本节要防的"看起来正确"；② **缺成本的行原样展示
> 服务端的 `profitText`（"未填成本，无法计算"）**，并单独列出「未填成本的商品」快捷补录；
> ③ **`costBasisNote` 原样展示**（不能改写成"当时的真实毛利"）。
> ⚠️ 顺带修了一处文案缺陷：`costBasisNote` 里原本写着 Markdown 记号 `**当前**`，
> 而这段文字是**直接渲染到小程序界面**上的，星号会原样显示。**后端下发给界面的文案不要写 Markdown。**
>
> **净利（2026-09-19 增补，同一端点）**：响应追加 `orderCount` / `deliveryFee` / `floorFee` /
> `totalIncome` / `wage` / `netProfit` / `profitBasisNote`，页面更名「利润报表」并加「今日」快捷区间。
> 四条判据：
> ① **净利 = 水费 + 配送费 + 楼层费 − 进货成本 − 计件工钱**，六个数字必须取自**同一订单集合**
> （结算站 + 排除已取消 + 同一时间窗）—— 混两批单算出来的净利没有意义，故单数/费用那条 SQL
> **刻意不 join `order_item`**（join 了配送费会被明细行数放大）；工钱按 `staff_earning.order_id`
> 挂到这批订单上，而不是按工钱自己的 `create_time` 筛（否则"今天下单、明天送完"会让净利两天跳）；
> ② **缺成本时 `netProfit` 与 `totalProfit` 一起为 null** —— 只 null 一个，站长会拿另一个继续当真；
> ③ 工钱只算**订单产生的计件**，人工调整（`order_id IS NULL`：迟到扣款/高温补贴）不进日净利；
> ④ 收入**不含押金**（可退的负债不是收入），"收入合计"与毛利的"水费收入"是同一个数、不得各算一套。
> ⚠️ 已知口径边界：收益在订单进入**送达**时才产生，故未送完的单暂时不计工钱，那几天净利偏高。

见 `16` §D4-a。现状：

- `inventory`（站级商品）**无 `cost_price`**（`schema.sql:292-309`）
- `inventory_record`（入库流水）**无 `unit_cost`**（`schema.sql:310-324`）
- 全仓 `cost_price|成本|进价|毛利|profit` 在业务代码中 **0 命中**

### 2.1 两个方案，建议选第一个

| 方案 | 形态 | 优点 | 缺点 |
|---|---|---|---|
| **① 站级当前成本**（推荐） | `inventory.cost_price`（可空） | 极简；毛利 = (售价−成本)×销量 | 成本变了以后历史毛利会用新成本重算 |
| ② 入库批次成本 | `inventory_record.unit_cost`（入库时填） | 历史毛利准确 | 需要加权平均/批次核算 → 那是 ERP |

**判据：先做①，成本变了就用新成本重算毛利——真实小水站就是这么算账的。** 做②等于开一个 ERP 的坑，而 D4 已明确"上游/供应链做不过来"。

### 2.2 展示

站长端加一个"毛利"视图：`(sale_price − cost_price) × 销量`。**成本字段不向顾客端暴露**（`AGENTS.md` §6 的越权与信息泄露红线同源）。

## 3. 桶损耗出账（一个语义，不是一套模块）

### 3.1 先澄清一个容易混的点

D5 说"桶是流动的、同品牌换桶"——**这解释的是为什么系统不需要给桶编号**，现有实现（`customer_barrel_asset` 只记数量、`BarrelLedgerService` 唯一写入口）是对的。

**但它推不出"不用管桶损耗"**：桶会被摔、会丢、有寿命。真实水站每年都有桶损耗。

### 3.2 现状：有一个通用口子，但没有业务语义

| 现有能力 | 落点 |
|---|---|
| 空桶差异（订单级） | `orders.barrel_discrepancy` / `barrel_discrepancy_note`（`schema.sql:472-473`） |
| 配送异常"水桶破损" | `DeliveryController:283` 的异常上报类型 |
| 桶异常单 | `order_barrel_exception`（`schema.sql:338`） |
| 人工调整（增/减） | `BarrelRecordType` = `6 人工调整(增)` / `9 人工调整(减)` |
| 站长撤桶权益 | `station_adjustment` 的 `BARREL_REVOKE`（`schema.sql:684`） |

**所以严格说不是"没有"，而是"只有一个通用口子"** → 后果很具体：**对账 E5（物理桶守恒）报不平时，分不清"是账写错了"还是"桶真的坏了、丢了"**，也算不出"今年损耗了几个桶"。

> ⚠️ **2026-09-17 复核修正**：上面这段结论**不准确**，实测（`grep LOST|DAMAGED|BarrelRecordType.LOST` 全仓）结果是：
> - `BarrelRecordType` **已经有** `3 丢失` / `4 损坏`，而且**已经在 E5 的 UNION 里**
>   （`ReconciliationService` 的 `type IN (3, 4)` 记负）—— 所以"没有损耗语义"是错的；
> - 真正的问题是**这两个类型全仓 0 处写入**：没有任何接口或流程会产生 type=3/4，
>   `5 赔偿` 同样 0 处写入。它们是"已声明、已纳入对账、但没有任何入口"的**休眠类型**。
>
> 准确的表述是：**语义位已有，缺的是写入口**。要补齐就得给站长一个"登记桶损耗"的入口，
> 并想清楚它在桶账上的正确落法（桶是客户弄丢还是水站在库房里破损，两者的账务方向不同 ——
> 前者应走 `over` 增加，后者才是水站自有资产减少）。**这件事本轮没做**：在没想清口径之前
> 动桶账守恒等式，风险大于收益。

### 3.3 修法：给 reason 收敛枚举

- 首选：给桶流水的 `note`/reason 收敛出 `报废 / 丢失 / 破损 / 盘点差异` 几个**枚举类型**（照 `constant/*.java` 的做法，不要自由文本）。
- 或：新增 `BarrelRecordType` 值。

⚠️ **硬约束（本仓已有明文）**：新增 `BarrelRecordType` 必须**同步扩展 `ReconciliationService` E5「物理桶守恒」的 UNION 项**，否则补录之后对账会误报（`constant/BarrelRecordType.java:10-12`、`AGENTS.md` §1）。

**不用做固定资产模块、不用给桶编号。**

### 3.4 与"客户欠桶"的区分

- **客户欠桶** = `customer_barrel_over` 为正（客户手上端的桶比权益多）→ 已有台账与站长只读入口。
- **本站桶损耗** = 水站自己的资产没了，与具体客户无关（配送员丢桶、仓储破损、报废）。

### 3.5 2026-09-18 的决定：**本站不做桶损耗出账**（只保留一个读数出口）

**产品决定（2026-09-18）**：**不做桶损耗**。理由不在代码里，在业务模式里 ——
**桶是跟水厂换的**：水站把空桶交回水厂、换回满桶，桶本身是水厂的资产，
破损与丢失由水厂承担（"这一般可以算是水厂的问题"）。所以它**不是水站的账**，
水站不需要在自己的账上记"损耗了几个桶"。

由此推开的几件事，都写清楚，免得下次又有人来补一个"登记损耗"入口：

- **`BarrelRecordType` 的 `3 丢失` / `4 损坏` / `5 赔偿` 保持休眠**（全仓 0 写入）。
  ⚠️ **不要因为它们空着就把它们从对账 E5 的 UNION 里删掉** —— 空集对等式没有任何影响，
  而删掉之后，真有人（比如将来水厂侧对接）写了 3/4，日结就会开始误报。
- **客户弄丢/欠着的桶不在这个口径里**：那是 `customer_barrel_over`（欠桶台账，应收），
  已有站长只读入口 `GET /api/manager/owed-barrels`。两者**不要混用同一个字段**，
  否则"客户欠桶"会被损耗数据污染。
- **只保留一个只读出口** `GET /api/manager/barrel-loss?from=&to=`（站长；站取自 `AuthContext`，
  按商品汇总 3/4），用途是让站长确认"系统确实不记这项"，以及将来水厂侧要记账时有个现成的读出口。
  用例 `BarrelLossStatsIntegrationTest`（2 例：按商品汇总 + 口径下发；按站隔离 + 时间上界含当天）。

`customer_station_config.offline_payment_enabled`（`schema.sql:238`）就是这个模式：**站长在客户画像里逐个开通货到付款**，全系统唯一控制点、无站点级总闸。已经在跑，也是行业习惯（老客户才给到付）。

D6 决定不做个人/企业显式区分，差异化落到"特权"——这与上述先例同源，**方向正确**。

### 4.2 但必须收敛成有限枚举

**风险**：如果"特权"是任意维度，它会退化成无类型的 JSON → 没有校验、没有展示口径、没有对账，等于"没有规则"。

**本仓铁律**：语义由类型决定（`DepositType.isIncrease`、`AdjustType`），**不靠调用方自觉**。

**建议形态**：`customer_privilege(customer_id, station_id, type, value, ...)`，`type` 用 `constant/` 里的枚举。典型 type：

| type | 是否动钱 | 落法 |
|---|---|---|
| `OFFLINE_PAYMENT`（货到付款） | 否 | 可直接并入现有 `customer_station_config` |
| `DISCOUNT_RATE`（折扣） | **是** | 必须影响计价 → 走 `PriceUtil` 口径 + 订单快照 |
| `FREE_DELIVERY_TIMES`（免配送次数） | **是** | **账户 + 流水**，见 §4.3 |
| `NO_MIN_ORDER`（免起送门槛） | 否 | 校验时读一个开关 |
| `TICKET_RETURNABLE`（允许退票） | 是 | 校验时读开关 |

### 4.3 判据：**能影响钱的 type，必须是账户 + 流水，不能是画像上的开关**

"免配送次数""折扣"这类一旦做成 UI 开关，就会出现"站长说还有 3 次、客户说还有 5 次"的扯皮。正确形态与 `19` §5.2 一致：**次数账户 + 流水 + 幂等 + 对账**。

## 5. 代客下单入口（后端已就位，只差一个页面）

### 5.1 现状

| 环节 | 状态 | 证据 |
|---|---|---|
| 后端端点 | **已有**：`POST /api/orders` 就是站长/配送员代客建单 | `OrderController:29` |
| 权限护栏 | **已有**："员工代客下单必须校验该客户确属本水站，禁止替他站客户下单消耗其水票/押金" | `OrderServiceImpl:190-194` |
| 渠道标识 | **已有**：`orders.source` = `1电话 2微信 3小程序` | `schema.sql:450` |
| 员工端页面 | **没有**：`miniapp-delivery` 只 `get(API.ORDERS)`，无创建入口 | `miniapp-delivery/api/station-mgmt.js:25` |
| 顾客端传值 | 显式传 `source: 3` | `miniapp-user/pages/order/create.js:550` |
| 后端缺省值 | `setSource(dto.getSource() != null ? ... : 2)` | `OrderServiceImpl:430` |

### 5.2 为什么建议补（D3 的边界）

D3 决定"不做电话/线下客户的下单入口，只给联系方式"——**联系方式这一半已经有了**：`GET /api/stations/{id}/public-phone`（`StationController:64`，公开、免登录、只回 id/name/phone），接到客户端展示 + 一键拨号即可。

> **2026-09-17 复核：这一半原来只做了一半，已补齐。** 顾客端「我的 → 客服」页
> （`miniapp-user/pages/service/`）确实有拨号按钮，但三处不对：
> ① **电话只读本地缓存** `selectedStation`（选站时存下的快照，不保证带 `phone`），
> 明明有公开接口却没用 —— 部分客户那里按钮会永远提示"暂未获取到客服电话"。
> 现改为**优先调公开接口**、缓存只兜底（`api/station.js` 的注释里记着同类事故：
> 误调站长路由导致电话恒定取不到，排查成本很高）。
> ② **客服微信 `aquaflow_service` 是编造的** —— `Station` 实体根本没有微信字段，
> 客户复制到的是一个不存在的账号。
> ③ **工作时间 `08:00-20:00` 也是硬编码的** —— 同样没有数据源。
> ②③ 已**删除**（要重新展示，先给 `Station` 加字段并让站长可配）。
> **判据：界面上不放假数据。没有数据源就不展示，而不是填一个"看起来合理"的值** ——
> 客户按假的营业时间打电话、或复制一个不存在的微信号，比不显示更糟，
> 而且这类错误不会报错、只会静默误导（与 `16` §3.0 那条"注释/字段悬空"同源）。


但要注意后端"站长代客下单"和顾客"打电话给站长"是**两个不同的口子**：

- 顾客打电话给站长 → **站长要有个地方把这单记下来**。
- 如果没有这个入口，站长会在系统外记账 → **该单的桶流动不落库** → 顾客端看不到、桶账不更新、对账不平。

**这是本项目的核心资产（桶账真实）的唯一支柱**：所有桶的流动都过 `BarrelLedgerService`。一旦站长在系统外接单，这个前提就破了。

**结论：这不是"要不要做个新功能"，而是"要不要花一天补一个表单页"**（选客户 + 选商品 + 选地址 + `source=1`），后端与护栏都已存在。**若确实不做，至少要让站长能把线下单补录进来**（现在资产调整单能补桶、补票，补不了订单）。

### 5.3 实施状态：✅ 已完成（2026-09-17）

> **落了本文 §5.1 的方案，但实施中发现后端"已就位"这个判断只对了一半** ——
> 建单端点在，可页面需要的三个读接口**一个都给不了**，而且两道判据在常见场景下会误拒。
> 所以本轮是「一个页面 + 三个读接口 + 两处判据修正」，**没有新建单端点**。

| 环节 | 落点 | 说明 |
|---|---|---|
| 页面 | `miniapp-delivery/pages/station-mgmt/place-order/`（客户 → 地址 → 商品/试算 → 下单） | 入口在站长端首页「代客下单」。金额全部由服务端下发，页面里没有任何金额算术 |
| 建单 | **复用** `POST /api/orders/create`（**不新建单端点**） | 两条建单路径算金额 = 重演"计价双轨"。`source` 固定 `1 电话`（站长代录） |
| 客户选择器 | `GET /api/manager/order-assist/customers?keyword=` | ⚠️ **不能复用 `GET /api/customers`**：它是 orders 驱动（客户画像口径），**站长刚建档、还没下过单的客户一行都查不出来**，而"给新客户下第一单"恰恰是代客下单最常见的场景 |
| 客户地址 | `GET /api/manager/order-assist/customers/{id}/addresses` | ⚠️ **`GET /api/addresses` 是顾客自助端点**（身份取自 `AuthContext.requireCustomerId()`），站长调它只会看到自己的地址 —— 页面根本拿不到"这个客户送到哪" |
| 试算 | `POST /api/manager/order-assist/quote?customerId=`，请求体**直接复用** `PaymentQuoteDTO` | `POST /api/payments/quote` 同样要求顾客身份，站长调不到；而电话叫水时"这单多少钱"是站长必须当场回答的。**`customerId` 走查询参数而不加进 DTO** —— 那个 DTO 是顾客端共用的，一旦带上 customerId，将来有人顺手在顾客端改成"用它指定的 customerId"就是一次越权 |

**实施中修掉的两处判据（都是"看起来能用、实际会误拒"）：**

1. **员工代客下单的归属护栏原本只查绑定行**（`OrderServiceImpl`，[AQ-012]）。
   老客户完全可能没有 `customer_station_config` 行，于是一种最难排查的拒绝出现了：
   **客户列表里点得到他，一下单却说"该客户不属于本水站"**。
   改为 `CustomerMapper.countCustomerOfStation`（绑定 **或** 本站订单，取并集）——
   放宽是安全的：只有与本水站已有关系的客户才放行，他站客户两条都不满足（有用例锁住）。
2. **`GET /api/customers` 与上面的护栏用了两套不同口径**：列表是 orders 驱动、
   护栏是绑定驱动，两者的并集才是"本站客户"。这也解释了为什么第 1 条直到接了页面才被发现 ——
   **接口各自能跑通，串起来才露馅**。

用例 `EmployeePlaceOrderIntegrationTest`（5 例）：无绑定行的老客户可下单、他站客户仍被拒、
选择器能搜到没下过单的新客户、站长可取客户地址、**试算 `totalAmount` 必须等于落库 `total_amount`**。

## 7. 微信支付：将来接入时的判据备忘（现在不改代码）

D1 决定测试阶段不接入。为免将来接的时候破坏"支付状态只前进"的口径，先把判据记在这里：

1. **唯一入账入口是 `OrderMapper.markPaidIfCollectable`**（`OrderMapper:52`）——从 `0 未付` 或 `1 待收款` 迁入，**绝不复活 `3 已退款 / 4 已取消`**。微信回调也必须走它，不要另写 `updatePaymentStatus`。

4. ⚠️ **在线购票的支付流水 `order_id` 为 NULL**，`uk_payment_active_order` 对它零保护（见 `19` §4）——**接微信支付前必须先修掉这个幂等漏洞**，否则支付回调的重复投递会产生重复入账。
5. **不要把"微信支付"与"货到付款"的确认逻辑混在一起**：`confirmOfflinePay`（`OrderWorkflowServiceImpl:244`）是配送员送达后的人工确认，与异步回调是两条独立路径。

## 9. 站长首页与「桶异常」页（2026-09-18）

### 9.1 待办聚合：只做读数，不新造口径

站长打开首页（`pages/coordination`，站长的 tabBar 首页）第一眼要看到"今天该处理什么"，
所以加了 `GET /api/manager/todo-summary`：逾期应收 / 未填成本 / 待确认结算单 / 待处理桶异常。

- **四类全部复用各自模块已有的读数入口**（逾期走 `ReceivableService.overview`、未填成本走
  `GrossProfitMapper.listMissingCost`、待确认结算单走状态计数、桶异常走异常单列表的同一个状态过滤）。
  首页若自己再写一遍 SQL，就会出现"首页说 3 笔逾期、点进去 5 笔"这种最难解释的不一致 ——
  与本站"计价双轨"事故同形（见 `util/PriceUtil` 文件头）。
- ⚠️ **不给"待办总数"这一个数字**：四类单位不同（客户 / 商品 / 张 / 单），相加没有业务含义。
  只给 `hasAny` 供角标用。响应里每项带 `key`，前端只做「key → 页面」的路由映射（后端不认识小程序路径），
  `label` 与金额一律后端下发。
- 用例 `ManagerTodoIntegrationTest`（3 例）：干净站全 0、四类各记各的数且逾期金额与台账逐字一致、
  不串站 + 顾客调不到。

### 9.2 「桶异常」页：只读，处置按钮**故意没做**

在此之前 `/api/manager/exceptions` 整个家族（列表 / 详情 / 处置 / 执行补偿 / 统计 / 配置）
**在两个小程序里都没有界面入口**，而运营告警页却写着"桶异常单去异常列表处置"——
站长点进去无处可去。现在补了只读页 `pages/station-mgmt/exceptions`（2026-09-19 前叫
`barrel-exceptions`，同日与「运营告警」合并成一个页面的两个页签）：
异常单列表（`pending` 标红）+ 近 30 天统计（`/stats`）；**损耗读数已于同日从界面下线**（§3.5）。

- ⚠️ **处置入口（handle / execute：同意、改判、忽略、退水票、退现金、调资产）没有接**。
  这些动作会**真动钱和桶账**（§8.17 的事故就是"界面显示已补偿、账上一分没动"），
  开放方案见 §9.3；开放前该页明确写着"现在需要处置请走站长端资产管理流程"。
- ⚠️ **前端不做任何状态判定**：为让页面标红"还等着处理"的那些，
  `OrderBarrelExceptionDTO` 新增了服务端派生的 `pending` 布尔 ——
  前端既不自带状态码表，也不比对中文文案（文案一改就静默失效）。断言在
  `BarrelExceptionFlowIntegrationTest`（列表契约那一条）。

### 9.3 桶异常「处置入口」怎么开放（方案，未实施）

**现状：缺的只是界面，后端与用例都在位。** 已经有的是
`POST /api/manager/exceptions/{id}/handle`（记录站长决定：APPROVE / MODIFY / IGNORE / ESCALATE +
补偿明细）与 `POST /api/manager/exceptions/{id}/execute`（真正执行：退水票 / 退现金 / 撤桶权益），
契约由 `BarrelExceptionFlowIntegrationTest` 钉住：补偿执行失败会整体回滚并**退回 STAFF_RECORDED 可重试**、
同时投 SYSTEM 告警；重复 handle / execute 被拒；他站站长处置不了本站单。

难点不是"按钮放哪"，而是**这两个接口会真的动钱和桶账**。所以方案按"先把风险关进笼子"来设计：

**A. 分两批开放（推荐先做 A1）**

- **A1（最小动作集）**：只开放两个动作 ——
  ① **忽略**（`IGNORE`，一分钱不动，已有断言）；② **按系统建议补偿**
  （`APPROVE`，且补偿明细**只能等于**后端下发的 `suggestedTicketQty` / `suggestedCashAmount`）。
  即：站长只能"确认后端算出来的补偿"或"否决"，**不能手工填金额**。
  这样每一分钱都能由后端复算、可审计 —— 而"人手输入金额"在本仓出过事故（§8.17 同族）。
- **A2（完整）**：再开放手工填写补偿明细（DTO 早就支持 `refundTicketQty` / `refundCashAmount` /
  `adjustAssetQty` / `adjustProductId`）。

**B. 无论 A1 还是 A2 都必须有的五条护栏**

1. **两步走，不合并**：第一步「登记处理意见」（动作 + 补偿明细 + `managerNote` 必填），
   第二步「确认执行」—— 第二步要把**将要发生的动作逐条列出来**再让人点确认
   （"将退水票 3 张（18.9L）、退现金 ¥30.00、撤桶权益 2 个"）。
   理由：§8.17 是"界面说做了、账上没做"，而反向的"钱多退了"同样不会报错。
2. **补偿项必须成对（数量 + 商品）**：退水票缺 `adjustProductId` 会被后端拒（这是**有意**的护栏，
   按商品各算才能对上批次单价）。所以界面上"退水票"不选商品**不允许提交**，
   而不是提交后等后端报错。
3. **一次只处理一张单**：不做批量执行、不做"全部同意"。一个填错的口径会被批量放大 N 倍。
4. **失败必须留在页面上**：`execute` 失败时后端已回滚到 `STAFF_RECORDED` 可重试；
   界面要把 `message` 原样显示并提供"重试"，**不能只弹一个 toast 就消失**。
5. **留痕**：`managerNote` 必填（一句人话理由）；执行后该单不可再改（状态 CAS 已保证）；
   执行与忽略都会投一条 OPERATION 告警（站长自己的告警列表里能看到）。

**C. 明确不做的**

- 不做"一键补偿全部待处理单"、不做自动补偿（金额必须有人确认）；
- 不把处置入口开放给配送员（`@RequireRole("STATION_MANAGER")` 已在类上，保持）；
- 不在这个页面里顺带做"调整资产"的自由录入 —— 那是 `docs/design/10-站长资产调整单.md` 的正门。

**D. 开放前的最后一道检查**：拿真实库的一份数据副本，跑一遍
`handle → execute` 的完整链路并核对三条账（水票 E8、押金等式1、桶账 E3/E5）仍为 0 ——
后端用例已经覆盖，但真实库的索引/配置与测试库不完全等价（AGENTS §8.12）。
