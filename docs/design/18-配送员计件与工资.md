## 1. 目的与范围

配送员按件取酬：一单送了几桶、爬了几层楼，算清之后由站长发钱。本文定义计件单价配置口径、收益明细的产生时点与归属、结算单生命周期、自定义工资条目的边界，以及独立对账等式 E-PAY。

**不在范围内**：打款、提现、钱包、余额、代发（需支付牌照与资金存管），以及个税、社保、考勤等薪酬外围。

## 2. 设计口径

### 2.1 系统只做台账，发钱是站长的线下动作

站长发工资在现实里就是微信转账或当面给现金。结算单状态独立为 `草稿 → 已确认 → 已发放`，发放时记 `paid_time` 与 `operator_id`。**判据：「算出来」与「发出去」必须分开** —— 只留一个状态时，站长改一条明细就会**悄悄改掉已经发过的钱**，下月对不上时无从追溯。与 `station_adjustment`「确认后不可原地改、要改走反向单或下期调整」同一条设计语言。

与外卖平台的差异：**谁发钱**是站长直接发（不做平台结算单、佣金抽成、骑手钱包）；**计件单位是桶不是单**（一单常 1~3 桶、约 19kg/桶，只按单计价会让配送员不愿接多桶单）；**任务双向**（送水 + 收空桶，回桶数当场核对）；**楼层必做**且拆两笔（§2.3）；**运力归属固定**（`staff.station_id`，跨站只是帮忙）。

### 2.2 计件构成只有两项

```
本次配送收益 = 送桶数 × per_bucket_amount      （商品专属价优先，未配则回落该站默认价）
             + max(0, 楼层 − 免费层) × floor_bonus_per_level
```

⚠️ 回桶奖励、每单固定补贴、少收空桶扣减三项已删除且无独立库列，理由：本仓对欠桶一贯的口径是**只提醒不扣钱**，「少收空桶自动扣钱」直接引发劳资纠纷。`EarningKind` 里 `RETURN_BUCKET` / `ORDER_BONUS` / `PENALTY` **保留但停用**，常量与 `textOf` 只为显示历史流水（删掉会让老账明细显示成「其他」）。⚠️ **少收空桶仍然有痕迹**：`barrel_discrepancy` 与桶异常单照旧，只是不再自动折算成扣款 —— 要扣就在结算单上手工做 `ADJUST` 并写清理由，**不要加回自动扣减**。

**单价配置**：真相源是**站级**；`product_id = 0` 为默认价，非空为商品专属价（18.9L 与 5L 搬运成本不同）；未配专属价回落默认价，两者都没有则按全 0 处理（= 不计件）；保存时**负值一律归零**；**不做阶梯价、加权价与复杂公式**。

### 2.3 楼层补贴与楼层费是两笔钱

`orders.floor_fee` 按**地址楼层**在下单时快照，是向客户**收**的收入；`FLOOR_BONUS` 在完成配送时产生，是给配送员**补**的成本，依据是上报楼层（§2.4）。**两者金额可以不同，必须分别配置、分别落库** —— 合成一个字段会导致客户投诉乱收费时查不清、工钱算不准、对账不平。

### 2.4 楼层补贴以配送员上报的楼层为准

客户在地址里填的楼层是**收费**依据，不能同时当**发钱**依据 —— 只有配送员知道自己爬了几层，只认客户填的值等于拿别人的话给自己发工资，虚报没有痕迹。

- 完成配送时**选填** `orders.reported_floor`：填了就以此为准，没填**沿用地址楼层**（不惩罚不填的人，也不多付）。
- 与地址不一致时，明细 `note` 写成「上报 8 层（与地址 6 层不一致），超 7 层」—— **这是防虚报的痕迹**，站长在结算单明细里直接能看到，**不许省**。
- 照片**不强制**：`order_image.type = 3` **楼梯凭证**（[2026-09-26] 由「楼层凭证」改名，两端统一），配送员可拍、**站长事后也能补传**（同一上传接口，两角色都允许）；与客户就楼层/爬楼有争议时它是唯一凭证。
- ⚠️ **电梯口径**：地址明确写了「有电梯」就不补；地址里电梯为 `null` 而配送员报了几层 → 按他报的给。
- ⚠️ **上报值只写一次**（`OrderMapper.saveReportedFloor` 带 `reported_floor is null`）：完工那一刻的快照，之后谁都不许悄悄改写发钱的依据；真要改走结算单上的人工调整（`ADJUST`）留痕。
- ⚠️ **完成配送页只在"有争议"时才问楼层**（[2026-09-26] 产品口径，原文：「楼层数藏在下面吧……不过楼层我觉得一般没有不清楚的现象，做成楼梯有争议时触发吧，楼梯凭证也一起」）：楼层输入与楼梯凭证**默认收起**，两种途径展开 —— ① 地址**没写清有没有电梯**（`addressHasElevator` 为空）时载入即自动展开并说明原因；② 配送员点「楼梯 / 楼层有争议」。**兜底判据**：不能因此让"该填而没人提醒"发生，所以 `null` 电梯是自动展开的唯一条件，改回常显前先读这句产品原话。同一页的 **「送达凭证」** 是常显的（原名「签收凭证」，[2026-09-26] 改名 —— **客户不一定在现场签收**，不要求签字，照片只证明送到了）。
- v71 的回桶计划按订单占用的权益数量和领取容量计算：新领部分免回桶，已有份额按后端计划回桶；前端只认 `barrelItem` / `suggestedReturnQty`，不能拿送出数当应回数。两份旧权益加一份新领容量的三桶单默认回两桶。
- 原 `first_barrel_order` 和“送达才增加权益”只属于存量未采用独立权益的路径，不再解释新订单。数量、可用量与占用的现行正本在[领域模型](../architecture/02-领域模型.md)，业务例子在[流程地图](15-业务流程地图.md)。
- 只有桶装水明细参与回桶。送水计件按实际送出桶数计算，不能因新领部分免回桶就少算送水工钱，也不能因少回桶自动扣工资。
- 少回桶显示应回/实回及差额红色提醒，原因选填；已填原因按数量合计校验，可只说明已知部分，不强制补齐或自动写“其他”。实际回桶、物理上限、出库及完成状态仍走原校验，不新增借桶审批或自动收费，裁定见 design/16 C-02。

### 2.5 收益产生时点钉在「送达」，天然免疫取消

`staff_earning` **只在订单状态进入 `3 已送达` 的那次状态变更中产生**：触发点是 `OrderWorkflowServiceImpl.completeDelivery` 里的**一次成功 CAS**（`OrderMapper.updateStatusIf`），之后才调 `recordDeliveryEarnings`；并发由唯一键兜底 —— **只要唯一键在，重复调用最多报 1062，而不是多算一笔工钱**。

状态**只前进、不倒滚**，可取消的时机只有 `1 待配送 / 2 配送中`（**此时还没有收益**），到 `3 已送达` 后就不可能再被取消 —— **不存在「收益产生了又要撤回」的回滚问题**。⚠️ **不要用「已接单」或「已分配」作为计件时点**，那会在取消单上留下需要人工清理的收益行。

⚠️ **计件按 `order_item` 逐商品产生，一单会有多条收益行**（`auto_uk` 含 `product_id`）：断言「一单一条收益」是错的，要断言「该单全部收益都归属正确的 (station, staff)」。某商品单价为 0 时不产生该行；金额为 0 的收益不落库（也不占唯一键）。

### 2.6 归属：人 = 实际完成人，站 = 履约站

- **归属人**取完成时刻的 `orders.delivery_staff_id`：经历转单后它指向最终完成的人，**不需要额外的转单分账**。
- **归属站取履约站**（`orders.delivery_station_id`）：工钱是履约成本、跟出车的人走，跨站外派单由接单站配送员跑腿就该接单站发。
- ⚠️ **履约站为空是异常数据**：该单不产生收益并告警，**不允许回落到归属站**（回落会把工钱记到一个没出车的站上，且事后无人能发现）。

### 2.7 工钱走独立对账 E-PAY，不进客户对账

`ReconciliationService` 的其余等式都是**客户/资产**维度（押金、支付、桶、库存、权益）；工钱是水站与人之间的账，与客户无关。

- **E-PAY** = `staff_payroll.total_amount == SUM(staff_earning.amount WHERE payroll_id = 本期)`，与押金等式1（`balance == SUM(deposit_record.amount)`）同构。
- ⚠️ **误接的后果**：把工资算进客户对账，每天 03:00 的日结必然报不平并触发 `SYSTEM` 告警，告警疲劳之后真问题会被淹没。
- **投递路由**：E-PAY 不平属**运营问题**，收件人是该站站长（`AlertType.OPERATION` + `station_id` 必填），**不是平台管理员**。V2 结果投递前按 `STATION_LEDGER_KEYS` 拆两张表：客户账 → `systemFault`，站长台账 → `alertStationLedgerImbalance` **按站逐张结算单**投 `stationFault`。
- ⚠️ `reconciliation_result.level` 是「严重度」，不是「投给谁」：E-PAY 落表仍是 `ERROR`，收件人由 `AlertType` 决定，**别把两者当成一个字段**。
- ⚠️ 投递条数按 `ALERT_MAX_PER_RUN` 封顶（单价录错会让整批结算单同时不平），**真实的差异总数写在告警正文与日志里**。

### 2.8 方向由类型决定，调用方一律传正数

**`kind` 决定正负、调用方一律传正数**，落库时由一处统一转符号（`EarningKind.isDecrease`）。唯一例外是 `ADJUST`：站长手工录入、本来就是两向调整，金额自带符号（`EarningKind.allowsSignedAmount`）。

⚠️ **不要在每个生成收益的地方各写一次 `amount.negate()`**：一旦分散，将来必然有一处写反，而「工钱算错」不像「账不平」那样有对账兜底。

### 2.9 自定义工资条目只是人工调整流水上的标签

`staff_earning_item`（加项/扣项字典）解决人工调整**只有一个自由文本 `note`** 带来的三个问题：同一扣款项在不同月份写成「迟到」「迟到扣款」「迟到罚款」；站长想知道「这个月迟到一共扣了多少」只能一页页数；打错字没人拦，而这是**会真的从人家工资里扣掉的钱**。

⚠️ **它刻意不是规则引擎**：不参与任何自动计算、不产生任何金额、不进对账等式。三条口径：

1. **方向由条目决定**（`constant/EarningItemDirection`：1 加项 / 2 扣项）：**传了 `itemId` 还传负数 → 直接拒绝**，不静默取绝对值 —— 让录的人每次自己判「这次是补还是扣」，等于把最容易错、错了直接从工资里体现的一步交给手感。不传 `itemId` 的老自由文本调整保持原样（金额仍自带符号，那是它唯一的用途）；金额为 0 的调整直接拒绝。同站条目名不得重复（唯一键 `uk_earning_item_name` 是最终依据），名称去空格后 1~20 字。
2. **`item_name` 是写入时的快照**：条目改名**不改写已经发生过的工资历史**（与 `order_item.product_name` 同一口径）；汇总优先显示条目当前名，条目已不存在才回落快照。
3. **被流水用过的条目只能停用、不能删**：删掉它，那些流水在界面上就成了「无条目的人工调整」，站长再也说不清那笔钱是什么。停用只挡**新录入**，历史照旧。

⚠️ **`itemSummary` 只统计带条目的流水，不等于 `unsettledTotal`**（自由文本调整没有条目）：两者不是同一口径，页面上不要把差额显示成错误。汇总的 `total` 是**带符号**的（扣项为负），免得前端自己再判一次方向。

### 2.10 人工调整的归属校验取并集

`POST /api/manager/payroll/adjust` 只收 `staffId` 时**不校验这个人与本站有没有关系**，而「我的工资」自助查询刻意**只按 `staff_id` 过滤、不带站点** —— 两者一叠加，任何站长传一个别站配送员的 id，就能往那个人的「未结工资」里塞钱或扣钱。

⚠️ **判据取并集**（与客户归属的 `countCustomerOfStation` 同一形状）：`staff.station_id == 本站` **或** 该人在本站已有 `staff_earning` 记录（跨站外派时人属于 B 站、给 A 站跑腿，A 站给他记一笔完全正常）；角色必须是 `DELIVERY` / `STATION_MANAGER`。

### 2.11 人工工资录入意图（2026-10-08）

自由录入和按条目录入均须携带 `idempotencyKey`，由工资页在发请求前持久保存。同一水站同一编号只记一次；员工、条目、金额或说明改变则拒绝。同一内容的新编号代表另一笔实际录入，不合并。金额最多两位小数，不静默舍入。

响应未知时保留原内容与编号，重开工资页恢复后原样重试；明确业务拒绝或成功后才释放本地意图。条目改名、停用或原流水已结入工资单，不改变已成功录入的重放结果。旧客户端和不带编号的服务调用明确拒绝，不临时生成新编号兜底。结构升级见 `sql/migration_v79_payroll_adjust_intent.sql`；存量流水不补造录入编号。

## 3. 数据模型

表结构与列定义以 `sql/schema.sql` 为准，本节只记设计理由。

- `staff_piece_rate`：主键 `(station_id, product_id)`，`product_id = 0` = 默认价。库列只有每桶价、每层补贴、免费层数三项；距离补贴**从未实现，也没有建那个列**（建了不接线就是「配了也不生效」的悬空字段）。本表后加、存量水站无配置行，故**调用方必须用 `StaffPieceRate.defaults` 兜底**。
- `staff_earning`：`station_id` 记**履约站**；`unit_amount` 是单价快照；`payroll_id` 为 NULL 表示未结算。**`auto_uk` 的 NULL 是有意的**：人工调整 `order_id` 为 NULL → `auto_uk` 也是 NULL → 允许多笔独立录入；自动收益由 `uk_earning_auto` 兜底，调整单另由 `uk_earning_adjustment` 兜底，工资手工录入由 `uk_earning_intent(station_id,idempotency_key)` 兜底 —— 这与 `uk_ticket_consume` 那种「NULL 导致零保护」的坑形状相同但**语义相反**，改生成列前先想清楚。
- `staff_payroll`：`status` = 1 草稿 / 2 已确认 / 3 已发放；`total_amount` 必须等于本期明细之和；`uk_payroll_period` 保证同一人同一期间只有一张结算单。`staff_earning_item`：`direction` 决定符号、`status` 决定能否新录、`sort` 决定展示顺序。

结算单确认后其下明细写死，**不允许再改动**（要改只能对下一期做 `ADJUST`）；确认动作用 CAS（`StaffPayrollMapper.updateStatusTo`，第二个参数是目标状态）从草稿迁到已确认，并在确认前**重新核一次总额**。

## 4. 接口与权限

**站点一律取自 `AuthContext.requireStationId()`，忽略请求体里的 `stationId`**；所有按 id 的写操作都带 `station_id` 并检查受影响行数。以下除末行外均为站长端端点（`STATION_MANAGER`），站点校验 = 该对象必须属于本站。

- 单价：`GET` / `PUT /api/manager/piece-rate`（负值归零；没配过返回全 0 默认配置而不是 404）。
- 明细：`GET /api/manager/earnings?staffId=` 必带；带 `?payrollId=` 时返回该单明细并校验结算单归属。
- 结算单：`POST /api/manager/payroll` 生成（同期重复生成直接拒绝）、`GET` 列本站、`POST /{id}/confirm` 草稿 → 已确认（重复确认与他站结算单拒绝）、`POST /{id}/pay` 已确认 → 已发放并落 `paid_time` + `operator_id`（未确认直接拒绝）。
- 调整与条目：`POST /api/manager/payroll/adjust`（`itemId` 选填、`idempotencyKey` 必填，员工须与本站有履约关系，§2.10–2.11）；`GET` / `POST /api/manager/earning-items`（列表默认含停用，`?enabledOnly=true` 只取启用的）；`PUT` / `POST` / `DELETE /api/manager/earning-items/{id}`（含 `/status`）改名与改向（不改写已有流水）、启用与停用、删除（用过的拒绝并提示改为停用）；`GET .../directions` 下发加项/扣项文案（前端禁止硬编码 1/2 映射表）。
- 配送员自助：`GET /api/delivery/earnings`（角色 `DELIVERY` / `STATION_MANAGER`，`?from=&to=` 缺省 = 本月 1 日 ~ 今天），返回期间明细 + 期间合计 + 未结合计 + 我的结算单。

⚠️ **`GET /api/delivery/earnings` 的身份只取自 `AuthContext`，端点不接受 `staffId` 参数** —— 一旦接受，配送员改个数字就能看到同事的工钱。站长端那个端点**必须**带 `staffId`（他看全站），两者校验点不同，**不要合并成一个**。⚠️ **自助查询只按 `staff_id`、不按 `station_id`**：履约站跨站外派时可能与配送员所属站不同，带上站点过滤会让外派挣的那部分工钱凭空消失；站长结算用的 `listUnsettled(stationId, staffId)` 则必须锁本站 —— 这两组查询刻意不共用同一个方法。

⚠️ **所有期间查询的上界必须是「结束日 + 1 天」**（`endExclusive`）。写成 `<= 结束日` 时 `LocalDate` 会退化成 `<= 当天 00:00:00`，**今天的工钱一条都看不到 / 一条都结算不到**；`attachToPayroll` 与自助查询两处都适用。

## 8. 结算关系与连续读取历史（2026-10-08）

生成结算单先核本站持久 `staff_earning` 凭据；没有本站收益时，才核当前员工行属于本站且角色为 `DELIVERY` 或 `STATION_MANAGER`。无关系拒绝发生在查询或写入结算单之前。本站历史收益可支持转站、解绑、离职及员工行已删除后的清结，不依赖当前员工列表仍能列出此人；挂接收益、确认和发放仍各自校验本站。人工调整沿 §2.10 的原校验，没有借生成修复扩大权限。

`GET /api/manager/payroll` 保留数组响应，站别来自会话；`limit` 默认100、夹到1～500，可选正数 `beforeId`，按本站 `id` 降序读取 `id < beforeId` 的更早记录。站长页面默认每页100张，继续加载追加去重，刷新重置；失败保留原记录/游标供重试，并防旧请求覆盖。员工和期间筛选只作用于已加载范围，不能把本地筛选声称为服务端全历史查询。
