## 1. 目的与范围

登记**经营口径上尚未闭合的小项**：单位客户月结与发票、进货成本、桶损耗出账语义、客户特权、代客下单入口、挂空列与死代码、微信支付接入备忘、站长首页待办与桶异常处置。各项**相互独立**，可单独实施、单独裁剪，每节标注状态（已实施 / 部分实施 / 不做 / 未实施）。

不在范围内：订单与支付状态机本身、桶账与对账等式的实现口径（正本为 `docs/architecture/02-领域模型.md`、`docs/architecture/03-数据模型.md`）。事实基准：`src/**` > `sql/schema.sql` > 集成测试 > 本文。

## 2. 设计口径

### 2.1 单位客户月结与发票

分三层：**A 应收账款**（已实施）、**B 对账单**（未实施）、**C 发票**（只攒数据、不对接服务商）。

1. 挂账订单的 `payment_status` 仍是 `1 待收款`，**禁止发明新的支付状态值**（`constant/PaymentStatus.java`）——支付状态只前进、不倒滚。
2. `orders.settlement_status` 语义 = **该订单的应收是否已核销**，只前进（未结算 → 已结算），走 CAS（`OrderMapper.settleIfCollected`）。
3. **核销 ⟹ 已收款**，由 CAS 钉在 SQL 层（`settleIfCollected` 带 `payment_status = 2`）——B2B 最怕"账面销了、钱没到"。
4. 账期到期**不能自动改任何金额**，只能提醒（对齐"欠桶只提醒不阻断"）——本功能没有任何写金额的分支。
5. 账期是**站级**不是客户级：存 `customer_station_config.due_days` / `settlement_cycle`——判别式「同一客户 A 站月结、B 站可现结」。⚠️ **`company_info.due_days` 已无人读取**（列与数据留着，效果 = 账期清空、由站长重设）；`CompanyInfoMapper.updateDueDays` 已无调用点，是墓碑。
6. **账期必须快照进订单**：下单时 `ReceivableService.resolveDueDate` 一次性写 `orders.due_date`、之后只读（站长事后改账期不得改历史单到期日）；锚点是**当月最后一天**（`MONTHLY`），不是下单日。唯一例外是站长显式触发的「未结账单重算」（只改 `payment_status = 1` 且未取消的单，逐单留痕）。
7. **只有现金（货到付款）单才有应付日期**：微信即时到账、水票下单即视同已付都不产生账期；未设账期 → `due_date` 为 NULL。
8. **金额真相源仍是 `payment_status = 1 AND status <> 5`**，与 `DashboardMapper` 的待收款合计逐字同源；本功能只**加账期维度**，不新造金额口径。
9. `settlement_status` 只在**挂账单**（`due_date IS NOT NULL`）上有意义：即时结清的现金单在配送员当场收款时不自动置 2，由站长在台账核销——**范围边界，不是缺陷**。
10. 对账 **E10** `settlement_status = 2 AND (payment_status IS NULL OR payment_status <> 2)` **只查单向**，抓"账销了、钱没到"；反向（收了钱还没核销）**是正常经营状态**（送货上门当场收钱、站长之后才走月结）——改成双向比较，日结天天误报。
11. 发票只补开票信息字段（抬头 / 税号 / 邮箱 / 普票或专票），**不对接税控或电子发票服务商**；加字段却无读写入口正是 §2.6 的"挂空列"——**攒数据也要有地方填**，故与开票信息表单一起做。
12. **归属判据不能用 `CustomerMapper.getStationCustomer`**——其 SQL 带 `exists (select 1 from orders ...)`，是「客户画像」口径，会把**没下过单的新客户**判成"不属于本站"，而给新客户设账期恰恰最常见；一律用 `CustomerMapper.countCustomerOfStation`（绑定 **或** 本站订单，取并集）。

### 2.2 进货成本（只加字段，不做采购模块）

落点是 `inventory.cost_price`（可空）+ `GET /api/manager/gross-profit` 与 `PUT /api/manager/gross-profit/cost`；**不做采购 / 入库批次核算模块**（端点见 §3）。

1. 形态取**站级当前成本**，不取入库批次成本：成本变了就用新成本重算历史毛利（真实小水站就这么算账）；批次成本要加权平均 / 批次核算，属 ERP 规模，超出范围。
2. **没填成本的商品不给毛利数字**，而不是把成本当 0 相减——后者会让站长以为自己赚了整整一个售价，是最坏的一种"看起来正确"；前端 `totalProfit` 为 null 时同样**显示"算不出"，绝不能当 0 相减**。
3. **清除成本必须显式传 `clear: true`**：缺 `costPrice` 且没声明 `clear` 一律报错（`dto/CostPriceDTO`），否则客户端把键名拼错就是一次静默清空。
4. 成本字段**不向顾客端暴露**（越权与信息泄露红线同源）。
5. 缺成本的行**原样展示服务端下发的 `profitText`**（"未填成本，无法计算"），另列「未填成本的商品」快捷补录——前端不自己拼文案；**`costBasisNote` 亦原样展示**，不能改写成"当时的真实毛利"。
6. **后端下发给界面的文案不写 Markdown**：`costBasisNote` 里曾写 `**当前**`，而这段文字直接渲染到小程序界面，星号会原样显示。
7. **净利 = 水费 + 配送费 + 楼层费 − 进货成本 − 计件工钱**，六个数字必须取自**同一订单集合**（结算站 + 排除已取消 + 同一时间窗）——混两批单算出来的净利没有意义。故单数 / 费用那条 SQL **刻意不 join `order_item`**（join 了配送费会被明细行数放大）；工钱按 `staff_earning.order_id` 挂到这批订单上，不按工钱自己的 `create_time` 筛（否则"今天下单、明天送完"会让净利两天跳）。
8. **缺成本时 `netProfit` 与 `totalProfit` 一起为 null**——只 null 一个，站长会拿另一个继续当真。
9. 工钱只算**订单产生的计件**：人工调整（`order_id IS NULL`：迟到扣款 / 高温补贴）不进日净利；收入**不含押金**（可退的负债不是收入），"收入合计"与毛利的"水费收入"是同一个数、不得各算一套。
10. 已声明但**没接线的列一个都不建**（"悬空字段"教训，处置原则见 §2.6）。**已知口径边界（不是缺陷）**：收益在订单进入**送达**时才产生，故未送完的单暂时不计工钱，那几天净利偏高。

### 2.3 桶损耗出账（一个语义，不是一套模块）

**现状：语义位已有，缺的是写入口。** 已通用口子：`orders.barrel_discrepancy` / `barrel_discrepancy_note`（订单级空桶差异）、`DeliveryController` 的"水桶破损"异常上报、`order_barrel_exception`（桶异常单）、`BarrelRecordType` 的 `6 人工调整(增)` / `9 人工调整(减)`、`station_adjustment` 的 `BARREL_REVOKE`（站长撤桶权益）。而 `BarrelRecordType` 的 `3 丢失` / `4 损坏` / `5 赔偿` **已声明、已纳入 E5 对账，但全仓零写入**。

- `3` / `4` 已在 E5 的 UNION 里（`ReconciliationService` 按 `type IN (3, 4)` 记负）；真正的问题是**没有任何接口或流程会产生 type=3/4/5**。后果很具体：E5（物理桶守恒）报不平时，分不清"是账写错了"还是"桶真的坏了、丢了"，也算不出"今年损耗了几个桶"。
- **与「客户欠桶」的区分**：客户欠桶 = `customer_barrel_over` 为正（客户手上端的桶比权益多），已有台账与站长只读入口 `GET /api/manager/owed-barrels`；本站桶损耗 = 水站自己的资产没了、与具体客户无关（配送员丢桶、仓储破损、报废）。**两者不要混用同一个字段**，否则"客户欠桶"会被损耗数据污染。
- 不用做固定资产模块、不用给桶编号（`customer_barrel_asset` 只记数量、`BarrelLedgerService` 是唯一写入口，这个实现是对的）。

**决策：不做桶损耗出账，只保留一个只读读数出口。** 理由在业务模式里——**桶是跟水厂换的**：水站把空桶交回水厂、换回满桶，桶是水厂的资产，破损与丢失由水厂承担，**不是水站的账**。

1. ⚠️ **硬约束**：新增 `BarrelRecordType` 必须**同步扩展 `ReconciliationService` E5「物理桶守恒」的 UNION 项**，否则补录之后对账会误报（正本 `constant/BarrelRecordType.java` 类注释）。据此，`3` / `4` / `5` **保持休眠**——⚠️ **不要因为它们空着就把它们从 E5 的 UNION 里删掉**：空集对等式没有任何影响，删掉之后真有人（如将来水厂侧对接）写了 3/4，日结就会开始误报。
2. 客户弄丢 / 欠着的桶**不在这个口径里**（那是 `customer_barrel_over`，欠桶台账、应收口径），两者不混用同一字段。
3. 只保留一个只读出口 `GET /api/manager/barrel-loss?from=&to=`：站长角色、站取自 `AuthContext`、按商品汇总 3/4。用途只剩两个——让站长确认"系统确实不记这项"，以及将来水厂侧要记账时有个现成的读出口。**写入口不存在，也不要补。**
4. ⚠️ **界面上不许把 0 显示成"损耗 0 桶"**（会被读成"没丢过桶"）。**产品裁定：界面读数整个下线**——不是"改成更聪明的展示"，而是**彻底不显示**（原先那张卡正常情况下恒为 0，还要配一句"0 表示没登记过"的免责声明，收益低且误导）。⚠️ **端点与用例都留着**（它是明确保留的读出口）——「**有读数出口 ≠ 界面上要显示它**」。

**读数的一条现实（将来真要统计时才会用到）**：真实库里"少桶"其实有数据（`order_barrel_exception` 有行），但配送员完成配送时选的 `lost` / `damaged` / `customer_kept` 只被拼进 `orders.barrel_discrepancy_note` 与异常单的 `staff_note` **自由文本**，没有落成可聚合的分类字段；想按"损坏 / 丢失"统计得先把分类落成字段。**不为统计去解析自由文本**（那种做法迟早把备注里的"少2桶(客户留存)"算成损耗）。

**修法备选（未实施）**：给桶流水的 `note` / reason 收敛出 `报废 / 丢失 / 破损 / 盘点差异` 几个**枚举类型**（照 `constant/*.java` 的做法，不要自由文本），或新增 `BarrelRecordType` 值——新增类型必须同步 E5。在没想清"桶是客户弄丢还是水站在库房里破损"（前者应走 `over` 增加，后者才是水站自有资产减少）之前，不动桶账守恒等式。

### 2.4 客户特权（把横向分层换成纵向配置）

`customer_privilege` 表 + `constant/PrivilegeType` + 站长端 `GET/POST /api/manager/customers/{id}/privileges`（列表 / 授予 / 撤销）；`NO_MIN_ORDER`（免起送门槛）**已真正接进计费链路**（`DeliveryFeeService.calcForOrder` 带 `customerId`，`DeliveryFeeUtil.compute` 有 `noMinOrder` 重载）。

**模式先例**：`customer_station_config.offline_payment_enabled`——站长在客户画像里逐个开通货到付款，**全系统唯一控制点、无站点级总闸**；已在跑，也是行业习惯（老客户才给到付）。

**风险**：如果"特权"是任意维度，它会退化成无类型的 JSON → 没有校验、没有展示口径、没有对账，等于"没有规则"。**本仓铁律：语义由类型决定**（`DepositType.isIncrease`、`AdjustType`），**不靠调用方自觉**——故特权必须收敛成有限枚举。形态：`customer_privilege(customer_id, station_id, type, value, ...)`。

**type 清单（`constant/PrivilegeType`）**：`NO_MIN_ORDER`（免起送门槛，不动钱）**是唯一已实现的类型**——校验时读一个开关，已接入 `DeliveryFeeUtil`；`DISCOUNT_RATE`（折扣，**动钱**）未实现，必须影响计价 → 走 `PriceUtil` 口径 + 订单快照；`FREE_DELIVERY_TIMES`（免配送次数，**动钱**）未实现，必须是**账户 + 流水 + 幂等 + 对账**；`TICKET_RETURNABLE`（允许退票，动钱）未实现，校验时读开关；`OFFLINE_PAYMENT`（货到付款，不动钱）**不落在本表**——已由 `customer_station_config.offline_payment_enabled` 承担。

1. **`isImplemented` 与 `isMoneyAffecting` 是两个必须分开的概念**——前者决定"能不能授予"，后者决定"该不该用账户 + 流水实现"。
2. **未实现的类型在授予时直接拒绝并给出原因**，而不是收下一行"配了也不生效"的特权；**可授予清单只返回已实现的类型**（未实现的连选项都不给前端，避免"选了却没反应"）。
3. **撤销本来就不存在的特权要报错**，不能无条件返回成功（拿不到受影响行数就不许返回 success）。
4. **判据：能影响钱的 type 必须是账户 + 流水，不能是画像上的开关**——"免配送次数""折扣"做成 UI 开关就会出现"站长说还有 3 次、客户说还有 5 次"的扯皮。
5. **归属口径的根因（已收口）**：`CustomerPrivilegeIntegrationTest` 曾三例全红，根因不是环境，而是**归属判据用错了口径**（同 §2.1 口径 12）：新客户一律被判成"不属于本站"，而免起送门槛的典型场景恰恰就是新客户第一单；改用 `countCustomerOfStation` 后全通过。
6. ⚠️ **通用判据**：**看到"大批用例同时红"，先看 `AquaFlowApplicationTests` 的 `Caused by`，不要逐个查业务断言。** 当时走 Spring 的用例一次全红、只有纯单元用例通过，根因是 `ProductImageResolver` 声明了两个构造器且都无 `@Autowired` → Spring 找不到默认构造器 → **上下文加载失败**。隔离验证手法见 `docs/audit/test-harness.md`。

### 2.5 代客下单入口

后端与护栏已存在，页面已补齐：`miniapp-delivery/pages/station-mgmt/place-order/`（客户 → 地址 → 商品 / 试算 → 下单），入口在站长端首页「代客下单」。

1. **复用** `POST /api/orders/create`，**不新建单端点**——两条建单路径各算金额 = 重演"计价双轨"（见 `util/PriceUtil` 文件头：结算页报价与下单落单各算各的，客户看到的价格与订单金额不一致）；金额全部由服务端下发，页面里没有任何金额算术。
2. `source` 固定 `1 电话`（站长代录）：`orders.source` = `1 电话 / 2 微信 / 3 小程序`；顾客端显式传 `3`，后端缺省值为 `2`。
3. 归属护栏用 `countCustomerOfStation`（绑定 **或** 本站订单，取并集）：⚠️ **老客户完全可能没有 `customer_station_config` 行**——只查绑定行时，客户列表里点得到他，一下单却说"该客户不属于本水站"。放宽是安全的：只有与本水站已有关系的客户才放行，他站客户两条都不满足。
4. 客户选择器走 `GET /api/manager/order-assist/customers?keyword=`：⚠️ **不能复用 `GET /api/customers`**——它是 orders 驱动（客户画像口径），**站长刚建档、还没下过单的客户一行都查不出来**，而"给新客户下第一单"恰恰是代客下单最常见的场景。
5. 客户地址走 `GET /api/manager/order-assist/customers/{id}/addresses`：⚠️ **`GET /api/addresses` 是顾客自助端点**（身份取自 `AuthContext.requireCustomerId()`），站长调它只会看到自己的地址——页面根本拿不到"这个客户送到哪"。
6. 试算走 `POST /api/manager/order-assist/quote?customerId=`，请求体**直接复用** `PaymentQuoteDTO`：`POST /api/payments/quote` 同样要求顾客身份，站长调不到，而电话叫水时"这单多少钱"是站长必须当场回答的。**`customerId` 走查询参数而不加进 DTO**——那个 DTO 是顾客端共用的，一旦带上 `customerId`，将来有人顺手在顾客端改成"用它指定的 customerId"就是一次越权。
7. 客服电话取 `GET /api/stations/{id}/public-phone`（公开、免登录、只回 id / name / phone），**优先调公开接口、本地缓存只兜底**：只读本地缓存的 `selectedStation` 快照（不保证带 `phone`）会让部分客户的按钮永远提示"暂未获取到客服电话"。

**为什么必须补这个入口**：顾客打电话给站长后，站长若在系统外记账 → **该单的桶流动不落库** → 顾客端看不到、桶账不更新、对账不平。**这是核心资产（桶账真实）的唯一支柱**：所有桶的流动都过 `BarrelLedgerService`，站长在系统外接单就破了这个前提。若确实不做页面，至少要让站长能把线下单补录进来（现状：资产调整单能补桶、补票，**补不了订单**）。

> ⚠️ **判据：界面上不放假数据。没有数据源就不展示，而不是填一个"看起来合理"的值。** 顾客端客服页曾展示编造的微信号（`Station` 实体根本没有微信字段）与硬编码工作时间 `08:00-20:00`（同样没有数据源），二者已删除；要重新展示，先给 `Station` 加字段并让站长可配。客户按假的营业时间打电话、或复制一个不存在的微信号，比不显示更糟，且**不报错、只静默误导**。

### 2.6 挂空列、死代码与未实施入口

**每一条都要二选一：接上或删掉；留存必须留下"为什么留"的注释。挂空列比没有更危险**——下一个人会以为它在生效。

### 3.1 桶异常处置入口的开放方案（未实施）

**现状：缺的只是界面，后端与用例都在位。** 已有 `POST /api/manager/exceptions/{id}/handle`（记录站长决定：APPROVE / MODIFY / IGNORE / ESCALATE + 补偿明细）与 `POST /api/manager/exceptions/{id}/execute`（真正执行：退水票 / 退现金 / 撤桶权益）；契约由 `BarrelExceptionFlowIntegrationTest` 钉住——补偿执行失败整体回滚并**退回 `STAFF_RECORDED` 可重试**、同时投 SYSTEM 告警；重复 handle / execute 被拒；他站站长处置不了本站单。难点不是"按钮放哪"，而是**这两个接口会真的动钱和桶账**，故方案按"先把风险关进笼子"设计。

**A. 分两批开放（推荐先做 A1）**：**A1（最小动作集）**只开放两个动作——① **忽略**（`IGNORE`，一分钱不动）；② **按系统建议补偿**（`APPROVE`，且补偿明细**只能等于**后端下发的 `suggestedTicketQty` / `suggestedCashAmount`）。即站长只能"确认后端算出来的补偿"或"否决"，**不能手工填金额**——每一分钱都能由后端复算、可审计。**A2（完整）**再开放手工填写补偿明细（DTO 早已支持 `refundTicketQty` / `refundCashAmount` / `adjustAssetQty` / `adjustProductId`）。

**B. 无论 A1 还是 A2 都必须有的五条护栏**

1. **两步走，不合并**：第一步「登记处理意见」（动作 + 补偿明细 + `managerNote` 必填），第二步「确认执行」——第二步要把**将要发生的动作逐条列出来**再让人点确认（"将退水票 3 张（18.9L）、退现金 ¥30.00、撤桶权益 2 个"）。既有事故有"界面说做了、账上没做"，而反向的"钱多退了"同样不会报错。
2. **补偿项必须成对（数量 + 商品）**：退水票缺 `adjustProductId` 会被后端拒（这是**有意**的护栏，按商品各算才能对上批次单价）；界面上"退水票"不选商品**不允许提交**，而不是提交后等后端报错。
3. **一次只处理一张单**：不做批量执行、不做"全部同意"——一个填错的口径会被批量放大 N 倍。
4. **失败必须留在页面上**：`execute` 失败时后端已回滚到 `STAFF_RECORDED` 可重试，界面要把 `message` 原样显示并提供"重试"，**不能只弹一个 toast 就消失**。
5. **留痕**：`managerNote` 必填（一句人话理由）；执行后该单不可再改（状态 CAS 已保证）；执行与忽略都会投一条 OPERATION 告警（站长自己的告警列表里能看到）。

**C. 明确不做的**：不做"一键补偿全部待处理单"、不做自动补偿（金额必须有人确认）；不把处置入口开放给配送员（类上 `@RequireRole("STATION_MANAGER")` 保持）；不在这个页面里顺带做"调整资产"的自由录入——那是站长资产调整单的正门。

**D. 开放前的最后一道检查**：拿真实库的一份数据副本，跑一遍 `handle → execute` 的完整链路并核对三条账（水票 E8、押金等式1、桶账 E3/E5）仍为 0——后端用例已覆盖，但真实库的索引 / 配置与测试库不完全等价。
