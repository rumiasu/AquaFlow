## 1. 部署形态

单进程 Spring Boot 应用 + 单个 MySQL 实例。**当前假定单实例部署** —— 限流计数与部分定时任务尚未做多实例改造（见 §8）。

| 组件 | 要求 |
|---|---|
| JDK | 17 |
| MySQL | 8.4 |
| 内存 / 磁盘 | 按水站数量评估；桶账与流水表是主要增长点 |

外部依赖都是**可选**的：腾讯云 COS（不配只影响图片上传）、告警 Webhook（不配则告警只落库）。

## 2. 配置

**所有配置走环境变量**，仓库内不落任何生产配置。变量清单的权威来源是
`AquaFlow-backend/.env.example`。分三类：

### 2.1 启动期硬校验（缺一即拒绝启动）

| 变量 | 约束 |
|---|---|
| `JWT_SECRET` | **长度必须 ≥ 32**，否则拒绝启动 |
| `WX_APP_ID` | 必填 |
| `WX_APP_SECRET` | 必填 |

### 2.2 生产环境必填

| 变量 | 说明 |
|---|---|
| `WX_STAFF_APP_ID` / `WX_STAFF_APP_SECRET` | 员工端微信登录。`application-prod.yml` 里无默认值，缺失即拒绝启动 |
| `DEV_LOGIN_ENABLED` | **生产必须为 `false`**。该开关提供免微信的开发者登录通道 |

### 2.3 不被硬校验（缺失后果由各组件决定）

`COS_SECRET_ID` / `COS_SECRET_KEY`、`DB_*`、`CORS_ALLOWED_ORIGINS`、`RATE_LIMIT_*`、
`MOCK_WECHAT_PAY`、`MYBATIS_LOG_IMPL`、告警相关变量。多数只 `log.warn`。

> ⚠️ **不要把它们写成「缺一即启动失败」** —— 只有 §2.1 的三项会拒绝启动。

### 2.4 Profile

| Profile | 用途 | 说明 |
|---|---|---|
| `local` | 本地开发 | 密钥读 `src/main/resources/application-local.yml`（**已 gitignore，含真实密钥，禁止提交、禁止回显**）。该文件还开着 dev-login 与微信**模拟支付渠道**，并按 IP 关掉了登录限流 |
| `prod` | 生产 | `--spring.profiles.active=prod` + 纯环境变量 |

## 3. 启动与停止

```bash
cd AquaFlow-backend
./gradlew bootRun                 # 开发
# 生产：构建后以 prod profile 启动，环境变量由部署环境注入
```

依赖 MySQL 就绪。**代码与数据库结构的顺序**：破坏性 DROP 类迁移必须**先上代码、再执行 SQL**（见 §4）。

## 4. 数据库迁移

**项目未启用 Flyway**：`sql/**` 全部靠手工执行，没有版本表、没有自动校验。

> **迁移清单与逐条执行证据的正本是 `AquaFlow-backend/sql/README.md`。**
> 本文不复述清单 —— 有正本就不要在两处定义同一份事实。

### 4.1 新建库

权威基线是 `AquaFlow-backend/sql/schema.sql`（全 `CREATE TABLE IF NOT EXISTS`，可重复执行）。

```bash
cd AquaFlow-backend/sql
mysql -uroot -p <库名> < schema.sql
```

> ⚠️ **必须走 shell 重定向（`<`）导入。** 不要用 PowerShell 管道
> （`Get-Content -Raw | mysql` 会按控制台代码页重编码，把中文注释写成乱码）。
> 核对是否写坏要**比字节**（`HEX(TABLE_COMMENT)`），不要看控制台输出。

### 4.2 老库升级

按 `sql/README.md` 的「基线之后必须补跑的迁移」顺序补跑，**执行务必带库名**：

```bash
mysql -uroot <库名> < 脚本.sql
```

> ⚠️ 该清单**已知有缺陷**（见 `sql/README.md` 与 `AGENTS.md` §4：漏列部分脚本、个别脚本之间存在顺序冲突）。
> **执行前人工核对**，不要盲跑。

### 4.3 脚本约定

- **迁移脚本必须幂等。** MySQL 8.4 没有 `DROP ... IF EXISTS`，统一用 `information_schema` 预检 + `PREPARE`。
- **破坏性 DROP 必须先上代码、再执行 SQL**，执行前先 `mysqldump`。
- ⚠️ **MySQL 在解析期校验列名**：脚本里对某列的 `MODIFY` / `WHERE col` 即使执行不到也会报 1054 ——
  删列时必须把**历史迁移里对该列的引用一并清掉**。
- 新建脚本前先 `ls sql/` 看编号是否占用，**不要照任何清单的最后一个数字 + 1**。

### 4.4 严禁在生产执行

`sql/reset_data.sql`、`sql/clear_data.sql`（都是 TRUNCATE 多表）、
`reconcile_order_814.sql`、`seed_dev_account.sql`、`seed_new_user_83.sql`、`sql/archive/**`（已过期且不可执行）。

## 5. 备份与恢复

- **执行任何破坏性迁移前先做 `mysqldump`**，备份文件放仓库外的备份目录（`backup/` 已被 gitignore，**勿提交**）。
- 恢复即用 `mysql <库名> < <备份文件>`。恢复后按 §6 跑一次对账，确认账目自洽。
- 备份里含真实客户数据，**按生产数据对待**：不外发、不进仓库、不进对话。

## 6. 对账作业

系统维护三条独立账线（桶 / 水票 / 押金）加支付与计件工资，各由守恒等式校验，
结果每日落 `reconciliation_result` 表（每检查项一行）。

| 项 | 说明 |
|---|---|
| 定时执行 | 每日定时任务写全平台对账结果 |
| 站长端查询 | `GET /api/manager/reconciliation`，**只读本站即时对账**（只有 `GET`）。原 `POST /run` 会写全平台结果 = 跨租户泄露，**已删除、不要加回** |
| 结果表 | `reconciliation_result` |

### 6.1 等式设计约束

⚠️ **写等式前先问：这个状态在正常经营里会不会合法出现？会就不能进差异计数。**
以下三种曾导致「日结永远不平」：

1. 核销只置 `payment_status = 2` 而不补 PAID 流水 → **收款必须两步**：先记流水（幂等）再 CAS 置状态。
2. 把 `order_id IS NULL` 当成孤儿 → **无订单在线购票是合法业务**。
3. 把配送中桶的 `DELIVERED` 状态当成异常 → **它是合法终态**。

### 6.2 告警分级

`alert_log` 表按类型分级投递，方向由 `AlertType` 决定，**不靠字符串比较或调用方自觉**：

| 类型 | 含义 | 投递给 | `station_id` |
|---|---|---|---|
| `SYSTEM` | 系统故障：对账不平、桶异常补偿失败、未预期 500 | **系统管理员** | 必须 NULL |
| `OPERATION` | 运营故障：桶异常待处置、补偿已执行、异常被忽略 | **该站站长** | 必填 |

**三条硬约束**：① 先落库再谈渠道（没配 Webhook 则 `notify_status = LOGGED`）；
② 落库走**独立事务**（`REQUIRES_NEW`，必须经代理调用）；③ 失败**绝不连累业务**。

> ⚠️ **系统告警没有 HTTP 入口** —— 漏给站长等于跨租户 + 越权知情。

**运维查询系统告警**：

```sql
select * from alert_log where alert_type = 'SYSTEM' order by id desc limit 50;
```

站长端只读 `GET /api/manager/alerts`。

## 7. 常见故障

| 现象 | 原因 | 处置 |
|---|---|---|
| 启动即失败，抛 `IllegalStateException` | §2.1 的三项之一缺失或 `JWT_SECRET` 短于 32 | 补环境变量 |
| 接口返回 401 | 未认证；或访问了不在公开白名单里的端点 | 检查 `Authorization` 头与 `WebMvcConfig` 白名单 |
| 真机微信登录失败，日志 `40013 invalid appid` | code 与 appid 不配对 | 确认两端 appid/secret 与签发 code 的那个一致 |
| 真机请求报「不在以下 request 合法域名列表中」 | 两处开关未同时打开 | ① `project.config.json` 的 `urlCheck` 为 `false`；② 真机右上角 `…` →「打开调试」 |
| 业务操作"看着成功但没生效" | 业务错误仍返回 HTTP 200 | **判响应体 `code`**，不要判 HTTP 状态 |
| 日结对账不平 | 见 §6.1 三种成因 | 先确认不是把合法业务状态算成了差异 |

## 8. 已知运维边界

- **单实例假定**：登录限流是内存计数；多实例部署前必须换成集中式计数器（如 Redis）。
- **微信支付未接入**：没有第三方支付回调面。⚠️ 本地模拟渠道（`MOCK_WECHAT_PAY`）在**生产必须关闭**。
- **客户端正向进度通知未接入**：站长端只有应用内红点。
- 本地开发与联调的特殊做法（不买服务器、局域网真机预览、appid 组合）见
  [`../本地运行-笔记本当服务器.md`](../本地运行-笔记本当服务器.md)。

## 9. 待确认事项

| 待确认内容 | 需要的验证手段 | 影响 |
|---|---|---|
| `sql/README.md` 的必跑清单与脚本实际需要是否一致（已知漏列与顺序冲突） | 在一个从早期基线重建的库上逐条核对清单，跑一遍全量测试 | 漏跑会让老库缺表缺列，运行时报 1054；这是当前最可能踩的运维坑 |
| 定时对账任务的具体执行时间与失败重试策略 | 读定时任务配置确认，并确认任务失败是否有告警 | 对账不跑或跑挂会静默失去账目保护 |
| 多实例部署所需的改造清单 | 压测确认单实例上限后再评估 | 限流可被分摊绕过；定时任务可能重复执行 |
