# 数据模型

> **表结构与字段的正本是 `AquaFlow-backend/sql/schema.sql`，本文不复述列定义。**
> 本文只说明：表按什么分组、每张表承担什么职责、金额的真相源在哪。
>
> 表数与字段以 `schema.sql` 实测为准（下表为 2026-09-23 的 50 张表）。
> 迁移脚本的清单与执行证据登记在 `AquaFlow-backend/sql/README.md`。

## 1. 分组总览

| 分组 | 表数 | 职责 |
|---|---|---|
| 客户与水站（主数据） | 11 | 全局客户身份、客户与水站的关系、组织与人员 |
| 商品与库存 | 4 | 通用商品库、站级定价、站长自定义商品、库存 |
| **桶账** | 9 | 桶权益批次、汇总、过占、配送中、退桶、异常、人工调整 |
| 订单与履约 | 6 | 订单、明细、转单、模板、图片 |
| 支付与资金 | 3 | 支付流水、押金账户与流水 |
| 水票 | 5 | 批次、账户汇总、流水、档位套餐、站级折扣 |
| 配送计费与计件工资 | 5 | 站级计费配置、计件单价、收益、结算单 |
| 运营支撑 | 7 | 公告、反馈、文件、审计、令牌、对账、告警 |

## 2. 客户与水站

| 表 | 职责 |
|---|---|
| `customer` | 客户（**全局身份，无 `station_id` 列**） |
| `customer_station_config` | 客户 × 水站的配置：线下支付授权、**账期**（`due_days` / `settlement_cycle`，自 v60 起账期为站级） |
| `customer_privilege` | 站长按客户逐个开通的特权；**只承载不动钱的类型** |
| `customer_notification` | 客户侧通知记录 |
| `address` | 收货地址（多地址、标签、经纬度、楼层与电梯） |
| `company_info` | 企业客户资料（⚠️ 其 `due_days` 列已无人读取，账期改由 `customer_station_config` 承担） |
| `customer_enterprise_apply` | 企业身份申请（受 `app.enterprise.enabled` 开关控制） |
| `station_enterprise_config` | 站级企业身份提示阈值；无行 = 用平台默认 |
| `station` | 水站（含营业状态与坐标） |
| `staff` | 员工（站长 / 配送员） |
| `staff_station_application` | 配送员与水站的绑定 / 解绑申请审批 |

⚠️ **`customer` 表永远不加 `station_id` / `owner_station_id`。** 订单、桶、水票、押金一律按
`(customer_id, station_id)` 隔离；「经营归属」是「绑定 ∪ 本站订单」的并集口径，不是字段。

## 3. 商品与库存

| 表 | 职责 |
|---|---|
| `product` | 商品表。**通用商品库 + 各站自定义商品**，靠可空的 `owner_station_id` 做逻辑隔离（NULL = 通用库） |
| `product_submission` | 站长自定义商品上报通用库的登记表（平台侧人工处理） |
| `inventory` | 库存 |
| `inventory_record` | 库存流水 |

商品类别用于桶账判定（`category = 1` 为循环桶，桶数与计费只数这一类）。

## 4. 桶账（系统核心）

| 表 | 职责 |
|---|---|
| `customer_barrel_lot` | **桶权益批次（押金条）：金额的唯一真相源** |
| `customer_barrel_asset` | 按 `(客户 × 水站 × 商品)` 的桶权益**派生汇总** |
| `customer_barrel_over` | 过占桶。**允许为负**（顾客多还的桶寄存在水站，是合法状态），按商品各算 |
| `customer_barrel_in_transit` | 配送中桶：已付款买下权益但尚未送达。送达后转为批次并计入权益 |
| `barrel_record` | 退桶申请与审批记录 |
| `barrel_record_lot` | 退桶时的权益批次核销明细（纯还桶不写本表） |
| `station_adjustment` | **站长资产调整单：人工补录 / 订正的唯一合法来源**，带反向单撤销与幂等键 |
| `order_barrel_exception` | 桶异常单（登记 → 处置 → 核销或撤回权益） |
| `station_exception_config` | 站级桶异常配置 |

**两条写入口约束**：

- 桶账的唯一写入口是 `BarrelLedgerService`；权益核销按 FIFO 逐批次消耗。
- 唯二可以绕开常规通道撤销权益的入口是 `station_adjustment` 与 `order_barrel_exception`
  对应的两条服务路径，**只应由站长人工发起并留单据痕迹**。

⚠️ 汇总类查询**必须取 `customer_barrel_lot`（或 `asset`）∪ `customer_barrel_in_transit`(PENDING) ∪ `customer_barrel_over`
的并集**。只遍历 `customer_barrel_asset` 会让「首单还在配送途中」的商品整行消失。

## 5. 订单与履约

| 表 | 职责 |
|---|---|
| `orders` | 订单。含三个水站列（`station_id` 归属站 / `delivery_station_id` 履约站 / `settle_station_id` 结算站）、费用列（配送费、楼层费各自成列）、账期快照（`settlement_status` / `due_date`） |
| `order_item` | 订单商品明细（计件工资按此逐商品计算） |
| `order_transfer` | 转单 / 外派记录。**转单状态一律查这张结构化表**，不要用 `special_note LIKE` |
| `order_template` | 常用订单模板 |
| `order_template_item` | 模板明细（一对多） |
| `order_image` | 订单图片（配送照片） |

**金额列只加不改**：配送费与楼层费绝不并入 `water_amount` 或 `deposit_amount`
（后者可退，混入会导致取消时多退钱）。

## 6. 支付与资金

| 表 | 职责 |
|---|---|
| `payment_record` | 支付流水。`station_id` 在**发起收款时**按结算站写死；换站由专用路径搬移，且**只搬 `PENDING`** |
| `customer_deposit_account` | 客户按水站隔离的押金账户余额 |
| `deposit_record` | 押金流水（**方向由类型决定，扣减类以负数落库**） |

**三条关键约束**：

- `uk_payment_active_order` = **一单一条活跃流水**（用 STORED 生成列实现的部分索引）。
  已有待收款流水时再插一条 `PAID` 必撞 1062，导致整笔送达回滚。
- **收款必须两步**：先记流水（幂等），再用 CAS 置 `payment_status = 2`。
  只置状态不补流水会让日结对账永远不平。
- `order_id IS NULL` **不等于孤儿**：无订单的在线购票是合法业务，判定孤儿流水时必须排除。

## 7. 水票

| 表 | 职责 |
|---|---|
| `ticket_lot` | **水票批次（单价快照）：余额的唯一真相源** |
| `ticket_account` | 水票账户**派生汇总**，必须等于 Σ 批次余额（对账校验） |
| `ticket_record` | 水票流水（记录消耗时的单价，供退款按原价回补） |
| `ticket_package` | 水票档位套餐（站级定价结构，**不是促销引擎**） |
| `station_ticket_discount` | 站级统一折扣档位：某款水没有自己的定制票时，按它打折卖票 |

**水票单价取实付均价**（`payment_record.amount / ticket_qty`）；消耗按 FIFO；
退款按流水里的当时单价还原。**任何改动水票数量的路径都必须过批次账**，
漏一条对账等式就报不平。

⚠️ `ticket_record` 的 `uk_ticket_consume(order_id, product_id, source)` 在 `order_id IS NULL` 时
**零保护** —— 无订单购票的幂等必须靠客户端幂等键（`uk_payment_idempotency`，且必须带 `customer_id`）。

## 8. 配送计费与计件工资

| 表 | 职责 |
|---|---|
| `station_delivery_config` | 站级配送计费配置（起送量 / 配送范围 / 运费 / 楼层费）。**无行 = 未配置，等同全 0 不拦单** |
| `staff_piece_rate` | 站级计件单价（`product_id = 0` 表示该站默认价） |
| `staff_earning` | 配送员收益明细。**工钱走独立对账等式，不进客户对账** |
| `staff_earning_item` | 站长自定义工资条目（加项 / 扣项字典）。**只是人工调整流水上的标签**，不参与自动计算 |
| `staff_payroll` | 工资结算单（草稿 → 已确认 → 已发放）。确认后明细锁定 |

**计件单位是桶不是单**，按 `order_item` 逐商品计。收益只在「送达」的状态 CAS **成功之后**产生，
因此免疫取消。结算单的期间上界必须用「结束日 + 1 天」，写 `<= 结束日` 会让当天收益一条都结算不到。

## 9. 运营支撑

| 表 | 职责 |
|---|---|
| `notice` | 公告（`status` = 0 下架 / 1 发布） |
| `feedback` | 意见反馈 |
| `file_info` | 文件管理（腾讯云 COS 对象登记） |
| `audit_log` | 审计日志 |
| `user_token` | 令牌记录（支持服务端失效） |
| `reconciliation_result` | 对账结果：每日每检查项一行 |
| `alert_log` | 分级告警：系统故障 → 系统管理员；运营故障 → 该站站长 |

**对账等式不能把「合法业务状态」算成差异。** 三条已实测踩过的坑：

- 核销只置 `payment_status = 2` 而不补 `PAID` 流水 → 每核销一单就报不平；
- 把 `order_id IS NULL` 当成孤儿 → 无订单购票是合法业务；
- 把 `customer_barrel_in_transit.status = 'DELIVERED'` 当成异常 → 它是合法终态。

**写等式之前先问：这个状态在正常经营里会不会合法出现？会就不能进差异计数。**

## 10. 待确认事项

| 待确认内容 | 需要的验证手段 | 影响 |
|---|---|---|
| **`station.creator_staff_id` 是死列** | 先确认"站长只能改自己创建的水站"这条语义是否要做；要做就必须让 `StationMapper.insert` / `update` 真的带上该列 | 代码里 `StationController` 调了 `station.setCreatorStaffId(...)`，但该表的 `INSERT` / `UPDATE` 语句**都不含这一列**，值被静默丢弃；归属校验实际走 `staff.station_id` 子查询。该列也不在 `schema.sql` 里，仅由 `migration_fix_schema_alignment.sql` 添加 —— 即新旧库结构不一致，且两边都用不到它 |
| 基线缺索引 `barrel_record.idx_barrel_record_station` | 补进 `schema.sql`（`migration_fix_schema_alignment.sql` 里有） | 按基线新建的库缺这个索引，旧库有 → 同一查询在新库上是全表扫。仅性能差异，无正确性影响 |
| `migration_fix_schema_alignment.sql` 不在 `sql/README.md` 的必跑清单里 | 核对清单与脚本，把该脚本补进「基线之后必须补跑的迁移」并标明顺序位置 | 老库升级若漏跑它，会缺 `barrel_record` 的 5 个列与索引、`ticket_account` 的 `product_id` / `update_time`、`order_template` 的 `station_id`、`order_template_item` 的索引 —— **这些列是被代码真实读写的**，缺了会在运行时报 1054 |
| 10 张表缺少表级 `COMMENT` | 补一条迁移脚本统一加上；影响面仅注释 | 无 `COMMENT` 的表：`barrel_record`、`company_info`、`customer_notification`、`deposit_record`、`order_template`、`order_template_item`、`staff`、`station`、`ticket_account`、`ticket_record`（2026-09-23 实测，其余 40 张均有且内容正确） |
| `order_barrel_exception` 与 `station_exception_config` 的注释是英文 | 统一改成中文，与其他 48 张一致 | 仅一致性问题 |
| `company_info.due_days` 已无人读取 | 确认无历史依赖后决定是否删列 | 账期已迁至 `customer_station_config`；删列属破坏性 DROP，须先上代码再执行 SQL |
| `customer_owed_barrel` 已停止写入 | 复核所有写入点后确认可删 | 欠桶现读 `customer_barrel_over` |
