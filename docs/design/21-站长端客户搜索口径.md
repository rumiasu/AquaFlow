## 1. 目的与范围

本文是「站长端怎么搜客户」的**正本**：候选集怎么取、关键字怎么归一化、相关性怎么打分、边界怎么兜。

需求来源：站长的输入习惯与姓名检索不同 —— **更注重地址**，最多记个姓氏。于是有三种典型输入：**缩写**（「阳光小区8栋1单元301」打成「阳光81301」）、**不爱打空格/标点**（「8-1-301」与「81301」是同一个地址）、**中文数字与阿拉伯数字混用**（「八栋」与「8栋」是同一个地址）。

旧的 `LIKE '%关键字%'` 强子串匹配对这三种输入**全部失配**，另有一个更隐蔽的问题：**SQL 粗筛只能宽、不能窄** —— 一旦在 SQL 里带关键字过滤，本该命中的候选在进入打分之前就被滤掉。因此口径分两步：**SQL 只取候选集（不带关键字），归一化与相关性打分全部在 Java 里做**。

范围不含：拼音首字母、把 `/api/search` 的地址块与订单块改成同口径、单站客户破万后的检索引擎、多关键词拆词（均见 §8）。

## 2. 三个入口，同一份实现

| 入口 | 端点 | 服务方法 | 口径 |
|---|---|---|---|
| 客户列表 | `GET /api/customers?keyword=` | `CustomerServiceImpl.listStationCustomers` | **画像口径（orders 驱动）**：有本站订单的客户；命中项回填 `addressText` 供展示 |
| 代客下单选择器 | `GET /api/manager/order-assist/customers?keyword=` | `CustomerServiceImpl.searchStationCustomers` | **并集口径（绑定 ∪ 本站订单）**：只绑定、没下过单的新客户也搜得到 |
| 综合搜索 | `GET /api/search?keyword=` 的 `customers` 块 | 复用 `searchStationCustomers` | 同上 |

- 三者**共用** `CustomerSearchMatcher`（归一化 + 打分排序）与 `CustomerMapper.listSearchCandidates`（候选集，取数统一走 `CustomerServiceImpl.loadSearchCandidates`）。
- ⚠️ **判据：三个入口对同一关键字必须返回同一个人。** 回归断言 `CustomerAddressSearchIntegrationTest.allEntryPointsShareTheSameImplementation`（三个入口分别请求 `阳光81301`，都要求命中同一个客户）。
- 两处口径差异是**既有设计**、不是缺陷：客户列表是 orders 驱动，所以「刚建档、没下过单」的新客户**不在**客户列表里（`CustomerAddressSearchIntegrationTest` 明确断言），而选择器必须能搜到 —— 代客下单第一步就是"给还没下过单的新客户建单"。
- ⚠️ **打分逻辑只允许存在于 `CustomerSearchMatcher`。** 再写一份 LIKE 或再写一套打分 = 重演本仓"计价双轨"事故（两条路径各算一套、界面与落库长期不一致）。
- ⚠️ `CustomerMapper.search(keyword)` 是**历史方法、全仓零调用**，两个硬伤正是新口径要解决的：不按水站过滤（跨站泄露）+ 只强子串匹配 `name`/`phone`、**不搜地址** —— **不要顺手拿它做新页面**。

## 3. 归一化规则（顺序即实现顺序）

`CustomerSearchMatcher.normalize(raw)` 严格按下列次序执行（`numeralsToArabic` 在 `stripStructuralWords` **之前**，所以「八栋」先变「8栋」再被删掉「栋」）：

1. **全角 → 半角**（`U+FF01~U+FF5E` 平移 `0xFEE0`；全角空格 `U+3000` 单独处理）；
2. **英文大小写统一**（`Locale.ROOT` —— 用默认 Locale 在土耳其语环境下会把 `I` 变成 `ı`）；
3. **中文数字 → 阿拉伯数字**（逐"数字串"处理，遇非数字字符断开）；
4. **去结构词 / 通名**（先删多字词，再删单字）；
5. **只保留字母、数字、汉字**（标点、空格、`-` `/` `#` 一律丢弃）。

### 3.1 中文数字：两种写法都要对

- **逐位写法**：`三零一` → `301`、`一单元` → `1`、`〇` / `○` 也当 `0`；
- **带单位写法**：`十二` → `12`、`二十三` → `23`、`三百零一` → `301`、`壹拾贰` → `12`（单位前没写数字时按 1 算，故 `十` = 10）；
- `万` / `亿` **刻意不当作单位**：它们更常出现在名字里（「万客隆」「万一」），当单位会把名字改成数字；代价只是「一万」不换算，可接受。
- 解析结果 `<= 0` 或 `> MAX_NUMERAL`（`999_999_999`）时**原样保留** —— 宁可匹配不上，也不要猜出一个错的数字。
- 换算只影响**两侧同时归一化**的比较，所以"两侧都写汉字"或"两侧都写数字"都能命中。

### 3.2 「删」名单（`STRUCTURAL_WORDS` + `STRUCTURAL_CHARS`）

- 多字词（整体删除，**先于单字执行**）：`小区`、`单元` —— 任何住宅地址都有，站长缩写时必省，删掉才能让「阳光81301」落进整串包含。
- 单字：`栋幢座楼层室房号梯第`（编号的包装）+ `省市区县镇乡街路道巷弄`（行政区划通名）。
- 判据是**「对所有候选一视同仁、零区分度」**：它们人人都有，删掉不会把两个不同地址混成一个，反而让缩写更容易被"整体包含"接住。

### 3.3 「刻意保留」名单（有区分度，删了就是把不同小区混为一谈）

`村`（**新村 ≠ 小区**）、`园` / `苑` / `花园` / `家园`（阳光花园 ≠ 阳光苑）、`城` / `广场` / `大厦` / `公寓` / `新村`。

> 判据原话："别把有区分度的词也删掉"。纯函数用例直接钉住了这几条（`CustomerSearchMatcherTest.normalize`：`阳光新村` 与 `阳光小区` **不得相等**）。

## 4. 打分与阈值

字段：**姓名 / 电话 / 地址**。地址 = 客户档案地址（默认地址在前，多条换行分隔）**拼接**本站订单的 `address_snapshot` —— 客户改过/删过地址后，仍能按当初实际送货的地址搜到人。

**单字段得分**：

- **整体包含**（归一化后关键字是字段的子串）→ `CONTAIN_SCORE = 100`。这是最强证据（"阳光81301" ⊂ "阳光81301"）。
- 否则 → `round(PARTIAL_MAX × (COVERAGE_WEIGHT × 字符覆盖率 + ORDER_WEIGHT × 最长公共子序列比))` = `round(90 × (0.6 × 覆盖率 + 0.4 × 顺序比))`：
  - **覆盖率**回答"关键字里的字到了几个"（按多重集合算：关键字里两个相同的字、候选里只有一个就只算一个）；
  - **顺序比**回答"到的字是否保持原顺序"（防止同几个字乱序堆砌也算命中）；
  - 部分命中**封顶 90**，保证"整体包含"永远排在"拼出来"的前面。

**候选最终分 = 三个字段得分的最大值**；⚠️ **同分时按 `姓名 > 电话 > 地址` 排**（地址是"间接指代人"，姓名电话才是身份标识）。排序**稳定**：完全同分同优先级的候选保留入参顺序（SQL 给的是建档倒序），所以同一关键字两次请求结果可复现。

**阈值 `MIN_SCORE = 60` 的推导**（不是拍脑袋）：非包含命中要拿到 60 分，需要 `0.6 × 覆盖率 + 0.4 × 顺序比 ≥ 2/3`，即**关键字里约 2/3 的证据必须同时"出现过"且"顺序对"**。于是：

- 全字命中但乱序（覆盖率 1.0、顺序比 0.6）得 **76 分 → 保留**；
- 四个字里只对上一个（覆盖率 0.25、顺序比 0.25）得 **23 分 → 丢弃**。

⚠️ 低于阈值**直接丢弃**，**不是**"返回全部"。参数化查询注入串（`' OR 1=1 --` 归一化后是 `or11`）正是被这一档挡掉的（集成回归 `OrderEntryAndInjectionIntegrationTest`；纯函数断言见 `CustomerSearchMatcherTest.justMiss`）。

## 5. 边界与上限

| 常量 | 值 | 含义与超限行为 |
|---|---|---|
| `MAX_CANDIDATES` | `3000` | SQL 粗筛一次最多取回多少条本站客户。产品口径给定"站长端客户量级是几百到几千"，3000 覆盖该上界 |
| `MAX_RESULTS` | `50` | 单次返回上限（命中很多时只给最相关的前 N 条） |
| `MIN_SCORE` | `60` | 命中阈值（推导见 §4） |

- **候选超限**：按**建档倒序截断**（`order by c.id desc`，新客户优先保住），接口**照常返回**，只把"结果可能不全"记进 `log.warn`（`CustomerServiceImpl.loadSearchCandidates`）。真到这一步说明单站客户量已超出产品口径。
- **关键字为空**（`CustomerSearchMatcher.isBlank`）：**不筛**，按"最近建档"返回前 `MAX_RESULTS` 条。⚠️ 代客下单页首屏就是这条路径，**返回空列表会让站长以为"客户没建档成功"** —— 必须保持"返回最近若干条"。
- **关键字全被归一化吃掉**（如只输入「小区」「单元」，或姓「楼」的客户）：回退 `normalizeLoose`（**不去结构词**）。站长真的会这么搜，一律返回空的表现是"搜了没反应"，比"搜得宽一点"更难排查。
- **关键字全是标点**（如 `--`）：两侧都归一化成空 → 返回空数组（没有任何证据可用，**不返回全部**）。
- **无匹配**：返回空数组、`code=0`，**不报错**（"搜不到"不是错误）。
- 列表项字段由后端定死（`id` / `name` / `phone` / `customerType` / `addressText`）：打分用的 `orderAddressText` **不外泄给前端**。

## 6. 性能实测（数字与测量条件）

纯函数、无 IO，成本 = `O(候选数 × 字段数 × 字段长度)`。**实测记录在 `CustomerSearchMatcher` 的类注释里**（正本），条件：

- **纯打分**（JDK 17，单次 `rank`，合成候选：姓名 + 11 位手机号 + 一条「阳光小区N栋N单元N室」地址）：**500 条 ≈ 1.2–2.4ms ／ 1000 条 ≈ 2.3–3.8ms ／ 3000 条 ≈ 12–19ms**；
- **端到端**（真实 MySQL + HTTP，测试库 3000 个本站客户、各一条地址）：`GET /api/manager/order-assist/customers` ≈ **50–105ms**；客户列表（多一次画像聚合查询）≈ **56–71ms**。

两个"为什么不慢"的优化，**改代码时别顺手删掉**：

1. **LCS 只在"覆盖率已够"时才算**（`scoreOne` 的上界剪枝）：把顺序比按 1 代入仍到不了阈值 → 这个字段救不回来 → 直接跳过 `O(|k| × |field|)` 的 LCS。⚠️ 该分支返回的是**上界**（≤ 真实分，必然 < `MIN_SCORE`），只用于"是否丢弃"的判断，**不进排序**。
2. **归一化每一趟在没有需要修改的字符时直接返回原串**，避免每次打分都重建 5 个中间串。

> 再往上（单站客户破万）就该**换检索引擎**，而不是加大 `MAX_CANDIDATES`（见 §8）。

## 7. 改权重 / 改名单之前：先看这几条用例会红

| 要改什么 | 会红的断言（先找到它们再动手） |
|---|---|
| `MIN_SCORE` 阈值本体 | `CustomerSearchMatcherTest` 的「阈值本体的值被改了」断言 |
| `PARTIAL_MAX` / 两个权重 | `CustomerSearchMatcherTest.justHit`（`阳光8` 对 `月光88` 仍 ≥ 阈值）、`justMiss`（`阳光花园8` 对 `阳光小区8栋` < 阈值）、`阳光301` 对 `阳光花园8栋1单元301` = **90**、注入串 = **23** |
| `STRUCTURAL_WORDS` / `STRUCTURAL_CHARS` | `CustomerSearchMatcherTest` 的缩写（含空格/连字符/`幢`/`房` 变体）、中文数字逐位与带单位、全角与 `壹拾贰`、纯结构词各条 |
| 「刻意保留」名单 | `CustomerSearchMatcherTest` 的 `新村` / `花园` / `苑` / `公寓` 保留（**新村 ≠ 小区**）、`万客隆` 保留与 `万一` → `万1` |
| 字段优先级（姓名 > 电话 > 地址） | `CustomerAddressSearchIntegrationTest.surnameQueryMatchesAndRanksNameHitFirst` —— 搜「王」时"姓名命中"必须排在"仅地址命中"之前 |
| `MAX_RESULTS` / 候选截断 | `CustomerAddressSearchIntegrationTest.blankKeywordKeepsRecentListSemantics`（不带关键字 = 最近建档若干条）、`noMatchReturnsEmptyArray` |
| 打分算子的可复现性 | `CustomerSearchMatcherTest` 的同分保留入参顺序断言 |
| 归一化本身 | `CustomerSearchMatcherTest` 全类（纯函数，毫秒级、不起 Spring，改完先跑它） |

端到端回归 `CustomerAddressSearchIntegrationTest`（8 条判据）：缩写命中 / 数字混用 / 姓氏排序 / 电话老能力 / 小区名命中且不误伤别的小区 / **他站客户不出现** / 无匹配返回空数组 / 三入口同一人。

⚠️ 跨租户那一条与 `CrossStationPoolRiskAndProfileIsolationIntegrationTest` 的画像隔离是一对：**改了候选集口径，两条都要看**。

## 8. 本批没做（边界写清，免得被当成"应该有效"）

| 没做 | 原因与边界 |
|---|---|
| **拼音首字母**（如「yg81301」） | 成本不在算法：要么引新依赖，要么加冗余列 —— 而加列意味着**全部写入点同步 + 一次性迁移回填**，属独立一批的量级 |
| **`GET /api/search` 的地址块与订单块仍是强子串 LIKE**（`AddressMapper.listByStation` / `OrderMapper.searchByKeywordAndStation`） | **只有 `customers` 一块走了新口径**，这是**有意的不一致**（那两块不在范围内，且 `OrderMapper` 属共享文件）。界面上会出现"同一个关键字，客户里有、地址里没有" —— **不要据此判断数据缺失** |
| **单站客户破万后的方案**（全文索引 / Elasticsearch） | `MAX_CANDIDATES = 3000` 是"SQL 取候选 + 内存打分"这条路的现实上界；破万要换检索引擎，**不是加大这个常量** |
| **不按空格拆词（多关键词）** | 归一化会**丢弃**空格与标点，所以「阳光 81301」与「阳光81301」等价（这正是产品要的）；但**两段彼此独立的词**（如「阳光 张三」＝地址 + 姓名）会被当成一整串去匹配单个字段，命中率低。要支持它得**先按空格拆词、每个词各自打分再合并**；产品确认的口径里没有这一条，故未做 —— 需要时再加，改动只在 `CustomerSearchMatcher.rank` 一处 |
