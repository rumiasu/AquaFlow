# 26 · 水票两个方案的评估（定制优先 + 统一水票兜底）· 定稿口径 + 实施计划

> 2026-09-19 立；同日产品给出裁定，本文档据此**定稿口径**。
> 产品原话：「有的商品可能有水票，有的可能没有，建议开一个混合支付吧，但是这个先别做。
> 还有一个解决方案，就是加一个统一水票功能，统一买多少单位（个数）打多少折这种，两个看看怎么做」
> → 追加裁定：「水票上，定制优先，**统一水票**是可以设置项，比如买 10 张都打 9.5 折、30 张统一 9 折这种，
> **定制和统一都有的情况下，定制优先，统一的仅在没有定制水票的桶时生效**。
> 混合支付不好做吗，**先做统一水票**，这个先评估，后面加上也行。」

## 26.0 定稿口径（先看这一节，其余是细节与实施）

| 项 | 定稿 |
|---|---|
| 优先级 | **定制（按商品的水票）优先**；统一水票**只在"该商品没有定制水票"时生效** |
| 统一水票的形态 | 站级**可设置项**：按购买**张数**分档折扣（如 10 张 9.5 折、30 张 9 折） |
| 顺序 | **先做统一水票**；混合支付**先评估**（本文档给了改动面与风险），后面再加 |
| 一句话理解 | 统一水票 = 站长的**折扣工具**（多买多送）；定制水票 = 某款水的专属票（继续按原样工作） |

## 26.1 现状（这是问题的根源）

| 事实 | 证据 |
|---|---|
| 水票账户是**按商品 × 按站**的：`ticket_account` 唯一键 = `(customer_id, product_id, station_id)` | 真实库 `information_schema.STATISTICS` |
| 批次（余额真相源）同样是按商品的：`ticket_lot` 索引 `(customer_id, station_id, product_id, status)`，带**单价快照** | 同上 + `docs/design/19` |
| 档位也是按商品的：`ticket_package` 唯一键 = `(station_id, product_id, qty)`，列 `qty/price/unit_price/title` | 真实库 |
| **"有的商品有票、有的没有"是真的**：站 1 的「农夫山泉 19L」`ticket_enabled=1`（水票价 20），同站「娃哈哈 18.9L」`ticket_enabled=0`；站 2 两个商品都是 0 | 真实库 `inventory` 实测 |
| 而真实库里 `ticket_package` **0 行**、`ticket_account` **0 行** —— 功能已上线但**还没人配档位、没人买过票** | 真实库实测 |
| 支付方式是**订单级单值**：`orders.payment_method`（1 微信 / 2 现金 / 3 水票），下单时选定、之后不改 | `constant/PayMethod.java` |
| 票的扣减发生在**下单之后那次支付请求**里（扣成功才置 `payment_status=2`，单子才进站长视野） | `TicketAccountServiceImpl` + AGENTS §1.1 派单判据 |

**两句话总结痛点**：① 同一个客户在同一个站，A 水能用票、B 水不能用票 → 想一次买两样时，
**整单只能选一种支付方式**（要么整单票、要么整单现金），这就是"混合支付"的动机；
② 票被绑在商品上，客户要记住"我哪张票能买哪桶水"，站长配档位也要逐商品配 —— 这是"统一水票"的动机。

## 26.2 方案 A：混合支付（一单里票 + 现金/微信）

**用户可见的效果**：一单同时含"能用票的水"和"不能用票的水"（或票不够）时，客户可以先抵扣票，
差额用现金/微信结。

| 维度 | 改动面 |
|---|---|
| 数据 | 一张订单要能挂**多条**支付流水（票一条、现金一条）。`payment_record` 已支持多行，但 `uk_payment_active_order`（`active_order_id` 生成列）**一单只允许一条活跃流水** → 该约束必须重新设计（例如改成"一单一条未完成流水"或按 `payment_method` 分组唯一） |
| 状态 | `orders.payment_status` 是**单值**（0/1/2/3/4）。混合支付下"部分已付"没有表示法 → 要么引入新状态（如 5=部分已付），要么约定"票先扣、差额付清才算已付"。⚠️ 本仓硬规则：**状态只前进、不倒滚**，加状态容易、回退极难 |
| 退款 | 退款必须**原路拆两路**：票退回批次（FIFO 回补，已有 `restoreTicketsForOrder`）+ 现金记负数冲正/微信走渠道。（微信渠道未接入 → 混合了微信的单根本退不了） |
| 对账 | 等式 2（`p2a`/`p2c`）与 E8（票账）都要按"一单多流水"重写；`DashboardMapper` 的待收款口径（`payment_status=1 且未取消`）也要重新定义"部分付款"算什么 |
| 前端 | 支付方式选择器从"三选一单值"改成"票抵扣 + 差额方式"，下单页/支付页/订单详情三处都要改；文案要能说清"已抵扣 X 张、还需付 ¥Y" |
| 风险 | **高**：动了支付状态机 + 两条退款路径 + 三张对账等式；客诉面也最大（"我付了钱为什么还是部分付款"）。而且**当前真实库里没有一张水票**（0 账户/0 档位），为一个还没被使用的功能动核心资金链路，性价比低 |

**结论**：**方案 A 暂缓**（与产品"先别做"一致），且建议**排在方案 B 之后**：B 做完后"A 水能抵、B 水不能抵"
这个分裂本身就消失了，混合支付的需求会大幅缩小。

## 26.3 方案 B：统一水票（站级"单位票" + 分档折扣）

**用户可见的效果**：站长配一张价目表 ——「买 10 单位 9 折 / 买 20 单位 8 折 / 买 100 单位 6 折」，
客户买"单位"，用单位抵扣本站的**任意**桶装水（不再逐商品绑票）。

| 维度 | 设计要点 |
|---|---|
| "单位"的定义（**必须先拍板**） | 建议 **1 单位 = 1 桶水**（按数量抵扣，与"桶数"这个全系统通用口径一致）。备选："1 单位 = X 元额度"（按金额抵扣）—— 后者会让"贵水/便宜水"的抵扣结果不同，站长更难解释 |
| 抵扣范围 | 建议**只抵桶装水（`category=1`）**，与押金/桶账口径一致（见 `docs/design/03` §3.12）；瓶装水/一次性桶/饮水机是否可用，需要单独拍板（它们没有桶，但"水票抵水费"业务上说得通） |
| 表结构 | `ticket_account`：去掉 `product_id`（或置 0 表示站级通用票）→ 唯一键变 `(customer_id, station_id)`；`ticket_package`：`product_id=0` 表示站级档位；`ticket_lot`/`ticket_record` 的 `product_id` 改为"抵扣时快照当时商品"（追溯用），**不再是账户维度** |
| 抵扣与定价 | 抵扣时按"桶数 × 该商品当前价"折算水费减免；批次单价快照的含义从"这张票值多少水"变成"这个单位买入时的均价"，退票仍按 FIFO + 买入均价退 |
| 对账 | **E8 恒等式要重写**（`remain_quantity == Σ lot.remain_qty` 仍成立，但 `right_amount` 的口径从"商品票面额"变成"单位数 × 均价"）；`ticket_record` 的 `uk_ticket_consume(order_id, product_id, source)` 语义跟着变 |
| 迁移 | 存量：真实库 0 账户/0 档位 → **迁移成本几乎为零**（这是个难得的窗口期，现在做改动面最小） |
| 风险 | **中**：不动支付状态机、不动退款的两路逻辑（票还是"支付成功那一刻"整体抵扣）、不动"先付款后派单"判据；主要是票账内部重构 + 对账等式重写 |

**站长侧价值**：档位一次配好全站通用，不用逐商品配；折扣是**经营工具**（多买多送）。
**客户侧价值**：不会再出现"我的票不能买这桶水"。

## 26.4 对比与建议

| 维度 | A 混合支付 | B 统一水票 |
|---|---|---|
| 解决的问题 | 一单多支付方式 | 票与商品解绑 + 分档折扣 |
| 动支付状态机 | **是**（引入"部分已付"） | 否 |
| 动退款路径 | **是**（两路拆分） | 否（仍是整体抵扣） |
| 动对账等式 | 等式2 + E8 | 仅 E8 |
| 动前端 | 下单/支付/详情三处 | 购票页 + 抵扣展示 |
| 存量迁移 | 无（但 0 数据也意味着收益低） | **几乎为零**（0 账户/0 档位） |
| 风险 | **高** | 中 |
| 建议顺序 | **第二步**（B 之后，需求会自然缩小） | **第一步**（趁 0 数据窗口做） |

**我的建议**：**先做 B（统一水票），A 记为"等 B 上线后再评估"**。理由：B 用很小的改动面换来
"票不再绑商品 + 分档折扣"这两个真实收益，且**当前 0 存量的窗口期**是最佳时机；A 要动的是本仓最硬的
两块（支付状态机、退款原路），而它解决的问题在 B 之后大部分会消失。

## 26.5 统一水票的实施计划（口径已定，待排期）

> **已于 2026-09-19 实现**（v54 + 后端 + 两端小程序）。逐条落地情况与**计划外的发现**见 §26.8 ——
> 其中第 4/8 两条按裁定收了（不够不补、只抵桶装水），另外发现**退款必须靠流水自证账户**（计划里没写，
> 不补上就会退错账户）。

| 步 | 做什么 | 关键设计 |
|---|---|---|
| 1 | **表结构**：`ticket_account` 与 `ticket_package` 的 `product_id` 增加"0 = 站级通用"语义 | 账户唯一键 `(customer_id, product_id, station_id)` 保持不动 —— `product_id=0` 就是通用票账户，**不必改唯一键**（比原评估里的"去列"更小改动） |
| 2 | **档位**：统一票档位 = `ticket_package(product_id=0, qty=N, price=折扣价)` | 复用现有唯一键 `(station_id, product_id, qty)`；`unit_price` 仍是 price/qty |
| 3 | **购买**：客户买统一票 = 走现有在线购票链路，只是 `productId=0` | 幂等键沿用 `uk_payment_idempotency(customer_id, idempotency_key)` |
| 4 | **抵扣顺序**（本次裁定的核心） | 结算时：**先看该商品有没有定制票账户余额** → 有则用定制票；没有（或定制票不够？见下）才用统一票 |
| 5 | **"不够"怎么办**（需补一条裁定） | 两种可选：**a) 定制票不够就整单不能用票**（简单、可解释）；**b) 定制票用完再用统一票补差额**（更友好，但要多付几条流水/批次）。**建议 a**，与"定制优先"的字面口径一致，且不动支付链路 |
| 6 | **批次与对账** | `ticket_lot` 已有 `product_id`，通用票用 `product_id=0`；**E8 恒等式 `remain_quantity == Σ lot.remain_qty` 不变**（只是多了一个"商品 0"的维度），`right_amount` 仍按批次均价算 |
| 7 | **退票** | 沿用 FIFO + 买入均价（`TicketLotService`），与定制票同一条路 |
| 8 | **禁区** | 只抵**桶装水**（与押金/桶账口径一致，见 `docs/design/03` §3.12）；瓶装水/一次性桶/饮水机是否可用，**仍需拍板**（建议不可用） |

**工作量大头**：不是表，而是**抵扣判定那一处**（`TicketAccountServiceImpl` 的扣票与报价页的"可用票"展示）——
必须把"这件商品该用哪张票"收敛成**一处判据**（同 `BarrelScope` 的做法），否则定制/统一两套逻辑会在
报价、下单、支付、退款四条路径上各写一遍，迟早分叉。

## 26.6 混合支付"不好做吗"——难在哪（评估结论：可做，但不该现在做）

不是"做不了"，而是**要动的都是本仓最硬的地方**：

1. **`uk_payment_active_order`（一单一条活跃流水）**：这是"先付款后派单/退款原路"的地基，改成"一单多条"
   要把所有按订单取流水的读法都审一遍（对账、退款、看板、催收）。
2. **`payment_status` 是单值**：混合支付要表达"部分已付"。本仓硬规则是**状态只前进、不倒滚**，
   加一个状态容易，将来撤掉极难；而且 `DashboardMapper` 的待收款口径、应收账款的 `settlement_status`
   都要跟着重新定义"部分付款算什么"。
3. **退款必须两路原路**（票回批次 + 现金冲正/微信渠道），而微信渠道**尚未接入** —— 混合了微信的单根本退不了，
   等于把"未接入"这件事从"不能用微信"扩散到"连票都用不利索"。
4. **客诉面**：客户看到"已抵扣 5 张、还需付 ¥12"时的疑问，比"整单一种支付方式"大得多。

**结论**：先做统一水票（改动集中、风险中）；等统一水票上线、票真正被用起来之后，
再看是否还需要混合支付 —— 届时"部分用票"的真实需求场景也更清楚了。

## 26.8 实施结果（2026-09-19 落地）与计划外的发现

### 26.8.1 逐条落地（对应 §26.5 的八步）

| 步 | 计划 | 实际 |
|---|---|---|
| 1 | `product_id = 0` = 站级通用票，**不动唯一键** | ✅ 照做。实测水票四张表（`ticket_account` / `ticket_lot` / `ticket_package` / `ticket_record`）的 `product_id` **都没有外键**（`information_schema.KEY_COLUMN_USAGE` 为空）→ 零结构障碍 |
| 2 | 统一票档位 = `ticket_package(product_id=0, …)` | ✅ 照做。**顺带定了"站级开关"**：配了**上架**的 `product_id=0` 档位 = 本站已开通统一票；全下架 = 关闭。**刻意不加开关列** —— 多一个开关就多一处会与档位状态打架的真值 |
| 3 | 购买走现有在线购票链路，只是 `productId=0` | ✅ 照做，**但加了一条硬约束：统一票只能按档位买**（`packageId` 必传）。原因：`product_id=0` 既没有商品也没有 `inventory` 行，散买会走"站级水票价 → `product.ticket_price`"两级阶梯、算出 **0 元** = 白送票。折扣本来就在档位上，这条限制不损失任何能力。**"平台给预设档（10/20/100 张）"落在 §26.8.5**：给建议、一键填入，但不替站长落库 |
| 4 | 抵扣顺序：定制优先，统一兜底 | ✅ 照做。判据收敛成**唯一实现** `util/TicketScope.resolveAccount`（同 `BarrelScope` 的做法），由 `TicketAccountService.resolveDeductAccount` 暴露给调用方 |
| 5 | "定制票不够"用 a 案（整单不能用票） | ✅ 按裁定收了 **a**：产品原话"统一的**仅在没有定制水票的桶时生效**"，字面就是这个。所以**余额 > 0 就只用定制票，不够也不拿统一票补差额** —— 这一条单独写进了 `TicketScope` 的注释与用例（防"顺手优化"成混合支付） |
| 6 | 批次与对账 E8 不变 | ✅ 不变：统一票就是一个 `product_id=0` 的账户/批次维度，`remain_quantity == Σ lot.remain_qty` 与 `right_amount == Σ remain×unit_price` 两条等式**逐字未改**，用例对**两个账户**分别复核 |
| 7 | 退票沿用 FIFO + 买入均价 | ✅ 沿用，**并补了一列**：见 §26.8.2 第 1 条 |
| 8 | 只抵桶装水 | ✅ 按建议收了：`TicketScope.unifiedEligible(product) = BarrelScope.isBarrel(product)`，与押金/桶账口径同源（`category=1`）。瓶装水/一次性桶/饮水机**不可用** |

### 26.8.2 计划外的发现（三条，都必须补上才不漏钱）

1. **`uk_ticket_consume(order_id, product_id, source)` 不能承载"账户"这个语义** → 新增 v54 列 `ticket_record.account_product_id`。
   - 消费流水必须记**订单行商品**（幂等键与 `countConsumeByOrderAndProduct` 都按它判重）。若把统一票的流水也写成 `product_id=0`，
     同一张单里**两个都走统一票的商品**会撞唯一键 → 第二条被 `catch (DuplicateKeyException)` 当成"并发重复"**静默跳过** → **少扣一张票**。
   - 取值：`NULL` = 与 `product_id` 同账户（**存量行全部如此**）、`0` = 站级通用票、其它 = 定制票账户（新流水一律显式写）。
   - 用例里专门有一条**两商品同单**的用例盯这个坑。
2. **退款必须回到"当初扣的那个账户"，不能重新判定** → 这就是上面那一列的用途。
   - 退款那一刻余额早已变化：客户把定制票**刚好用光**之后再取消订单，重新跑一遍 `TicketScope` 会判成"用统一票" → 票退进客户从没扣过的账户。
   - 判别用例：`refundGoesBackToCustomAccountEvenWhenBalanceHitZero`（定制 2 张、下单 2 桶 → 余额归 0 → 取消）。
     **已做反证**：临时把回补改成"重新判定账户"，只有这一条红、其余全绿。
3. **`product_id=0` 在展示层是"没有名字、没有价格"的** → 三处补了可读口径：
   - 客户水票明细（`TicketAccountMapper.listByCustomerAndStationWithDetail`）：名称兜成「统一水票（站级通用）」，
     面值取**派生列** `right_amount / remain_quantity`（= 批次加权均价）—— 统一票没有"站级水票价"这个参考物，这是它唯一的真实价值口径；
   - 水票流水（`TicketRecordMapper.RECORD_DETAIL_COLUMNS`）与客户画像资产明细（`CustomerServiceImpl`）：`product_id=0` 的 `productName` 用 CASE 兜，否则下发 `null` → 界面显示空；
   - 站长"加票 / 资产调整补录"统一票时的**推断单价**：取本站上架档位里**均价最低**的那个（`TicketAccountServiceImpl.inferredUnitPrice`）。
     不这么兜就是 0 —— 那会让 `right_amount` 凭空少一块。仍标记为推断值（退票需二次确认）。

### 26.8.3 顺带补的一处体验（结算页）

`PaymentServiceImpl.quote` 在客户选了水票支付时**下发可读提示**（与配送费提示合并进同一个 `warnings` 数组）：
"将使用本站统一水票（1 张抵 1 桶），余额 N 张" / "定制水票余额 N 张、本单需要 M 张" / "不能用票支付：没有定制水票，本站也未配置统一水票"。
**只提示、不拦阻**：真正的闸门在提交路径（下单闸门 + 扣票的原子 SQL）。结算页拦一道会让"票刚好在别处补上了"的客户无法下单。

### 26.8.5 平台预设档（产品要求「平台给预设档（10/20/100 张）」）

**形态是"一键填入的草稿"，不是自动落库的档位。** 这一条是刻意的：`product_id = 0` 的上架档位
**就是统一水票的站级开关**，平台若替所有水站自动插三行，等于替他们开通了一个折扣工具 ——
定价是站长的经营决定，系统只给建议。

| 项 | 定稿 |
|---|---|
| 预设张数 | **10 / 20 / 100 张**三档（产品原文举的例子是"10 张 9.5 折、30 张 9 折"；张数与折扣都在 `util/TicketPreset` 一处常量里，要加 30 张那档改一行即可，站长本来也能自己改张数） |
| 预设折扣 | **9.5 折 / 9 折 / 8.5 折**（`950‰ / 900‰ / 850‰`，整数运算不用浮点） |
| 基准价 | **本站已上架桶装水里最便宜的那一桶**，单价走 `PriceUtil.calcUnitPrice(…, TICKET)` 那一级（站级水票价 → 通用库水票价 → 零售价）—— 与客户**用票抵扣时订单水费的计算口径同源**，否则按建议价卖票会亏 |
| 依据文案 | 按**最终胜出的那个商品**判定（配过水票价 → "最低水票价"；只能按零售价 → "最低零售价（还没配水票价）"）。判据是 `PriceUtil.hasEffectiveTicketPrice`，与 `calcUnitPrice` 共用同一个覆盖判定，不会分叉 |
| 金额算法 | 总价 = 基准 × 张数 × 折扣（2 位）；**均价 = 总价 ÷ 张数**（2 位）—— 与 `TicketPackageController.save` 逐字相同，所以"界面显示的均价"与"保存后快照进批次的均价"必然是一个数 |
| 没有桶装水怎么办 | **不给建议**（`presets: []` + `basePriceBasis: null`），前端提示"先上架桶装水或自己填价"，绝不凭空捏一个数（同 `DeliveryConfigGuideService` 的"拿不准就不给"） |
| 端点 | `GET /api/ticket-packages/presets`（`@RequireRole("STATION_MANAGER")`；顾客令牌调不动 —— 这是站长定价的辅助信息，不是商品数据） |
| 正本 | `util/TicketPreset`（纯规则）→ `service/impl/TicketPackagePresetService`（IO：算基准价）→ `TicketPackageController.presets`；用例 `TicketPresetTest`（5 例）+ `TicketPackagePresetIntegrationTest`（3 例，含**把预设原样 POST 回真实保存端点**并断言均价逐字相等） |

⚠️ 实现时踩过一个坑并靠单测抓到：千分比换"折"要 **÷100**（950‰ → 9.5 折），
我第一版写成 ÷10 → 界面会显示「95 折」。`TicketPresetTest.discountText` 钉住了这条。

## 26.10 第十批：结算页口径（2026-09-19）

产品口径（原话）：「默认订单里，会沿用上次支付方式，我觉得前端记一下就好，不用再写进后端，
然后水票支付时，水票支付方面就不显示计费了，只计费除去水票的部分。**不用写混合支付**，
点击水票后，优先水票支付，但是经校验后，发现水票不足以覆盖该订单时，会启用微信支付，
即剩下的金额使用微信支付。」

拍板结果：**只做「显示 + 校验 + 引导」，写路径一行不动**（见下表"为什么不做差额支付"）。

| 项 | 定稿 |
|---|---|
| 支付方式沿用 | **纯前端**（`utils/storage.js` 的 `payMethodStorage`，只存本地）。产品明确说"不用再写进后端" —— 它是**交互偏好**不是业务事实，存后端就要跟客户档案走、考虑多端同步与脏数据。写入时机是**下单成功那一刻**：失败/被拒不该污染"上次成功用过的"那一项。记住的方式在本站不可用时，仍按 `PayMethod.availableMethods()` 下发的 `enabled` 回退到默认项 |
| 水票支付的计费区 | 产品口径「只计费除去水票的部分」。落在 `quote.ticketPay`：选中水票且**整单可被票结清**时，计费区不再逐项列水费/押金/配送费，只显示「水票抵扣 N 张 · ¥X」+「本次需付 ¥0.00」 |
| ★ 口径关键（我实现时先想错过） | **水票支付是整单结清**：`createPayment` 在 `paymentMethod=3` 时扣票成功后直接置 `PAID` 并 `applyDepositOnPaid` —— 水费、押金、配送费、楼层费**全部随票一并结清**。所以"票够"时本次要付的是 **0**，**不是「合计 − 水费」**（那会凭空多出一笔押金+配送费）。已用反证钉住：把 payable 改回"合计 − 水费"，两条"票够"用例立刻红 |
| 覆盖判据（与真实扣票逐条对齐） | 逐行判定：账户由 `TicketAccountService.resolveDeductAccount` 选（内部 `util/TicketScope`），且必须**余额 ≥ 整行数量**才算这行能抵 —— `consumeTicket` 用的是 `remain_quantity >= qty` 的原子 SQL，**不存在"先抵一部分"**。所以预览也必须是全有或全无；否则页面说"还差 1 桶"，提交时整行被拒 |
| 票不足时 | **提交前就地拦住**并提示改选。放过去让它失败的后果很实际：`deductTickets` 抛错 → 订单已创建但 `payment_status` 停在 0 → 按派单判据**这单进不了站长视野**（客户以为下单成功，实际没人看得见）。拦截前会**重跑一次报价**（客户可能刚补了票），不会误伤 |
| 展示值 vs 真实金额 | `totalAmount` 永远是**真实订单金额**；展示值单独放 `ticketPay.payableAmount`（前端 `payableAmountText`）。两者刻意分开：展示值混进提交参数就是"计价双轨" |
| **为什么不做差额支付**（「剩下的金额使用微信支付」） | 两处硬拦：① **微信支付渠道全仓未接入**（`PayMethod.availableMethods()` 里恒 `enabled=false`「暂未开通」）→ 做出来是一条**付不掉的**待支付单；② "票 + 差额" = **一单两条活跃流水**，会撞 `uk_payment_active_order`（生成列 `active_order_id` 在 `status∈(1,2)` 时等于 `order_id`，唯一键保证一单一条）—— 这正是 §26.6 列的混合支付第一处地基，与"不用写混合支付"冲突。⇒ 等微信渠道接入后再评估 |
| 正本 | `PaymentServiceImpl.quote`（`ticketPay` 预览 + 逐行文案）、`miniapp-user/pages/order/create.{js,wxml,wxss}`、`utils/storage.js`；用例 `TicketPayPreviewIntegrationTest`（3 例） |
| 顺带修的既有缺陷 | `miniapp-user/pages/order/create.wxss` 自第 1027 行起是 **GBK 编码**（同一文件前半 UTF-8、后半 GBK 混排，**已在 HEAD 里**）。微信开发者工具按 UTF-8 解码会报「编译 .wxss 错误且不指名文件」，而四个静态门禁都发现不了（它们不解析编码）。已逐行转成 UTF-8 无 BOM；顺手扫了两端 **721 个文件**，确认再无第二处文本文件（其余命中全是图片）。**判据：`.wxss`/`.wxml` 里出现"编译错误但不指名文件"，先查 BOM、再查**这一条**（混编码），不要只查 BOM** |

## 26.11 形态收口：统一水票 = 站级「统一折扣」，不是一种票（2026-09-20，v58/v59）

> ⚠️ **本节取代 §26.0～§26.10 关于"统一票是什么"的全部表述。** 那些章节里
> 「站级通用票账户 `product_id = 0`」的形态是**理解错了** —— 裁定原文与实施记录保留在原文，
> 但**以本节为准**。

产品原话（2026-09-20）：「统一水票，**在站长端是特殊化的**，但在**用户端看起来没区别**，
执行上**也不是统一定价**，而是**对应水怎么统一打折、统一打几折**的区别，**不是专门卖统一水票**。」
+ 追问后拍板：客户按统一折扣买的票 **进该商品的账户、只能抵那款水**。

### 26.11.1 我上一批错在哪

| 我做的（v54） | 应该是（v58） |
|---|---|
| 统一票 = **站级通用账户**（`product_id = 0`），买 10 张全站通用 | 统一票**不是一个账户**；账户永远是**那一款水**的 |
| **统一定价**：站长填一个站级总价（10 张 ¥85.50），1 张 = 8.55，全站同价 | **统一折扣**：站长只填折扣（10 张 9.5 折），价格 = **各款水自己的水票价 × 折扣** |
| 用户端多一个商品「统一水票（站级通用）」 | 用户端**只有真实商品**，看不出两种来源 |
| 判据 `util/TicketScope`：定制余额 > 0 用定制，否则用统一票账户 | 判据 `TicketTierService`：该商品**开了定制票**就走定制（散买按站级水票价、档位按绝对价目表），否则按统一折扣折算档位 |
| 为此加列 `ticket_record.account_product_id`（"扣自哪个账户"） | 账户恒等于 `product_id` → **该列由 v59 撤回** |

### 26.11.2 定稿口径

| 项 | 定稿 |
|---|---|
| 「统一」统一的是什么 | **折扣率**（站级一处配：买 10 张 9.5 折、30 张 9 折）。**不是价格** —— 农夫山泉按农夫山泉的价打 9.5 折（20 → 19.00），娃哈哈按娃哈哈的价（12 → 11.40） |
| 数据 | 新表 `station_ticket_discount`（`(station_id, qty)` 唯一，**只存折扣**：`discount_per_mille` 950 = 9.5 折）。**价格不落库** —— 落库就会与"各款水的价"分叉 |
| 生效判据 | **有没有上架的折扣档**（不另设开关列）。全下架 = 关闭 |
| 定制优先 | 该商品 `inventory.ticket_enabled = 1` 且站级水票价 > 0 → 走**定制**那套（散买按站级水票价、档位按 `ticket_package` 绝对价目表）；即使站里配了统一折扣也不走 |
| 统一折扣覆盖范围 | 只覆盖**桶装水**（`category = 1`，与押金/桶账同口径）；且该商品**没开定制票**、本站**有上架折扣档** |
| 只能按档买 | 走统一折扣的商品**没有单张价**（它连站级水票价都没配），所以只有档位可买 —— 这不是限制，是"折扣长在张数档上"的必然 |
| 账户与退款 | 票进**该商品**的账户；抵扣/退款与定制票**完全同一条路**（`consumeTicket` / `refundTicket` 恒用 `productId`）。退款不再需要读流水自证账户 |
| 用户端 | 列表只放**真实商品**（开了定制票的 + 桶装水）；档位拉回来看不出两种来源（`source` 只给前端决定回传 `packageId` 还是 `unifiedQty`） |
| 站长端 | 保持"特殊化"：商品选择里那个橙色入口配的是**折扣**（表单只有张数 + 折扣，没有总价输入框） |
| 端点 | `GET/POST/DELETE /api/ticket-discounts`（+ `GET /presets` 平台预设），全 `@RequireRole("STATION_MANAGER")`；顾客端档位仍走 `GET /api/ticket-packages?stationId&productId` |
| 正本 | `entity/StationTicketDiscount`、`service/impl/TicketTierService`（判据唯一实现）、`util/TicketPreset`（纯规则：预设档 + 折扣文案 + 定价算术）；用例 `StationTicketDiscountIntegrationTest` |

### 26.11.3 迁移与风险

- **v58**（纯加表）已在真实库执行；**v59**（DROP `ticket_record.account_product_id`）是**破坏性**操作 ——
  按规程**先上代码、再执行 SQL**，脚本自带「列内有非 NULL 值就中止」护栏。**当前待执行**。
- **数据零风险**：真实库 `ticket_record` / `ticket_account` / `ticket_package` 实测**均为 0 行**
  （功能上线但没人配过档位、没人买过票）→ 这次形态收口**没有任何存量要迁**。
  这也是 §26.3 说的"趁 0 数据的窗口期做"第二次兑现。
- 行为变化：`GET /api/ticket-packages?productId=0` 现在返回空（不再有"站级通用票"这种商品）；
  `POST /api/tickets/purchase` 不再接受 `productId = 0`（会以"商品不存在"拒绝）。

### 26.11.4 已知偏差（未闭合，与 §26.7 最后一行同源）

水票抵扣时订单水费仍走 `PriceUtil.calcUnitPrice(…, TICKET)`（站级水票价 → 通用库 → 零售价）。
对**走统一折扣的商品**来说，它没配站级水票价 → 实际按**零售价**记订单水费，而客户实付是
**折扣价**。这是"折扣只在购买那一刻固化进批次均价"这条既有口径的延续（不是本批引入），
但**统一折扣把这个差额放大了**（折扣越深、账面与实收差得越多）。
**要不要改成"按批次均价记账"需要产品拍板** —— 改了会动营收/毛利报表口径。
