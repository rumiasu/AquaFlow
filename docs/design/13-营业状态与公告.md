## 1. 产品口径（站长原话）

> 「加一个状态设置，**不阻断下单等功能，但是弹提示**；站长也能留言发公告。」

| # | 决定 | 说明 |
|---|---|---|
| 1 | **软状态，一律不阻断下单** | 顾客照常下单，只是会看到提示（页面横幅 + 下单响应 `warnings`）。**不做任何下单校验。** |
| 2 | 状态由**站长自己设**，随时可改 | 无审批、无平台干预 |
| 3 | 站长能写**一句留言** | 配合状态的具体说明（如"今天休息，明早 8 点正常送"），≤100 字，原样展示给顾客 |
| 4 | 站长能**发公告** | 本站公告（标题 + 内容），支持草稿/下架；顾客端只读已发布的 |
| 5 | 文案由**后端下发** | 前端不写状态映射表（本仓历史事故：前端自带 1/2/3 映射导致下单必失败） |

### ⚠️ 与 `station.status`（硬状态）的分界，谁都不能混

| | `station.status`（硬状态，旧） | `station.operating_status`（软状态，本次新增） |
|---|---|---|
| 取值 | 1 营业 / 2 停业 | 1 正常运营 / 2 休息中 / 3 配送延迟 / 4 暂停配送可预约 |
| 对下单的影响 | **直接拒绝**（`OrderServiceImpl` 抛"水站不存在或已停业"） | **不阻断**，只提示 |
| 对选站列表 | `status=2` 不出现在 `/api/stations/public` | 仍出现在列表里（带状态文案） |
| 谁来改 | 站长（建站/资料） | 站长（日常运营） |
| 判据 | "这家站没了" | "这家站现在什么情况" |

> 把"休息中"塞进 `station.status` 就等于把"休息"实现成"关张"，会真的挡住客户下单 —— 这是本次设计的**唯一红线**，回归用例 `StationOperatingStatusIntegrationTest.restingDoesNotBlockOrderButWarns` 锁住了它。

## 2. 状态取值与提示文案

| 值 | 文案 | 典型场景 | 顾客看到的提示 |
|---|---|---|---|
| 1 | 正常运营 | 默认 | **不提示**（`customerHint` 为 null） |
| 2 | 休息中 | 打烊 / 午休 | 「水站当前：休息中 · ⟨留言⟩（仍可下单，站长会按上面的说明安排配送）」 |
| 3 | 配送延迟 | 爆单 / 天气 / 人手不足 | 同上，文案换「配送延迟」 |
| 4 | 暂停配送，可预约 | 今天不送了，订单明天统一处理 | 同上，文案换「暂停配送，可预约」 |

- 文案唯一来源：`constant/StationOperatingStatus`（`textOf` / `customerHint`）。
- 提示里**必须包含"仍可下单"**：否则客户会误以为下不了单而放弃。
- 要不要加状态？加的话只需在 `StationOperatingStatus` 里加常量 + 文案 + 前端 `statusOptions` 一项（前端只提交 value）。
  候选（暂未加，等站长点头）：`5 仅配送预约单`、`6 暂停营业（长期）`——后者其实应当用硬状态 `status=2`。

## 3. 数据模型（v32）

```sql
ALTER TABLE station
  ADD COLUMN operating_status   tinyint NOT NULL DEFAULT 1,  -- 软状态，不阻断下单
  ADD COLUMN status_note        varchar(100) NULL,           -- 站长留言（≤100 字）
  ADD COLUMN status_update_time datetime NULL;               -- 最近修改时间
```

- 三列全部**可空或带默认值**，存量水站自动为 `1 正常运营`（与现状一致，前端零感知）。
- **不要**用 `StationMapper.update`（它会整行覆盖 name/phone/address/status）来改状态，用专用的
  `updateOperatingStatus`（只改这三列并校验 affected 行数）。

## 4. 接口

| 方法 | 路径 | 角色 | 说明 |
|---|---|---|---|
| GET | `/api/manager/station-status` | 站长 | 读本站状态（含 `statusText` / `note` / `customerHint`） |
| PUT | `/api/manager/station-status` | 站长 | 设状态 + 留言；校验取值与长度，**只改登录站长所属站** |
| GET | `/api/stations/{id}/status` | **公开**（免登录） | 顾客端横幅用；含 `hardStatus` 便于前端区分 |
| GET | `/api/stations/public` | 公开 | 选站列表，实体自动带出三个新字段 |
| GET/POST/PUT/DELETE | `/api/notices**` | 站长（写）／公开（读已发布） | 公告（原有能力，本次补前端入口） |

- 公开端点已在 `WebMvcConfig` 白名单里（`/api/stations/{id}/status`）—— 漏配会得到 401 而不是业务错误。
- 下单响应：`OrderServiceImpl` 在 `warnings` 末尾追加同一条提示（客户可能没注意到横幅）。

## 5. 前端

### 员工端
- 新页 `pages/station-mgmt/station-status/index`：上半 = 营业状态（4 选 1 + 留言 + 保存 + **顾客视角预览**），
  下半 = 本站公告（列表 + 发布/编辑/上下架/删除，草稿态可见）。
- 入口：卡片墙新增「营业状态与公告」卡片。
- 卡片墙「商品与库存」描述同步改为"选品上架、本站定价、库存流水"。

### 客户端
- `pages/shop/index`（商城）与 `pages/order/create`（下单页）：顶部**黄色横幅**显示 `customerHint`，
  **不隐藏商品、不禁用下单按钮**；接口失败时静默（不能因为提示失败让人买不了水）。
- 下单成功后：`proceedToPayment` 先展示 `warnings`（营业状态 / 欠桶 / 缺货），点"知道了"再进支付/成功页
  —— 此前前端**从未读过 warnings**，等于后端白提醒（欠桶提醒也一直没显示过）。

## 9. 2026-09-18 复核：公告这一半"接了但没接对"，修了两处

复核起因：死端点评估（`docs/audit/2026-09-16-死端点评估.md` §6.6）判定"公告写端无前端调用方"，
本次按"接线"排期时重新取证，发现**判定已过期** —— 公告的读/写/改/删四件事都在
`pages/station-mgmt/station-status/` 里，且已有契约用例。**但复核同时暴露两处真实缺陷**：

| 缺陷 | 症状（都是"界面说了、系统没做到"） | 修法 |
|---|---|---|
| **管理列表 SQL 多带 `status = 1`** | `NoticeMapper.listByStationId` 是 `where station_id = ? and status = 1`，而它服务的端点是"本站公告（含未发布草稿）"。于是① 保存草稿后提示成功、**列表里却没有它**（界面文案还写着"草稿只有你自己可见"）；② 点「下架」后公告**从列表消失、再也点不回来** —— 可草稿/下架这两个状态在界面上等于不存在 | 改为 `listForStation(stationId)`（不带发布状态过滤）并改名；控制器 javadoc 同步 |
| **前端自带状态映射表** | `station-status/index.js` 写 `statusText: n.status === 1 ? '已发布' : '草稿'` —— 与 §1 第 5 条"文案由后端下发"直接冲突 | 新增 `constant/NoticeStatus.java`（`textOf` / `isPublished`）+ `Notice.getStatusText()` 派生下发；页面只渲染后端字段；用例断言发布与草稿两条文案 |

**仍然没做（属可见性口径，需产品决定，不是"接线"）**：`GET /api/notices`（顾客端列表）**不做站过滤** ——
`listPublished()` 是 `where status = 1`，所以任何顾客都能看到**所有水站**的已发布公告。
`[AQ-038]` 当年只修了"按 id 读他站草稿"那条，列表这条一直没修。建议形态：加可选 `stationId`，
SQL 改为 `status = 1 and (station_id = #{stationId} or station_id is null)`（NULL = 平台级公告），
客户端用 `utils/station.js` 的 `resolveStationId()` 传入；**详情端点要一并处理**，否则按 id 仍能读到别站公告。
