## 1. 目的与范围

评估跨站拒付：**归属站把单外派给履约站，履约站送达时客户拒付** —— 这张异常单由谁看、谁结案、怎么补偿。本评估**不动代码**；非跨站单的拒付不在范围内。

**术语**：**归属站** = `orders.station_id`（定价方，客户资产记它）；**履约站** = `orders.delivery_station_id`（库存 / 配送员 / 计件工钱记它）；**结算站** = `orders.settle_station_id`（本单营收归谁，跨站单上 = 履约站）；**异常单** = `order_barrel_exception`。

### 1.1 现状：一处权限与损失错位

| # | 事实 | 证据 |
|---|---|---|
| 1 | 异常单**只记归属站**一个站 | `order_barrel_exception` 只有 `station_id`；手工发起与送达自动生成都写 `order.getStationId()` |
| 2 | 所有管理动作按这**一个站**判权 | `ManagerExceptionController` 的列表 / 详情 / 发起 / 核销 / 处理 / 执行 / 统计 / 配置 |
| 3 | 「拒付结案」动的账**分属两个站** | 核销应收 = `payment_status` 待收款(1) → 已取消(4)，而待收款口径认**结算站** → 抹掉的是**履约站的钱**；撤权益 + 记欠桶走 `barrelLedgerService`、站别取 `ex.getStationId()` → 动的是**归属站的桶账**；告警也发给归属站 |

> **归属站（不承担那笔钱）可以单方面抹掉履约站的应收；履约站（承担那笔钱的那个站）连这张异常单都看不见。**

后果：履约站的日结只看到「待收款少了一笔」、**查不出原因**；履约站当场被拒付**没有任何手段**记进系统；而既有裁定「外派出去的本单只能接单站管」——**该管的没权限，有权限的已退出**。

## 2. 设计口径：四件可独立决定的事

| 编号 | 内容 | 结论 |
|---|---|---|
| **①** | 异常单对**履约站**也可见 | ✅ 赞成（不必改表） |
| **②** | 结案需要**双方点头** | ⚠️ 收窄后再做（只在「两本账都被动」时要求） |
| **③** | 补偿：**下次让上一个履约站送** | ✅ 方向对，但**不要做成自动分配** |
| **④** | 谈不拢怎么办 | ➕ 建议补：钱按天自动收口、桶继续挂账 |

### 2.1 ① 双方可见：赞成，不用加字段

可见判据：**是这张单的归属站（`ex.station_id`）或履约站（`orders.delivery_station_id`）**。零 schema 改动 ⇒ 不会出现「异常单上的合作站与订单上的履约站不一致」的漂移（同一事实存两份是本仓最怕的），也修掉不对称的一半 —— 履约站至少能看到「我送的那单被核销了、为什么」。

⚠️ **可见面必须收窄**：只给**这一单的事实**（水费 / 桶数 / 差异 / 谁结的案），**不给客户在归属站的整本账**（欠桶汇总 `customer_barrel_over`、历史欠款、客户画像）—— 与 `util/CustomerProfileMask`（跨站不下发画像、只给订单快照）同一条口径，复用它即可；不做这一步就是**跨租户泄露**。**「看得见」≠「能结案」**（结案权限见 ②）。

**判据**：跨站可见面只给「这一单的事实」，不给「这个客户在别站的经营信息」。

### 2.2 ② 双方点头：按「会不会动到对方的账」分类

一刀切 = **每笔小额拒付都变成两个站长之间的一个待办**，而站长主要是力工 —— 本仓一贯反对「让系统成为负担」。判据：**结案时会不会动到对方站的账？**

| 情形 | 结案要动谁的账 | 建议 |
|---|---|---|
| 桶全还回来了、只差钱 | 只动**履约站的应收** | **履约站单方结案**（自己的损失自己认），归属站只读可见 |
| 桶没还（要撤权益 + 记欠桶） | 履约站的应收 **+** 归属站的桶账 | **双方点头**：一方发起 → 另一方确认 |
| 客户后来把钱还了 | 走收款链，不是异常单 | 置「已解决」即可，**无需协商** |

**为什么这样切对**：`writeOffForRefusal` 做三件事（核销应收 / 撤权益 / 记欠桶），后两件**只有客户手上还有桶时才有实际动作**（`take = min(该单桶数, 当前权益)`）→ 桶还回来时只动履约站一本账，没有理由要求归属站点头；「桶还了但不付水钱」正是最常见的拒付。**落地便宜**：状态机已够用（`STAFF_RECORDED → MANAGER_PENDING → MANAGER_APPROVED → EXECUTING → EXECUTED`），「待对方确认」直接落 `MANAGER_PENDING`，**不必新增状态**。

### 2.3 ③ 「下次还让他送」：别做成自动分配

好在哪：小水站网络里「这单我亏了、下次活补给你」是真实存在的结算方式，比「平台扣款 / 分账 / 保证金」轻得多，**不需要新账本、新字段**。

**「自动分配给上次的履约站」不建议做，四条理由**：① **定价方是归属站**（`DeliveryFeeUtil` 按 `orders.station_id` 算费），履约站拿的是归属站定的配送费 + 自己的计件单价，有些单它送是**亏的** —— 给谁送是商务决定，不该由系统替他们算；② 履约站的情况会变（停业 / 超范围 / 与该客户有纠纷 / 配送员离职）；③ **必须定义终止条件**（「直到异常解决为止」—— 桶还了算不算？）—— 定义不清就是**永久绑定**，解绑又要有人点一次，等于把「协商」换成「维护一条规则」；④ **错了伤的是客户**：客户被陌生站送而毫不知情、也没得选。

**替代做法**：补偿做成归属站侧的「一次点击」—— 下次看到该客户下单时提示「9-22 那单由 B 站配送，客户拒付 ¥70（已核销）；是否仍外派给 B？」，点一下走**现成的定向外派**（`POST /api/delivery/orders/{id}/dispatch` → `OrderWorkflowService.dispatchExternal`），双方照旧留痕确认；决定权留在人手里，**不新增字段 / 状态 / 定时任务**，终止条件天然存在（不点了就结束）。

> ⚠️ 与既有约束不冲突：**含押金 / 桶权益的单禁止进抢单池**，但**定向外派允许**（双方确认后）—— 能做的是定向外派，不是丢回池子。

### 2.4 ④ 僵局兜底：只做 ①②③ 等于把死结从「没权限」换成「没共识」

两边谈不拢（或一方长期不看）时，订单继续停在**已送达 + 待收款**，与现状一样。兜底：

> **钱的事不拖，桶的事慢慢追**：异常单在「待对方确认」上挂满 **N 天（建议 7 天）**无人响应 → 自动按「**仅核销应收**」收口（损失落在承担它的那一方），**桶的欠账继续挂在归属站**，走既有的欠桶（`owed_since`）与追桶流程。

理由：应收挂着压在**对方的日常**（日结 / 看板 / 台账一直挂着一条待收款）；欠桶挂着压在**追桶流程**，而那个流程本来就慢。

⚠️ **这是「系统替人做决定」且动的是钱**：**必须产品明确点头**；建议**先只做提示不自动执行**（超时在站长端标红 + 进 P0 待办），观察一轮再决定是否自动化。

### 2.5 相邻的两条既存口径（本文不改）

- **`category` 入参必须白名单校验**（正本 `constant/ExceptionCategory`，7 个取值 + `textOf` / `isValid`）：入口不校验时，集合外的值（曾实测写进 `REFUSAL`）会成功落库，之后所有 `switch` 都认不出它 —— 界面显示英文代号、统计漏掉它，**没有任何一处报错**。**已修**：入口加白名单，两处逐字重复的 `switch`（`OrderBarrelException.getCategoryText`、`NotificationServiceImpl.getCategoryName`）改为委托正本；用例 `CustomerRefusalWriteOffIntegrationTest.categoryMustBeWhitelisted`。
- **`writeOffForRefusal` 不校验 `category` —— 判定「不修」**：它只对 `payment_status = 待收款(1)` 的订单生效，语义是「这笔钱收不回来了」，与当初按哪个类别记的无关；真正的问题是**名字比行为窄** —— 留作命名建议，**不动代码**（改名会牵动端点与前端文案，收益不抵风险）。

### 2.6 落地成本、风险与顺序

| 项 | 改动面 | 风险 | 可否独立上线 |
|---|---|---|---|
| **① 双方可见** | 查询 join `orders` 取履约站；判权点改成「或」；再加可见面收窄 | **低**（读路径，出错表现为「看不到」） | ✅ 可先做 |
| **② 分类点头** | 复用 `MANAGER_PENDING`；确认留痕落 `manager_note` 或新增「确认站」列 | **中**（状态机改动必须补用例；写坏会「两边都以为对方结了」） | 需与 ① 一起 |
| **③ 一次点击外派** | 纯前端提示 + 复用 `dispatchExternal` | **低** | ✅ 可先做 |
| **④ 超时兜底** | 定时任务（可搭 03:00 日结那趟） | **中高**（自动核销别人的钱） | ❌ 放最后一轮 |

**顺序结论**：先做 **① + ③**（不动状态机、可逆、纯读路径 + 复用现成写路径），跑一轮再决定 ② + ④。

## 3. 数据模型

**①②③ 都不需要改表**：唯一可能加字段的是 ② 的「谁确认过」留痕 —— 复用 `manager_note`（零 schema 改动，代价是自由文本）或新增「确认站」列（可查询，代价是一列 + 一条迁移），推荐先复用 `manager_note`。「待对方确认」复用 `MANAGER_PENDING`，状态枚举（正本 `entity/OrderBarrelException`）**不新增取值**。

## 4. 接口与权限

| 判权点 | 现状 | ① 落地后 |
|---|---|---|
| 列表 / 详情 | 只认 `ex.station_id` | 追加「或 `orders.delivery_station_id`」（可见面按 ① 收窄） |
| 发起 / 处理 / 执行 / 统计 / 配置 | 只认 `ex.station_id` | 不变 |
| `POST /api/manager/exceptions/{id}/write-off` | 只认 `ex.station_id` | 按 ② 分类：只动履约站的账 → 履约站单方；两本账都被动 → 双方 |
| `POST /api/delivery/orders/{id}/dispatch` | 双方确认留痕 | 不变（③ 复用它） |

## 5. 前端落点

- **③**：归属站侧的下单 / 外派界面，一句提示 + 一次点击，**不做自动分配**。
- **④**：站长端「异常订单」页标红 + 进 P0 待办；**第一轮只提示**。

## 6. 验收用例

| 要锁住的判据 | 用例 |
|---|---|
| 履约站能看到跨站单，且**看不到客户在归属站的经营信息**（欠桶汇总 / 历史欠款 / 画像） | 新增跨站可见性用例（参照 `CrossStationPoolRiskAndProfileIsolationIntegrationTest`） |
| 桶已还清 → 履约站可单方结案；桶没还清 → 必须双方确认 | 新增 ② 的分类用例 |
| 结案后履约站应收被核销、归属站桶账被动到；**只允许从「已录入 / 已审批」进入**（重复核销报错而非静默跳过） | 扩 `CustomerRefusalWriteOffIntegrationTest` |
