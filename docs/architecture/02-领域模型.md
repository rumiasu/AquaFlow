# 领域模型

> 本文说明 AquaFlow 的业务域划分与不可凭直觉改写的核心不变量。
> 枚举取值以 `constant/*.java` 为准，表结构以 `AquaFlow-backend/sql/schema.sql` 为准，本文不复述。
>
> 本文的每一条都是**判据**（能判定真伪的约束），不是背景介绍。

## 1. 业务域

系统按三个层次组织：

**端** —— `miniapp-user`（顾客）、`miniapp-delivery`（站长 + 配送员）。

**后端业务域**：

| 域 | 职责 |
|---|---|
| 安全基座 | 认证、授权、限流、审计 |
| 客户 | 客户档案、地址、客户与水站的关系 |
| 水站人员 | 水站、员工、角色与绑定关系 |
| 商品与桶目录 | 通用商品库、站级定价、自定义商品 |
| **桶权益账本** | 桶权益批次、过占、配送中（系统的核心） |
| 订单 | 下单、状态机、转单与外派 |
| 支付与押金 | 支付流水、押金账户、退款 |
| 水票 | 水票批次、档位套餐 |
| 配送履约 | 接单派单、送达、回桶核对、计件工资 |
| 运营支撑 | 看板、对账、告警、报表、公告 |

**数据层** —— 主数据 / 桶账 / 交易（订单 · 支付）/ 水票 / 运营（告警 · 对账）。

## 2. 客户是全局身份

**`customer` 表没有 `station_id` 列，永远不加。** 客户是一个全局身份，可以自由选择不同水站下单。

订单、桶、水票、押金一律按 `(customer_id, station_id)` 隔离。

「经营归属」（这个客户算谁开发的）不是一个字段，而是一个**并集口径**：

```
某站客户 = 绑定关系（customer_station_config） ∪ 在该站有过订单的客户
```

采用并集而非只用订单，是为了保护水站已开发但尚未下单的客户不被别站抢走。
⚠️ 判定「是否本站客户」必须用并集实现（`CustomerMapper.countCustomerOfStation`），
**不要用只按订单统计的变体** —— 它会把没下过单的新客户判成"不属于本站"。

## 3. 三站语义

这是本项目最容易写错、写错就真丢钱的一组口径。一笔订单同时关联三个水站：

| 字段 | 名称 | 含义 |
|---|---|---|
| `orders.station_id` | **归属站** | 客户选定的水站，也是**定价方** |
| `orders.delivery_station_id` | **履约站** | 实际配送的水站：库存从它扣、进它的配送员清单、计件工钱记它 |
| `orders.settle_station_id` | **结算站** | 本单营收（水费 + 配送费 + 楼层费）归谁 |

**结算站的取值规则**：

- 下单时 = 归属站
- 抢单成功 / 定向外派成功 = 履约站
- 召回 / 退回抢单池 / 指定退回被同意 = 回归属站

**判权表** —— 每一笔钱、每一个桶认哪个站，是这张表说了算：

| 事项 | 认哪个站 |
|---|---|
| 配送费与楼层费计算、起送量与配送范围判定 | 归属站 |
| 库存扣减、配送员清单、计件工钱归属 | 履约站 |
| 看板、毛利报表（成本 join 也按此）、应收账款与核销 | 结算站 |
| 确认收款的判权、退款的判权 | 结算站 |
| `payment_record.station_id` 的写入 | 结算站 |
| **客户资产**：押金账户、水票、桶权益 | **归属站** |
| **欠桶、桶异常单的归属** | **归属站** |

> ⚠️ 「钱认结算站」「客户资产认归属站」是两条并列规则，不要互相套用。
> 退款曾经认归属站，已统一改为认结算站。

**SQL 读取结算站一律写** `coalesce(o.settle_station_id, o.delivery_station_id, o.station_id)`。
末级是防御性兜底 —— 正常写入路径必须落 `settle_station_id`。

## 4. 桶权益模型（系统核心）

**桶是资产，不是消耗品。** 顾客买水时买下的是桶的**权益**；喝完要还桶，最后要退押金。

### 4.1 四个数

按 `(客户 × 水站 × 商品)` 维度：

| 数 | 定义 | 性质 |
|---|---|---|
| **权益** | 已到手的桶数（`customer_barrel_asset.quantity`，送达时入账） | 真相源是批次表 |
| **配送中** | 已付款买下权益但尚未送达的桶（`customer_barrel_in_transit` 的 `PENDING`） | 独立表 |
| **持有** | 权益 + 配送中 | **仅用于展示** |
| **占用** | 权益 + 过占（over） | **还桶上限**，不含配送中 |

恒等式：**`占用 = 权益 + 过占`**

两条容易搞错的推论：

- **下单抵扣与退押金只认权益**：`shortage = max(0, 需要桶数 − 权益)`，按桶型逐个算。
  配送中的桶在结束前**不参与抵扣、也不可退**。
- **还桶上限用「占用」不用「持有」**。

### 4.2 过占可以为负

`customer_barrel_over` **允许为负**，表示顾客多还了桶、寄存在水站。这是**合法状态**，不是数据错误。

过占**按商品各算**：A 水的桶多还不能抵 B 水的欠。

欠桶「只提醒、不阻断」：下单每次都下发提醒，但**不阻断下单**（历史上曾有硬性上限，已移除且不要加回）；
物理护栏保留 —— 占用不得为负。

### 4.3 批次与写入口

- **金额的唯一真相源是 `customer_barrel_lot`（押金条批次）**，`customer_barrel_asset` 是派生汇总。
- **桶账的唯一写入口是 `BarrelLedgerService`。** 任何改动桶数量的路径都必须经它。
- 权益核销按 **FIFO** 逐批次消耗。

### 4.4 合法绕开通道只有两条

退桶与欠桶互斥：**欠着空桶就不许退桶，先还清**。硬拦两处（预览时拒绝、退款时再查一次），按商品分别判定。

唯二可以绕开常规通道撤销桶权益的入口是：

- **站长资产调整单** —— 人工补录历史资产的唯一合法来源，带单据头、反向单撤销与幂等键，纳入对账；
- **桶异常单** —— 异常处置流程，带类别白名单。

两者都**只应由站长人工发起**，并留下单据痕迹。

### 4.5 汇总口径（高频错误）

**任何「按商品 / 按桶型」的桶汇总，必须取 `权益 ∪ 配送中 ∪ 过占` 的并集。**

只遍历 `customer_barrel_asset` 会让「首单还在配送途中」的商品**整行消失** —— 这是本仓库历史上
反复出现的一类缺陷。

### 4.6 「这个商品是不是桶」的唯一判据

**押金与桶账只对桶装水生效**，这条口径写死在 `product.deposit` 与 `inventory.deposit_price`
两处列注释里。判断「是不是桶」的实现只有一个：

> **`util/BarrelScope.isBarrel` / `isBarrelCategory`** —— 不要在调用点写 `category == 1` 或 `category != 1`。

⚠️ **历史教训**：这条判据曾被散落在六七个文件里各写一遍（历史写法是反选 `category != 1`），
于是长出两条偏离设计的路 ——

1. **非桶装也收押金**：报价与下单都对非桶装按件收押金，而押金的唯一出口是「按桶型押金条退桶」，
   非桶装没有押金条，钱进了押金账户却没有自动退还路径；
2. **非桶装污染桶账**：送达时按订单明细统计「本单送出」，把非桶装的数量也算成桶，
   凭空生成桶权益。

两处都已修，并由 `DisposableBarrelLedgerBoundaryIntegrationTest` 钉住（一次性桶不产生桶权益、不收押金）。

## 5. 三本账

系统同时维护三条独立的账线，各自的真相源与写入口都不同：

| 账线 | 真相源 | 唯一写入口 | 对账口径 |
|---|---|---|---|
| **桶** | `customer_barrel_lot.remain_qty` | `BarrelLedgerService` | 守恒等式（含合法终态豁免） |
| **水票** | `ticket_lot.remain_qty` | `TicketLotService` | `ticket_account` 必须等于 Σ 批次余额 |
| **押金** | `deposit_record` 流水 | 押金服务 | `balance == SUM(deposit_record.amount)` |

共同约束：

- **方向由类型决定，调用方金额一律传正数。** 扣减类以**负数**落库 —— 这是押金对账等式成立的前提。
- **金额列只加不改**：费用绝不并入水费或押金（押金可退，混入会导致取消时多退钱）。
- **水票单价取实付均价**（`payment_record.amount / ticket_qty`），消耗按 FIFO，退款按流水里的当时单价回补。

### 5.1 押金入账时机

**下单只把「应收押金」记在订单上，不入账；收到钱才入账。**

入账由 `PaymentService.applyDepositOnPaid` 完成，挂在每一次「订单支付成功」上，
按订单幂等（以 `related_order_id` 去重），因此重复调用安全。这条口径直接决定对账是否能平 ——
若下单即入账，顾客一分钱未付时押金余额就已经存在了。

**押金与水票认归属站，不随结算站走。** 跨站履约时收钱的人是履约站，但押金仍入在客户的归属站账上
（释放时同理）。这与「钱认结算站」是两条并列规则，不要互相套用。

## 6. 并发与快照契约

### 6.1 桶账的加锁协议

桶账是本系统并发压力最大、也最容易写错的地方。三条铁律：

1. **只加行锁不够，必须用当前读。** MySQL 默认隔离级别是 REPEATABLE READ ——
   第二个事务即使成功拿到了行锁，普通 `SELECT` 读到的仍是**事务开始时的快照**。
   要取最新已提交值，必须用加锁读（`SELECT ... FOR UPDATE`，属当前读）。
2. **`FOR UPDATE` 对不存在的行不加锁。** 并发写入前必须先 upsert 把行建出来，否则锁不住任何东西。
3. **多行加锁必须按 `productId` 升序。** 两个并发事务若以相反顺序锁同一批商品，会互相等待成环（死锁）。
   桶账的所有多行路径共用同一套加锁顺序。

> 违反第 1 条的表现是「偶发少扣一个桶」；违反第 3 条的表现是「偶发死锁」。
> 两者都只在并发下出现 —— 单线程测试与手工点击都发现不了。

### 6.2 快照契约

订单在**下单那一刻**把地址快照进订单：`orders.address_snapshot`（地址文本）、
`orders.address_snapshot_lat` / `address_snapshot_lng`（经纬度）。
订单明细 `order_item` 同时留有商品名快照。

**快照之后，客户修改地址或商品不影响历史订单** —— 配送员看到的永远是下单时那个地址。
这也是为什么「改地址」不会、也不应该触发任何订单重算。

## 7. 状态机

### 7.1 订单

`1 待配送 → 2 配送中 → 3 已送达 → 4 已完成`，另有 `5 已取消`。
非法流转由 `OrderStatus.isValidTransition` 拒绝。

- **可取消只有两个状态：`1 待配送` 与 `2 配送中`**（判据在 `OrderStatus.isCancellable`）。
  **已送达、已完成、已取消一律不得取消** —— 已送达的单货物已经出门，走取消链会把货与钱同时倒回去。
- 拒绝取消时的提示文案由 `OrderStatus.notCancellableReason` **单点下发**（它对已送达、已完成、已取消各有专门措辞），不要在各处另写一套。
- **状态只前进，不倒滚。** 要表达异常态就新设状态，不要把状态改回去。

### 7.2 支付

`0 未付 / 1 待收款 / 2 已付 / 3 已退款 / 4 已取消`。唯一真值是 `orders.payment_status`。

- **只前进，不倒滚**：`0 未付`、`1 待收款` 表示钱还没到手；`2 已付` 是收钱的结果；`3` / `4` 是终态。
- 现金单**下单即进入待收款**。
- 「发起收款」与「送达未收款」都**不许改写支付状态**。
- 唯一写「已付」的入口是带 CAS 的 `markPaidIfCollectable`，从 `0` 或 `1` 迁入，**绝不复活 `3` / `4`**。

### 7.3 其他

| 状态机 | 取值 |
|---|---|
| 退桶审批 | `1 申请 → 2 确认收到空桶 → 3 已退押金`，**不允许跳步**；界面必须给到「退押金」那一步，否则顾客押金退不出来 |
| 工资结算单 | `草稿 → 已确认 → 已发放`；确认后明细锁定 |
| 公告 | `0 下架 / 1 发布`；站长端管理列表**必须含草稿与已下架** |

## 8. 术语约定

| 统一用 | 不要用 | 说明 |
|---|---|---|
| **配送中** | 在途 | 已付款买下桶权益但未送达。表名 `customer_barrel_in_transit` 与类名 `CustomerBarrelInTransit` 是**历史命名**，仅为兼容保留；注释与文案一律写「配送中」 |
| **进行中** | —— | 待配送 + 配送中 的合称 |

**展示文案（`statusText` / `payMethodText` / `payStateText`）一律由后端下发，前端禁止自带映射表。**
两端各写一套曾导致新客户下单 100% 失败。

## 9. 待确认事项

| 待确认内容 | 需要的验证手段 | 影响 |
|---|---|---|
| 免押金循环桶如何表达 | 需要产品确定是否存在该业态 | 现有模型无法表达"循环桶但不收押金"：押金覆盖判据把 0 当成"未覆盖"，且商品维护侧不允许 0 押金 |
| `GET /api/notices` 是否应做水站过滤 | 产品判定公告是否本就该全平台可见 | 当前任一顾客能看到所有水站的已发布公告 |
| 跨站拒付（异常单）如何双站协商 | 需要产品在几种方案间拍板 | 异常单目前只盖归属站，但核销会动两个站的账 |
| 微信支付接入时机 | 取决于是否具备商户资质 | 影响新客户的自助下单通道与退款链路 |
| 多实例部署所需的限流与定时任务改造 | 压测确认单实例上限后再决定 | 当前限流计数与部分定时任务假定单实例 |
