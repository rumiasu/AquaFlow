# 测试体系

> 件数以 `AquaFlow-backend/build/test-results/test/*.xml` 为准。
> **`master` 提交状态**：95 个测试类 / 466 个用例 / 0 失败。
> 本机工作区若含有未提交的新用例，实测值会更大（差别的原因见 §6）。
> 按业务场景组织的覆盖地图见 `docs/audit/2026-09-16-场景测试矩阵.md` —— **新增用例前先看它找空白**。

## 1. 为什么以集成测试为主

本项目的正确性几乎全部落在**跨表、跨事务、跨角色**的地方：桶权益的批次核销、三条账线的守恒、
并发下的状态改写、跨站场景里"钱记谁、货走谁"。这些用 Mock 掉的单元测试证明不了 ——
Mock 掉的正是出问题的那一层。

所以测试基类启动**完整 Spring 容器**，连**真实 MySQL**，发**真实 HTTP**（JDK `HttpClient`），
断言直接查库。代价是慢，收益是"测试绿了 = 应用真的能起来、接口真的通、账真的平"。

## 2. 两个基类

### 2.1 `support/AbstractIntegrationTest`

```java
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
@ActiveProfiles({"local", "test"})
```

- **随机端口**启动容器，用真实 `HttpClient` 发请求，因此测的是真实的序列化、拦截器与切面链。
- **每个用例前 TRUNCATE 所有表**。执行前先查 `SELECT DATABASE()` 并**断言库名含 `test`** ——
  杜绝误清开发库。
- ⚠️ **`SET FOREIGN_KEY_CHECKS = 0` 与随后的 `TRUNCATE` 必须在同一条连接上。** 该设置是**会话级**的：
  若逐条发送（`SET` → 循环 `TRUNCATE` → `SET`），每条都可能从连接池拿到另一条连接，
  于是 `TRUNCATE` 在"外键检查仍开着"的连接上执行，报
  `ERROR 1701 Cannot truncate a table referenced in a foreign key constraint`。

**夹具**（造数）与**令牌**：

| 类别 | 方法 |
|---|---|
| 造数 | `createStation` / `createStaff` / `createCustomer` / `createProduct` / `createAddress` / `createOrder` / `createOrderFull` / `createOrderCrossStation` / `createOrderItem` / `createInventory`（及 `Full` / `WithStationPricing` 变体）/ `createInventoryRecord` |
| 令牌 | `customerToken(id)` / `staffToken(id, role, stationId)` / `unselectedStaffToken(...)` |

### 2.2 `support/AbstractScenarioTest`

在集成测试基类之上，把「一个能真实经营的水站」封装成一个 `World`
（`stationId` / `managerId` / `driverId` / `productId` …），并给出链路级的动作与断言。

**动作**：

| 方法 | 含义 |
|---|---|
| `openStation(label)` / `openStation(label, price, deposit, stock)` | 开一个可经营的水站，返回 `World`；`label` 同时用作站名、员工名、客户名与 openid 前缀 —— **一次用例里开多个站时必须各不相同** |
| `placeOrder(w, idempotencyKey, payMethod, qty)` | 客户下单 |
| `acceptOrder` / `assignOrder` | 配送员接单 / 站长派单 |
| `completeDelivery(w, orderId, expected, returned, collected)` | 送达并回桶核对 |
| `completeDeliveryNoCollectedField` | **不传** `collected` 字段的变体 —— 专门用来验"字段有没有被静默丢弃" |
| `confirmOfflinePay` | 站长确认线下收款 |

**断言**：

| 方法 | 验什么 |
|---|---|
| `assertReconcileBalanced(what)` | 全量对账等式 |
| `assertStationReconcileClean(w, what)` | 本站视角的对账 |
| `assertInventoryConserved(w, what)` | 库存守恒 `inventory.quantity == SUM(inventory_record.delta)`。单独再查一遍而不是只靠全量对账 —— 全量等式是**全平台**聚合，本站造错数可能被别站的正数抵消 |
| `assertBarrelLedgerClosed(w, what)` | 桶账闭合。权益取 `customer_barrel_lot.remain_qty`（**真相源**），不是 `customer_barrel_asset.quantity`（派生汇总） |

**造数有一条硬约束**：**不能用 SQL 直接往 `customer_barrel_asset` / `customer_deposit_account` 塞数** ——
它们是派生表，直塞会与批次账脱节，对账立刻不平。同理**库存必须成对造**
（只插 `inventory` 不插 `inventory_record` 会让库存守恒等式不平），`openStation` 已代为处理。

## 3. 断言约定

**一律判响应体里的 `code`，不判 HTTP 状态码。** 业务错误仍返回 HTTP 200，只有未认证是真 401。

并发场景参考 `ConcurrencyIntegrationTest.fireTogether`。

## 4. 静态门禁

CI 与 `scripts/verify.sh` 会跑六个 Python 脚本（都在仓库根目录，**按裸文件名调用，因此不能移动**）：

| 脚本 | 检查内容 | 为什么需要 |
|---|---|---|
| `audit_wxml_handlers.py` | `wxml` 绑定的事件处理函数是否真实存在 | 缺失时点击**静默无反应**，没有任何报错 |
| `page_reach_audit.py <端名>` | `app.json` 注册页是否缺 `.js`、是否跳转到未注册页 | 需传端名，两端各跑一次 |
| `static_audit_user.py <端名>` | `require` 相对层级错误、`wxml` 里调用全局对象或 Page 方法 | 同上 |
| `audit_comments.py` | 悬空 javadoc | 无归属的注释会误导读代码的人 |
| `audit_js_syntax.py` | JS 解析期错误（重复 `const` 声明、少括号） | 这类错误**其余脚本都不解析 js**，会让整个模块加载失败 |
| `audit_scenario_matrix.py` | 场景矩阵声称的测试类 / 方法必须真实存在 | 矩阵是"被指定为入口"的文档，它一过期就会把下一个改代码的人带错方向；件数声明不得与 `build/test-results` 漂移 |

一条命令跑完（含敏感信息扫描）：

```bash
bash scripts/verify.sh
```

## 5. CI

`.github/workflows/ci.yml` 在仓库根（放进 `AquaFlow-backend/` 下 GitHub 不会读）。步骤：

1. Checkout / Set up JDK 17
2. **初始化测试库**：`schema.sql` 是权威基线，必须显式建表，否则集成测试上下文加载即失败
3. **后端集成测试**（真实 MySQL + 真 HTTP）
4. **小程序静态扫描**（两端）
5. **场景测试矩阵一致性门禁**
6. **敏感信息扫描**（只报位置，不回显内容）
7. 上传测试报告（失败时也保留，便于排查）

### 在本机复现 CI

要判断"CI 会不会绿"，在本机照抄三步，**缺一步都会得出错误结论**：

1. `DROP DATABASE aquaflow_test; CREATE DATABASE aquaflow_test;` 后**按字节级重定向**导入 `schema.sql`；
2. `./gradlew cleanTest test` —— **必须带 `cleanTest`**，否则 Gradle 报 `:test UP-TO-DATE` 而**根本没跑**；
3. **把 CI 的环境变量也照抄一遍**（尤其 `DEV_LOGIN_ENABLED=false`）。本机默认为 `true`，
   不一致会让"只在 CI 上红"的用例长期隐身。

## 6. 统计件数的两个陷阱

统计测试件数必须把所有 XML 相加，并且**用真正的 XML 解析器**：

- ❌ 不要 `Get-Content -Raw` 再转 `[xml]` —— 按 ANSI 解码会弄坏测试名并**静默少算**。
- ✅ PowerShell 用 `$d = New-Object System.Xml.XmlDocument; $d.Load($path)`；Python 用 `xml.etree.ElementTree`。

另外，**工作区未提交的新用例会让件数与 HEAD 不一致**。矩阵里的件数声明必须写
「**要提交的那个状态**」的件数，而不是本地工作区跑出来的数。

## 7. 已知空白

- 链路级（scenario）用例只覆盖现金单生命周期，其余支付方式与跨站外派场景尚未落到这一层。
- `src/test/.../util/` 下是测试辅助类，不构成独立用例。
- 限流默认在测试中关闭，只有 `RateLimitIntegrationTest` 用 `@TestPropertySource` 打开 ——
  因此"限流是否真的生效"只由那一个类保证。
