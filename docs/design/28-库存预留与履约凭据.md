## 0. 一句话

**把"扣库存"从一个动作拆成两个量：下单**预留**（占可用量、不动实物）、完成配送**出库**（动实物、锚定当时履约站）。**
缺货那部分留在"预留不足"里、由入库补齐；换站时预留跟着搬；取消时释放预留而不是回补库存。

---

## 1. 要解决的两个场景（都已实测）

| 场景 | 当前实际行为 | 正确行为 |
|---|---|---|
| **① 跨站外派后取消**<br>A、B 各 10 桶；客户在 A 下 2 桶 → A 变 8；定向外派给 B；客户取消 | 回补记**履约站 B** ⇒ **A=8、B=12**（A 少掉的 2 桶永不回来，B 凭空多 2）。2026-09-25 探针实测得到的就是这两个数字 | 下单只是**预留**，实物没动；换站把预留从 A 搬到 B；取消在 B **释放**预留 ⇒ **A=10、B=10** |
| **② 缺货下单后补货**<br>库存 3、下单 10（`confirmShortage`）、补货后完成配送 | 只记 `deducted_qty=3`，剩下 **7 桶永远不落账**；实物与账目永久漂移。全后端只有两处改库存（下单扣、取消补），补货与完成都不碰 | 下单预留 3、缺 7 记"预留不足"；**入库时按 FIFO 自动补预留**；完成配送时按订单量**出库**（此时预留已足） |

补充事实（决定了修法）：`orders.delivery_station_id` 在下单那一刻等于归属站，换站由 `OrderMapper` 的三个 CAS 改；
而扣减发生在**下单那一刻的归属站** ⇒ "订单在某站履约"根本不足以证明"该站曾为它扣过库存"。
另外：对账等式 V1-4（`库存数量 == Σ 库存流水`）**抓不到**这两种漂移 —— 缺的事件在等式两边同时缺失，等式照样平。

---

## 2. 目标与非目标

**目标**
1. 库存的每一次变化都能回答三个问题：**哪个站、为哪张单、什么时点**（凭据化）。
2. 跨站履约（放池/定向外派/抢单/召回）不再产生库存归属漂移。
3. 缺货预订（`needConfirm` + `confirmShortage`）**保留**：客户仍可下超量单，缺的部分由补货补齐。
4. 完成配送前，实物出库量与订单量必须对得上（**不许静默少扣**）。

**非目标**
- 不做多仓/调拨单/采购单；不引入消息中间件、分布式锁（单库 + 本地事务 + 行锁 + 唯一键足够）。
- 不改金额口径（水费/押金/配送费一律不受影响）。
- 不改客户可见的价格与库存展示文案（商城"暂时没货"的判断依据换成"可用量"，见 §5）。
- **不动 `orders.station_id` / `delivery_station_id` / `settle_station_id` 的三站语义**（问题 4 只补"货"的凭据，不动"钱"的归属）。

## 3. 数据模型（新增一张表，不改既有列的含义）

```
inventory_reservation                       -- 库存预留/出库凭据（一单 × 一商品 一条）
  id                bigint PK
  order_id          bigint  NOT NULL        -- 关联订单
  order_item_id     bigint  NOT NULL        -- 关联明细（逐桶型计）
  product_id        bigint  NOT NULL
  station_id        bigint  NOT NULL        -- ★ 这份凭据当前挂在哪个站（换站时改这一列）
  reserved_qty      int     NOT NULL        -- 已预留在库量（≤ 订单量；差额 = 缺货待补）
  shipped_qty       int     NOT NULL 默认0  -- 已出库量（完成配送时一次性写满）
  released_qty      int     NOT NULL 默认0  -- 已释放量（取消/换站旧凭据）
  status            tinyint NOT NULL        -- 1 预留中 / 2 已出库 / 3 已释放
  create_time / update_time
  UNIQUE KEY uk_reservation_order_item (order_item_id)      -- 一条明细一份凭据
  KEY idx_reservation_station_product_status (station_id, product_id, status)
  KEY idx_reservation_order (order_id)
```

**四个量各自的口径**（写进列注释，不要再靠推导）：

| 量 | 含义 | 谁写 |
|---|---|---|
| `inventory.quantity` | **在库实物**（语义不变） | 入库 / 盘点 / **出库**（完成配送）/ 退货入库 |
| `reserved_qty` | 已承诺给某张单的实物量 | 下单预留、入库补预留、换站重建 |
| **可用量**（派生，不落库） | `quantity − Σ(reserved_qty where status=1)` | 只读，缺货判断与商城展示都读它 |
| 缺货待补（派生） | `order_item.quantity − reserved_qty` | 只读，站长端提示 + 完成配送的硬门槛 |

**为什么另立一张表而不是给 `inventory` 加一列**：预留天然是 `(订单, 商品, 站)` 三元组，还要能表达
"换站搬到别处""取消释放""出库了多少"三段生命周期；挤进 `inventory`（站 × 商品）会立刻丢掉订单维度。
`order_item.deducted_qty` **保留但改口径**：它是"下单实际预留在库量"（原义是"下单实际扣减量"），
取消路径不再读它做回补 —— 见 §4 的注释要求（AGENTS §6.1：口径改了必须当场改注释，否则下一个读的人会照旧理解）。

## 4. 生命周期（唯一写入口：新增 `InventoryReservationService`）

| 时点 | 动作 | 关键约束 |
|---|---|---|
| **下单**（`createOrder`） | 对每个明细：`reserve = min(可用量, 订单量)`；写一条 `status=1` 的凭据 + 一条 `RESERVE` 库存流水 | **不再减少 `quantity`**；`可用量 < 订单量` 仍走既有的 `needConfirm`（客户确认后照建单，差额就是"缺货待补"） |
| **入库 / 盘点增加**（`inbound`、`setStock` 增量） | `backfillShortages(stationId, productId, delta)`：把新增的可用量按**订单创建时间 FIFO** 补给本站"缺货待补"的单（只加到 `reserved_qty`，不动 `quantity`） | 补预留不得让 `Σ reserved > quantity`（补到刚好为止） |
| **完成配送**（`completeDelivery`） | 对该单每条凭据：`shipped_qty = 订单量`、`status=2`，并 `quantity -= 订单量` + 一条 `CONSUME` 流水 | **硬门槛**：`reserved_qty < 订单量` ⇒ 直接拒绝："本站库存预留不足（缺 N 桶），请先入库补足后再完成配送"（不许静默少扣 —— 那正是场景 ② 的病根） |
| **换站**（放池 / 定向外派 / 抢单 / 召回） | 在同一个事务里：旧站凭据 `released_qty = reserved_qty`、`status=3`；新站按该站**可用量**重建凭据（`station_id` 换掉、`reserved_qty = min(可用量, 订单量)`） | 顺序固定：先订单 CAS → 再搬凭据（都以订单行为锁对象）；重建后若仍有缺货，给接单站**下发提示**（"本站库存不足，请补货后配送"），不阻断接单（保留"缺货可预订"） |
| **取消 / 拒单 / 退款**（`refundOrder`） | 该单所有 `status=1` 的凭据 `status=3`（释放），**不再 `increaseStock`** | 按 `order_id` 全量释放，幂等（重复取消由订单状态 CAS 拦住） |
| **未付微信单超时扫单**（`UnpaidWechatOrderSweeper`） | 走同一条取消链 ⇒ 自动释放预留 | 无需单独改 |

**锁顺序（写进服务类注释）**：`orders` 行 → `inventory_reservation` 行 → `inventory` 行。
理由：换站要先确认订单还能改（CAS），再动凭据与实物；反序会与"完成配送"形成交叉等待。

## 5. 读侧口径（哪些地方必须跟着改）

1. **缺货判断**（`createOrder` 的 `shortages` 收集）：从 `quantity` 改成 **可用量** —— 否则两个客户会各自
   把同一批实物承诺出去（下单单据不再扣 `quantity`，这个判断是唯一的护栏）。
2. **商城/下单页的"暂时没货"**：⚠️ **实现时改了口径（2026-09-25 落地记录）**：
   *缺货判断*（下单响应里的 `shortages` / `needConfirm` 与 `warnings` 文案）已改用**可用量**；
   但*商品列表下发的 `quantity`* 仍是**在库实物**（站长端与顾客端共用同一个字段，改它要连带改
   商品列表 SQL 与顾客端文案，属独立小任务）。
   影响：顾客可能看到"库存 10"而下单 8 时收到"仅剩 8 桶"的确认弹窗 —— 判断更保守、不会超卖，
   属于**可接受的显示滞后**；后续要一致就把列表也改成下发可用量（那时必须同时改列注释与文案）。
   站长端的「库存数量」保持**在库实物**（他盘点的是实物）—— 两处口径不同必须在列注释与接口文档里写清。
3. **低库存告警**（`DashboardMapper.lowStock = quantity < 20`）：保持实物口径不变，避免连带改站长端语义；
   若后续要"可用量低"告警，另开一列字段（不要偷改现有字段的含义）。
4. **对账**：V1-4 等式不变（它只看 `quantity` 与流水）。**新增一条只读校验**（建议 E11）：
   `Σ(reserved_qty where status=1) > inventory.quantity` ⇒ 报差异（"预留超过实物"）。
   它抓不到 §1 的两个场景，但能抓住新模型自身的破坏性 bug。
5. **站长端提示**：选品/库存页对"缺货待补"的单显示数量（`GET /api/manager/...` 由待办接口补一个计数字段）。
   ⚠️ **本条未实现（2026-09-25 界面走查核实）**：`InventoryReservationService.shortageOfOrder` 在生产代码里**零调用方**，
   `constant/PendingItem` 的待办项里也没有"缺货待补"这一条 —— 站长目前唯一能知道缺货的时机，是配送员点完成被拒之后。
   证据与修法建议见 `docs/audit/history/review/2026-09-25-界面走查-库存可用量与缺货恢复.md`；**别把本条读成已完成**。

## 7. 迁移草案（`v63_inventory_reservation.sql`）

1. **建表**（上面 §3，`CREATE TABLE IF NOT EXISTS`；不带外键 —— 与 `inventory_record` 一致，避免删单被外键挡住）。
2. **回填在途单**（只回填 `status IN (1,2)` —— 已完成/已送达的单货已出去，凭据无意义）：
   ```sql
   INSERT INTO inventory_reservation(order_id, order_item_id, product_id, station_id,
                                     reserved_qty, shipped_qty, released_qty, status, create_time, update_time)
   SELECT oi.order_id, oi.id, oi.product_id, o.station_id, oi.deducted_qty, 0, 0, 1, NOW(), NOW()
     FROM order_item oi JOIN orders o ON o.id = oi.order_id
    WHERE o.status IN (1,2) AND oi.deducted_qty > 0
      AND NOT EXISTS (SELECT 1 FROM inventory_reservation r WHERE r.order_item_id = oi.id);
   ```
   ★ **站别取 `o.station_id`（归属站）**：老实现在**下单那一刻**扣的就是归属站，换站不会搬库存 ——
   所以这正是"当初扣在哪一站"的真实答案，回填后这些在途单的取消/换站立刻走上正确路径。
3. **不动的**：`inventory.quantity` 一个数都不改（老实现已经在**下单时**减过了，凭据只是把这件事记下来）。
   ⚠️ 这条是回填能否安全的关键：如果实现时改成"下单不减、只在出库减"，那**存量在途单**必须
   先把它们的 `deducted_qty` **加回** `inventory.quantity`（否则那些单的出库会二次扣减）。
   ⇒ **实现顺序必须是**：先代码（新模型）→ 再把存量在途单的扣减**加回**（一次性脚本，带备份）→ 再建凭据。
   本设计稿推荐**先加回再建凭据**，两步都在同一个迁移里、且用 `information_schema` 预检防重复执行。
4. `schema.sql` 同步（新建库基线），`sql/README.md` 登记（v63）。

## 8. 验收算例（每条都要走 HTTP + 逐站核对数量与流水）

| # | 场景 | 期望 |
|---|---|---|
| E1 | 同站完整履约：A 有 10，客户下 2，接单→送达 | 下单后 `quantity` 仍 10、`reserved=2`；送达后 `quantity=8`、`reserved→shipped=2`；Σ流水 = −2 |
| E2 | 场景 ②（缺货补齐）：A 有 3，下单 10 并确认缺货，入库 10，完成配送 | 下单：`reserved=3`、缺 7；入库：`quantity=13`、**FIFO 补预留 7** ⇒ `reserved=10`；完成：`quantity=3` |
| E3 | 场景 ①（A→B 外派后取消）：A、B 各 10，A 下单 2 → 外派 B → 取消 | 外派：A 的凭据释放、B 重建 `reserved=2`（A、B 的 `quantity` 都没动）；取消：B 释放 ⇒ **A=10、B=10** |
| E4 | A→B→A 召回 | 凭据搬回 A；最终 A 持有预留 |
| E5 | 取消 / 拒单 / 超时扫单 | 三种入口都只释放预留，`quantity` 不变；重复取消不产生第二次释放 |
| E6 | 并发抢单（两站同时抢） | 订单 CAS 只允许一个成功；凭据只在一个站存在（另一个站无残留释放记录） |
| E7 | 重复提交（同幂等键） | 只建一次预留（`uk_reservation_order_item` 兜底） |
| E8 | 完成配送时预留不足 | 拒绝并给出"缺 N 桶"的可读文案；订单状态**不动**、不出库、不产生工钱 |
| E9 | 对账 | V1-4 仍平；E11（预留 > 实物）无差异 |

## 9. 风险与回滚

| 风险 | 说明 | 对策 |
|---|---|---|
| 取消路径改错 | 新模型下取消**不能**再 `increaseStock`，改错会凭空造库存 | E5 用例 + 在 `refundOrder` 原处留护栏注释（"这里曾经 increaseStock，含义已变，不要加回来"） |
| 存量在途单二次扣减 | 见 §7.3 | 迁移里"加回 → 建凭据"两步一次性完成，带备份与预检 |
| 可用量口径扩散 | 商城/低库存/站长盘点三处语义不同 | §5 逐条钉死；实现时在 `inventory` 列注释里写明"quantity=在库实物，不等于可用量" |

⚠️ 回滚前必须先把在途单的预留**落回 `quantity`**（等价于反向执行 §7.3），否则库存会凭空少。

## 11. 返工修订（2026-09-25 第二轮；依据《架构评审交付验收意见》R1–R7）

> **本节的效力高于 §1–§10**：前文是首版设计（已实施但被验收退回），本节给出**修正后的协议**。
> 标注约定：**【计划】** = 本轮要做的、**【已实现】** = 本轮已落地并有测试、**【未验证】** = 明确没验的。
> 验收矩阵 V01–V13 与回传包要求见 `docs/audit/history/handoff/2026-09-25-下一轮任务契约-库存与并发返工.md`。

### 11.1 事实来源、派生量与 `deducted_qty` 的唯一语义

| 量 | 事实来源（唯一） | 怎么得到 | 谁能写 |
|---|---|---|---|
| **在库实物** | `inventory.quantity` | 直接读 | `InventoryServiceImpl`（入库/盘点）、`InventoryReservationServiceImpl.shipForOrder`（出库） |
| **活跃预留** | `inventory_reservation`（`status=1`）的 `reserved_qty` | 直接读 | **只有** `InventoryReservationServiceImpl`（预留 / 补位 / 换站 / 出库 / 释放） |
| **等待需求（缺货待补）** | 派生 | `order_item.quantity − 该明细活跃凭据的 reserved_qty` | 不落库 |
| **可用量** | 派生 | `quantity − Σ(活跃 reserved_qty)` | 不落库（**展示与判断都读它**，见 §5.2 的边界说明） |
| **已出库** | `inventory_record`（`CONSUME`）+ 凭据 `shipped_qty/status=2` | 直接读 | 出库时同事务成对写 |
| **已释放** | 凭据 `released_qty/status=3` | 直接读 | 释放/换站时写 |

**`deducted_qty` 的唯一语义（本轮统一）**：**该明细"当前活跃凭据"的 `reserved_qty` 镜像；没有活跃凭据时为 0。**
⇒ 全仓只有 `InventoryReservationServiceImpl.syncDeductedQty(orderItemId, qty)` 会写它，调用点是**五处**（可对着代码数）：
`reserveForItem`（建凭据，写预留量）、`backfillReservations`（补位增加，写新预留量）、`transferForOrder`（换站重建，写新站预留量）、
`shipForOrder`（出库，归 0）、`releaseForOrder`（释放，归 0）。
首版只在"下单/换站"两处维护它（**补位没同步**）——那个不一致就是 R5 的第二条。
（列注释与实体注释同步改成这一句，别再出现"下单实际扣减量"的旧说法。）

### 11.2 全部预留写入口 → 收敛成一个分配入口

**只有 `InventoryReservationServiceImpl` 能改 `reserved_qty`**，它对外只暴露这几个命令：

| 命令 | 何时调 | 语义 |
|---|---|---|
| `reserveForItem(orderId, itemId, stationId, productId, requested)` | 下单 | 预留 `min(可用量, 需求)`；不足部分即"等待需求" |
| `backfillReservations(stationId, productId)` | 入库/盘点增加之后、**以及每一次释放之后** | 把该站该商品的可用量按 **§11.3 的顺序**补给等待需求 |
| `releaseForOrder(orderId)` | 取消 / 拒单 / 超时扫单 | 释放该单活跃凭据 ⇒ **并触发受影响 (站,商品) 的补位**（R4：首版漏了这半句） |
| `transferForOrder(orderId, toStationId)` | 放池/定向外派/抢单/召回/指定退回同意 | 旧站释放 + 新站重建 ⇒ **并触发旧站补位**（释放出来的货要能给别人） |
| `shipForOrder(orderId, expectedStationId)` | 完成配送 | 出库；**先做出库完整性检查**（§11.4） |

⚠️ 首版把"补位"放在 `InventoryServiceImpl.backfillReservations`（为了避免两个服务互相依赖）——
**那会让"释放"这条路径天然漏掉补位**。本轮改为：新增 `InventoryLedgerService`（只依赖 `InventoryRecordMapper`，
专门写 `inventory_record`），预留服务依赖它而不是依赖 `InventoryService`，
于是**补位回归分配入口**、依赖方向变成 `InventoryServiceImpl → InventoryReservationService → InventoryLedgerService`（无环）。

### 11.3 补位顺序（FIFO 判据）与"不插队"

- **排序依据 = 业务需求时间**：`orders.create_time ASC, order_item.id ASC`。
  ⚠️ **不能用凭据 id**：换站会新建凭据、带上新 id，而它的业务需求时间其实是**原下单时间**（该单被接受得更早），
  按 id 排会把老单排到新单后面（GPT R4 的第二半）。
- **统一入口**：补位只有 `backfillReservations` 一处实现；下单/换站/释放/入库都调它，**任何调用点都不许自己写一份分配算法**。
- **不插队**：补位在**同一次事务里、同一把库存行锁下**完成 —— 新请求要排队等这把锁，
  所以"刚释放的货"不会先被新单抢走（V03/V04 的断言点）。
- **不新增实物流水**：补位只改 `reserved_qty`（不动 `quantity`、不写 `inventory_record`），否则 V1-4 等式会不平。

### 11.4 锁序与当前读（**真实顺序**，修正首版注释的错误）

| 命令 | 真实锁获取顺序（**二次收口 B1 后：全部先库存、后凭据**） |
|---|---|
| 下单预留 | `orders`（INSERT 自身）→ **`inventory` 行（按 `(station_id, product_id)` 升序，多商品按稳定键序）** → `inventory_reservation` 行（插入）→ `order_item` 行（镜像 `deducted_qty`） |
| 入库补位 / 盘点增加 | 调用方先 `UPDATE inventory`（= 已持有该行 X 锁）→ `inventory_reservation` 行（当前读全部活跃凭据）→ `order_item` 行（镜像） |
| 完成配送出库 | `orders` 行（状态 CAS 前先读）→ **①发现**（普通读本单活跃凭据，只为决定锁谁）→ **②`inventory` 行（升序）** → **③当前读凭据 + 重新验证资源集合** → 扣实物 → 凭据置已出库 → `order_item` 行（镜像归 0） |
| 换站 | `orders` 行（订单 CAS）→ ①发现（旧站在哪）→ ②`inventory` 行（旧站 + 目标站，**一次升序锁全**）→ ③当前读凭据 + 重新验证 → 旧站释放 + 新站插入 → 镜像 → 旧站补位（已持锁） |
| 取消 / 拒单 / 超时释放 | `orders` 行（取消链）→ ①发现 → ②`inventory` 行（升序）→ ③当前读凭据 + 重新验证 → 释放 → 镜像归 0 → 补位（已持锁） |

⚠️ **`order_item` 也在锁序里**（它是镜像 `deducted_qty` 的写入目标）：每个分配命令最后都会 `UPDATE order_item`，
所以"改某条明细的预留"必然要拿它那一行的 X 锁。它**只按明细 id 单独更新**（`syncDeductedQty`），
不参与跨行批量更新，因此不会与其它表构成环；`UPDATE` 本身是当前读，不需要额外 `FOR UPDATE`。

⚠️ **没有会话级缓存**（契约 §3 第 3 条的"会话缓存策略"）：这些 mapper 方法**不开 MyBatis 二级缓存**，
一级缓存只活在单个 `SqlSession` 内、且任何 `UPDATE` 都会清空它；更重要的是**分配决策不读缓存**——
可用量/预留量每次都从库里**重新取当前读**（`OrderServiceImpl` 里那个 `invCache` 只用于算价与显示，
它算出的 `availableQty` 只喂给"缺货提示"，**不参与预留量的决定**）。
判据：把 `reserveForItem` 里任何一次 `...ForUpdate` 换成普通读或缓存，屏障用例 V01 立刻变红。

⚠️ **首版的错**（二次验收 B1）：上一版把"补位/预留先锁 inventory、出库/换站/释放先锁凭据"写进了实现，
注释却说"只有出库例外" —— 于是「完成配送」与「同站同商品入库」能构成固定锁环
（T1 持凭据等库存、T2 持库存补位时等凭据）。**现在没有例外**：见 §11.9 的"发现 → 加锁 → 重新验证"协议。

⚠️ 首版注释写的是"订单 → 凭据 → 库存"，但**入库补位实际是先持库存锁再锁凭据** —— 首版注释与实现不符（GPT §4 第一条）。
本轮统一为：**凡是"改动某 (站,商品) 的分配"的动作，一律先拿 `inventory` 行 X 锁，再动该 (站,商品) 的凭据行**；
`shipForOrder` 是唯一例外（它按凭据决定扣哪个站，所以先锁凭据、再锁各自的库存行），
因此它**不与其他分配动作交叉**：分配动作只锁一个 (站,商品)，出库按明细逐条锁、顺序按 `product_id` 升序。

**当前读（R1 的核心）**：任何**分配决策**（预留量、补位量、重建量）读活跃预留时，必须是
`SELECT ... FOR UPDATE` 的**当前读**，不能是普通 `SELECT`（REPEATABLE READ 下普通读是事务开始时的快照）。
本仓对这条早有判据（`AGENTS.md` §8.2「只加行锁不够，必须加锁 + 当前读两件套」）——
首版只给 `inventory` 加了锁、`sumReserved` 却是普通读，于是并发下 `Σ预留` 可以超过实物（R1 的反例：两单各预留 8、实物 10 ⇒ 16）。
**协议（两件套）**：① `SELECT ... FROM inventory WHERE station_id=? AND product_id=? FOR UPDATE`；
② `SELECT ... FROM inventory_reservation WHERE station_id=? AND product_id=? AND status=1 ... FOR UPDATE`（当前读 + 行锁）。
由①串行化同一 (站,商品) 的并发分配，由②保证读到的是**最新已提交**的预留事实。

### 11.5 出库完整性检查（缺凭据 / 错站 = **明确失败**，不是放行）

`shipForOrder(orderId, expectedStationId)` 在扣实物之前必须逐项通过：

1. **覆盖**：该单每个"需要管库存"的明细（所有 `order_item`）都有**活跃凭据**；缺任何一条 ⇒ 抛 `BusinessException`
   （文案说明缺哪一行），**不许**"整单没凭据就 return"（首版那条兼容分支会把漏建凭据的单放过去 —— GPT R2 第二半）。
2. **站别**：凭据的 `station_id` 必须等于该单**当前履约站**（`coalesce(delivery_station_id, station_id)`）；
   不等 ⇒ 抛错，文案是「本单的库存凭据挂在 X 站，而当前履约站是 Y；请让配送员在本站提交「指定退回」把单退回归属站后重新派单，
   或联系运维按 v64 修复脚本核对凭据，再完成配送」。
   ⚠️ **文案里给的处置动作必须是当时真能执行的**（2026-09-25 界面走查发现）：本检查在"配送中(2)"触发，
   而归属站的「召回」只放行 `待配送(1)`（`cancelDispatch`）—— 初版文案让站长"去召回"等于给了一个点了没用的按钮；
   真能走的是配送端的「指定退回」。
3. **数量**：`reserved_qty == order_item.quantity`（即缺货待补为 0），且 `0 ≤ reserved_qty ≤ quantity`；
   不满足 ⇒ 抛错并给出缺几桶。
4. **实物**：`quantity ≥ Σ 本次出库量`，否则抛错（先入库）。

> "历史单没有凭据"这个兼容分支**只在"该单在当前库里根本没有凭据表记录、且它是在 v63 之前就已出库完成"**时才允许 ——
> 实际做法是：**v63/v64 迁移保证所有在途单都有凭据**，所以运行时遇到"在途单缺凭据"一律视为数据缺陷并报错（进 §11.7 的对账）。

### 11.6 升级路径（停机窗口；R3）

```
① 停止业务写入（停后端实例 / 摘流量）——新代码依赖新表新列，不能带着旧结构收业务请求
② 备份：mysqldump 业务库到 backup/
③ 预检：**先跑只读探针 `sql/probe_inventory_reservation_state.sql`**，按它输出的 `state` + `ROUTE`
   决定跑 v63 还是 v64（判据是**数据转换状态与转换证据**，不是"表在不在、有没有两列"；
   "跑没跑过首版 v63"是历史问题、不能替代数据状态判据）；通用路径 v65 → v63 → v64 **已作废**
③b **坏需求快照先修**（探针 `state = 状态6`，即 `need_mismatch > 0`）：它是**阻断项**，不是"存量差异" ——
   v63/v64 都会在 **DML 之前**拒绝（marker `__ABORT_V63_DIRTY_NEED_SNAPSHOT__` /
   `__ABORT_V64_DIRTY_NEED_SNAPSHOT__`）。探针末尾会打印一份**带现成 UPDATE 语句**的清单：
   把 `need_qty` 改回真相源（= 对应 `order_item.quantity`；`need_time` = `orders.create_time`），
   改完**重跑探针确认 `need_mismatch = 0`**，再谈跑哪个脚本
④ 结构准备：缺 `need_qty`/`need_time` 两列则先跑 v65；表不存在则由 v63 建表（自带这两列）
⑤ 数据搬迁：**一个显式事务**内完成（见下；v63/v64 的路由预检会在 DML 之前中止不该跑的库，
   marker 见 `__ABORT_V63_USE_V64_FOR_WRONG_STATION_CREDENTIALS__` /
   `__ABORT_V63_USE_V64_FOR_ACTIVE_ON_FINISHED_ORDER__` /
   `__ABORT_V64_DELIVERED_ACTIVE_WITHOUT_SHIP_EVIDENCE__`）
⑤b **已送达(3) 不得补建活跃预留**（R1）：状态 3 = `completeDelivery` 里 `shipForOrder` 已出库、
   凭据已置为"已出库"，订单只是**现金还没收**才停在 3 —— 它**不属于"等待备货"**。
   任何脚本都不许为它重建活跃预留，收款流程（只做 3→4）也不补库存动作。
   3/4/5 单上已经存在的活跃凭据由 v64 的 ⓪ 步释放（终态 4/5 无条件；状态 3 要先拿出库证据）
⑥ 校验：**判据是提交前门禁**（`precommit_violations_must_be_zero` = **新出现的差异键**
   `newly_created_violations` + **原有键数值变大** `worsened_preexisting_diffs`）；
   末尾那几条回读自查是人工核对用，`quantity <> Σ inventory_record.delta` 这类**存量**漂移
   只比"差额有没有变大"，不要求 0 行
⑦ 部署新版本、恢复服务
```

**数据搬迁的三步必须原子**（这是 R3 的修法）：先把**凭据**写进去（它同时充当"这条明细处理过了"的去重标记），
再按刚建的凭据**加回实物**、**补 INBOUND 流水**；三步同处 `START TRANSACTION ... COMMIT`
（现行脚本在这三步之外还有"全局 FIFO 补位 / 镜像同步 / 提交前门禁"，**全在同一个事务里**，
步骤编号见脚本内的 3-1 … 3-6）。
中断/报错时 mysql CLI 退出会让事务回滚，重跑看到凭据已存在（或不存在）→ **结果与成功执行一次完全相同**。
首版把去重标记放在最后写、且三步各自 autocommit ⇒ 中断重跑会**多加一次库存**。

> 顺序上的一个细节：凭据先写，但它的 `reserved_qty` 要**按"当前实物 + 本轮加回量"**算
> （`migration_v63` 里用 `tmp_v63_restore` 把加回量 join 进来）。不这么做就得"先加回再算"，
> 与"凭据先写"的去重语义冲突；两种写法结果相同，但前者顺序上先落标记。
> 分配本身按 `orders.create_time` FIFO：`reserved_qty = min(需求量, 剩余可用量)`（与运行时补位同一算法）。

**旧账归位 vs 新承诺（R2 的修法）**：这两件事的站别**不同**，必须分开算：
- **旧扣减恢复到"当初扣货的站"** = `orders.station_id`（老实现下单那一刻从归属站扣的，换站不搬库存）；
- **新凭据建在"当前履约站"** = `coalesce(delivery_station_id, station_id)`（凭据要跟着履约站走，否则 B 完成配送会去扣 A 的库）。
- **0 预留明细也要建凭据**：`deducted_qty = 0` 的明细（下单时库存为 0、纯缺货）**必须有凭据**（`reserved_qty=0`），
  否则补位找不到这条需求、`shipForOrder` 的覆盖检查也会漏（首版 WHERE `deducted_qty > 0` 把它们排除了）。

**已执行过旧版 v63 的库**：用 `v64_v63_repair_for_already_migrated.sql`。它在一个事务里做这些事（可重复执行，
按脚本内的步骤编号 0–6）：**⓪ 释放不该有活跃预留的单上的凭据**（两类：**已完成 4 / 已取消 5 无条件**释放 ——

### 11.9 二次收口修订（2026-09-25 第三轮；依据《库存返工二次验收意见》B1–B3）

> 效力同 §11：与 §1–§10 冲突时以本节为准。本节只写"改了什么、为什么、怎么验"。

#### B1 · 锁协议统一（**取消"出库例外"**）

**协议（全仓唯一，没有例外）**：
```
① 发现：普通读（不加锁）查出这次可能要动的 (站,商品) / 凭据 —— 只用来决定"锁谁"，不能当决策依据
② 锁库存：把涉及的 (站,商品) 按 (station_id, product_id) 升序逐个 SELECT ... FOR UPDATE
③ 当前读 + 重新验证：凭据行 FOR UPDATE，并与①发现到的资源集合（明细 → 所在站）比对
        不一致 ⇒ 抛可读冲突，由调用方**从事务外重试**（不许在事务里 catch 后继续）
④ 写：凭据 CAS + order_item 镜像
⑤ 补位：需要补位的 (站,商品) 的 inventory 行已在②持锁，此时当前读凭据并分配
```
**为什么"发现"必须是普通读**：换站的资源集合是"由凭据内容决定的"（旧站在哪、目标站在哪），
如果先加锁再发现，就会出现"锁了 A 又要锁 B"的乱序；先无锁发现、再按全序加锁、再加锁后复核，
是唯一能做到"锁序稳定 + 资源变化可检测"的组合。
**复核失败必须失败**（不许猜着继续）：`assertResourceSetUnchanged` 比对 `orderItemId → stationId`，
不一致就报"该订单的库存凭据刚刚被其他操作变更（并发换站/取消），本次…未执行，请刷新后重试"。

**验证**：`InventoryLockProtocolIntegrationTest` 五条反例 ——
① 入库与完成配送**停在同一把第一锁**（`inventory` 行，且锁证据绑定到阻塞方 trx_id）；
② 新预留与取消释放同样停在同一把第一锁；③ 加锁窗口里凭据被换站 ⇒ 可读拒绝且零改动；
④ A→B 与 B→A 相向换站 + 商品反序 ⇒ 都成功、凭据与各自履约站一致；
⑤ B2 的新等待单场景（见下）。

#### B2 · 补位的数据视图（凭据自带需求量快照）

`inventory_reservation` 新增 **`need_qty`**（下单那一刻 `order_item.quantity`）与
**`need_time`**（下单那一刻 `orders.create_time`），补位**只读这两列**（当前读凭据行），
**不再 join** `orders`/`order_item`。真相源仍是那两张表，本列是只读副本：
- 写入点：建凭据（下单）、换站重建（从旧凭据复制）；
- 回填：v63 建表时即写入 / v64 补齐 / v65 给老表加列并回填；
- 一致性校验：对账 **E15**（`need_qty ≠ order_item.quantity` 或 `reserved_qty > order_item.quantity`）；
- **缺 meta 不许当 0**：`requireNeed` 遇到空/非正快照直接抛业务错（列是 NOT NULL，走到那里说明有人绕过本服务写库）。

#### B3 · v63 的支持范围与分配公式

- **支持混合状态**（代码先上、新订单已建凭据、老单还没迁移 —— 这是文档要求的部署顺序下的**常态**）：
  分配公式改为 `可用量 = 实物 − **Σ该对全部活跃预留**`，再按 `need_time` FIFO 分给所有有缺口的活跃凭据
  （既有的 + 本次新建的），不再只减"本批前缀和"。
- **凭据一律先以 `reserved_qty = 0` 插入**，分配统一交给"全局补位"那一步（与 v64 同一算法）。
- **原扣减站没有库存行 ⇒ 预检中止**（DML 之前），不生成依赖不存在实物的承诺。
- **提交前不变量门禁**：六条不变量（Σ预留 > 实物 / 凭据无库存行 / 在途缺凭据 / 凭据错站 /
  预留越界或快照不一致 / 镜像不一致）在**同一个事务里**校验，不满足就**不 COMMIT**。
  实现方式：把 `COMMIT` 本身做成条件语句（不满足时执行的是必然失败的 marker 语句）——
  这样即使有人加了 `--force`，不合规的数据也不会被提交。
- **防二次加回的持久证据**：加回流水按**订单逐条**写（`ref_id = order_id`、note 以 `v63 库存预留模型迁移` 开头），
  它是"这单已经加回过"的第二判据 —— 手工 `DELETE` 凭据行后重跑不会再凭空加一次实物（演练实测过 10 → 14 的后果）。

| `E15_needSnapshotMismatch` | `SE11_needSnapshotMismatch` | 活跃凭据 `need_qty ≠ order_item.quantity`，或 `reserved_qty > order_item.quantity` |
| `E16_credentialWithoutInventoryRow` | `SE12_credentialWithoutInventoryRow` | 活跃凭据所在的 (站,商品) **没有 inventory 行**（E11 是内连接，看不见这类）**且 `reserved_qty > 0`** |

**R1 · 状态 3（已送达）的语义 —— 不许给它补建活跃预留**

- **状态 3 = 货已出库**：`completeDelivery` 先调 `shipForOrder`（实物已减、凭据置为"已出库"），
  现金还没收时订单才停在 3；之后收款只做 3→4，**不会再出库**。它**不属于"等待备货"**。
- 所以**"已送达单没有活跃凭据"是正确状态**：任何脚本都不许为它重建活跃预留，也不许让收款流程去补库存动作
  —— 补一条活跃凭据 = 把已经送出门的货**又占住一次**。
- 修法：`migration_v64` 的**补建凭据**与**搬迁（`tmp_v64_move`）**范围**都收回 `(1,2)`**（原来错误地含 3）；
  v63 本来也只处理在途 1/2。
- 已经存在的 3/4/5 活跃凭据由 v64 第 ⓪ 步**释放**（`status=3` + `released_qty` 留痕，不动实物、不造库存）：
  终态 4/5 **无条件**；**已送达 3 必须先拿出库证据**（该单有 `inventory_record` 的 `CONSUME` 流水且
  `ref_id = order_id`，**或**该明细有一条**已出库(2)** 的凭据），拿不到证据的**在 DML 之前中止**
  （marker `__ABORT_V64_DELIVERED_ACTIVE_WITHOUT_SHIP_EVIDENCE__`）—— 不凭订单状态伪造出库、也不恢复实物。
- 演练实测：实物 8、已送达单 2 桶 ⇒ 上一版 v64 补出 ACTIVE(reserved=2)，**可用量 8 → 6**，
  且后续 3→4 收款不会清掉它；修复后同场景 v64 是空操作（可用量仍 8）。
- 镜像跟着对齐：v63 重写 `order_item.deducted_qty` 的范围 **(1,2,3)**、v64 是 **(1,2,3)** + 第 ⓪ 步释放过的终态单
  —— **已送达 3 的镜像必须是 0**（货已出库、没有活跃凭据）。
- 判据落点：v63 新增 **DML 之前**的 `__ABORT_V63_USE_V64_FOR_ACTIVE_ON_FINISHED_ORDER__`
  （有活跃凭据挂在 3/4/5 上就中止、把路由指向 v64）；`routing_hint` 同时报 `wrong_station_active`
  与 `active_on_finished_order` 两个数；v64 的自查新增 `still_active_on_finished_orders`。

**R2 · 坏需求快照 = 阻断项（不再是"存量差异、迁移不修"）**

- 需求快照决定**补位分多少货**：坏快照会把错误**放大**，而且在"只比差异键"的旧门禁下**看不出来**
  （差异键还是原来那一个 ⇒ `newly_created_violations = 0` ⇒ 照样提交）。演练实测：实物 10、真实需求 2、
  快照 `need_qty = 10` ⇒ 预留被补到 10、**可用量归 0** —— 一个只要 2 桶的订单占满整站可用量。
- 判据：`reserved_qty < 0` 或 `reserved_qty > need_qty` 或 `need_qty <> order_item.quantity`

## 2026-10-01 v71 业务调整

本节落实 design/16 §11.3 的已采用口径。以下 v71 规则适用于有新分配/申请凭据的流程；未注明替代的历史流程保留原来源，不凭数量重建资产。

仍采用在库实物 quantity 与可用 quantity−活跃预留的既有模型；独立买桶权益不预留水。新水单预留、不减实物，完成配送校验当前履约站凭据与实物后出库；定向外派与抢单一样迁移预留，取消只释放并 FIFO 补配。

新增真实损失入口接受 expectedQuantity 与 targetQuantity，拒绝过期盘点请求；只允许下调实物，不能用它伪装入库。保留较早 FIFO 预留，较晚被影响预留缩减、明细镜像同步，缺口进入站长待补；不自动取消已付款承诺。普通盘点仍有预留护栏，需亏损时显式选择“真实损失”。
