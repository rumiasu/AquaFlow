# 25 · 站长信息完善引导（规则目录 + 已落地部分）

> 2026-09-19 立。产品要求：「所有需要/建议填写的字段，都加一层引导」「商品第一时间引导」
> 「最好都给一些默认字段，降低填写门槛，可以从官网调取」，并追加三条硬要求：
> **电话加进建站必填**、**有员工则工资结构必填（选固定工资则不填）**、**配送费相关必填**。
>
> 本文档只解决一件事：**把"站长该填什么、为什么必须填、不填会怎样、建议值是多少"从口头经验变成系统行为。**
> 判据一律以代码为准（每条都带 `文件:行号`）。

## 25.0 已实现的规则目录（单一数据源）

`service/impl/StationSetupGuideService` + `GET /api/manager/setup-guide`（`@RequireRole("STATION_MANAGER")`，
站点取自登录态）。**每加一条规则只改这一个类**，页面只渲染后端下发的中文
（`label` / `why` / `where` / `level` / `done` / `suggestion` / `action`），前端不自建 key→文案映射。

| key | 级别 | 判据（现在完善了没有） | why（不填的真实后果） | 去哪填 | 建议值 |
|---|---|---|---|---|---|
| `stationPhone` | P0 | `station.phone` 非空 | 客户下单页/退桶靠它联系你，缺了显示「请咨询客服」 | 水站资料 | — （**建站已改为必填**，老站补一下） |
| `stationLocation` | P0 | `station.lat` 与 `lng` 都非空 | 没坐标算不出配送距离 → 你设的**配送范围整段失效**（超范围单照接） | 水站资料 | — （点地图选点） |
| `stationAddress` | P1 | `station.address` 非空 | 客户选站与找路靠它 | 水站资料 | — |
| `catalogOnShelf` | P0 | 至少 1 个 `inventory.enabled=1` 的商品 | 客户看不到商品就没法下单；**「选品」不等于「上架」** | 商品与库存 | 「先选 1~2 款常卖的水」 |
| `deliveryFee` | P0 | `station_delivery_config` **有行**（哪怕全 0） | 没保存过 = 起送量/范围/运费/楼层费一条都没生效 | 配送计费 | 金额门槛：最低水价 ×2 / ×3（一键填入） |
| `staffPayroll` | P1 | 无配送员 **或** 站级默认计件单价已配 | 有配送员却没单价 → 他送的水**按 0 元记工钱**（结算单也是 0） | 工资设置 | — （需站长定；固定工资模式见 §25.7 待拍板） |
| `ticketPackage` | P1 | 开了水票的商品都有上架档位 | 客户想买票却看不到价目表（点名是哪个商品） | 商品与库存 | 预设档位（10/20/100 张） |
| `stationNotice` | P2 | 恒 true（软状态） | 歇业/放假时客户能提前知道（不阻断下单） | 营业状态与公告 | — |

**「配送计费」为什么用"有没有保存过"当判据**：这样"没配"与"配成全 0（= 明确表示不收）"就区分得开 ——
不必强迫站长填一个假数字，也不会把"我本来就不收"误判成"没配"。这就是「配送费相关必填」的可操作定义。

## 25.1 为什么需要：缺字段的真实后果（不是"不完整"，是"功能静默失效"）

| # | 字段 | 缺了会怎样（真实后果） | 证据 | 优先级 |
|---|---|---|---|---|
| 1 | **水站坐标**（lat/lng） | **配送范围校验整段失效**：算不出距离 → 不判范围、只提示"本次不做范围校验"。站长以为自己设了 3 公里范围，实际上超范围单照接 | `DeliveryFeeServiceImpl` 取站/址坐标 → `GeoUtil.distanceMeters` 可为 null；`DeliveryFeeUtil` 的"拿不准就不判"分支。⚠️ **真实库两台水站的坐标都是 NULL**（建站页把定位标了 `*` 却不校验） | **P0** |
| 2 | **水站电话** | 客户找不到人：下单页资产说明里写的是"水站电话：请咨询客服"（占位文案），退桶/催单都只能干等 | `miniapp-user/pages/order/create.wxml` 的 `{{stationPhone \|\| '请咨询客服'}}`；端点 `GET /api/stations/{id}/public-phone`。⚠️ **真实库济阳水站电话是空串** | **P0**（**已改为建站必填**） |
| 3 | **金额类门槛**（起送量金额 / 免运费金额） | 上架瓶装水/一次性桶/饮水机后，那条规则**对这类订单不生效**（非桶装不占桶，桶数条件不适用） | `DeliveryFeeUtil.belowMinOrder` / `isFreeDelivery` 的 `buckets <= 0` 分支；已加"上架前强制补金额门槛"（`DeliveryConfigGuideService`） | **P0**（已落地） |
| 4 | **商品上架**（`enabled` + 售价 + 库存） | 客户在目录里看不到（选品 ≠ 上架；`enabled=0` 就是没卖），站长以为"我选了品就能卖" | `inventory.enabled`；`saveStationSetting` 注释"选用≠自动开卖" | **P0** |
| 5 | **桶装水押金** | 桶白送（退桶退 0），与桶账模型冲突 —— 已有**硬校验**拦住建自定义商品 | `CatalogServiceImpl`「桶装水必须设置大于 0 的押金」 | P0（已有护栏） |
| 6 | **水票档位** | 开了「推出水票」却没配档位 → 客户想买票但**没有价目表**。真实库现状正好是这个组合：站 1 的农夫山泉 `ticket_enabled=1`，而 `ticket_package` **0 行** | `inventory.ticket_enabled` vs `ticket_package`（唯一键 `station_id,product_id,qty`）；真实库实测 | **P1** |
| 7 | **员工工资结构** | 有配送员却没配计件单价 → 送的水按 **0 元**记工钱，结算单是 0（**真实库正是这个状态**：1 名在职配送员 + `staff_piece_rate` 0 行） | `StaffEarningServiceImpl.rateOf` 在没配时回落到 `StaffPieceRate.defaults`（零价），**不报错** | **P1** |
| 8 | **营业状态 / 公告** | 软状态（不阻断下单、只提示），缺了客户不知道你歇业 | `docs/design/13`；`station.operating_status` | P1 |
| 9 | **楼层费与免费楼层** | 没配就不收楼层费（保守，不会乱收钱），但站长可能以为在收 | `DeliveryFeeUtil` 楼层费分支"拿不准就不收" | P2 |
| 10 | **配送员计件单价**（同 7） | 同上 | `staff_piece_rate`（`product_id=0` 为站级默认价） | P2 |

**共同点**：这些字段缺失时系统**不会报错**，只会"少做一件事"——正是本仓最忌讳的**静默失效**（AGENTS §8.22 同形）。
所以引导的目标不是"让资料看起来完整"，而是**让站长知道他现在哪条规则是空转的**。

## 25.2 引导机制（三层，从"提醒"到"一键完成"）

1. **待办层（入口级）**：把"资料/配置缺口"做成待办条目，站长一进「水站管理」就能看到。
   并行工作流已经建好了机制：`constant/PendingItem`（key/中文标签/默认级别，P0 不处理卡住配送、P1 影响钱或他人、P2 不处理也不出事）
   + `ManagerPendingSummaryController`（按目录逐条算数、级别可被配置覆盖）。
   → **建议新增 `STATION_PROFILE_INCOMPLETE`（P1）**：缺坐标/电话/金额门槛时亮一条，点进去直达对应页面。
   ⚠️ 该目录是并行工作流的文件，本批**没有去改**（避免同文件冲突），登记为对接项。
2. **页面层（就地引导）**：字段所在页面自己说清"为什么必须填"。已落地：配送计费页的「还差金额门槛」引导卡
   （`miniapp-delivery/pages/station-mgmt/delivery-config`，文案与建议值由后端 `guidance` 下发）。
3. **一键层（降低门槛）**：能算的默认值绝不让站长手填。已落地：金额门槛的**建议值**
   = 本站最便宜的一桶水 × 2（起送）/ × 3（免运费），取整到元，点「一键填入建议值」即完成；
   没有已上架商品时**不给建议值**（不凭空捏造一个数）。

## 25.3 默认值从哪来（给谁默认、不给谁默认）

| 字段 | 能否给默认值 | 来源 | 为什么 |
|---|---|---|---|
| 起送量金额 / 免运费金额 | ✅ 建议值 | 本站已上架**桶装水最低价** × 2 / × 3 | 站长的心理单位就是"几桶水的钱"，可解释、可改 |
| 起送桶数 / 免运费桶数 | ⚠️ 不给默认 | —— | 给了默认等于**替站长决定接不接单**，属于经营决策 |
| 水站坐标 | ✅ 可预填 | 地图选点（前端已有） | 不能凭空给；引导"点一下地图" |
| 水票档位 | ✅ 可预置 | 平台预设档位（10/20/100 张，价格按当前水票价 × 折扣） | `ticket_package` 有 `title`/`sort`，天然支持"预设" |
| 商品规格 / 品牌 / 图片 | ✅ 平台预设库 | 见 25.4 | 这是"从官网调取"的合规落地 |
| 营业状态 | ✅ 默认"营业中" | `station.operating_status` 默认值 | 已经是默认值 |

**原则**：**只有"能算出来、且改错了不会改变接单行为"的才给默认值**；凡是会改变"接不接单、收不收钱"的，一律
给**建议值 + 一键填入**，让站长按一下确认 —— 这一按就是他的决定，而不是系统替他决定（同 AGENTS §0.3 的精神）。

## 25.4 「可以从官网调取」怎么落地（不做抓站）

现实约束：① 小程序端抓品牌官网在技术与合规上都不可行（跨域、反爬、图片版权）；
② 就算抓到，品牌官网的价格也不等于本站售价（本站价由站长定）。
**可行且已经有一半基础的方案 —— 平台预设库**：

- 已有：商品图片库（v38）、`docs/design/14-商品图片库与常见水种清单.md`（常见水种清单）、
  `ProductImageKeys` 常量、平台通用商品库（`product.owner_station_id IS NULL`，站长只读）。
- 建议扩展：把"常见品牌 + 官方规格（容量/箱规/单桶净重）+ 参考价 + 官方图"作为**平台维护的目录行**
  写进通用商品库（`sql/migration_v52/v53` 那条线正在做济南水种目录，方向一致）。
  站长建自定义商品时：**选品牌 → 自动带出规格与图片 → 只填售价与押金**。
- 好处：站长少填 3~4 个字段、"规格"这种最容易写错的字段不再手打；平台侧只维护一份数据。

## 25.8 我建议补充的引导项（你问"还有补充吗"）

| 建议 | 理由 | 级别 |
|---|---|---|
| **营业时间**（而非只有营业状态开关） | 客户最常问的是"你们几点送"；现在只有 `operating_status` 软状态与 `status_note` | P1 |
| **配送范围**（半径）未配但有坐标 | 有坐标却不设范围 = 白设；引导项可加"你把坐标选好了，要不要顺手设个范围" | P1 |
| **货到付款逐客户开通**的进度提示 | 货到付款**没有站点级总闸**（只能逐个客户开）；新站常见困惑是"客户选不了货到付款" | P1 |
| **员工入职引导**（绑定后提示站长配工资结构） | 把 §25.7 的第 1 条落在"新员工加入"这个时机，比让站长自己想起来更有效 | P1 |
| **水票档位预设**一键生成（10/20/100 张三档，按当前水票价 × 折扣） | 与统一水票（`docs/design/26`）一起做，避免两套档位口径 | P1 |
| **平台预设库**（品牌 + 官方规格 + 图片 + 参考价，选品牌自动带出） | 见 §25.4，"从官网调取"的合规落地 | P1 |
