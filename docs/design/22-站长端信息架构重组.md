## 1. 目的与范围

站长端「水站管理」原本是一张平铺的宫格：同类功能（桶 / 钱 / 客户）彼此不相邻，且同类功能还散落在另外两个入口。本文给出**按经营对象重新分组**的结构与判据。范围限于入口与页面盘点、问题清单、分组方案、明确不合并的三处；后端与数据库零改动，页面内部交互改版与订单列表分页、客户建档闭环等缺口另立项。

## 2. 设计口径

### 2.1 现状基线

站长能到达的页面来自**三个互不相链的入口**：**首页 tab**（`pages/coordination/index`，待分配 / 审批 / 抢单池 / 外派 / 他站外派 五页签 + 「待办」聚合卡）、**配送 tab**（`pages/home/index`，配送员视角）、**我的 tab**（`pages/mine/index`，「我的水站」卡 + 配送员管理与绑定申请页签 + 菜单：水站管理 / 我的工资 / 空桶记录 / 配送历史 / 转让记录）、以及**水站管理宫格**（`pages/station-mgmt/index`，**只能从「我的」进**、有两处重复入口，平铺功能卡）。

宫格卡覆盖：数据看板、订单管理、客户查询、商品与库存、营业状态与公告、代客下单、应收账款、计件工资、水票档位、毛利报表、配送计费、退桶审批、欠桶台账、桶异常、运营告警、客户反馈、待确认收款、员工管理。**宫格之外但从宫格某页可达**：客户画像、资产调整单、员工画像。**从宫格完全不可达、只在其他入口的**：建站与绑定申请（首次入驻流程）、桶记录、我的工资、配送历史、转让记录。

### 2.2 分组判据与归类结果

一条水站的经营主线只有四样东西 —— **订单、钱、桶、客户**；其余是「货（商品与定价）」与「人（员工与水站自身）」。逐张归类**不需要新造任何概念**，只是把已经成组的东西摆到一起；分组后**页面仍然各自独立**，变的是入口层级与归类。

| 目标分组 | 收进哪些（现状卡片 / 页） | 合并后形态 |
|---|---|---|
| A. 订单 | 首页 tab 的 5 个页签 + 订单管理 + 代客下单 | 1 个页 + 6 页签 |
| B. 资金 | 待确认收款 + 应收账款 + 计件工资 + 毛利报表 | 1 个页 + 4 页签 |
| C. 桶 | 退桶审批 + 欠桶台账 + 桶异常 + 资产调整单 | 1 个页 + 4 页签 |
| D. 客户 | 客户查询 + 客户画像 + 企业身份审核 + 客户反馈 | 1 个页 + 4 页签 |
| E. 商品与配置 | 商品与库存 + 水票档位 + 配送计费 + 营业状态与公告 | 1 个页 + 4 页签 |
| F. 员工与水站 | 员工管理 + 员工画像 + 绑定申请 + 水站资料 / 坐标 | 1 个页 + 3~4 页签 |
| G. 独立保留 | 数据看板 | 并列第 7 张卡（它是「看」，不是「办」） |

**A 组的页签顺序 = 一天里的时间顺序**：待处理（现「待分配」，含转单审批）/ 审批（客户与站内两个子页签保留）/ 抢单池 / 外派（现「外派」与「他站外派」合并为一组，它们是同一件事的两个方向）/ 订单台账 / 代客下单。

### 2.3 明确不合并的三处

⚠️ **待确认收款 ≠ 应收账款**：前者是 `payment_record` 待确认流水（钱已到、系统未确认），后者是 `payment_status=1 且未取消`（钱还没到、有账期）。一个写「确认到账」，一个写「核销 + 设账期」—— **合并会诱导站长点错按钮**，只同页页签相邻即可。

⚠️ **桶异常 ≠ 运营告警**：告警是投递流水（含补偿已执行等），异常单是业务单据；`alert_log` 还有 `SYSTEM` 类型**永远不给站长看**。同组但不同页签。

⚠️ **退桶审批 ≠ 欠桶台账**：前者是**待办**（有同意 / 驳回 / 退押金按钮），后者是**只读台账**。一个页面里「有的行能点、有的不能点」会让站长困惑；分页签，但同页可互相看到。

### 2.4 已查实的七个问题

| # | 问题 | 性质 |
|---|---|---|
| P1 | **员工管理有两个平行实现**：宫格「员工管理」（搜索 + 筛选 + 画像 + 解除 + 新增）与「我的」里的「配送员管理」（列表 + 解除）操作同一份数据，同调 `getStaffList` / `detachStaff` / `MANAGER_BIND_RELEASE` | 重复实现 |
| P2 | **绑定申请审批**只在「我的」里，宫格「员工管理」页没有它 | 拆分断裂 |
| P3 | **水票档位有两个写入口**：商品「本站设置」弹窗内可增删改档位，独立「水票档位」页也可改（同一份 `/api/ticket-packages` 数据） | 有意设计，需在 UI 上讲清 |
| P4 | **客户画像页是一张长滚动页**，塞了画像头 / 消费概览 / 本站资产 / 客户特权 / 消费特征 / 权限设置 / 最近订单 | 单页过载 |
| P5 | **企业身份审核挂在「客户查询」页顶**，一个搜索页兼任审批队列 | 门面不符 |
| P6 | **代客下单 = 订单 + 客户两个模块的交叉点**，第 1 步就是客户查询，且会引导「去客户管理建档」 | 跨类耦合 |
| P7 | **两个死接口**：`getDashboardToday` / `getDashboardOverview` 全端零调用，却仍在接受客户端传的 `stationId` | 死代码 |

⚠️ P7 的后端端点只看 `AuthContext.requireStationId()`，**传了也被忽略**（所以不是漏洞），但它是「让人以为能查别站」的错误示范，且使 `/api/dashboard/today` 与 `/overview` 成为零消费端点。删除属于删除类改动，**必须先证一遍零引用**，证据登记在 [`docs/audit/删除登记表.md`](../audit/删除登记表.md)。

## 3. 接口与权限

本方案**不改任何后端接口**：`controller/**` 与 `sql/**` 零改动，页面用既有端点，因此没有新增角色或站点归属校验。

## 4. 前端落点

⚠️ **`app.json` 的 tabBar 保持 3 项**：微信限制 2~5 项，且加 tab 会改变「首页」语义；分组卡在宫格内完成。**首页「待办」卡的 key → 页面映射要跟着改**，改成指到分组页 + 页签参数。分组容器页的页签切换用 `wx.redirectTo`（避免 `navigateTo` 堆历史栈）；容器页必须转传 `options`（客户画像与资产调整单靠 query 传 `id` / `customerId`）。⚠️ **不改口径**：金额、状态与全部展示文案仍由服务端下发，**不新增任何前端算术或 1/2/3 映射表**。

## 5. 验收判据

1. 同一功能不再出现两处平行实现（P1 的判据）。
2. 每张卡片都能被归入「订单 / 钱 / 桶 / 客户 / 货 / 人」之一，无「其他」兜底组。
3. 后端零改动（`controller/**` 与 `sql/**` 无 diff）；`app.json` 的 tabBar 项数为 3。
4. 合并后的页签数与分组方案一致，且「不合并的三处」保持独立页签。

## 6. 待确认事项

| 待确认内容 | 需要的验证手段 | 影响 |
|---|---|---|
| 是否接受「平铺卡 → 6+1 张分组卡」这一层级 | 产品裁定 | 不接受则方案整体作废 |
| 宿主页是**新建 6 个容器页**（结构清晰、改动大），还是**只改宫格分组 + 加二级页签入口**（改动小、见效快） | 产品裁定，或先做小改 | 决定整轮工作量与回归面 |
| 「员工管理」以宫格那份为主、「我的」里那份是否降级为快捷入口 | 产品裁定 | 不合并则 P1 不闭环 |
| 首页 tab 的 5 个订单页签是并入「订单」分组页，还是保持现状、分组页只做台账 | 产品裁定 | 全局最大的一处改动，见 `23` 的冲突清单 |
| 宫格当前卡片数与本文基线是否一致 | 逐个数 `pages/station-mgmt/index` 的 `module-card` | 基线若已漂移，分组清单需重新核对 |
