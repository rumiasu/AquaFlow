# 系统架构

写给评估系统边界和模块责任的工程师。核对日期：2026-10-01，部署细节另见 operations/01，业务目标另见领域模型。

## 1. 维护边界

一个 Spring Boot 后端、一个 MySQL 数据库、两个原生微信小程序。客户使用 miniapp-user，站长和配送员使用 miniapp-delivery；没有在维护的 Web 管理后台或水厂端。历史归档不作为第三个发布产品。

## 2. 部署拓扑

两个小程序通过认证 HTTP API 访问后端，后端读写 MySQL；微信登录、对象存储和告警渠道分别集成。生产通过正式 HTTPS 入口部署。当前采用单应用实例，内存限流和部分作业不能直接按多实例解释。

Spring Boot、MyBatis、Java 及构建依赖以 build.gradle 和锁定文件为准，不在文档手抄类数或端点计数。业务源文件和页面以源码及 app.json 为准；结构索引工具不可用时直接检索源码。

## 3. 分层和状态事实

Controller 处理身份、输入和响应；Service 编排业务事务与责任；Mapper 读写事实；纯计价规则由 util 复用。订单、付款、桶交接与实际退款分别有结论，不能整行更新订单绕过具名业务动作。

账户派生汇总与批次事实分开。桶账写入通过 BarrelLedgerService，票批次通过 TicketLotService，计件收益通过 StaffEarningService；库存预留和实物分别保留，站间约定和实际回款分别保留。

## 4. 身份、站别和可见性

客户全局，资产按站隔离；员工按登录态站别判权，代客下单不允许任意指定别站。未选角色会话只访问引导入口。角色注解和站别校验都必须覆盖相应业务，不能把“存在 AOP”理解成无注解方法全部安全。

跨站只给订单履约快照，客户画像由唯一遮罩规则限制。收款判权、资产判权和履约判权各有依据，不能用一个 stationId 替代。

## 5. 外部能力与降级

微信登录两端各自使用签发 code 的 AppID。真实微信支付和退款尚未接通，模拟仅本地。COS 未配时上传不可用而不是整个业务必须失败；告警先落库，渠道不可用保留落库事实。

微信 code2Session 响应日志由 MaskUtil 按 JSON 对象脱敏，空白布局和转义字段名沿用同一 openid 前缀规则，session_key 全部遮蔽。非对象或无法解析的响应只记录固定省略提示；解析失败日志仅保留异常类型，不附可能携带响应片段的解析异常。实际登录仍解析原响应，脱敏只改变日志输出。

正常 code2Session 和 40029 后的另一端换码诊断共用同一 RestTemplate。连接/读取超时由 `wechat.miniapp.connect-timeout-ms/read-timeout-ms` 配置（环境变量 `WX_CONNECT_TIMEOUT_MS/WX_READ_TIMEOUT_MS`），默认 3000/5000 毫秒，非正值拒绝启动。正常调用超时返回固定业务失败，不附含 URL 的异常；诊断超时只记异常类型，保持原 40029 拒绝。它们是每次调用的 transport 超时，不承诺整次登录硬截止；未验证真实微信等待行为。

系统故障告警交系统管理员，经营告警交相关站长，失败不连累主事务。当前应用内提醒不能宣称真实外部推送已发送。

## 6. 配置与生产边界

RequiredConfigChecker 检查安全配置及生产危险开关；prod 要求两端微信配置、数据源和明确 CORS。PasswordInitializer 在 prod 排除，不发默认密码；正式产品登录方向是微信，现有密码端点并非仅凭这道排除就从路由消失。

BarrelBusinessPolicy 在新模型启用时检查 v71 表组完整性。切换开关不是已有新资产的经营暂停工具；产生新业务后不能关闭开关继续创建旧模型订单。

## 7. 架构取舍

采用单体保留桶、票、库存和钱的事务边界；不引入平台钱包、微服务或自动跨站资产搬迁。单库一致只能保证记录按规则变化，不能证明线下实际交接或资金到手，因此仍需具名事实和业务确认。

## 8. 待完善的目标
